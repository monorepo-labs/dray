# Analytics

**Five events, hosted PostHog** ([analytics.rs](../src-tauri/src/analytics.rs)): `app_started`, `active_day`, `session_started`, `feature_used` and `error`. Nothing about *what the reader writes* is measured — no prompt, no path, no title. `session_started` carry harness, model, effort, permission mode and whether the session is a worktree or was spawned, read off the index entry rather than `send_msg`'s arguments, and reported **after** the index write, since everything before it can still fail and a session counted before its row exists is a start that never happened.

**`session_started` also carry `location`, and one process owns each count.** `local` is reported by the core that wrote the session down, as before. `remote` is reported by **the reader's app** for a session its own `send_msg` created on an external server — `server_invoke` reads the created snapshot off the reply — with `remote_os` (`macos`/`linux`/`other`, `unknown` from a server too old to say) read off the welcome frame's `os`, a closed tag since the welcome is the server's own text. The app owns it because the server cannot: a Linux `dray-serve` carries no `POSTHOG_KEY` (release-cli.yml sets none) and must send nothing, and a remote Mac's own server would count it under *its* install id as a local session of somebody else. So the app's hello to a remote carries `counts: true`, `serve.rs` runs that connection's calls inside `analytics::CLIENT_COUNTS`, and `client_counts()` silences both `session_started` and `send_msg`'s `active_day` there — the reader was active on their own install, so `server_invoke` reports that `active_day` instead. A create the server refused *after* writing its row still counts, the local rule: on an error the app asks `session_index_item` for it. A task-local rather than a parameter because the create path is eighteen arguments deep; it holds because the report runs inline in the dispatched future. **Sessions an agent's `dray new` starts on a remote are still the server's**: counted local by a remote Mac, not at all on Linux. No app is told of them reliably (none may be connected, several may be), so there is no single owner to hand them to.

**`app_started` is the install and version signal, never the activity one.** People leave this app open for days, so launches undercount use badly. What a launch uniquely answer is which build is in the wild.

**`active_day` is the activity one, and nothing else answer it.** PostHog compute actives off *any* event, but the events beside this one only fire where they fire: `app_started` want a launch and `session_started` want a session being **created**, so somebody working all day in one resumed session used to fire nothing at all and the most engaged reader read as churned. Three call sites, each covering a hole the others leave. **Launch**, beside `app_started` in `setup`, is the only one guaranteed to fire — [focus.ts](../src/lib/focus.ts) seed itself from `document.hasFocus()` and report *changes* alone, so a window coming up already frontmost never report gaining focus and somebody who open Dray, work and quit without switching app would go uncounted. **Focus gained**, through that same module's subscription and the `track_active_day` command beside `track_feature`, catch coming back to check on a session an agent is running — no prompt, and real use of an app about parallel agents. **The `send_msg` command** cover a reader who leave the app open and frontmost across a date boundary. All three share one key, so whichever get there first claim the day and the other two are no-ops — which is why none of them ask what the others did: "report this only if nothing reported today" is what the claim already is.

**The send site is the Tauri *command*, never `SessionManager::send_msg` one call down**, and that is the whole gate. The orchestration socket reach the manager directly for both of its jobs — relaying a `dray send` and starting a session `dray new` ask for — so an agent finishing at 3am would mark the day active with nobody in the room. A gate on `from.is_none()` catch only the relay half and read as if it caught both. A Tauri command is reachable from the webview alone, so getting there already mean somebody pressed send.

**`track_daily` throttle it, and it is deliberately *not* persisted.** At most one report per local day per key, per process, over a `Mutex<BTreeMap<String, String>>` of key → date. **The day is claimed inside `send`, *after* the install id is in hand** — never at the spawn. Claimed up front, a run whose id write failed would claim the day, send nothing, and silence itself until midnight. PostHog count distinct people per day, so one install reporting three times is still one active user — a restart re-reporting cost one event and move no number, where remembering across runs cost a file, a lock and a corruption path on the launch path. `claim_day` is split out so the throttle test need no clock and no request. Known wrinkle nobody is fixing: local date and the PostHog project's timezone disagree at the edges.

**`source` separate the two populations reporting into one project** — `"app"` in `base_properties`, `"site"` registered on the web SDK. The app carry a stable install uuid where the site carry a browser cookie, so an unfiltered "unique users" figure is the sum of two things that mean different things. `$lib` half-separate them already, but a dashboard built on a property's *absence* break the day something else stop setting one. **The one thing here that cannot be backfilled.** The site register it from `init`'s `loaded` callback rather than after `init` return, since the first pageview is captured inside `init` and a super property only ride captures made after it.

**Screen views were cut, not deferred** — which tab is open is not a question being asked, and `$pageview` would be the wrong name for it anyway: that event drive PostHog's Web Analytics product, which is clean and site-only today.

**`feature_used` is one event with the feature as a property, never an event per feature.** PostHog break one insight down by property, where a name each is a chart each to keep in step, and a feature added later then show up in the existing breakdown with no dashboard change. Reported on the feature *working*, not the control being pressed — **with one stated exception, the handoff row**, which report on the press. `handleSendMsg` catch its own failures and resolve either way, so awaiting it report identically on success and failure, and a real fix mean changing that function's contract, which the main composer path share. The question that number answer is whether a row parked behind the composer get *found*, which the press is the signal for; a send failing past there is the agent failing, and the transcript is where that show. Every other one sit at the **chokepoint every route pass through** — `transcribe_audio` rather than the two dictation commands, so a retry that finally produced words count like a stop that did; `connect_linear` after both the key and the account are down, so it report a connection rather than an attempt.

Today: `dictation` — which carry the **model id** beside it, since nothing else say whether `recommended()` is a pick people keep or which catalog entries are worth carrying, and a closed `via` (`app`, `island`, or `phone` for an iOS upload) — plus `fork`, `pr_merged`, `linear_connected`, `space_created`, `worktree_deleted`, `settle` / `unsettle` / `pin` / `unpin` / `set_aside` / `unset_aside`, `handoff_commit` / `handoff_pr` / `handoff_runServer` / `handoff_custom` (every button the reader added, as one name), and `browser_open` with its closed `target` (`localhost` or `site`). Three carry `via`, a closed tag and nothing else — never a port, session, address or server name: `share` (`app` for the reader, `cli` for an agent, on a new link only), `server_added` (`ssh` or `address`) and `server_connected`, the one **daily** feature (`track_daily`, keyed per `via`), since a reconnect is not news and a server in use that day is. **The island's three — `island_open`, `island_send`, `island_card` — are counted by the server off the island's connection** (`client: "island"` in its hello, honoured on the local listener alone, `island_used` in [serve.rs](../src-tauri/src/serve.rs)), never off a per-call argument, and each claims `active_day` too: somebody working through the island all day with the window hidden is active. The island holds no PostHog client and reads no consent. Dictation's `via` follows the same rule — `tag_dictation` overwrites whatever `via` a caller sent before forwarding to the app. `remote_access` reports when the address attaches after somebody turned it on, never for a launch serving from the saved setting; `os` on every event already tells a Mac from a Linux server.

**`error` report *where* it broke, never *what it said*, and that rule is the whole feature.** An error string or a stack frame carry file paths, and a path carry the project, the branch and the client's name — so a property may be a closed tag (a stage, a harness, a `file:line` of our own source) and never a `String` that came out of an error. Three kinds today, one event with `kind` as a property, the same bargain `feature_used` make. **Panics** ride a `set_hook` chained to the previous hook, so abort behaviour is unchanged, and carry location and thread name, **never the payload** — a panic message is arbitrary text and `expect` is routinely handed a path to explain itself with. A `Location` is a compile-time constant naming the *build* machine, and `trim_source_path` cut the rest: `trim-paths` is the proper cure and is **not stable on the toolchain the release workflow pin**, so a registry or git-checkout path keep the part naming the crate and anything else still absolute is cut to its file name. **Parse failures** report at `harness::record_failure` — the same chokepoint as `store::record_parse_failure` one call down, which cannot name the harness — carrying `stage` and harness alone; `raw` is the whole CLI line and `detail` a serde message free to embed the value, so neither leave the machine. **Once per `<harness>/<stage>` per run**, since a wire format that moved fail every line of a live session and the second failure say nothing the first did not. **Failed update installs** report `InstallError`'s tag, a closed set, from a single point `install_update` wrap its body for. **Render errors** come from `CrashScreen`, the boundary around `App`, as React's error code plus up to eight `name@bundle:line:col` frames of our own bundle, filtered again in Rust — never the message. Other frontend uncaught errors are deliberately out — JS messages and stack frames carry paths, and scrubbing them is its own piece of work (DRA-200).

**The four flag actions come out of `set_session_flags`, which is both buttons' one chokepoint**, and they report only where the flag **changed**: the frontend send the value it wants rather than a toggle, so `pinned: true` on an already-pinned session is a no-op and not somebody pinning it. Collected before the fields move and reported *after* the write, so a failed write report nothing. Named in the reader's vocabulary, not the field's — the row say Settle where the index say `archived`, and the question asked of the number is about the button.

**`space_created` check for the name twice, and the duplicate is the point.** A space is declared in local storage, so the only chokepoint is a `setState` updater — and React may call one twice, which would count one space as two. The report therefore sit *outside* it, judged against `spaces`, the union: re-declaring a name some project already carry as a tag is no new space to the reader, whatever the declared half of the list say. **`browser_open` counts the reader's own opens and nothing else, so it is reported at their entry points, never at `create_tab`** — a page's own `window.open` reach that too, and so does every `dray browser` an agent runs. The entry points are the URL bar and its suggestions, a transcript link opening here, and the empty state's dev servers, shared links and recent pages (`trackBrowserOpen` in [browser.ts](../src/lib/browser.ts)). Not counted, on purpose: an agent's open, in-page navigation, back/forward/reload, a duplicated tab, a reopened or woken one. It carries `target`, `localhost` or `site`, from `browserTarget` — loopback, `.localhost`, `.local` and the private LAN ranges read as a dev server — and **no URL, host or port ever leaves the webview**: `track_feature` takes `target` as a Rust enum, so the webview can send its two words and nothing else.

**`track_feature` is the one command the frontend report through**, for the handful whose chokepoint is a click handler — the handoff row, whose `action.builtin` is a closed union with every custom button folded into `handoff_custom`, so no button arrives nameless and none carries the reader's text. It take a `String` and validate nothing: the only caller is this app's own frontend, and a permitted list there would be a second copy of one the call sites already are. The opt-out and the install id are still read inside `track`, so the webview cannot report anything Rust would not. The frontend side ([analytics.ts](../src/lib/analytics.ts)) **swallow every failure**, since the one thing worse than a missing event is a feature failing because counting it did.

**There is no opt-out in the app; `DRAY_NO_ANALYTICS` is the only one.** Settings had a switch and it was removed on purpose: every install reports, including one that switched it off on an older build. `analytics_enabled` stays on `AppSettings` with its `#[serde(default)]` so an older build sharing `~/.dray` still parses the file and a rewrite carries its value through, but **nothing reads it** — not as consent, not for migration. The variable is checked in one place (`env_opt_out`), and the app passes it to the background server.

**A persistent install id, minted for every install on first use and never cleared.** A uuid **v4** on `settings.json` — not the v7 used for session ids, which embed the moment they were minted, one more thing an identifier meant to say nothing would say. `ensure_install_id` live in [settings.rs](../src-tauri/src/settings.rs): a lock-free read answers the common case, and a miss mints through `update`, whose `get_or_insert` re-checks under the lock.

- **Nothing caches the id in-process.** The file read it saves is small and happens a few times a session, and a cache is one more copy to keep in step.
- **`settings::update` is the only way to change a setting, and `write` is private so that is true rather than aspirational.** `read` take no lock, so a read-modify-write in two steps can be interleaved and lose the other's field. There was a `pub write` beside `read` and seven callers pairing them — the shape that fails, and it fails **across features, not within one**: a Linear account or transcription pick read before the id was minted, then written back after, takes the id with it. Taking the write away is what stop the next one.
- **`update` recover from a *malformed* file and never from an *unreadable* one**, and `is_malformed` — an anyhow downcast to `serde_json::Error`, which the context chain preserve — is what tell them apart. Bytes that cannot be parsed can never be preserved, and erroring there would block every settings write — the install id's included, so analytics would go silent for good — until somebody deleted the file by hand. Bytes that cannot be *read* are the opposite: the file may be perfectly good and merely unreachable for a moment, so writing over it would erase the Linear account, the install id and every transcription pick to change one unrelated setting. Where it does recover the fallback is `Default`.
- **A failed write answer `None`.** With no cache, an id that did not reach disk would be re-minted on the very next event and every event arrive as a different person — no events beat a fabricated population.

**No transport plugin, and no new dependency.** `reqwest` is already here for Linear, and PostHog's capture API is one POST, so an event is a request rather than a queue with a flush interval — at single figures per session, batching would buy nothing and cost a drain on the quit path. `tauri-plugin-aptabase` came out with 282 lines of `Cargo.lock`.

## Surveys, and the one thing the POST cannot do

**`posthog-js` is in the webview, and it is there for surveys alone** ([surveys.ts](../src/lib/surveys.ts)). A survey is fetched and drawn client-side by that SDK and by nothing else, so with the POST as the only surface there was nothing in this app a survey could appear *in* — and no amount of targeting fixes a window with nothing to draw it. The SDK captures nothing of its own: `autocapture`, `capture_pageview`, `capture_pageleave` and session recording are all off, and every event this app reports still goes out of `analytics.rs`. **It is not a second analytics client so much as a second surface of the same one**, which is what decides everything below.

**Targeting reads *persons*, which is the half that had nothing behind it.** `source: "app"` rides every event as an *event* property, and a survey cannot be aimed with one — so the app's install-uuid persons carried nothing at all and `source` was simply absent from the survey UI's field list. `person_profiles: "always"` plus a `$set` of [`base_properties`] is the fix, and it is why `SurveyIdentity` carries that map rather than the frontend naming the fields again. Pinned by test: dropping one from `base_properties` costs a targeting option in PostHog's UI and says nothing whatever in this tree. `identified_only` is the *site's* setting, where a visitor is an anonymous cookie id and there is deliberately no person; here it would leave nothing to target.

**The marketing site can never draw a survey however one is aimed**, since it loads `posthog-js/dist/module.slim` and surveys are one of the four things that build drops. So the app/site split costs nothing here beyond the filter being there when it is wanted.

**Whether to start is Rust's answer, and `analytics_identity` is the one place it is given.** It answers with a key, a host, the install id and the person properties together, or with `None` — the refusal, on the grounds `send` refuses on: no key compiled in or `DRAY_NO_ANALYTICS` (plus an id that could not be persisted). The frontend never asks anything else. Key and host ride along rather than becoming a `VITE_POSTHOG_KEY` beside `POSTHOG_KEY`: two build-time variables for one project are two things that can drift, and the drift is silent.

- **`bootstrap`, never `identify`.** The POSTs have already made the install id a person; identifying into it would alias an anonymous id nobody ever used.
- **Started once, from [main.tsx](../src/main.tsx), not an effect**, the same bargain the focus subscription beside it makes — the SDK lives for the process, and StrictMode double-invokes a mount. Unconditional, since it refuses itself. Nothing calls it again: the id is never cleared, so the bootstrapped one never goes stale.

**`session_count` is on the identity, and it is what a survey is aimed with.** PostHog receives nothing that counts sessions; the index is the only place the answer lives, so `analytics_identity()` reads it. Added there rather than in `base_properties`, a `OnceLock` answering once for the life of the process where this moves with every session made. A failed read leaves the property absent, which a survey targeting a minimum reads as **not** matching — the safe direction, and the cure is opening the app again. The threshold is PostHog's to change, which is the point of it being a person property rather than a rule in this tree.

**PostHog draws the card, and Dray draws nothing.** A survey is written, targeted and reworded entirely in its UI with no Dray release. The cost, stated: the card is *theirs* — colours and radius are settable, the layout is not, and the byline only comes off on a paid plan, so it will not match [DESIGN.md](../DESIGN.md).

**A Dray-drawn card was built and reverted, and the reason is worth keeping.** `getActiveMatchingSurveys` hands the questions over, `disable_surveys_automatic_display` silences PostHog's own display loop, `capture("survey sent", …)` reports back and the answers still land in the survey results view — it works, and the whole of it is in the history of DRA-257 if the stock card ever grates. What it costs is a payload this tree has to build correctly: the response key is `$survey_response` for the first question and the question's **id** or index after that, `id` being optional on the wire, and which key the results view reads has moved between PostHog versions. A wrong one loses the answer silently. That is a real price to pay for a nicer card, and it is not worth paying until the stock one has actually been seen and disliked.

**Frontend uncaught errors are still out of scope.** The SDK arriving does not change that JS messages and stack frames carry paths and that scrubbing them is its own piece of work (DRA-200).

**Nothing is stamped for us.** Aptabase's plugin put `appVersion`, `osName` and friends on every envelope itself; PostHog do not, so `base_properties` build that set once — `app_version` (from `CARGO_PKG_VERSION`, which `tauri.conf.json` hold too), `os`, `arch`, `is_debug`. **OS version is deliberately absent**: nothing in the tree knows it, and reading it mean a new dependency or spawning `sw_vers` on the launch path for a figure nobody has asked a question of. Event properties are merged **over** the base set, so a call site can correct one.

**Every event carries `$raw_user_agent` (`Dray/<version> (<os>; <arch>)`), and the HTTP header does not stand in for it.** PostHog classifies bot traffic at query time off that *property* alone and reads a missing one as `Automation`, so without it every app event was `$virt_is_bot` and any bot-filtered insight dropped the app — silently, the header having been sent the whole time.

**`track` is not `async` and take no `AppHandle`**, which is what let the feature sites call it — several are synchronous commands with no handle in reach, one of them on CEF's main thread. It spawn, and the opt-out is read *inside* the spawned half on every call, so a new call site cannot forget to ask. `app_started` therefore fire from `setup` as one line that returns immediately.

**An empty key = a build that sends nothing, and that is the ordinary state.** `API_KEY` come from `option_env!("POSTHOG_KEY")`, so every local build compile with none and `pnpm tauri dev` stay out of the numbers. Checked **before** the settings read, or every event cost a file read on a build that sends nothing. `build.rs` declare `rerun-if-env-changed` for it and for `POSTHOG_HOST`, since `option_env!` resolve at compile time.

**`POSTHOG_HOST` treat the empty string as unset, and that is not defensive.** [release.yml](../../../.github/workflows/release.yml) pass it through from a repository **variable**, which expand to `""` when undefined rather than being absent — so `Some("")` is the ordinary case for every build that has not set one, and taking it literally would post every event to `/i/v0/e/` with no host in front of it. Pinned by test. Region is worth a knob at all because the wrong one is a key that authenticates nowhere: a 401, logged, and no events.

**A non-success status is logged, not dropped.** Best effort otherwise — analytics that surfaced an error would be worse than analytics that went missing — but the two ways this silently reports nothing, a wrong key and a wrong region, both land there.

**The install id lives in `~/.dray/settings.json`, not local storage, and timing is the whole reason** ([settings.rs](../src-tauri/src/settings.rs)): `app_started` send from `setup`, before the webview exists. **Anything the frontend can read for itself belongs in local storage, not there**, or that file becomes a second settings store free to disagree with the first.

**`install_id` is `#[serde(default)]`, and that is load-bearing the way every field on that file is** — the settings file is rewritten whole, so an entry written before the field existed failing to parse would take every other setting in it down to defaults. Pinned by test.

**`read` answers defaults on any failure** — missing, empty, unparseable, unreadable, no home dir. Never an error: this sits on the launch path. It used to fail *closed* to opted out, to protect somebody who had turned the switch off; with no switch left, that would only let a corrupt file silence analytics.

**The marketing site report to the same project, and it is a different bargain.** [instrumentation-client.ts](../../web/src/instrumentation-client.ts) — Next run it before hydration, which is why there is no provider and nothing mounted in the layout; a `<Script>` or a layout `useEffect` both start measuring a page view later than the page view happened. `@vercel/analytics` came out, so the site has one analytics tool rather than two that disagree.

- **A cookie, no banner** (`persistence: "localStorage+cookie"`), on the site and the docs both, so one visitor is one id across pages, visits and the `/docs` rewrite. Cookieless made every page load a new person, so a download on `/` after landing on `/changelog` was credited to our own domain and the real source lost it. No consent banner is a decision, EU exposure accepted. Autocapture, session recording and person profiles are still off; source attribution reads the `sessions` table's entry referrer.
- **Ingest is proxied** through `drayhq.com/ingest`, rewritten in [next.config.ts](../../web/next.config.ts), so a content blocker see a first-party request. **Two rewrite rules, not one**: the SDK fetch its own assets from a *different* host to the one it post events to, so a single catch-all leave the script 404ing and nothing measured at all. `skipTrailingSlashRedirect` go with it, since PostHog's API care about the trailing slash Next would otherwise strip. `api_host: "/ingest"` is the other half — change one and the other stop working silently.
- **[lib/posthog.ts](../../web/src/lib/posthog.ts) is the site's one import of the SDK, and that is not tidiness.** `posthog-js` export a default instance *per module record*, so a file importing `"posthog-js"` beside one importing the slim build get a second instance `init` was never called on, whose `capture` calls go nowhere **silently**. It also pin the slim path: 148KB against 309KB, 45KB off First Load JS, everything it drop already disabled. The deep path is no declared export, so a version bump move it — which fail as a build error rather than quietly, the acceptable direction.
- **The download click use `transport: "sendBeacon"`**, since the href is a plain off-site navigation and the default transport is a request the browser is free to cancel as the page goes.
