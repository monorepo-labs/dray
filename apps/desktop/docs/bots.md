# Bots

**A bot is one ongoing chat with instructions and memory of its own, and everything it starts runs hidden and reports back to it after every turn** (#816, [bots.rs](../src-tauri/src/bots.rs), [bots.ts](../src/lib/bots.ts)). The shape Grok Bot, Cursor Projects, Claude Projects and OpenBot all ship: the reader runs everything from one chat and never switches sessions.

**A bot is a folder, and its session is known by running in it.** `bots/<id>/` under the home holds `INSTRUCTIONS.md` and a `memory/` folder; `bots.json` holds the list (id, name, path). The bot's chat is an ordinary session whose `cwd` is that folder — no field on the index says "bot", so an older build reading the index loses nothing, and every reader asks `bot_at(cwd)` / `botAt(bots, cwd)` instead. The chat is the newest unsettled session there (`botSession`); were it settled, the next send would start another with the same instructions and memory.

**Switching agent keeps the conversation** (#878). Each CLI resumes only its own sessions, so a switch is a new session in the same folder, and the chat is every unsettled session there, oldest first (`botChat`, `chat_sessions`), drawn as one with a quiet "Switched to Codex" line between them (`chatItems`). The model picker keeps its agent strip in a bot chat; a pick there is the chat's unsent pick, a line under the composer says the next message moves the chat, and that send mints the new session (`handleSendMsg`, refused mid-turn). Model, effort and stance on the same agent still apply in place. The backend knows a switch as a new session in a bot folder that already has one (`mark_new_chat`): it stops the old child and sends the new agent a **replay**, never a summary, ahead of the reader's first message — the reader's messages, the bot's replies and its tasks' reports, newest kept up to 30k characters, plus every earlier log's path and the tasks still open. The replay is sent and never logged, since the earlier logs already hold it. A switch writes no welcome. Tasks started before a switch still name the old session as parent, so `send_message` reroutes anything for a bot chat to its newest session (`current_chat`), and the Tasks tab walks the earlier sessions' children too (`crewRows`'s `also`). An earlier session is drawn only once the one after it is read back to its start, so no gap opens between them (`drawnSegments`).

**Instructions ride every harness's system-prompt slot; memory never does** through `bots::system_prompt(base, cwd)`: Claude Code's `--append-system-prompt`, Codex's `developerInstructions` (on `TurnSettings`, restated on start and resume), fx's `systemPrompt`, grok's `rules`, pi's `--append-system-prompt`. The bot's text is [bot_prompt.md](../src-tauri/src/bots/bot_prompt.md) and its first turn [kickoff_prompt.md](../src-tauri/src/bots/kickoff_prompt.md), their `{placeholders}` filled in one pass so a bot's own file naming one is never filled. `INSTRUCTIONS.md` starts empty: the bot is told its job in its first message and writes it down itself, and only it edits it, adding standing rules of its own too (below). Read at spawn, which needs no reload for the bot's own edits — it made them. grok and fx keep the prompt on their own session record and take none on resume, so there only a new chat rereads it. It is capped at 16k characters, and a closing tag inside it is broken up so the text cannot end its block early. **Memory is a folder the prompt only points at**: one `YYYY-MM-DD-title.md` per memory, a one-line `description` in frontmatter, which the bot lists and greps when it needs to. Loaded whole, a bot's memory cost its size on every start and grew without bound; as files it costs nothing until read, and the date in the name sorts them.

**A bot learns from its mistakes, and files each lesson where it fires** (#973, [learn.rs](../src-tauri/src/bots/learn.rs)). The failure this answers: a bot forked a Boat sandbox whose Claude login had expired, fixed that one sandbox, and saved the lesson to `memory/`, which nothing loads. So there are three homes. Standing rules go in `INSTRUCTIONS.md`, which the bot may now add to itself but never remove a rule the user wrote from. How-tos go in skills at `.claude/skills/<name>/SKILL.md`. Facts go in `memory/`. Claude Code reads the skills since the bot runs in its folder. Codex and pi read `.agents/skills` and never `.claude/skills`, so `ensure_skills` links one to the other; both follow the link, checked against Codex's `skills/list` and pi's docs. The prompt asks the bot to fix the cause in the same turn as a failure or correction, and to say so in one line. Its rules come from Hermes Agent: lessons, not logs (the check that would have caught it, no PR numbers or dates), and its "Do NOT capture" list. Caps: 8k for a skill, 4k for a memory, 16k for instructions. A skill or memory over its cap owes a review. Instructions over theirs do not, since a review may only add there: the prompt's cut notice has the bot ask the user what to cut.

**Dray asks for a review when the bot doesn't learn on its own.** `note_prompt` reads each prompt as it is logged: the reader's message against a list of correcting phrases, and a task's report against failure words (never a stall nudge). Where the turn that took it changed no lesson, Dray sends a hidden `Review:` prompt ([review_prompt.md](../src-tauri/src/bots/review_prompt.md)) once that turn ends. It is sent through `send_review` and marked as Dray's own the way the kickoff is: `user_message.kickoff`, so an older app hides it too, matched on session *and* text so a message the reader sends meanwhile is never taken for one. The bot patches a skill, its instructions or memory, or ends silently. A turn a review was in never owes another. Only a turn opened by a review alone counts as one for the add-only rule, kept apart from "a review joined", so a review queued behind the reader's message cannot claim their turn. A chat gets one review per five minutes, and its reply never draws, live or logged (`inReviewTurn`, `in_review`). **A review may only add to `INSTRUCTIONS.md`**: where its turn took a line away, `keep_rules` puts the file back before the commit. The phrase lists are generous on purpose: a false hit costs one silent turn, a miss costs a lesson.

**A plain line in the chat shows each lesson, and opens to its diff and Undo.** `commit_turn` reads its own commit back, keeping only `INSTRUCTIONS.md`, `.claude/skills/` and `memory/`. Each file gets a summary line: the first rule added (a heading only where nothing else was), or the file's frontmatter `description`. Dray logs these as a `learned` event right after the turn's `turn_completed`, minted on the read loop's own counter, since `post_event`'s slot lock can be held by a send waiting on that loop. A click reads the file before and after (`bot_learned_diff`) into `DiffView` beneath the line. Undo (`bot_undo_learned`) reverts that one file as a reverse patch, so a later edit to it survives and an overlapping one refuses. It commits just that file as "Undone by the user: …", which the prompt tells the bot never to add back, and logs `learned_undone`, which turns the row to Undone. A hidden review-shaped note then tells the bot, since a running child read its instructions at spawn and would keep following the undone rule. A file the bot is mid-edit on refuses too. The frontend draws them from `botItems`' `learned` items as `LearnedLine`: the kind in grey (`lessonKind`: Rule, New skill, Removed memory), then the summary, with no background, border or icon, and Undo, the one icon, only under the open diff. Picked from six takes on [learned-chip.html](../demo/learned-chip.html). Hermes keeps a ledger of skill writes; here the folder's git history is that ledger.

**Everything under a bot runs hidden** (`create_session`, `in_bot_tree`): its children and theirs, whatever `--hidden` said. The walk is bounded at 8, so an index pointing a session at its own ancestor costs a wrong answer rather than a hung turn. A bot's folder is no project, so a create naming it or anything inside it is refused with "pass --project" rather than starting a worktree of the bot's notes.

**A bot's folder is a local git repository, and Dray commits it after every turn** (#893, `start_history`, `commit_turn`). The point is a timeline: when the bot overwrites or deletes something, it or the reader can look back and restore. Made with the bot, and on first use — any spawn, through `system_prompt` — for a bot older than this. Dray commits, not the bot, which could forget: on every main-thread `TurnCompleted` in a bot's folder, everything staged with `add -A` and committed where anything changed, the message naming the files. **Awaited inside `ingest_event`**, before the queued flush, or the next turn could overwrite a note before it was saved. Every commit is given the bot's name and an email made from its id, never written to config once, which a setup cut off after `init` would skip; so no global identity is needed. Every git call here passes `-c` for no hooks, no global ignore file and no signing: a reader's hook could fail or hang a commit, their ignore rules could leave its notes untracked, and a signing key would prompt every turn. No remote and no push, and the prompt says so; it tells the bot the history is there, not to commit. `.git` is looked for rather than asked of git, which would answer for a repository the home sat inside. **The app's git features stay off for a bot's chat**: no handoff row at all, not even Run server or the reader's own buttons, and no pull request lookup (`inBotFolder` in `App`), and the side panel never had Changes or PR. The turn snapshots still run there, unread.

**Every turn a child closes is sent to its parent, by Dray, not by the agent** (`report_to_parent`, from `ingest_event` on a main-thread `TurnCompleted`). A report the agent is asked to send is one it can forget — OpenBot's weak spot, whose delegation rules are prompt-only. It goes through `send_message`, the path `dray session send` takes, so the bot reads it exactly like a message the child sent. Only Claude Code fills `final_text`; the others say their answer in `AssistantText`, so the last one of the turn is kept (`LAST_REPLY`) and used instead. A turn with no text still reports, saying it failed or ended silently, and a child dying mid-turn reports from `settle_dead_child`, whose close never passes through `ingest_event` — so the bot is never left waiting. Each task is told so in its own prompt ([task_prompt.md](../src-tauri/src/bots/task_prompt.md), added by `system_prompt` where the session's index entry has a parent in a bot's tree): unaware, a task also sent its answer with `dray session send`, and the bot read every report twice. A settled child or a settled bot chat takes no report: sending would resume a conversation the reader closed. The flag is read again after the send and the chat stopped if it was settled meanwhile, since settling writes the flag before it stops the child. **Boxed**: the read loop calling it lives inside a harness's `init`, and the send can reach `init` again, so unboxed the compiler cannot name either future.

**What the reader does to a bot's tasks reaches the bot on its next prompt, never as a turn of its own** (#984, `SINCE` in [bots.rs](../src-tauri/src/bots.rs)). A merge, settle, stop or delete the reader makes is noted per bot folder, one line per task with its acts folded in, eight tasks at most, and `deliver_prompt` sends the list ahead of whatever the bot gets next — a message, a task report, a stall nudge — beside the switch replay, sent and never logged. Recorded where the act lands so every client counts: `merge_pr` itself (only ever a client's; agents merge with `gh`), which asks GitHub for the PR's head branch only where a bot task sits in that repo, and the client wire's `set_session_flags`, `interrupt_session` and `delete_session` in `serve.rs` — not the shared functions, which `dray` also reaches, since that is how the bot acts itself. So a reader's own `dray session settle` in a terminal goes unnoted, and so does anything done to a `--machine` task, whose server holds no bot. A stop is noted *before* it runs and taken back if it fails, since the stopped task reports at once and the report must carry why; a settle or delete only once it landed, since a sent note cannot be taken back. The list is trusted text, so it carries no PR title (the PR author's words), a task title is kept to one line that cannot close it, and a fork's PR never matches. In memory: a server restart drops what was not yet sent.

**The frontend.** Bots lead the live sidebar in a Bots section (`BotRow`: the session row's rail and orb, nothing else); their ongoing chats leave the session list (`inSidebar(items, bots)`), their settled ones stay in the settled list, the only way back to one. The section reads the active side of the index alone and is empty while the settled side is loaded. The space check spares anything in a bot's tree (`inBotTree`), or a task opened from the Tasks tab in another space's project closed at once. Opening a bot with no chat aims the empty composer at its folder (`handleNewBotSession`, not `handleSelectProject`, which would remember a bot as a project) and the toolbar drops the project pickers without naming the bot, which the header already does; a send there takes no worktree. A bot chat always runs on Auto (`botStance`), so its toolbar draws no stance picker, except on an agent with no Auto. Cards still come to the bot's chat (#807). ⌘⇧↑/↓ and the jump digits walk the bots' chats first, then the sidebar's order, so ⌥1 is the top bot. In a bot's chat `&` offers its own active tasks — not settled, not set aside — since they run hidden in projects the composer is not on.

**A bot's side panel is Tasks, Browser and More**: no PR and no Changes, since its folder holds notes, not work to review. Tasks lists its children at any depth off `crewRows` — which walks every held session, not the space's, since a bot hands work to any project. Pinned first, then waiting, working and done, set-aside ones last and faded. Each row is the sidebar row's: its face (the working orb mid-turn), title, the PR glyph *with its number*, ⋯ and Settle on hover, and the sidebar's right-click menu bar Mark unread. **A ready pull request draws Merge on the row** (`readyToMerge`, the PR panel's split button and confirm step cut to a row): an agent's own `gh pr merge` is often refused by its permission classifier, so the reader lands them. It merges from the repo root, since the worktree may be gone, then settles the task and removes its worktree — landed work needs no tidying by hand. The bot's prompt tells it to settle finished tasks itself with `--delete-worktree`, never one whose work is unmerged and still wanted.

**A bot's tasks don't sit stalled unseen** ([stalled.ts](../src/lib/stalled.ts), `useStalledTasks`, [StalledTasks](../src/components/chat/StalledTasks.tsx)). Each idle task is sorted by its PR's `prStatus`. **Only what truly waits on the reader reaches the reader**: a PR ready to merge, and a task idle on a question, each once it has sat `STALL_MS` (5 minutes). Everything else goes to the bot. Failing checks, a conflict, a branch behind base and changes requested are the task's to mend, so the bot gets a **nudge** naming the problem and has the task fix it with `dray session send` — **with no wait**, on the first check after the task goes idle. The one gate is a mark asked for after the task last moved: a mark from before the task's push would nudge the bot about checks the task had just fixed. Both sides are on the app's clock — `readAt` is stamped when the `gh` read was *issued*, and the move when the app saw `modified` change, since `modified` is the server's stamp and a remote clock running behind would let an old read pass. A mark that never refreshes falls back to the 5-minute wait. A task idle on the reader nudges the bot too, with its last message (`nudge_bot` in [orchestration.rs](../src-tauri/src/orchestration.rs), reading the log tail): the bot answers it where the reader's earlier word settles it, and otherwise writes one line with `dray session need <id> "…"` (`TaskNeed` on the index, protocol v19). A nudge is a `send_message` from the task, so it is sender-tagged and hidden like a task report (#912), and the bot prompt tells it to post no chat reply. **The card draws two kinds of row**: a ready PR (face, title, PR glyph and number, Merge, time) and a task idle on the reader, which carries its need underneath once written after the task last moved (`needLine`: `need.at >= modified`). While the bot is still on a waiting task its row draws a skeleton in the line's place; if the bot answers the task itself, the task moves and the row goes. A need clears itself the moment the task moves. Running checks, an unknown mergeability, a merged PR, mid-turn tasks, ones with a background shell or subagent, ones behind a card, set-aside ones and ones on the usage limit are all left out. One nudge per stall: a stall's key is task, kind and `modified`, kept in local storage (`ade.nudgedStalls`) so a relaunch sends nothing twice, and nudges hold for a minute after mount so PR marks have landed — unread, a ready PR looks like an idle task. PR marks are read for every bot task's repo, not just the open chat's, and those holding an open PR keep reading every five minutes while the window is in the background, where the rest of the marks pause. **Stalls are read for every bot, once a minute**, so new card rows landing while the window is in the background post one desktop banner per bot ("Ops: 2 tasks waiting on you"); the first read after launch is silent. **A row click stays in the bot**: the chat scrolls to the bot's reply to the task's last report (a nudge is skipped) and lights it for a moment. The report itself stays folded, since the reply already says what it held (`taskContext`, `data-bot-focus`; the scroll is `Chat`'s). A plain **Open task** button with an up-right arrow, shown on hover, is the way into the task. Dismiss stores each row's key, so it comes back only after the task changes and stalls again. Merge is the Tasks row's (`MergeControl`, `mergeTask` in `App`). A Haiku summary of the last message (`task_need`) and a glimpse of the message itself were both tried for the need line and dropped: the bot reads the task with its context and can act on it, where a summary only restated it. Demo: [stalled-tasks.html](../demo/stalled-tasks.html).

**A ready PR is nudged too, and its row takes a need only where the task asked for one.** `nudge_bot` takes `ready` with the PR number and sends the task's last message, as for a waiting task. Where that message asks the reader to try or check something before merging ("this part is untested"), the bot writes a need and the row draws it under the title; otherwise the bot writes nothing and the row stays Merge alone. No skeleton on a ready row, since most never get a line. A need left from the PR's wait on review is cleared first, since approval does not move the task and the line would outlive the review; so a ready stall is nudged even under one. An older server takes the nudge as a waiting one, `ready` being an argument it never reads.

**A task mending its PR says so on its Tasks row** (#966). A fix stall nudges the bot and the task goes off to work, so the row reads "Fixing merge conflicts · 3m" under its title, in a muted line a step quieter than the need line: the PR status the fix was asked about, and the time since, through `compactAge`. No model writes it. The time is recorded when the nudge for that stall lands — `nudge_bot` answering `true`, never a bare success, since an older server answers `null` and a task's server holding no bot used to answer that way with nothing sent — and by nothing else — the merge card's Fix conflicts records none — in `useFixAsks`, kept in local storage (`ade.fixAsks`) so a relaunch still says how long. A second ask about the same PR and status keeps the first time, so a task stuck on one problem shows how long it has been. The line goes the moment the PR moves off that status (`fixAskDone`): conflict gone, checks running again or passing, merged, a new PR. `unknown` holds it, being GitHub's recompute after the push. Asks are pruned in `useStalledTasks`, which reads every bot's tasks, not in the tab, which shows one bot at most.

**A task opens as a tab in the bot's row** (#881, [taskTabs.ts](../src/lib/taskTabs.ts)). A click on a Tasks row, a "Started a new task" line or a "Messaged" line adds the task after everything else in the bot's titlebar row and lights it: the main column, composer and side panel are the task's, the row stays the bot's, and the sidebar keeps the bot marked. ⌘-click switches to the task alone, the way a click used to, with the breadcrumb back. × , middle-click and ⌘W close a tab; ⌘⇧T puts one back. Settling a task leaves its tab, deleting it takes it. In memory, like the rest of the row, and keyed by the bot's id rather than its chat's session, so an agent switch, which starts a new session, keeps them. The bot's row is drawn over a task only while the task is open in it and the bot was the last row a task tab was picked from (`stripOf`'s `via`); ⌘-click clears that, so the task draws its own row. The task's own Diff and files are not in the bot's row; the side panel still reaches them.

**The row shares one side panel** (`rowOf` under `openKey`, the split group's mechanism): open or shut, and which tab is picked, are held under the bot chat's id for the chat and every task lit in its row, so the pane stays put while the reader moves along the row and shows the lit session's own content. A pick the lit session does not draw — PR on the bot, Tasks on a task — falls back to its default as anywhere and comes back where it is drawn.

**Every task has its own browser, and the bot keeps its own** (`bots::browser_owner`, `botBrowser`). The bot chat's pages live on its oldest session, which an agent switch leaves in place, and the server resolves a step from any of the chat's sessions to it. Tasks were once routed into the bot's browser too (#881) and that was undone: a recording locked every task's tabs, and with many tasks everyone's pages piled into one strip and agents picked the wrong one. The row's page tabs are the bot's; the side panel shows the lit session's own. A link opens in the browser of the chat it was clicked in: from the bot chat as a new page tab in the row, from a lit task in the side panel, since the row's tabs are the bot's.

**Diff and Files in a bot's row pick which session they show** (#892, `PickTab` in [taskTabs.ts](../src/lib/taskTabs.ts)). + offers both every time, so several of each can be open, each on its own pick; an ordinary session's + still hides one already open. The pick is the first row of the view's side column ([PickTarget](../src/components/PickTarget.tsx)), above the sub-tabs or the file filter, and the tab is labelled with the picked title. Diff lists the bot's tasks alone, since its folder holds notes, not work to review; Files lists the bot's own folder first, then the tasks. The list is the Tasks tab's — active tasks at any depth — newest activity first, and a new tab opens on the newest; Diff is greyed out until there is a task. The bot chat stays selected while one is lit (view `pick`), so the reader looks at a task's work without stepping into it. Picks are keyed by bot id like task tabs, and the bot's own folder is picked as the bot id, resolved to whichever chat session it has now, so an agent switch keeps them. A Files pick's files open as tabs of the row, as Files does, in a store keyed by tab *and* target (`pickFilesKey`): repicking brings up that task's own set, and the open is quiet (`openInFiles`'s `bring`), or it would flip the bot chat's own view to Files. Those stores are never written to local storage, like the tabs. With the task's transcript unloaded, its index `modified` and status stand in for the turn revisions the views re-read on. Settling a task closes its Files picks, since a settled task has nothing to open; its Diff picks stay for review until the worktree is deleted, and deleting the task closes every pick on it — all read off `session_changed`, since the bot settles tasks as often as the reader does. A settled target leaves the index's active side, so the lit pick asks for it with `session_index_item` on every index change.

**A bot chat opens on its tail and reads back as the reader scrolls** (#955, `askOlder` in [Chat](../src/components/Chat.tsx)). The chat never ends, and the transcript's own rule — read the tail, then page the rest in until the log is whole — drew all of it: on a 36MB, 1500-turn log the first reply painted in 0.4–1.6s and the page then never went quiet, ~115s of main-thread work in two minutes with half the replies drawn. Bot chats have no rail, so nothing needs the whole history: the chat reads a page further back whenever the reader comes within a screen of the top, or while the pane holds less than a screen above its bottom, and puts the row at the top of the view back where it was when a page lands. Opening the same log now paints its first reply in ~0.3–0.7s and is quiet ~100ms later. Three things lean on history the chat may not hold yet. **The NEW divider** waits until a message of the reader's is loaded, or the whole chat is, since the first unread reply may sit above the tail (`unreadStart`); a reply arriving after the open never moves it. **A row picked from "Waiting on you"** reads back 64 turns at a time until the task's reply is drawn, since every page lands as one render of the whole app; and a jump to within a screen of the top is instant, because a smooth one is cut short by the next page landing. **Rows are memoized and compared by the events they were built from** (`ChatRow`, `sameRow`), so a page landing draws only its own rows, and the focus block is spliced into the one keyed list, since moving the rows into slots remounted every row in the chat. The transcript's faces are `still`: blobatar's gaze measures each face on every scroll anywhere on the page even with its eyes at rest, hundreds of layouts per scroll once history is loaded. Timed with [bot-chat-open.html](../demo/bot-chat-open.html).

**The chat draws the conversation, not the work** ([BotTranscript](../src/components/chat/BotTranscript.tsx), [botTranscript.ts](../src/lib/botTranscript.ts)). Tool calls show only as the live orb line naming the current tool. A task the bot starts is a "Started a new task [face] title" line, read off its `dray session new` call and the id that command prints. A message it sends, read back out of every `dray session send` in a command, is "Messaged [face] title"; a run of them with nothing between folds into "Messaged [faces] 2 bots", which opens to one railed row per message, each opening its own text. A task's report-back draws no row for now — the bot's reply carries it; the line that drew it is commented out in `BotTranscript`. So the prompt tells the bot the reader never sees a report, and to say nothing at all when one needs nothing from them: a bot turn ending with no words is read at once (`silent_bot_turn` in `ingest_event`), so it raises no Done and no unread mark over a chat that drew nothing. **Claude Code would not let a turn end empty** (#993): it re-prompts one with no text ("[Your previous response had no visible output…]"), and the bot answered with filler, often a lone zero-width space. It skips that when the turn's last tool call is named in `CLAUDE_CODE_TERMINAL_MCP_TOOLS`, so a Claude Code bot is spawned with one, `mcp__dray__no_reply_needed`, an SDK MCP server Dray answers in its read loop ([no_reply.rs](../src-tauri/src/harness/claude_code/no_reply.rs)); the prompt tells the bot to call it before a silent end. Whitespace and format characters alone are no reply anywhere this is judged (`has_text` in Rust, `hasText` in TS), so a filler reply still draws nothing. Messages between bots do draw, and never fold into a task run: "Message from [face] Ops" with the message beneath it on the reader's side, and "Messaged [face] Ops" on the bot's, read back from each `dray bot send` and the bot id it prints, since the name typed there stops naming the bot once it is renamed. Both wear the other bot's own face, and its name opens its chat (`onOpenBot`, App's `openBot`). Tasks wear a face seeded from their session id through `seededAvatar`, never the library's own seeding, so the droplet, which `SHAPES` leaves out, never appears. A NEW divider marks where unread replies begin. A merge card the bot posts with `dray session merge-card` draws whole, its Merge settling the task as the Tasks tab's does; Dray posts one itself once GitHub says the PR is ready (#953), so the prompt tells the bot only not to restate what the card shows.

**Made from the sidebar, known by its face.** The bots sit above All Projects, since a bot belongs to no project, with a **New bot** row under them whether there are none or several. No heading: the Blobatar face on a row is what says it is a bot. The dialog ([NewBotDialog](../src/components/NewBotDialog.tsx)) asks a name, one of nine Blobatar shapes (no droplet), a hue and the agent and model — no instructions — and New bot first moves to the new-task composer, since the dialog shares that composer's picker and on an open chat would change its model. **The bot speaks first**: `start_bot` sends a kickoff prompt asking it to greet the reader by name and guess its job from its name, in two or three sentences, listing no tools. The prompt is logged with `kickoff: true` and drawn as nothing, so the chat opens on the greeting. Which session is a kickoff rides a list in `bots.rs` read where the prompt's event is built, rather than a flag through `send_msg`'s twenty parameters.

**The rows are inbox rows**, laid out like the stalled-task rows in a bot's chat: a 32px face, the name (bold while unread) with how long since its last activity at the right (`relativeTime`, the session rows' own), and one line of its last reply under it (`previewLine`, in `text-foreground/70`). While the bot works, typing dots take the reply's place; list rows use dots and other views the shimmer. State sits on the face as a badge cut out of it with a mask, since the sidebar is glass: an orange dot while it waits on the reader, the unread count once a reply lands, kept beside the typing dots through a turn the bot starts on its own until the chat is read. The face's eyes follow the pointer over the row. [bot-rows.html](../demo/bot-rows.html) draws them beside task rows. Its reply is read off the end of the log (`last_reply`, the newest two turns) through `bot_previews`, again whenever a chat's status or last activity moves, so no transcript is loaded for it. The face is stored as a shape *name* and hue degrees (`BotAvatar`), drawn by pinning `traits.shape` to the middle of that shape's band ([botAvatar.ts](../src/lib/botAvatar.ts)) and a fixed mid `tone`, since left to the seed most names land pale and the colour barely shows. A bot made before there was a pick draws the face its id seeds. Right-click: Delete, which settles the chat first — once the folder is gone nothing marks it a bot's and it would land in the session list. Clicking a bot while the settled list is up switches back to the active side before opening, since the active chat is not in the settled one. There is no Settings section.

**Every user starts with Dray Bot** (#880). `list_bots` makes it the first time anything asks, under the list's lock, and leaves a marker file (`bots/.dray-bot-made`) so a reader who deletes it is not handed it back: like any bot it can be renamed or deleted. Its face is fixed, the cloud in amber, and it carries a `welcome`: its chat opens on that text with no session behind it ([BotWelcome](../src/components/chat/BotWelcome.tsx), the composer below, not centred), so the picker can still switch agent and model. The agent is the reader's own where installed, else the first installed in `HARNESS_ORDER`. The first send starts the session, and `deliver_prompt` writes the welcome into the log as event 0, ahead of the prompt, so the chat reads the same after a restart; the agent is not given it. Bots made with New bot carry no welcome and keep greeting with a real turn.

**`dray bot` makes, lists, messages, renames and deletes them** (#879): `new <name>` with `--shape` and `--colour` optional, picked at random otherwise; `ls` with each one's chat session; `send`, `rename`, `rm`. A bot is named by its id or its name in any case, so two may not share a name — `create_bot` refuses one taken, for the dialog too, and a clash made before that rule is refused with the ids to pick from. `rm` is `delete_bot`, the sidebar's Delete. Each answers with `bots_changed`, which the app reloads that server's list on. A bot made here has no chat until the first message to it: no kickoff greeting, since whoever made it is about to brief it.

**Bots message each other by name, and nothing reports back between them.** `dray bot send <bot>` sends into the bot's chat through `send_message`, the path `dray session send` takes; a bot with no chat yet starts one with the message, on the agent its last chat ran, else the sender's — but on its own last stance, else Auto, never the sender's, since a bot chat has no picker to show a Plan or bypass it inherited. A per-bot lock (`first_chat_lock`) is held from that lookup until the chat is on the index, or two first messages start two agents in one folder; `delete_bot` takes it too, so a chat opened as the bot is deleted is settled with it rather than left on a missing folder. Replying is the receiving bot's to choose, with a send of its own. The sender is stamped `MessageSender.bot_id` wherever the sending session runs in a bot's folder — `dray session send` to a bot's chat too — with the bot's name for `title`, and the agent reads `[message from the Dray bot "Ops" (id)]`. Each bot's prompt names the other bots, read at spawn like the rest of it, and tells it to say when it wants an answer and to send no thanks: two polite bots would otherwise answer each other forever.

**In a bot's chat `@` names the other bots, not files** (#941). The bot's folder holds its notes, which nobody mentions, so `ChatInput` takes `bots` — every other bot on this one's server, the only ones `dray bot send` reaches, from `App` — and the `@` token opens [BotMentionMenu](../src/components/composer/BotMentionMenu.tsx) in place of the file picker, with no file index started at all. A pick writes `@Name (id)`, the `&Title (id)` task tag's shape: the id is what `dray bot send` matches exactly, and the bot prompt says so. The name may hold neither `@` nor `&`, which is what keeps `parseBotTag` from reading a file mention and the prose after it up to a later tag's id as one name, and only a known bot's id makes one, so `@README.md (id)` in a task's chat stays a file. The composer chips it like a task tag; the transcript draws the bot's face and current name and opens it. Demo: [bot-mention.html](../demo/bot-mention.html).

**A bot runs on one server, and every server can hold bots** (#887). Its folder, files, chat and tasks live on the server it was made on; nothing moves a bot between servers. The app asks every server `list_bots` as it reads that server's projects (`readServer`), and the store in [bots.ts](../src/lib/bots.ts) keeps each server's list apart, This Mac's first. A remote's paths come back qualified like any other, so `serverOfPath(bot.path)` names a bot's server and every `botAt` comparison stays unique across servers. Bot commands go to the bot's server: `create_bot` and `start_bot` to the one picked, `delete_bot` to `serverOfBot`, `bot_previews` split by each chat's server (`readPreviews`). A remote bot's row looks like a local one, with no server name on it; an unreachable server's bots stay, faded with the offline mark, and its list rides the server cache (`ServerCache.bots`) so they survive a restart; one turned off or removed takes them with it. New bot's dialog has a server picker beside the agent picker, drawn only with a remote turned on, defaulting to This Mac; while it is open the composer's `activeServer` is that server (`botServer`), so the models offered are the ones it runs. **Dray Bot comes from the app's own server alone**: `list_bots` makes it only under the `desktop` feature, so a `dray-serve` never makes one and adding a remote never adds a Dray Bot.

A bot starts tasks on its own server. `--machine <name>` starts one on another, which is not hidden unless asked but **reports back like any task** (#958, [remote_reports.rs](../src-tauri/src/remote_reports.rs)). The far server knows no bot and usually cannot reach the bot's server, since reach follows tokens, so the route back runs the other way: the bot's server marks the forwarded create `Caller.bot_tree`, the far server records the task as owing reports (`parent-reports.json`, before the spawn so the task gets [task_prompt.md](../src-tauri/src/bots/task_prompt.md)) and keeps each report there, since its parent is in no index it holds. The bot's server tracks the task (`remote-tasks.json`) and asks that machine `parent_reports` every 10s over its own link, delivers each through `deliver_report` — the local report's path, the sender named as the task on that machine — then acks only what it delivered. Unacked, a report comes again, so a lost ack costs a duplicate and never a lost report. **The destination is the tracked parent, never the one the answer names**: that machine holds no token here, so it must not choose which chat runs a turn. A task settled or gone there, a machine removed, or one too old to answer `parent_reports` stops the tracking; a parent settled here does too, after telling the task's server to `forget` it, so its reports are not kept for nobody. A report nobody collects expires after seven days. A machine that fails to answer backs off to five minutes. **A stall nudge rides the same route**: the app sends `nudge_bot` to the task's server, which holds no bot, so where the task owes reports it files the nudge with them (`NudgeRoute::Outbox`) and the bot's server delivers it like a report. **A task on another machine carries a server glyph** on its Tasks row and its tab, the name in the glyph's tooltip, and the titlebar's far end names the machine while its tab is lit, as it does for any remote session; a task on This Mac carries none. Glyph alone because the row is already full: a name, a ring on the face and a badge on its corner were tried first. Demo: [machine-mark.html](../demo/machine-mark.html).

**Not built.** Moving a bot between servers. `dray bot` takes no `--machine`: it acts on the server it runs on, so bots message only bots on their own server. No rename and no editing a bot's files from the app; ask the bot, or `dray bot rename`.
