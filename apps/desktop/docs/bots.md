# Bots

**A bot is one ongoing chat with instructions and memory of its own, and everything it starts runs hidden and reports back to it after every turn** (#816, [bots.rs](../src-tauri/src/bots.rs), [bots.ts](../src/lib/bots.ts)). The shape Grok Bot, Cursor Projects, Claude Projects and OpenBot all ship: the reader runs everything from one chat and never switches sessions.

**A bot is a folder, and its session is known by running in it.** `bots/<id>/` under the home holds `AGENTS.md`, a `memory/` folder and a `docs/` folder for documents the user opens later, sorted by the bot into category folders (`docs/personal/` and its own), and a bot older than it is told once by hidden note when its spawn makes the folder, since grok and fx resume on their old prompt; `bots.json` holds the list (id, name, path). The bot's chat is an ordinary session whose `cwd` is that folder — no field on the index says "bot", so an older build reading the index loses nothing, and every reader asks `bot_at(cwd)` / `botAt(bots, cwd)` instead. The chat is the newest unsettled session there (`botSession`); were it settled, the next send would start another with the same instructions and memory.

**Switching agent keeps the conversation** (#878). Each CLI resumes only its own sessions, so a switch is a new session in the same folder, and the chat is every unsettled session there, oldest first (`botChat`, `chat_sessions`), drawn as one with no line between them (`chatItems`), since the reader just picked the agent. The model picker keeps its agent strip in a bot chat; a pick there is the chat's unsent pick, a line above the composer says "Your next message goes to Codex", and that send mints the new session (`handleSendMsg`, refused mid-turn). Model, effort and stance on the same agent still apply in place. The backend knows a switch as a new session in a bot folder that already has one (`mark_new_chat`): it stops the old child and sends the new agent a **replay**, never a summary, ahead of the reader's first message — the reader's messages, the bot's replies and its tasks' reports, newest kept up to 30k characters, plus every earlier log's path and the tasks still open. The replay is sent and never logged, since the earlier logs already hold it. A switch writes no welcome. Tasks started before a switch still name the old session as parent, so `send_message` reroutes anything for a bot chat to its newest session (`current_chat`), and the Tasks tab walks the earlier sessions' children too (`crewRows`'s `also`). An earlier session is drawn only once the one after it is read back to its start, so no gap opens between them (`drawnSegments`).

**A task switches agent too, in place** (#1414). Its row, worktree, branch, PR and log stay, so it keeps its session id rather than minting one: the app calls `switch_agent` ahead of the send, once a sleeping machine is awake, so a server from before it answers `unknown command` and nothing is sent. That command and `dray session model` are the only ways a task moves: `send_msg` never moves one, and a caller holding a stale harness (a relay, the auto-continue timer) sends on whatever the task runs now. Both go through `move_agent`, which stops the old child and its whole process tree and clears its tasks off the panel itself (refused mid-turn; the marker takes that child's `seq` counter, since its reader can still log a late line), drops a replay still queued for an earlier switch, logs an `agent_switched` event, which draws nothing, and only then moves the index: `harness`, the new agent's model, effort, stance and fast pick in one write, `switched`, and the agent it leaves in `other_agents` if that agent joined the conversation (a prompt or a turn of its own since it got the task, never an unspawned fork bar pi's, whose session file is copied whole). `dray session model <id> <alias>` does the same when the alias is listed by another installed agent and not by this one, since pi, grok and fx take any name, and only once this agent's probe has answered; fast mode stays behind and the stance narrows as `stanceFor` does, except that a moved `plan` task stays `plan` on pi, which runs it read-only (`taskStance` in the composer; a new pi task never takes `plan`). `switch_agent` reads the index under the slot lock, so two racing moves log one. The app judges a move against the index row and follows `agent_switched` as well as `session_changed`, so a move made elsewhere is never missed. A queued replay is kept whole beside `HANDOVERS` (`TASK_REPLAYS`), so it is found and dropped by its own text however much of this code its chat quotes. The hand-over is read back off that event at the next spawn (`mark_switch_if_unanswered`, skipped for a task never `switched`), so a failed send or a restart still delivers it: a switch the new agent has not answered queues the replay through `HANDOVERS` and `take_hidden`, after any lead-in already waiting, as a bot's does. Only the new agent's own lines count as an answer, never a late one from the child it replaced. Claude Code, grok and pi keep their conversation under the Dray id, so a switch back to one in `other_agents` resumes it (`resumed`) and is handed everything since it last joined; Codex and fx hold one `thread_id`, so they always start a fresh thread with the whole replay. A task's replay is bigger than a bot's: up to 200KB (a quarter of a 200k window), the first 30KB kept as the brief, then the newest, with each tool call one line and no output. A fork starts with no `other_agents`, since its copy of the conversation lives only on its current agent.

**The bot's block rides every harness's system-prompt slot; its instructions ride none** (#1118). `bots::system_prompt(base, session_id, cwd, harness)` fills Claude Code's `--append-system-prompt`, Codex's `developerInstructions` (on `TurnSettings`, restated on start and resume), fx's `systemPrompt`, grok's `rules` and pi's `--append-system-prompt`. The bot's text is [bot_prompt.md](../src-tauri/src/bots/bot_prompt.md) and its first turn [kickoff_prompt.md](../src-tauri/src/bots/kickoff_prompt.md), their `{placeholders}` filled in one pass so a bot's own file naming one is never filled. **The job and rules live in `AGENTS.md`, which the agent loads from its cwd on its own**, so Dray never injects them: doing both would put them in context twice. Checked per harness: Codex walks cwd to the git root, and the folder is its own repository; pi takes one file per directory, `AGENTS.md` before `CLAUDE.md`; fx reads `AGENTS.md` from the ACP `cwd` and never `CLAUDE.md`; grok reads both names in each directory and skips gitignored ones. **Claude Code reads `CLAUDE.md`, so the folder holds one that is just `@AGENTS.md`** (`write_pointer`). Measured on 2.1.322: one load through the import, and one through its own `AGENTS.md` fallback with no `CLAUDE.md`. The pointer covers a Claude Code without that fallback or with it set off, and with both files on it never loads an imported file twice. It is listed in the folder's `.gitignore`, so grok never reads the pointer beside the file, and it stays out of the bot's history. A `CLAUDE.md` already there is left alone. The block says nothing of the file's text, only a line where the bot must act: an empty file is its job still to write down, one past 16k characters means ask the user what to cut. `AGENTS.md` starts empty: the bot is told its job in its first message and writes it down itself, and only it edits it, adding standing rules of its own too (below). A session already running keeps the file as it loaded it, which needs no reload for the bot's own edits — it made them. **A bot made before #1118 kept `INSTRUCTIONS.md`**; its next spawn moves it to `AGENTS.md`, appended below any `AGENTS.md` already there, and commits the move alone (`move_legacy_instructions`), so the next turn's commit reads no rule as removed and re-added. A move cut off before the old file went finds its text already there and appends nothing. grok and fx resume without a prompt, so their resume calls `bots::prepare` for the folder alone, and since that resumed chat's stored prompt still names the old file, a hidden note tells the bot it moved. Until the move runs, a review may not take a line from the old file either. **Memory is a folder the prompt only points at**: one `YYYY-MM-DD-title.md` per memory, a one-line `description` in frontmatter, which the bot lists and greps when it needs to. Loaded whole, a bot's memory cost its size on every start and grew without bound; as files it costs nothing until read, and the date in the name sorts them.

**A bot learns from its mistakes, and files each lesson where it fires** (#973, [learn.rs](../src-tauri/src/bots/learn.rs)). The failure this answers: a bot forked a Boat sandbox whose Claude login had expired, fixed that one sandbox, and saved the lesson to `memory/`, which nothing loads. So there are three homes. Standing rules go in `AGENTS.md`, which the bot may now add to itself but never remove a rule the user wrote from. How-tos go in skills at `.claude/skills/<name>/SKILL.md`. Facts go in `memory/`. Claude Code reads the skills since the bot runs in its folder. Codex and pi read `.agents/skills` and never `.claude/skills`, so `ensure_skills` links one to the other; both follow the link, checked against Codex's `skills/list` and pi's docs. The prompt asks the bot to fix the cause in the same turn as a failure or correction, and to say so in one line. Its rules come from Hermes Agent: lessons, not logs (the check that would have caught it, no PR numbers or dates), and its "Do NOT capture" list. Caps: 8k for a skill, 4k for a memory, 16k for instructions. A skill or memory over its cap owes a review. Instructions over theirs do not, since a review may only add there: the prompt's cut notice has the bot ask the user what to cut.

**Dray asks for a review when the bot doesn't learn on its own.** `note_prompt` reads each prompt as it is logged: the reader's message against a list of correcting phrases, and a task's report against failure words (never a stall nudge). Where the turn that took it changed no lesson, Dray sends a hidden `Review:` prompt ([review_prompt.md](../src-tauri/src/bots/review_prompt.md)) once that turn ends. It is sent through `send_review` and marked as Dray's own the way the kickoff is: `user_message.kickoff`, so an older app hides it too, matched on session *and* text so a message the reader sends meanwhile is never taken for one. The bot patches a skill, its instructions or memory, or ends silently. A turn a review was in never owes another. Only a turn opened by a review alone counts as one for the add-only rule, kept apart from "a review joined", so a review queued behind the reader's message cannot claim their turn. A chat gets one review per five minutes, and its reply never draws, live or logged (`inReviewTurn`, `in_review`). **A review may only add to `AGENTS.md`**: where its turn took a line away, `keep_rules` puts the file back before the commit. The phrase lists are generous on purpose: a false hit costs one silent turn, a miss costs a lesson.

**A plain line in the chat shows each lesson, and opens to its diff and Undo.** `commit_turn` reads its own commit back, keeping only `AGENTS.md`, `.claude/skills/` and `memory/`. Each file gets a summary line: the first rule added (a heading only where nothing else was), or the file's frontmatter `description`. Dray logs these as a `learned` event right after the turn's `turn_completed`, minted on the read loop's own counter, since `post_event`'s slot lock can be held by a send waiting on that loop. A click reads the file before and after (`bot_learned_diff`) into `DiffView` beneath the line. Undo (`bot_undo_learned`) reverts that one file as a reverse patch, so a later edit to it survives and an overlapping one refuses. It commits just that file as "Undone by the user: …", which the prompt tells the bot never to add back, and logs `learned_undone`, which turns the row to Undone. A row logged before the move names `INSTRUCTIONS.md`: its diff still reads from history, and Undo points the patch's header at `AGENTS.md`, where the rule now lives. A hidden review-shaped note then tells the bot, since a running child loaded its instructions at start and would keep following the undone rule. A file the bot is mid-edit on refuses too. The frontend draws them from `botItems`' `learned` items as `LearnedLine`: the kind in grey (`lessonKind`: Rule, New skill, Removed memory), then the summary, with no background, border or icon, and Undo, the one icon, only under the open diff. Picked from six takes on [learned-chip.html](../demo/learned-chip.html). Hermes keeps a ledger of skill writes; here the folder's git history is that ledger.

**The reader can hand a bot a pull request** from the pull requests page (Send to bot, [pull-requests.md](pull-requests.md)): Dray makes the task itself, `start_pr_session` with the bot, on the PR's own branch, hidden under the chat on the chat's picks, and notes it for the bot like any act on its tasks it did not make ("the user started it on PR #n"). No `dray` flag does this, so a bot cannot yet start a task on a PR's branch itself.

**The reader can hand a bot a task already running** (#1395, `attach_to_bot`): the sidebar row's Attach to bot, `dray session attach <id> --bot <name>`, and the `attach_session` serve command iOS will use. Detach's reverse, and the one place `parent_session_id` stops meaning who created a session. `store::attach_session` hangs the task under the bot's newest chat session and hides it and everything below it, as a bot's own tasks run, which takes it out of the sidebar and into the Tasks tab; it also moves `modified`, so the stall clock starts at the hand-over rather than nudging the bot about a week it was just told of. Reports then follow on their own: `report_to_parent` only asks whether the task is in a bot's tree. The bot is briefed by a message from the task, the way a stall nudge is, starting "Attached:" and naming the project, branch, whether a turn is running and the task's last message. A child already running read its system prompt with no bot to report to, so it gets a hidden lead-in on its next prompt (`bots::lead_in`, on the hand-over queue) saying its turns now go to the bot; a later spawn reads the task block itself. Refused for a bot's own chat or a routine run, a task already in a bot's tree, a settled one, a bot with no chat yet, and a task on another machine than the bot: its reports go out from its own server, and a bot elsewhere would need the outbox a cross-machine create sets up. The sidebar offers only bots on the row's own server.

**A bot keeps its turns short, and long work leaves the chat** (#1152). It answers and takes quick looks inline. Repo changes, work wanting its own branch or PR, and anything on another machine go to a task. Other long or multi-step work (setting up a machine, checking logs, research) goes to a **background subagent on Claude Code and grok**, the two harnesses measured on a Mac running one past the turn and waking the bot with its result (`long_work` fills `{long_work}`, so `system_prompt` takes the harness). Every other harness is told to start a `--no-worktree` task instead, which works on any harness: **Codex** keeps the child running but never wakes the parent, so the result reaches only the subagent row; **fx** holds the parent's turn over ACP until the `subagent` call answers; **pi** has none. **Each line names the tool and its background flag** (the Agent tool with `run_in_background: true`; grok's `spawn_subagent` with `background: true`), since Codex, told only "a background subagent", reached for a background shell first. Re-measure before moving a harness across: a subagent that holds the turn or never reports back holds the chat or loses the result. One packed shell command still counts as several steps: worded without that, a bot ran a whole machine snapshot inline as one `Bash`.

**Everything under a bot runs hidden** (`create_session`, `under_bot`, `in_bot_tree`): its children and theirs, whatever `--hidden` said, on whichever machine they run, and `dray draft start` too, which on another machine is tracked for reports like a create. A server holding a bot's task from another machine knows no bot, so its walk ends at a task it owes reports for (`remote_reports::owed_tasks`): that task's own sub-tasks there run hidden and report to it like a local bot task's. A forwarded create from a bot's tree also carries `hidden: true` itself, for a far server older than that. Settling such a task still takes its sub-tasks with it (`keeps_children` asks for a bot here), since nothing on that machine could adopt them. The walk is bounded at 8, so an index pointing a session at its own ancestor costs a wrong answer rather than a hung turn. A bot's folder is no project, so a create naming it or anything inside it is refused with "pass --project" rather than starting a worktree of the bot's notes.

**A bot's task's sub-tasks outlive it** (#1072). A task may start tasks of its own, whose parent is the task, not the bot. Settling or deleting the task leaves them running, where any other session's hidden children go with it (`keeps_children`; a bot's own chat still takes its whole tree, and the app reads each child back rather than repeating the cascade from the one side of the index it holds; a hidden child on another server, which the parent's server cannot reach, is settled or deleted by the app unless `session_keeps_children` says the parent keeps it). Their reports, stall nudges and merge cards go to the task while it is live, and otherwise to the nearest live session above it, up to the bot (`live_ancestor`); the task's prompt tells it sub-tasks report to it. Clients hold one side of the index and cannot walk through a settled parent, so the server writes `adopted_by` on each sub-task whose parent is not live — that nearest live ancestor — whenever a task above it is settled, unsettled or deleted (`readopt`), and announces the rows it changed. Settled sessions below get one too, since a settled child is still the step its live children walk up through. A deleted parent's place in every walk is that adoption (`tree_parent`, `treeParent`), and its tasks on other machines are tracked under the ancestor instead (`retarget`, put back if the delete fails). Detaching clears it. So the Tasks tab and iOS's Tasks sheet list a sub-task under its adopter and the sidebar keeps it hidden. A row does not say which task started it: that matters to the bot, not the reader.

**A bot's folder is a local git repository, and Dray commits it after every turn** (#893, `start_history`, `commit_turn`). The point is a timeline: when the bot overwrites or deletes something, it or the reader can look back and restore. Made with the bot, and on first use — any spawn, through `system_prompt` — for a bot older than this. Dray commits, not the bot, which could forget: on every main-thread `TurnCompleted` in a bot's folder, everything staged with `add -A` and committed where anything changed, the message naming the files. **Awaited inside `ingest_event`**, before the queued flush, or the next turn could overwrite a note before it was saved. Every commit is given the bot's name and an email made from its id, never written to config once, which a setup cut off after `init` would skip; so no global identity is needed. Every git call here passes `-c` for no hooks, no global ignore file and no signing: a reader's hook could fail or hang a commit, their ignore rules could leave its notes untracked, and a signing key would prompt every turn. No remote and no push, and the prompt says so; it tells the bot the history is there, not to commit. `.git` is looked for rather than asked of git, which would answer for a repository the home sat inside. **The app's git features stay off for a bot's chat**: no handoff row at all, not even Run server or the reader's own buttons, and no pull request lookup (`inBotFolder` in `App`), and the side panel never had Changes or PR. The turn snapshots still run there, unread.

**Every turn a child closes is sent to its parent, by Dray, not by the agent** (`report_to_parent`, from `ingest_event` on a main-thread `TurnCompleted`). A report the agent is asked to send is one it can forget — OpenBot's weak spot, whose delegation rules are prompt-only. It goes through `send_message`, the path `dray session send` takes, so the bot reads it exactly like a message the child sent. Only Claude Code fills `final_text`; the others say their answer in `AssistantText`, so the last one of the turn is kept (`LAST_REPLY`) and used instead. A turn with no text still reports, saying it failed or ended silently, and a child dying mid-turn reports from `settle_dead_child`, whose close never passes through `ingest_event` — so the bot is never left waiting. Each task is told so in its own prompt ([task_prompt.md](../src-tauri/src/bots/task_prompt.md), added by `system_prompt` where the session's index entry has a parent in a bot's tree): unaware, a task also sent its answer with `dray session send`, and the bot read every report twice. The same prompt asks a task to end with proof that scales with the change: one short video for a new interaction, a cropped screenshot (`dray image add`) for a static change, a line for a small tweak, the tests that ran for an invisible one, and whatever the reader asked for over all of it. Captured only where nothing of the reader's own is driven (a sandbox, a VM, a simulator, the session browser) unless the reader asks; the bot prompt has the bot pass each path on, where it draws (#1057). A settled child or a settled bot chat takes no report: sending would resume a conversation the reader closed. The flag is read again after the send and the chat stopped if it was settled meanwhile, since settling writes the flag before it stops the child. **Boxed**: the read loop calling it lives inside a harness's `init`, and the send can reach `init` again, so unboxed the compiler cannot name either future.

**What happens to a bot's tasks outside its chat reaches the bot within seconds, as a quiet turn of its own** (#984, #1305, `SINCE` in [bots.rs](../src-tauri/src/bots.rs)). A merge, settle, stop or delete is noted per bot folder, one line per task with its acts folded in, eight tasks at most, each act a clause naming who did it ("the user settled it", "its PR #9 was merged"). Ten seconds after the last act (`wake`), so a merge and the settle behind it make one turn, the list goes to the bot's chat as Dray's own prompt through `send_review`: logged `kickoff`, drawn as nothing, and taken like any prompt by every harness, Claude Code's included — no CLI tells an agent a PR merged. Waiting for the reader's next message was the first take, and a task report waking the bot first then had it ask the reader to merge what was already merged. A prompt reaching the bot before the wake carries the list instead, ahead of its text as before (`deliver_prompt`, sent and never logged), and the wake then finds nothing to send. A wake whose send fails puts the list back and tries again, its wait doubling, four times in all. A routine's run shares the folder and never takes it. The bot prompt has it settle what merged, bar a task that moved on to other work, and end the turn silently unless something needs the reader.

Recorded where the act lands, so every client and machine counts. On the client wire: `set_session_flags`, `interrupt_session` and `delete_session` in `serve.rs` — not the shared functions, which `dray` also reaches, since that is how the bot acts itself; so a reader's own `dray session settle` in a terminal goes unnoted. `merge_pr` (only ever a client's; agents merge with `gh`) weighs the task the client names as `settle`, wherever it runs; with a `github:` repo key, tasks on other machines whose machine last reported this PR (`stalls::remote_with_pr`); and this server's own tasks in that checkout. **A merge note tells the bot to settle, so it goes only to a task still on the PR's head** (`on_branch`): the head is read back from GitHub, which answers none for a fork's PR, and the task's branch off its tree's HEAD, here or on its machine (`work_status` there), since a task that moved on holds work the merge did not land. `settle_merged` notes the settle it makes. **A task on another machine is noted by its own server and collected by the bot's** (#958's channel): with no bot there, the act is kept in `parent-reports.json` (`KeptAct`) for the owed task it hangs under, answered on the next `parent_reports` poll beside its reports — even where the settle made the task gone — and acked like one. Such an act is kept *before* it runs and dropped if it fails (`drop_act`): a settle or delete is what makes the next poll call the task gone, after which nothing asks for it again. A server collecting for a bot further up, on a third machine, keeps the act again for that one, and acks it only once kept. They are noted before that poll's facts are taken in. **A merge made on GitHub, or by an agent, is seen by the stalls judge**: a bot task's PR read open on one pass and merged on a later one is noted as "its PR #n was merged", unless a merge through Dray already told it (`MERGES_TOLD`); a PR first seen merged, as after a restart, says nothing. A stop is noted *before* it runs and taken back if it fails, since the stopped task reports at once and the report must carry why; any other act on a task here only once it landed, since a sent note cannot be taken back. The list is trusted text, so it carries no PR title (the PR author's words), a task title is kept to one line that cannot close it, and a fork's PR never matches. In memory on the bot's server: a restart inside the ten-second wait drops it; on a task's server, kept a week for collecting.

**The frontend.** Bots lead the live sidebar in a Bots section (`BotRow`: the session row's rail and orb, nothing else); their ongoing chats leave the session list (`inSidebar(items, bots)`), their settled ones stay in the settled list, the only way back to one. The section reads the active side of the index alone and is empty while the settled side is loaded. The space check spares anything in a bot's tree (`inBotTree`), or a task opened from the Tasks tab in another space's project closed at once. Opening a bot with no chat aims the empty composer at its folder (`handleNewBotSession`, not `handleSelectProject`, which would remember a bot as a project) and the toolbar drops the project pickers without naming the bot, which the header already does; a send there takes no worktree. A bot chat always runs on Auto (`botStance`), so its toolbar draws no stance picker, except on an agent with no Auto. Cards still come to the bot's chat (#807). ⌘⇧↑/↓ and the jump digits walk the bots' chats first, then the sidebar's order, so ⌥1 is the top bot. In a bot's chat `&` offers its own active tasks — not settled, not set aside — since they run hidden in projects the composer is not on.

**A bot's side panel is Tasks and More**: no PR and no Changes, since its folder holds notes, not work to review. With Tasks alone the strip draws no tab row, just the list under it, and More counts only media the chat hides (`hiddenInBotChat`: tool-result screenshots, reports' pictures, a recording no reply names), since the rest already plays in the chat. **The bot's own runs sit under its task list, not in More** (#1192, [BotRuns](../src/components/BotRuns.tsx)): Subagents, then Background tasks, each drawn only with rows. Running subagents show; finished ones fold under the Subagents heading, which carries their count and a chevron and is closed by default; each shows its time. The chat loads only its tail, so finished runs are also read off the logs of every session in the chat (`list_subagents`, lifecycle lines only), read backwards from the end until ten finished runs are in hand, with a byte-offset cursor for Load more; the count reads "10+" while more remain; a run known only from the log has no events here, so it lists but does not open. Tasks lists its children at any depth off `crewRows` — which walks every held session, not the space's, since a bot hands work to any project. Pinned first, then by what the reader acts on (#1074, `taskRuns`): waiting on them, a PR ready to merge, one about to be (checks running, review needed, mergeability computing), idle, working, set-aside ones last and faded. Not the sidebar's order, which leads with working: here a running task needs nothing yet, and a task's PR state outranks its working, since Merge is what the reader came for. iOS's Tasks sheet sorts the same way. Each row is the sidebar row's: its face (the working orb mid-turn), title, the PR glyph *with its number*, ⋯ and Settle on hover, and the sidebar's right-click menu bar Mark unread. **A ready pull request draws Merge on the row** (`readyToMerge`, the PR panel's split button and confirm step cut to a row): an agent's own `gh pr merge` is often refused by its permission classifier, so the reader lands them. It merges from the repo root, since the worktree may be gone, then settles the task and removes its worktree — landed work needs no tidying by hand. Whatever the tree still holds goes with it, unasked, from every merge surface (`mergeTask`: the row, Waiting on you, the merge card), and a bot's task the reader settles by hand loses its tree the same way: the settle notice's "Delete worktree?" is for the reader's own sessions alone (#1085). iOS hands the task to `merge_pr` as `settle` instead, and the server settles it once the merge lands (`settle_merged`), on whichever machine holds it: the phone holds no row for a task on another machine, so its own settle skipped those (#1208). The same branch rule holds, read off the tree's HEAD on the task's machine (`work_status` there), so a machine that does not answer is left to the bot. `merge_pr` answers whether it took the settle, and a server from before it answers null, which sends the phone back to settling a task it holds itself. The bot's prompt tells it to settle finished tasks itself with `--delete-worktree`, never one whose work is unmerged and still wanted.

**A bot's tasks don't sit stalled unseen** ([stalled.ts](../src/lib/stalled.ts), `useStalledTasks`, [StalledTasks](../src/components/chat/StalledTasks.tsx)). Each idle task is sorted by its PR's `prStatus`. **Only what truly waits on the reader reaches the reader**: a PR ready to merge, and a task idle on a question, each once it has sat `STALL_MS` (2 minutes). Everything else goes to the bot. Failing checks, a conflict, a branch behind base and changes requested are the task's to mend, so the bot gets a **nudge** naming the problem and has the task fix it with `dray session send` — **with no wait**, on the first check after the task goes idle. **A draft's failing checks are not among them** (#1198): a draft waits on the reader's look, with feedback committed locally and unpushed, so its red check (often Greptile's first review) is stale by design, and the task waits on the reader like any draft. Read as a fix, each poke of the bot's moved the task, minted a new stall and nudged the bot again every minute or two. The one gate is a mark asked for after the task last moved: a mark from before the task's push would nudge the bot about checks the task had just fixed. Both sides are on the app's clock — `readAt` is stamped when the `gh` read was *issued*, and the move when the app saw `modified` change, since `modified` is the server's stamp and a remote clock running behind would let an old read pass. A mark that never refreshes falls back to the 2-minute wait. A task idle on the reader nudges the bot too, with its last message (`nudge_bot` in [orchestration.rs](../src-tauri/src/orchestration.rs), reading the log tail): the bot answers it where the reader's earlier word settles it, and otherwise writes one line with `dray session need <id> "…"` (`TaskNeed` on the index, protocol v19). A nudge is a `send_message` from the task, so it is sender-tagged and hidden like a task report (#912), and the bot prompt tells it to post no chat reply. **The card draws two kinds of row**: a ready PR (face, title, PR glyph and number, Merge, time) and a task idle on the reader, which carries its need underneath once written after the task last moved (`needLine`: `need.at >= modified`). While the bot is still on a waiting task its row draws a skeleton in the line's place; if the bot answers the task itself, the task moves and the row goes. A need clears itself the moment the task moves. **A ready PR stays on the card while GitHub works out its mergeability again**, as it does for every open PR after a merge: same key, so no second notice or nudge, with Checking… where Merge sits until GitHub answers (#1112). Running checks, an unknown mergeability on a PR not last seen ready, a merged PR, mid-turn tasks, ones with a background shell or subagent the agent waits on, ones behind a card, set-aside ones and ones on the usage limit are all left out. One nudge per stall: a stall's key is task, kind and `modified`, kept in local storage (`ade.nudgedStalls`) so a relaunch sends nothing twice, and nudges hold for a minute after mount so PR marks have landed — unread, a ready PR looks like an idle task. PR marks are read for every bot task's repo, not just the open chat's, and those holding an open PR keep reading every five minutes while the window is in the background, where the rest of the marks pause. **Stalls are read for every bot, once a minute**, so new card rows landing while the window is in the background raise one notice per bot ("Ops: 2 tasks waiting on you"), counting the rows the card draws (`cardRows`: no fix stall, nothing dismissed). Dray Island shows it on its done pill, the note in place of "Done", and the banner is the fallback where no Island runs; the first read after launch is silent. **A row click stays in the bot**: what the bot said about the task opens under its row ([BotReply](../src/components/chat/BotReply.tsx)), and a second click closes it; on iOS a tap opens it in a sheet with Open task, and the card there holds five rows too (#1181). That is the bot's reply to the task's newest report it answered, never the task's own message, which was written for the bot. A report the bot let pass — answered by messaging the task, as a real haiku bot did, or a turn that failed — is looked past, up to ten, since its reply to the one before is still its latest word on the task; a failed turn's error sentence is never a reply. The bot's server finds it with `bot_task_reply` ([bots.rs](../src-tauri/src/bots.rs)), in two passes: back from the end of its chat's log, each 256 KB chunk searched for the task's id and only a line holding it parsed, to a report; then forward, parsing to the reply's end. On a real 20 MB bot chat (release) that is ~1.5 ms for a recent report and 15–35 ms walking the whole log, capped at 32 MB. It is read only when a row opens and dropped when it closes. Reports landing back to back share the text after them; a stall nudge closes a reply and opens none. With no reply — none written, a sub-task reporting to its parent, a failed read, a server too old to ask — the click opens the task instead (iOS reads before deciding, so no sheet flashes). Scrolling the chat back to that reply, the first take, read up to twenty pages on a 1300-turn chat and stalled the app for seconds; the task's last message, the second, showed the reader the wrong side of the conversation. **Open task**, shown on hover with its ⌘-click hint, and ⌘-click on the row are the ways into the task. Dismiss stores each row's key, so it comes back only after the task changes and stalls again. Merge is the Tasks row's (`MergeControl`, `mergeTask` in `App`). A Haiku summary of the last message (`task_need`) and a glimpse of the message itself were both tried for the need line and dropped: the bot reads the task with its context and can act on it, where a summary only restated it. Demo: [stalled-tasks.html](../demo/stalled-tasks.html).

**The bot's server judges the card, and nudges the bot itself** (#1259, [stalls.rs](../src-tauri/src/stalls.rs)). The rules below were the desktop's `stalledTasks` and are now that module, so the desktop and iOS draw the same rows and the bot hears of a stall with no app open. It reads only what lives on the server: the index, the live flags clients get in `live_state` (`serve::live_flags`: behind a card, background tasks, serving), and PR marks it asks `gh` for itself, every 30s for repos where a task could stall (10 minutes after `no_cli`/`no_remote`, a minute after any other failure, the last good answer standing). It runs every 15s and at once, debounced, on any event that can put a row on or off (`stalls::poke` from `Hub::publish`). A task is not judged until its repo has been read once, the server's stand-in for the app's one-minute hold. Fix asks and nudged marks live in `stalls.json`, so a restart never nudges twice; `nudge_bot` checks and writes the same marks (`nudge_mark`: task, `modified`, what it says), so an older app nudging beside the server is told it already went. **A task on another machine is judged by the bot's server**: that machine answers `facts` (`TaskFacts`: item, busy, asking, background, its own PR read, `prFresh`, `prKnown`) on the `parent_reports` poll it already serves, so no new connection is made, and the bot's server nudges it through that machine's `nudge_bot`, whose outbox brings the nudge back. A poll that fails marks the machine's tasks offline from what it last said (`stall-remote.json`, so a restart keeps them), reads their PRs by GitHub repo through its own `gh`, and nudges nothing. **The wire**: `bot_stalls` answers every bot's `BotStalls` (`botId`, `chatId`, `rows`, `tasks` with set-aside ones left out, `fixes`); `bot_stalls_changed` carries one bot's when it moves; `live_state.stalls` carries all, held in `Live`, and its absence is how a client knows the server is too old; the welcome says `stalls: true`. A `StallRow` is `key` (the desktop's own format, so dismissals carry over), `kind` (`waiting`/`ready`), `checking`, `since` (unix ms, the order), `need`, `pr`, `item` (as the task's own server indexes it), `machine`, `offline`, `repo` (the PR's, so a client that cannot reach the task's machine merges through the bot's server). A task's server passes along the facts it collects from machines further on, named, and forwards a nudge for one (`forward_nudge`), so a sub-task two machines away still reaches the card. Dismissals stay per device. **Clients** ([serverStalls.ts](../src/lib/serverStalls.ts), iOS `Store.stallCards`/`judgedStalls`) draw a task they hold from their own row, so open and merge go where they always did, and leave out one that moved since the server judged it, so a row still clears the moment its task moves. A server too old to judge, or one not connected, is judged by the client as below.

**A task left serving counts as idle** (#1221). Tasks often end their turn with a dev server up for the reader to try, and that task waits on the reader, not on work. No harness says whether a backgrounded command is a server, and a command's text is a poor guess (`pnpm dev`, `cargo run`, `make serve`), so the server reads it off the OS: every 15s, for each session whose turn is over with only shells in the background (`local_bash`, grok's `bash`; a subagent is the agent working), it counts the agent's child shells that hold a localhost listener anywhere under them (`serving` in [local_servers.rs](../src-tauri/src/local_servers.rs)). As many listening shells as tasks means serving; a build beside a dev server is two tasks and one listener, and stays working. Only shells count, so an MCP server listening on its own port passes for none. The verdict goes out as `session_serving {sessionId, ports}`, unlogged, held in `serve.rs`'s `Live` for a reconnect, and voided by the next `background_tasks_changed` on server and client alike. `CrewRow.serving` carries it: `background` reads false, so the Tasks row draws its face with the port beside it, files with idle, and reaches Waiting on you and the bot's nudges like any idle task. iOS reads the same event (`Store.inBackground`). **A test run hosting a server is still working**: Playwright's `webServer` or an integration test binding a port ends on its own, so a shell counts only while no live process under it is a test runner (`is_test_run`, read off each process's argv: `test`, `test:e2e`, `jest`, `pytest`, `cypress`…). The shell's own command line is skipped, since it holds the agent's whole script and `cargo test && pnpm dev` past its tests is serving. CPU was rejected (a server in use burns it, an e2e run waiting on a page idles), and so was "the listener is the shell's own command", since `pnpm tauri dev` wraps its server and Playwright nests one under itself.

**A ready PR is nudged too, and its row takes a need only where the task asked for one.** `nudge_bot` takes `ready` with the PR number and sends the task's last message, as for a waiting task. Where that message asks the reader to try or check something before merging ("this part is untested"), the bot writes a need and the row draws it under the title; otherwise the bot writes nothing and the row stays Merge alone. No skeleton on a ready row, since most never get a line. A need left from the PR's wait on review is cleared first, since approval does not move the task and the line would outlive the review; so a ready stall is nudged even under one. An older server takes the nudge as a waiting one, `ready` being an argument it never reads.

**A bot schedules its own checks as routines, and the reader sees and stops them** (#972, [routines.rs](../src-tauri/src/routines.rs), `dray bot routine`, [RoutinesSection](../src/components/RoutinesSection.tsx)). Built after OpenBot's routines and Hermes Agent's cron jobs. A routine is a name, a prompt, a schedule (`--every 30m`, at least 5m, or `--at 09:00` with `--days`, local time) and an optional `--check`. **The server runs them**, so they fire with the window closed: `routines.run` ticks every 30s against the wall clock. **Each run is a hidden session of its own** (`start_routine_run`): in the bot's folder, on its chat's agent, model, effort and stance, no worktree, its parent the chat, so it reports back the way a task does (`report_to_parent`) and the bot decides what the user hears. Its prompt says what it is, that the user never reads it, and that it may ask the bot for context with `dray session send`. A run's own send to its bot marks it waiting (`asked`): the turn that ends after asking records nothing and reports nothing, and the run stays in flight, under its cap, until the turn after the answer. `current_chat` leaves a run's id alone, or the bot's answer would be redirected to its own chat. Not through `create_session`, which refuses a bot's folder as a project. A session in a bot's folder is otherwise part of the bot's chat, so the run is stamped `routine_run` on its index entry's first write (`pending_run`), and the chat (`chat_sessions`, `botChat`), the task trees (`crew`, `crewRows`) and `last_session_of` all skip it; nothing in the app draws a run. Its report is signed as the routine (`sender`: `[message from the Dray routine …]`), which `learn` never reads as a failed task. The run's first `TurnCompleted` is its result (`turn_ended`): silent, replied (its first line) or failed. **Runs of different routines go side by side**; only a routine whose last run is still going waits, staying due. **A run that found nothing ends with `NOTHING NEW`, and the bot is not woken for it** (`found_nothing`): asked for no text at all, Haiku wrote a line explaining its silence every time, so a word to match replaced silence. **A run stops at 30 minutes, or its interval where shorter** (`run_cap`, `time_out`): settled first so its dying child reports nothing, recorded "Timed out". **The next run is written before the run fires, measured from now**, so a Mac waking from a night's sleep runs an `--every` routine once, never once per slot it slept through. **An `--at` routine catches up only the same day**; a slot from an earlier day is recorded "Missed", since a morning digest at midnight is noise. A run more than two minutes late is told by how much and asked to judge what is still worth reporting. **A run cut off by a restart is tried once more**: `run_session` on the file names it, the next start sets `retry_due`, and a retry cut off again records failed and waits for its next slot. A run dying while the server exits (`session::exiting`, set by `hold_sends`) counts as cut off, not failed, since a SIGTERM stop kills each child before the process ends. **A restart waits for a check too**: each tick and each run until its session exists hold `Sending`, the guard a send holds, so `close_if_idle` sees them. **A check runs first, in the bot's folder**, with the agent's `PATH` and a 60s cap, and starts a run only when the SHA-256 of its stdout differs from the last run that got through's — saved when the run's turn ends well (`SEEN`), never at its start, so a run cut off, failed or timed out leaves the change new for the next one (Hermes's rule: exact bytes, so a check must print stable output); the first run starts one as a baseline. A failing check is never a change: the first failure of a run of them starts a run whose report lets the bot mend it, the rest only record. `routines.json` under the home holds the list, outside the bot's folder, whose every turn is committed and would churn with run times; deleting a bot drops its routines, and the scheduler drops any whose bot is gone. Schedule and result outcome are strings and options rather than enums, so a kind a later build adds cannot fail an older one's read. **Routines are a section of the More tab**, under Attachments, drawn only where the bot has one, as every More section is. Each routine is a card with a centred clock, the name, "Every 2h · Next in 34m" or "Paused", and the last result with its age, red where it failed. A switch turns it off and on, and Delete sits in the right-click menu. A click does nothing: what it does, running it now and changing it are asked of the bot, which has `ls`, `run`, `rm` and `add` for that, so the section is a view and an off switch rather than a second editor. It reads `list_routines` from the bot's server on every `routines_changed` and once a minute. **Claude Code's own schedulers are refused in a bot chat** (`--disallowedTools`: `CronCreate`, `ScheduleWakeup`, `RemoteTrigger`, `/loop`, `/schedule`, OpenBot's list), and the prompt bans every other kind, since the reader can neither see nor stop that work. The stall checks stay in the app: they read PR marks the app polls from `gh`, which the server does not hold. Not built: one-shot reminders, cron expressions, a calendar, a history beyond the last run.

**A task mending its PR says so on its Tasks row** (#966). A fix stall nudges the bot and the task goes off to work, so the row reads "Fixing merge conflicts · 3m" under its title, in a muted line a step quieter than the need line: the PR status the fix was asked about, and the time since, through `compactAge`. No model writes it. The time is recorded when the nudge for that stall lands — `nudge_bot` answering `true`, never a bare success, since an older server answers `null` and a task's server holding no bot used to answer that way with nothing sent — and by nothing else — the merge card's Fix conflicts records none — in `useFixAsks`, kept in local storage (`ade.fixAsks`) so a relaunch still says how long. A second ask about the same PR and status keeps the first time, so a task stuck on one problem shows how long it has been. The line goes the moment the PR moves off that status (`fixAskDone`): conflict gone, checks running again or passing, merged, a new PR. `unknown` holds it, being GitHub's recompute after the push. Asks are pruned in `useStalledTasks`, which reads every bot's tasks, not in the tab, which shows one bot at most.

**A task opens as a tab in the bot's row** (#881, [taskTabs.ts](../src/lib/taskTabs.ts)). A click on a Tasks row, a "Started a new task" line or a "Messaged" line adds the task after everything else in the bot's titlebar row and lights it: the main column, composer and side panel are the task's, the row stays the bot's, and the sidebar keeps the bot marked. ⌘-click switches to the task alone, the way a click used to, with the breadcrumb back. × , middle-click and ⌘W close a tab; ⌘⇧T puts one back. Settling a task leaves its tab, deleting it takes it. In memory, like the rest of the row, and keyed by the bot's id rather than its chat's session, so an agent switch, which starts a new session, keeps them. The bot's row is drawn over a task only while the task is open in it and the bot was the last row a task tab was picked from (`stripOf`'s `via`); ⌘-click clears that, so the task draws its own row. The task's own Diff and files are not in the bot's row; the side panel still reaches them.

**The row shares one side panel** (`rowOf` under `openKey`, the split group's mechanism): open or shut, and which tab is picked, are held under the bot chat's id for the chat and every task lit in its row, so the pane stays put while the reader moves along the row and shows the lit session's own content. A pick the lit session does not draw — PR on the bot, Tasks on a task — falls back to its default as anywhere and comes back where it is drawn.

**Every task has its own browser, and the bot keeps its own** (`bots::browser_owner`, `botBrowser`). The bot chat's pages live on its oldest session, which an agent switch leaves in place, and the server resolves a step from any of the chat's sessions to it. Tasks were once routed into the bot's browser too (#881) and that was undone: a recording locked every task's tabs, and with many tasks everyone's pages piled into one strip and agents picked the wrong one. The row's page tabs are the bot's, and a task's own show when it is opened alone (⌘-click). A link from the bot chat or a lit task opens as a new page tab in the row, in the bot's browser (#1121).

**Diff and Files in a bot's row pick which session they show** (#892, `PickTab` in [taskTabs.ts](../src/lib/taskTabs.ts)). + offers both every time, so several of each can be open, each on its own pick; an ordinary session's + still hides one already open. The pick is the first row of the view's side column ([PickTarget](../src/components/PickTarget.tsx)), above the sub-tabs or the file filter, and the tab is labelled with the picked title. Diff lists the bot's tasks alone, since its folder holds notes, not work to review; Files lists the bot's own folder first, then the tasks. The list is the Tasks tab's — active tasks at any depth — newest activity first, and a new tab opens on the newest; Diff is greyed out until there is a task. The bot chat stays selected while one is lit (view `pick`), so the reader looks at a task's work without stepping into it. Picks are keyed by bot id like task tabs, and the bot's own folder is picked as the bot id, resolved to whichever chat session it has now, so an agent switch keeps them. A Files pick's files open as tabs of the row, as Files does, in a store keyed by tab *and* target (`pickFilesKey`): repicking brings up that task's own set, and the open is quiet (`openInFiles`'s `bring`), or it would flip the bot chat's own view to Files. Those stores are never written to local storage, like the tabs. With the task's transcript unloaded, its index `modified` and status stand in for the turn revisions the views re-read on. Settling a task closes its Files picks, since a settled task has nothing to open; its Diff picks stay for review until the worktree is deleted, and deleting the task closes every pick on it — all read off `session_changed`, since the bot settles tasks as often as the reader does. A settled target leaves the index's active side, so the lit pick asks for it with `session_index_item` on every index change.

**A bot chat opens on its tail and reads back as the reader scrolls** (#955, `askOlder` in [Chat](../src/components/Chat.tsx)). The chat never ends, and the transcript's own rule — read the tail, then page the rest in until the log is whole — drew all of it: on a 36MB, 1500-turn log the first reply painted in 0.4–1.6s and the page then never went quiet, ~115s of main-thread work in two minutes with half the replies drawn. Nothing needs the whole history (task chats share this since #1155, see [rendering-code.md](rendering-code.md)): the chat reads a page further back whenever the reader comes within a screen of the top, or while the pane holds less than a screen above its bottom, and puts the row at the top of the view back where it was when a page lands. Opening the same log now paints its first reply in ~0.3–0.7s and is quiet ~100ms later. Three things lean on history the chat may not hold yet. **The NEW divider** waits until a message of the reader's is loaded, or the whole chat is, since the first unread reply may sit above the tail (`unreadStart`); a reply arriving after the open never moves it. **A row picked from "Waiting on you"** reads back 64 turns at a time until the task's reply is drawn, since every page lands as one render of the whole app; and a jump to within a screen of the top is instant, because a smooth one is cut short by the next page landing. The hunt holds the window whole and no scroll reads as the reader back at the end until it lands (#1112): a window left following dropped each page the moment it landed, and Chromium's scroll anchoring, or a glide's first frame, sat within reach of the end and let the window go with the row in it. Checked with [bot-focus-jump.html](../demo/bot-focus-jump.html). **Rows are memoized and compared by the events they were built from** (`ChatRow`, `sameRow`), so a page landing draws only its own rows, and the focus block is spliced into the one keyed list, since moving the rows into slots remounted every row in the chat. The transcript's faces are `still`: blobatar's gaze measures each face on every scroll anywhere on the page even with its eyes at rest, hundreds of layouts per scroll once history is loaded. Timed with [bot-chat-open.html](../demo/bot-chat-open.html).

**A chat left open draws a window, not everything it has held** (`drawn` in [Chat](../src/components/Chat.tsx)). Reading back loaded rows that nothing ever let go, and every turn that landed added more; on a 2600-event log read back, each streamed event cost ~40ms. While the reader follows the bottom, the chat draws the last 24 turns and slides as turns land (`lastTurns`, cut only at a main-thread message so a task's start and its id stay together). Scrolled up, the top holds on an event, so landing turns never move what the reader is looking at; nearing it draws 16 more held turns before any page is read (`earlierTurns`), and once everything held is drawn, pages draw as they land, as before. Back at the bottom the window slides again and the pages read above it are dropped from memory (`dropOlder`), back to the nearest page start, whose byte offset `loadOlder` recorded. Turns that landed live stay held, since nothing says where in the log they began. **`taskOf` changes only with a session or a title**: it followed `crew`, which moves on every status change, so each `session_status` redrew every row. `bot-chat-open.html`'s `&soak=<turns>&chat=<id>` streams synthetic turns into the open chat and reports per-event cost, DOM and heap; `&top=1` reads the whole log back first.

**The chat draws the conversation, not the work** ([BotTranscript](../src/components/chat/BotTranscript.tsx), [botTranscript.ts](../src/lib/botTranscript.ts)). Tool calls show only as the live orb line naming the current tool. A task the bot starts is a "Started a new task [face] title" line, drawn from the `task_started` event the server logs in the bot's chat as it creates a session whose parent is that chat (`announce_task` in orchestration.rs, #1159) — wherever the task runs, and from `dray session new` or `dray draft start` alike. Reading the bot's shell call missed a task whenever the id line never reached the tool output: `| tail -1`, a script, a harness reporting output its own way. That reading stays only for logs written before the event, for an id no event names, so no task draws twice. A message it sends, read back out of every `dray session send` in a command, is "Messaged [face] title"; a run of them with nothing between folds into "Messaged [faces] 2 bots", which opens to one railed row per message, each opening its own text. A task's report-back draws no row for now — the bot's reply carries it; the line that drew it is commented out in `BotTranscript`. So the prompt tells the bot the reader never sees a report, and to say nothing at all when one needs nothing from them: a bot turn ending with no words is read at once (`silent_bot_turn` in `ingest_event`), so it raises no Done and no unread mark over a chat that drew nothing. **Claude Code would not let a turn end empty** (#993): it re-prompts one with no text ("[Your previous response had no visible output…]"), and the bot answered with filler, often a lone zero-width space. It skips that when the turn's last tool call is named in `CLAUDE_CODE_TERMINAL_MCP_TOOLS`, so a Claude Code bot is spawned with one, `mcp__dray__no_reply_needed`, an SDK MCP server Dray answers in its read loop ([no_reply.rs](../src-tauri/src/harness/claude_code/no_reply.rs)); the prompt tells the bot to call it before a silent end. Whitespace and format characters alone are no reply anywhere this is judged (`has_text` in Rust, `hasText` in TS), so a filler reply still draws nothing. Messages between bots do draw, and never fold into a task run: "Message from [face] Ops" with the message beneath it on the reader's side, and "Messaged [face] Ops" on the bot's, read back from each `dray bot send` and the bot id it prints, since the name typed there stops naming the bot once it is renamed. Both wear the other bot's own face, and its name opens its chat (`onOpenBot`, App's `openBot`). Tasks wear a face seeded from their session id through `seededAvatar`, never the library's own seeding, so the droplet, which `SHAPES` leaves out, never appears. A NEW divider marks where unread replies begin. A merge card the bot posts with `dray session merge-card` draws whole, its Merge settling the task as the Tasks tab's does, so the task's start line takes its name from the card once the settle takes it off the active index; Dray posts one itself once GitHub says the PR is ready (#953), so the prompt tells the bot only not to restate what the card shows.

**A bot can react instead of replying** (#1044, [react.rs](../src-tauri/src/bots/react.rs)): 👍 got it (an ok or go-ahead), 👀 looking into it, ✅ done, 🎉 celebrate, ❤️ thanks, 😂 funny, 😢 sorry, on the user's newest message — never a report or another bot's message, and only in the same session, so a chat's earlier sessions are never searched. A Claude Code bot calls `react`, a second terminal tool beside `no_reply_needed` on the same in-process MCP server, so the turn ends with no nudge; the read loop answers that call itself, minting the event through `ingest` on the child's own counter. Every other harness runs `dray session react <emoji>` (protocol v20), which logs rather than posts, so the turn stays silent: no Done, no unread. The event is a logged `reaction` naming the message by event id, and the newest on a message wins, so 👀 can become ✅. It draws no row: `botItems` reads every reaction first and hangs the emoji on its `user` item, drawn as a round chip on the bubble's corner on the bot's side (`ReactionBadge` in [Reactions](../src/components/chat/Reactions.tsx), and its twins on iOS and Android). The prompt's Talking section says when to reply, react or say nothing; starting or messaging a task takes neither, since the chat already draws that row. **The reader reacts back** (#1398), to the bot's main-thread `assistant_text`, from the same set, in a bot's chat only (👎 is in it for the reader; the prompt teaches the bot no use for it): a task is talked to in words, so `react_to_message` refuses one, and a routine's run. It logs a `reaction` with `byUser` (the bot's side keeps its own badges, and the newest of each side wins), then sends the bot a hidden prompt naming the emoji and quoting the message's start, through `send_review`, so it is a kickoff and draws nothing: the badge is the whole of it on screen. The turn it opens is an ordinary one, so the bot may reply, react back or stay silent. In a chat's earlier session the event lands in that session's log and the prompt goes to the bot's newest chat; a settled chat is refused. Desktop draws a hover button beside the bubble; Android takes a long-press, which opens the set and nothing else (#1406): no Copy, a reaction and a copy being two different things, so a bot's message in an open chat cannot be copied there, the press no longer starting a selection. iOS does the same (#1416): a long press opens the set in a popover over the message, and a reactable message's text is not selectable. **A reaction lands without moving anything** (#1406), on every client: the badge sits out to the side of the bubble's corner, the bottom one on the bot's message and the top one on the reader's, in the room no bubble reaches and inside the bubble's own height, which one line of text gives it. Hung under or over the bubble it needed a margin to clear the next row, and the message and everything after it jumped. It laps the bubble by its padding less the ring, so no text is under it; on a message of pictures alone it sits on the first picture's corner. Desktop's hover button steps past the badge by a transform, since a margin would narrow the bubble and rewrap it. [reaction-shift.html](../demo/reaction-shift.html) reacts to every message at three widths and says what moved. On iOS both badges are overlays on the bubble, which is what takes no room (#1416). **A reaction is never said twice** (#1332). Claude Code's silent-turn reminder ("The user hasn't heard from you in a while…") rides a tool result after a few textless model calls, the `react` one included, and a bot obeying it wrote its reaction out as a reply; `CLAUDE_CODE_TERMINAL_MCP_TOOLS` does not cover it, so Claude Code bots spawn with `CLAUDE_CODE_SILENT_TURN_REMINDER=0`. Both tools' results also carry `_meta: {"claude/endTurn": true}`, which ends the turn on the result with no model call after; without it the model still answered the result, and narrated its silence ("I haven't written a reply here…") often enough to matter. A refused `react` carries none, so the bot can reply instead. As a backstop on every harness, `ingest_event` drops a main-thread reply that is only the emoji reacted with this turn (`react::echoes`) and clears it from `final_text`, so the turn stays silent. And once the bot calls either tool, Dray drops everything else it writes that turn, stream included, and clears `final_text` (`session::CLOSED`, #1339): a CLI that ignores `endTurn` (older than 2.1.322, npm's `stable` among them) or a batch holding an errored result still gives the model a call, and it wrote "(Turn ended without a reply.)" as a bubble. The close is keyed on the call's own `tool_call_started`, never on Dray's answer to it (#1353): the CLI runs the tool while the response still streams, and Haiku often generates on past the call (`stop_reason: end_turn`), so a stray token ("ↀ") could reach the pipe before the `tools/call` did. A call that errors, a refused `react`, reopens the turn, since the bot must answer it. A shell `dray session react` closes nothing, since a bot on another harness can react 👀 and keep working in the same turn.

**Made from the sidebar, known by its face.** The bots sit above All Projects, since a bot belongs to no project, with a **New bot** row under them whether there are none or several. No heading: the Blobatar face on a row is what says it is a bot. The dialog ([NewBotDialog](../src/components/NewBotDialog.tsx)) asks a name, one of nine Blobatar shapes (no droplet), a hue and the agent and model — no instructions — and New bot first moves to the new-task composer, since the dialog shares that composer's picker and on an open chat would change its model. **The bot speaks first**: `start_bot` sends a kickoff prompt asking it to introduce itself by its name and guess its job from that name, in two or three sentences, listing no tools. The prompt is logged with `kickoff: true` and drawn as nothing, so the chat opens on the greeting. **Edit…** on a row's right-click opens the same dialog filled in, name and face only (`edit_bot`): its server and agent are its chat's. A rename retitles the open chat and reaches the bot before its next prompt as a hidden note (`note_bot`, sent with the `SINCE` list), since a running child read its name at spawn. Which session is a kickoff rides a list in `bots.rs` read where the prompt's event is built, rather than a flag through `send_msg`'s twenty parameters.

**The rows are inbox rows**, laid out like the stalled-task rows in a bot's chat: a 32px face, the name (bold while unread) with how long since its last activity at the right (`relativeTime`, the session rows' own), and one line of its last reply under it (`previewLine`, in `text-foreground/70`). While the bot works, typing dots take the reply's place; list rows use dots and other views the shimmer. State sits on the face as a badge cut out of it with a mask, since the sidebar is glass: an orange dot while it waits on the reader, the unread count once a reply lands, kept beside the typing dots through a turn the bot starts on its own until the chat is read. The face's eyes follow the pointer over the row. [bot-rows.html](../demo/bot-rows.html) draws them beside task rows. Its reply is read off the end of the log (`last_reply`, the newest two turns) through `bot_previews`, again whenever a chat's status or last activity moves, so no transcript is loaded for it. The face is stored as a shape *name* and hue degrees (`BotAvatar`), drawn by pinning `traits.shape` to the middle of that shape's band ([botAvatar.ts](../src/lib/botAvatar.ts)) and a fixed mid `tone`, since left to the seed most names land pale and the colour barely shows. A bot made before there was a pick draws the face its id seeds. Right-click: Edit, and Delete, which settles the chat first — once the folder is gone nothing marks it a bot's and it would land in the session list. Clicking a bot while the settled list is up switches back to the active side before opening, since the active chat is not in the settled one. There is no Settings section.

**Every user starts with Dray Bot** (#880). `list_bots` makes it the first time anything asks, under the list's lock, and leaves a marker file (`bots/.dray-bot-made`) so a reader who deletes it is not handed it back: like any bot it can be renamed or deleted. Its face starts as the nub in blue (#1076; one made before that keeps the amber cloud), and it carries a `welcome`, which now only marks it: `list_bots` words its `greeting` afresh on every read, from the bot's current name, so a renamed Dray Bot introduces itself by the new one. Its chat opens on that greeting with no session behind it ([BotWelcome](../src/components/chat/BotWelcome.tsx), the composer below, not centred), so the picker can still switch agent and model. The agent is the reader's own where installed, else the first installed in `HARNESS_ORDER`. The first send starts the session, and `deliver_prompt` writes each greeting message into the log ahead of the prompt, so the chat reads the same after a restart, and the agent is handed the same words in the hidden lead-in: it never wrote them, and the reader's first message may answer its question. Bots made with New bot carry no welcome and keep greeting with a real turn.

**`dray bot` makes, lists, messages, renames and deletes them** (#879): `new <name>` with `--shape` and `--colour` optional, picked at random otherwise; `ls` with each one's chat session; `send`, `rename`, `rm`. A bot is named by its id or its name in any case, so two may not share a name — `create_bot` refuses one taken, for the dialog too, and a clash made before that rule is refused with the ids to pick from. `rm` is `delete_bot`, the sidebar's Delete. Each answers with `bots_changed`, which the app reloads that server's list on. A bot made here has no chat until the first message to it: no kickoff greeting, since whoever made it is about to brief it.

**Bots message each other by name, and nothing reports back between them.** `dray bot send <bot>` sends into the bot's chat through `send_message`, the path `dray session send` takes; a bot with no chat yet starts one with the message, on the agent its last chat ran, else the sender's — but on its own last stance, else Auto, never the sender's, since a bot chat has no picker to show a Plan or bypass it inherited. A per-bot lock (`first_chat_lock`) is held from that lookup until the chat is on the index, or two first messages start two agents in one folder; `delete_bot` takes it too, so a chat opened as the bot is deleted is settled with it rather than left on a missing folder. Replying is the receiving bot's to choose, with a send of its own. The sender is stamped `MessageSender.bot_id` wherever the sending session runs in a bot's folder — `dray session send` to a bot's chat too — with the bot's name for `title`, and the agent reads `[message from the Dray bot "Ops" (id)]`.

**Bots know what the others are for and work on, and the server stops them looping** (#1303, [talk.rs](../src-tauri/src/bots/talk.rs)), after OpenBot's teammate list and Hermes Agent's bot chains. **A bot's role is the first line of its `AGENTS.md`**, markdown marks off, 160 characters at most (`role_line`); the prompt asks each bot to write it when told what it is for. Each bot's prompt lists the others with their roles at spawn (`roster`), and `ROSTER_SEEN` keeps what each session was given, so a new bot, a rename or a changed role reaches a running chat as a hidden `[Dray: the other bots changed…]` note ahead of its next prompt, through `take_since`. A chat with nothing on record — fx and grok resume after a restart without a fresh prompt — is sent the current roster once. Roster lines name no ids: a message names its sender by chat session, and a bot reading a second id for the same bot took it for a second bot. **Open tasks are pulled, never pushed**: `dray bot ls` gives each bot's role, whether its chat is mid-turn and its unsettled tasks at any depth (`listing`, `stalls::crew`, every session in the bot's folder a root so a routine run's tasks count), and `dray session new` from a bot's tree answers a `warning` naming other bots' open tasks in the same project (`overlap`), which the CLI prints. Ownership is that warning and the prompt's rule to ask the owning bot first; nothing is refused. **`dray bot send --ask` passes the answer back** (protocol v24, since an older app would deliver it and pass nothing back): the ask is armed when the prompt reaches the child (`delivered`, from `deliver_prompt`), so a queued one waits for the turn that takes it, and that turn's end sends its last words to the asker as `[reply from the Dray bot …; it needs no answer]` (`pass_back`): a bot's newest chat session, or the task or routine run that asked, which is marked waiting like a run's own question. A send that never reaches the child takes its ask back (`undo_ask`, on `HandoverGuard`'s drop), or the next turn's words would answer it; an fx batch whose turn fails to open drops every ask it armed. From a terminal `--ask` is refused, having nowhere to answer. A bot answering by hand with a send of its own disarms it (`answered`). **The guards are server-side, in memory, and the model cannot reset them.** A chain is a run of bot messages, each sent from a turn another bot's message started: `delivered` records the chain and hop of a bot's message on the session it reaches and clears it on anyone else's, the user's above all, and `stamp_bot_message` numbers each bot send one deeper. A fifth message in one chain (`MAX_HOPS`), the same text to the same bot twice in one chain, or a 21st message between one pair of bots in 5 minutes either way fails the send with the reason; the first and last also post a `notice` in the sender's chat ("Dray stopped Ops messaging CI…"), which `botItems` draws as a quiet line. A passed-back answer counts against the window but is never refused, since the asker is waiting on it. The prompt adds the etiquette both references ship: messages that stand alone, hand work on once and never back, nothing hard to undo on another bot's word alone, no acks.

**In a bot's chat `@` names the other bots, not files** (#941). The bot's folder holds its notes, which nobody mentions, so `ChatInput` takes `bots` — every other bot on this one's server, the only ones `dray bot send` reaches, from `App` — and the `@` token opens [BotMentionMenu](../src/components/composer/BotMentionMenu.tsx) in place of the file picker, with no file index started at all. A pick writes `@Name (id)`, the `&Title (id)` task tag's shape: the id is what `dray bot send` matches exactly, and the bot prompt says so. The name may hold neither `@` nor `&`, which is what keeps `parseBotTag` from reading a file mention and the prose after it up to a later tag's id as one name, and only a known bot's id makes one, so `@README.md (id)` in a task's chat stays a file. The composer chips it like a task tag; the transcript draws the bot's face and current name and opens it. Demo: [bot-mention.html](../demo/bot-mention.html).

**A bot runs on one server, and every server can hold bots** (#887). Its folder, files, chat and tasks live on the server it was made on; nothing moves a bot between servers. The app asks every server `list_bots` as it reads that server's projects (`readServer`), and the store in [bots.ts](../src/lib/bots.ts) keeps each server's list apart, This Mac's first. A remote's paths come back qualified like any other, so `serverOfPath(bot.path)` names a bot's server and every `botAt` comparison stays unique across servers. Bot commands go to the bot's server: `create_bot` and `start_bot` to the one picked, `delete_bot` to `serverOfBot`, `bot_previews` split by each chat's server (`readPreviews`). A remote bot's row looks like a local one, with no server name on it; an unreachable server's bots stay, faded with the offline mark, and its list rides the server cache (`ServerCache.bots`) so they survive a restart; one turned off or removed takes them with it. New bot's dialog has a server picker beside the agent picker, drawn only with a remote turned on, defaulting to This Mac; while it is open the composer's `activeServer` is that server (`botServer`), so the models offered are the ones it runs. **Dray Bot comes from the app's own server alone**: `list_bots` makes it only under the `desktop` feature, so a `dray-serve` never makes one and adding a remote never adds a Dray Bot.

A bot starts tasks on its own server. `--machine cloud` starts one on a fresh Dray Cloud machine (#1006, [cloud.md](cloud.md)), which is then a remote task like any other. `--machine <name>` starts one on another, which runs hidden and **reports back like any task** (#958, [remote_reports.rs](../src-tauri/src/remote_reports.rs)). The far server knows no bot and usually cannot reach the bot's server, since reach follows tokens, so the route back runs the other way: the bot's server marks the forwarded create `Caller.bot_tree`, the far server records the task as owing reports (`parent-reports.json`, before the spawn so the task gets [task_prompt.md](../src-tauri/src/bots/task_prompt.md)) and keeps each report there, since its parent is in no index it holds. The bot's server tracks the task (`remote-tasks.json`) and asks that machine `parent_reports` every 10s over its own link, delivers each through `deliver_report` — the local report's path, the sender named as the task on that machine — then acks only what it delivered. Unacked, a report comes again, so a lost ack costs a duplicate and never a lost report. **A video or screenshot the report names is copied here first** over the same link's `/file`, into the bot chat's own recordings (`<chat>/<far folder>-<file>`, deleted with the chat), and the report names the copy: the chat plays only what its own server holds (#1057). The far machine's text picks what is fetched, so a report copies three at most and a chat holds 1 GB of copies. A copy that fails leaves the far path, and a duplicate finds its copy made. Machines are asked side by side and each task's reports run on their own, so a slow copy holds up no other task. **The destination is the tracked parent, never the one the answer names**: that machine holds no token here, so it must not choose which chat runs a turn. A task settled or gone there, a machine removed, or one too old to answer `parent_reports` stops the tracking; a parent settled here does too, after telling the task's server to `forget` it, so its reports are not kept for nobody. A report nobody collects expires after seven days. A machine that fails to answer backs off to five minutes. **A stall nudge rides the same route**: the app sends `nudge_bot` to the task's server, which holds no bot, so where the task owes reports it files the nudge with them (`NudgeRoute::Outbox`) and the bot's server delivers it like a report. **A task on another machine carries a server glyph** on its Tasks row and its tab, the name in the glyph's tooltip, and the titlebar's far end names the machine while its tab is lit, as it does for any remote session; a task on This Mac carries none. Glyph alone because the row is already full: a name, a ring on the face and a badge on its corner were tried first. Demo: [machine-mark.html](../demo/machine-mark.html).

**A task whose machine is down stays on the card, and merges from here** (#1178). Its row is kept like any offline row, and its PR is read by its GitHub repo through This Mac's `gh`, on the `github:` key a merge card uses (`offlineRepo` and `taskPr` in `App`). The repo comes off the mark last read this run, else `prRepo`, which the server cache keeps on each row, since after a relaunch the row's own key cannot be read at all. The card row draws the offline mark in its time's place. Merge needs only GitHub, so it goes through that key too (`mergeRow`); the settle after it is held on This Mac (`hold_session_settle`, [held_flags.rs](../src-tauri/src/held_flags.rs)) and drawn at once, so the task leaves the card and the Tasks tab, and the machine's reconnect writes it there and removes the worktree. A row cached before this build has no `prRepo`, so it needs its machine to answer once first. **That merge runs as This Mac's `gh`, so it is offered only where that account may make it** ([mergeAccess.ts](../src/lib/mergeAccess.ts)): write access to the repo (`can_merge_repo`, `gh api repos/…` permissions, cached ten minutes; a repo it cannot see is a no), and, for a github.com repo, the same login the task's machine used; another host is judged on access alone, its logins not being known for both machines. Each machine's login is read off `get_integrations` on every connect and kept in its server cache (`ghLogin`), since a machine that is down cannot be asked. A machine never heard from is not held against. Otherwise the row keeps its offline mark with no Merge, and the mark's tooltip says why; the Tasks tab draws the mark in Merge's place, and the merge card says "Can't merge from here" with the reason on hover. The check runs only for a task whose machine is down, one that answers merging as its own `gh`, and it asks the machine the merge runs through: This Mac for a row, the chat's server for a merge card. An answer stands ten minutes, one GitHub could not give a minute. A message to a task drops its held settle before it goes, and never puts it back, since a settle landing after it would stop the turn it starts and a lost reply can hide a message that arrived. A held settle's worktree removal that fails raises the usual cleanup notice.

**The reader's name comes from their Dray account where it is a real one, is asked otherwise, and is shared by every bot** (#1076, #1313). Git's `user.name` is never read. `name_for` picks, best first: a name told to any bot (`bots/.user-name`), the bot's own `USER.md`, then the signed-in account's first name (`account_name`, off `account.json`, no network). The account's name counts as real only where it reads like one — a capitalised word of letters that is not the username — since GitHub falls back to the login where a profile has no name and email sign-up names the account after the address. A real one is written to the bot's `USER.md` at spawn where it has none (`write_user_file`), committed on its own so it draws no "Learned" row, and the bot greets by it and asks nothing. A handle is never used unasked: the question becomes "Should I call you yogesharc, or something else?" (`UserName::Handle`). With no account name at all it is "What should I call you?" (`ASK_NAME`). Either way a bot's first greeting is then two messages: the greeting, then Dray's own question — Dray Bot's from its `greeting`, a New bot's posted by Dray once the kickoff turn ends (`take_name_ask` in `ingest_event`), since one model turn cannot promise two messages; the kickoff tells the bot the question is coming. The bot prompt tells it to write the answer, just the name, to `USER.md` in its own folder, where every harness's sandbox lets it write. After the turn's commit Dray copies a `USER.md` that commit changed to `bots/.user-name` (`learn_user_name`; only a change made now, or a bot told long ago would undo a newer name), and notes it to every other bot's chat. Dray's own write of the account's name is never one of those, being its own commit. Every bot's prompt then names the reader, a bot made after that greets them by it and asks nothing, and Dray Bot's greeting says it too.

**The app opens on the first bot**, once the live index has landed so its chat is found, and only while the reader has gone nowhere yet; with no bot it stays on the new-task page. Deleting a bot lands on the first bot left, else the new-task page.

**`dray --machine <name> bot …` acts on that machine's bots** (#1461), forwarded like any `--machine` request. A `bot send` carries its sender as `session send` does, so the far bot reads who wrote and from which machine, and skips the bot-to-bot guards, which key on a chat the far server does not hold. `routine add` without `--bot` is refused, its default being the calling bot, which is here; the other routine verbs run unscoped there.

**`--ask` to a bot on another machine comes back by collection** (#1463, [remote_asks.rs](../src-tauri/src/remote_asks.rs)). The bot's server usually holds no token for the asker's, so it cannot send the answer; it keeps it, and the asker's server collects it over the link the question went out on, as a far task's reports come back (#958). The asking server mints a question id onto the forward (`Forward.ask`) and, once the far side answers `BotSent`, tracks it in `remote-asks.json`. The far side files the question in `bot-answers.json` before the message can reach the bot, carries the id on the sender in memory alone (`MessageSender.ask_id`, never logged) into `talk::delivered`, and `pass_back` files the turn's last words there instead of delivering them. The asker polls `bot_answers` every 10s per machine, backing off to 5 minutes on one that fails to answer, and delivers each answer as a local `--ask`'s is, signed by the bot and its machine. **Never twice**: a question is marked delivered on disk before its answer is sent on, never asked for again, and acked after; a lost ack is retried, a crash between mark and send loses that one answer. **Not silently lost**: an offline asker's answers wait on the bot's server for 7 days. A question the far side no longer holds — a restart ended the bot's turn first, as it drops every unanswered one at start, or 7 days passed — is a `notice` in the asking chat, and so is a removed machine or a week with no answer. An asker gone or settled by the time the answer lands is reported back as `undelivered`, and the bot's server puts a `notice` in the bot's chat. An asking bot's answer goes to its chat's newest session, as locally. A far server older than this refuses the ask, and an older asking server sends no id, which the far side refuses by name.

**Not built.** Moving a bot between servers. No editing a bot's files from the app; ask the bot.
