# Bots

**A bot is one ongoing chat with instructions and memory of its own, and everything it starts runs hidden and reports back to it after every turn** (#816, [bots.rs](../src-tauri/src/bots.rs), [bots.ts](../src/lib/bots.ts)). The shape Grok Bot, Cursor Projects, Claude Projects and OpenBot all ship: the reader runs everything from one chat and never switches sessions.

**A bot is a folder, and its session is known by running in it.** `bots/<id>/` under the home holds `INSTRUCTIONS.md` and a `memory/` folder; `bots.json` holds the list (id, name, path). The bot's chat is an ordinary session whose `cwd` is that folder — no field on the index says "bot", so an older build reading the index loses nothing, and every reader asks `bot_at(cwd)` / `botAt(bots, cwd)` instead. The chat is the newest unsettled session there (`botSession`); were it settled, the next send would start another with the same instructions and memory.

**Switching agent keeps the conversation** (#878). Each CLI resumes only its own sessions, so a switch is a new session in the same folder, and the chat is every unsettled session there, oldest first (`botChat`, `chat_sessions`), drawn as one with a quiet "Switched to Codex" line between them (`chatItems`). The model picker keeps its agent strip in a bot chat; a pick there is the chat's unsent pick, a line under the composer says the next message moves the chat, and that send mints the new session (`handleSendMsg`, refused mid-turn). Model, effort and stance on the same agent still apply in place. The backend knows a switch as a new session in a bot folder that already has one (`mark_new_chat`): it stops the old child and sends the new agent a **replay**, never a summary, ahead of the reader's first message — the reader's messages, the bot's replies and its tasks' reports, newest kept up to 30k characters, plus every earlier log's path and the tasks still open. The replay is sent and never logged, since the earlier logs already hold it. A switch writes no welcome. Tasks started before a switch still name the old session as parent, so `send_message` reroutes anything for a bot chat to its newest session (`current_chat`), and the Tasks tab walks the earlier sessions' children too (`crewRows`'s `also`). Earlier sessions load whole, page by page, while the chat is open.

**Instructions ride every harness's system-prompt slot; memory never does** through `bots::system_prompt(base, cwd)`: Claude Code's `--append-system-prompt`, Codex's `developerInstructions` (on `TurnSettings`, restated on start and resume), fx's `systemPrompt`, grok's `rules`, pi's `--append-system-prompt`. The bot's text is [bot_prompt.md](../src-tauri/src/bots/bot_prompt.md) and its first turn [kickoff_prompt.md](../src-tauri/src/bots/kickoff_prompt.md), their `{placeholders}` filled in one pass so a bot's own file naming one is never filled. `INSTRUCTIONS.md` starts empty: the bot is told its job in its first message and writes it down itself, and only it edits it. Read at spawn, which needs no reload for the bot's own edits — it made them. grok and fx keep the prompt on their own session record and take none on resume, so there only a new chat rereads it. It is capped at 16k characters, and a closing tag inside it is broken up so the text cannot end its block early. **Memory is a folder the prompt only points at**: one `YYYY-MM-DD-title.md` per memory, a one-line `description` in frontmatter, which the bot lists and greps when it needs to. Loaded whole, a bot's memory cost its size on every start and grew without bound; as files it costs nothing until read, and the date in the name sorts them.

**Everything under a bot runs hidden** (`create_session`, `in_bot_tree`): its children and theirs, whatever `--hidden` said. The walk is bounded at 8, so an index pointing a session at its own ancestor costs a wrong answer rather than a hung turn. A bot's folder is no project, so a create inheriting it as the project is refused with "pass --project" rather than starting a worktree of the bot's notes.

**A bot's folder is a local git repository, and Dray commits it after every turn** (#893, `start_history`, `commit_turn`). The point is a timeline: when the bot overwrites or deletes something, it or the reader can look back and restore. Made with the bot, and on first use — any spawn, through `system_prompt` — for a bot older than this. Dray commits, not the bot, which could forget: on every main-thread `TurnCompleted` in a bot's folder, everything staged with `add -A` and committed where anything changed, the message naming the files. **Awaited inside `ingest_event`**, before the queued flush, or the next turn could overwrite a note before it was saved. The repo's own config carries the bot's name and an email made from its id, so no global identity is needed, and every git call here passes `-c` for no hooks, no global ignore file and no signing: a reader's hook could fail or hang a commit, their ignore rules could leave its notes untracked, and a signing key would prompt every turn. No remote and no push, and the prompt says so; it tells the bot the history is there, not to commit. `.git` is looked for rather than asked of git, which would answer for a repository the home sat inside. **The app's git features stay off for a bot's chat**: no handoff row at all, not even Run server or the reader's own buttons, and no pull request lookup (`inBotFolder` in `App`), and the side panel never had Changes or PR. The turn snapshots still run there, unread.

**Every turn a child closes is sent to its parent, by Dray, not by the agent** (`report_to_parent`, from `ingest_event` on a main-thread `TurnCompleted`). A report the agent is asked to send is one it can forget — OpenBot's weak spot, whose delegation rules are prompt-only. It goes through `send_message`, the path `dray session send` takes, so the bot reads it exactly like a message the child sent. Only Claude Code fills `final_text`; the others say their answer in `AssistantText`, so the last one of the turn is kept (`LAST_REPLY`) and used instead. A turn with no text still reports, saying it failed or ended silently, and a child dying mid-turn reports from `settle_dead_child`, whose close never passes through `ingest_event` — so the bot is never left waiting. Each task is told so in its own prompt ([task_prompt.md](../src-tauri/src/bots/task_prompt.md), added by `system_prompt` where the session's index entry has a parent in a bot's tree): unaware, a task also sent its answer with `dray session send`, and the bot read every report twice. A settled child or a settled bot chat takes no report: sending would resume a conversation the reader closed. The flag is read again after the send and the chat stopped if it was settled meanwhile, since settling writes the flag before it stops the child. **Boxed**: the read loop calling it lives inside a harness's `init`, and the send can reach `init` again, so unboxed the compiler cannot name either future.

**The frontend.** Bots lead the live sidebar in a Bots section (`BotRow`: the session row's rail and orb, nothing else); their ongoing chats leave the session list (`inSidebar(items, bots)`), their settled ones stay in the settled list, the only way back to one. The section reads the active side of the index alone and is empty while the settled side is loaded. The space check spares anything in a bot's tree (`inBotTree`), or a task opened from the Tasks tab in another space's project closed at once. Opening a bot with no chat aims the empty composer at its folder (`handleNewBotSession`, not `handleSelectProject`, which would remember a bot as a project) and the toolbar drops the project pickers without naming the bot, which the header already does; a send there takes no worktree. A bot chat always runs on Auto (`botStance`), so its toolbar draws no stance picker, except on an agent with no Auto. Cards still come to the bot's chat (#807). ⌘⇧↑/↓ and the jump digits walk the bots' chats first, then the sidebar's order, so ⌥1 is the top bot. In a bot's chat `&` offers its own active tasks — not settled, not set aside — since they run hidden in projects the composer is not on.

**A bot's side panel is Tasks, Browser and More**: no PR and no Changes, since its folder holds notes, not work to review. Tasks lists its children at any depth off `crewRows` — which walks every held session, not the space's, since a bot hands work to any project. Pinned first, then waiting, working and done, set-aside ones last and faded. Each row is the sidebar row's: its face (the working orb mid-turn), title, the PR glyph *with its number*, ⋯ and Settle on hover, and the sidebar's right-click menu bar Mark unread. **A ready pull request draws Merge on the row** (`readyToMerge`, the PR panel's split button and confirm step cut to a row): an agent's own `gh pr merge` is often refused by its permission classifier, so the reader lands them. It merges from the repo root, since the worktree may be gone, then settles the task and removes its worktree — landed work needs no tidying by hand. The bot's prompt tells it to settle finished tasks itself with `--delete-worktree`, never one whose work is unmerged and still wanted.

**A task opens as a tab in the bot's row** (#881, [taskTabs.ts](../src/lib/taskTabs.ts)). A click on a Tasks row, a "Started a new task" line or a "Messaged" line adds the task after everything else in the bot's titlebar row and lights it: the main column, composer and side panel are the task's, the row stays the bot's, and the sidebar keeps the bot marked. ⌘-click switches to the task alone, the way a click used to, with the breadcrumb back. × , middle-click and ⌘W close a tab; ⌘⇧T puts one back. Settling a task leaves its tab, deleting it takes it. In memory, like the rest of the row, and keyed by the bot's id rather than its chat's session, so an agent switch, which starts a new session, keeps them. The bot's row is drawn over a task only while the task is open in it and the bot was the last row a task tab was picked from (`stripOf`'s `via`); ⌘-click clears that, so the task draws its own row. The task's own Diff and files are not in the bot's row; the side panel still reaches them.

**The row shares one side panel** (`rowOf` under `openKey`, the split group's mechanism): open or shut, and which tab is picked, are held under the bot chat's id for the chat and every task lit in its row, so the pane stays put while the reader moves along the row and shows the lit session's own content. A pick the lit session does not draw — PR on the bot, Tasks on a task — falls back to its default as anywhere and comes back where it is drawn.

**A bot and everything under it share one browser, the bot chat's** (`bots::browser_owner`, `botBrowser`): the chat's oldest session, which an agent switch leaves in place. The server resolves a `dray browser` step from any session in a bot's tree to it before it reaches CEF or headless Chromium, so a task's agent opens pages where the reader sees them from any of the bot's tabs: the row's pages, the panel's Browser and a link clicked in a task's chat all name the bot chat. A link from a lit task moves to the bot's Browser view, since the task's tab has no pages of its own. Each agent still drives a page of its own among the shared tabs: the server passes the caller as `BrowserRequest.driver`, and `automation.rs` keys `DRIVEN` on it, so one task's `open` never navigates another's page.

**Diff and Files in a bot's row pick which session they show** (#892, `PickTab` in [taskTabs.ts](../src/lib/taskTabs.ts)). + offers both every time, so several of each can be open, each on its own pick; an ordinary session's + still hides one already open. The pick is the first row of the view's side column ([PickTarget](../src/components/PickTarget.tsx)), above the sub-tabs or the file filter, and the tab is labelled with the picked title. Diff lists the bot's tasks alone, since its folder is no repository; Files lists the bot's own folder first, then the tasks. The list is the Tasks tab's — active tasks at any depth — newest activity first, and a new tab opens on the newest; Diff is greyed out until there is a task. The bot chat stays selected while one is lit (view `pick`), so the reader looks at a task's work without stepping into it. Picks are keyed by bot id like task tabs, and the bot's own folder is picked as the bot id, resolved to whichever chat session it has now, so an agent switch keeps them. A Files pick's files open as tabs of the row, as Files does, in a store keyed by tab *and* target (`pickFilesKey`): repicking brings up that task's own set, and the open is quiet (`openInFiles`'s `bring`), or it would flip the bot chat's own view to Files. Those stores are never written to local storage, like the tabs. With the task's transcript unloaded, its index `modified` and status stand in for the turn revisions the views re-read on. Settling a task closes its Files picks, since a settled task has nothing to open; its Diff picks stay for review until the worktree is deleted, and deleting the task closes every pick on it — all read off `session_changed`, since the bot settles tasks as often as the reader does. A settled target leaves the index's active side, so the lit pick asks for it with `session_index_item` on every index change.

**The chat draws the conversation, not the work** ([BotTranscript](../src/components/chat/BotTranscript.tsx), [botTranscript.ts](../src/lib/botTranscript.ts)). Tool calls show only as the live orb line naming the current tool. A task the bot starts is a "Started a new task [face] title" line, read off its `dray session new` call and the id that command prints. A message it sends, read back out of every `dray session send` in a command, is "Messaged [face] title"; a run of them with nothing between folds into "Messaged [faces] 2 bots", which opens to one railed row per message, each opening its own text. A task's report-back draws no row for now — the bot's reply carries it; the line that drew it is commented out in `BotTranscript`. Tasks wear a face seeded from their session id through `seededAvatar`, never the library's own seeding, so the droplet, which `SHAPES` leaves out, never appears. A NEW divider marks where unread replies begin.

**Made from the sidebar, known by its face.** The bots sit above All Projects, since a bot belongs to no project, with a **New bot** row under them whether there are none or several. No heading: the Blobatar face on a row is what says it is a bot. The dialog ([NewBotDialog](../src/components/NewBotDialog.tsx)) asks a name, one of nine Blobatar shapes (no droplet), a hue and the agent and model — no instructions — and New bot first moves to the new-task composer, since the dialog shares that composer's picker and on an open chat would change its model. **The bot speaks first**: `start_bot` sends a kickoff prompt asking it to greet the reader by name and guess its job from its name, in two or three sentences, listing no tools. The prompt is logged with `kickoff: true` and drawn as nothing, so the chat opens on the greeting. Which session is a kickoff rides a list in `bots.rs` read where the prompt's event is built, rather than a flag through `send_msg`'s twenty parameters.

**The rows are one line**, a session row's height: a 20px face, the name (bold while unread) and the time, which typing dots replace while the bot works. State sits on the face as a small dot cut out of it with a mask, since the sidebar is glass: orange while it waits on the reader, green while a reply is unread. The face's eyes follow the pointer over the row. An inbox design — a 40px face, the last reply on a second line and a badge carrying the unread count — is commented out in `Sidebar` and drawn by `BotRow` without `compact`, kept to try again. Its reply is read off the end of the log (`last_reply`, the newest two turns) through `bot_previews`, again whenever a chat's status or last activity moves, so no transcript is loaded for it. The face is stored as a shape *name* and hue degrees (`BotAvatar`), drawn by pinning `traits.shape` to the middle of that shape's band ([botAvatar.ts](../src/lib/botAvatar.ts)) and a fixed mid `tone`, since left to the seed most names land pale and the colour barely shows. A bot made before there was a pick draws the face its id seeds. Right-click: Delete, which settles the chat first — once the folder is gone nothing marks it a bot's and it would land in the session list. Clicking a bot while the settled list is up switches back to the active side before opening, since the active chat is not in the settled one. There is no Settings section.

**Every user starts with Dray Bot** (#880). `list_bots` makes it the first time anything asks, under the list's lock, and leaves a marker file (`bots/.dray-bot-made`) so a reader who deletes it is not handed it back: like any bot it can be renamed or deleted. Its face is fixed, the cloud in amber, and it carries a `welcome`: its chat opens on that text with no session behind it ([BotWelcome](../src/components/chat/BotWelcome.tsx), the composer below, not centred), so the picker can still switch agent and model. The agent is the reader's own where installed, else the first installed in `HARNESS_ORDER`. The first send starts the session, and `deliver_prompt` writes the welcome into the log as event 0, ahead of the prompt, so the chat reads the same after a restart; the agent is not given it. Bots made with New bot carry no welcome and keep greeting with a real turn.

**Not built.** Bots live on This Mac's server only — `list_bots` asks the local one. No "instructions changed" line in the chat when the bot edits its own file; the prompt asks the bot to say so. No rename and no editing a bot's files from the app; ask the bot.
