# Dray Cloud

Hosted machines Dray starts and stops itself (#857), **one per task**. The contract between the app, the control plane in `apps/web` and `dray-serve` is fixed in the issue; this is the app's half. [cloud.rs](../src-tauri/src/cloud.rs) talks to the control plane, `servers.rs` turns its answer into connections, and [cloud.ts](../src/lib/cloud.ts) starts a task's machine.

**Every machine is a connection like any other**, a `Saved` marked `cloud` with its sandbox id, so everything a server already does — `server_invoke`, events, the sidebar, `dray --machine` — works on it unchanged. The control plane keeps no database, so the list is read again every 30s while Dray Cloud is on (`watch_cloud`), and a failed connect asks for a fresh read at most every 10s. A machine the list no longer names goes, token, kept lists and kept transcripts with it. One token serves every machine, kept under each one's `server:<id>` as any token is.

**A new task on Cloud gets a machine of its own** (`placeTask`): `start_cloud_machine` has the control plane create one from the `dray-cloud` snapshot and answers once it is connected, then `clone_github_repo` clones the project there. Never a running or stopped machine another task used: a task's checkout, agents and memory are its own, which is the whole point over the pool this replaced. The composer shows `CloudNotice` meanwhile and the prompt is held on disk as a resume holds it. A reader who moves away keeps their place; the task still starts.

**A failure says so, with Retry.** No machine started (control plane down, boat refused), a clone that failed, or a resume that didn't land each show `CloudFailedNotice` with the reason in full — "Couldn't start a cloud machine: …" — and Retry sends the composer's text again. The send restores that text the way any failed send does. A machine whose clone failed is deleted on the spot, so a retry starts clean and nothing runs for nothing. Each wait has a deadline (`cloud::START`, then `BOAT_WAKE`), so none hangs.

**A settled task's machine is deleted** (`drop_cloud_machine`, the control plane's `DELETE /machines/:id`) once no live session is left on it — a fork or a spawned child can share it. A machine already stopped is not woken to write the settle; it goes whole. Boat deletes in the background, so the app remembers what it dropped (`CLOUD_DROPPED`) and a listing that still names one does not bring its row back. A settled cloud task leaves the sidebar with its machine.

**A cloud machine is never drawn as stopped, sleeping or offline.** It is Dray's own service, not a server the reader added: `shownOffline` and `offlineLine` pass over it, so no offline mark, no dimmed row, no stopped notice. Underneath it still carries a `BoatRow` (`ServerInfo.boat`) with no boat link, so a send to a task on a stopped machine wakes it through `resume_boat`, which asks the control plane rather than `boat resume`; the send also wakes one merely unreachable, since the listing that would say it stopped can be 30s behind. The provisional prompt and the working indicator are what the reader sees meanwhile. A listing never closes a resume, only `wake_boat` does — the waiter reads any other phase as the resume having failed.

**A cloud task's transcript is kept on this machine** ([cloudTranscripts.ts](../src/lib/cloudTranscripts.ts), `<app home>/cloud-transcripts/<server>/<session>.json`), written whenever a loaded one stops changing outside a turn. Opening a task whose machine is stopped reads it from there and never wakes the machine; a send does, and the reconnect catches the transcript up. Permission asks and answers are left out, since only the child that raised them can act on them.

**One row in Settings, never one per machine.** Its dot says whether Dray Cloud answers, never whether a machine runs. The key is checked against the control plane before it is saved, sits in `credentials.json` under `dray-cloud`, and is never read back. The switch lives in `settings.json` (`drayCloud`), since Rust lists the machines at launch; off turns every cloud connection off the way a server's own switch does. `DRAY_CLOUD_URL` moves the control plane.

**Every cloud checkout reads as "Cloud"** (`serverName`). The composer's `MachineSelector` folds them into one Cloud entry, offered on a project with a GitHub remote while Dray Cloud is on and keyed. The pick is per project key in local storage (`ade.cloudPicks`), apart from the checkout pick, since Cloud is no one checkout until a task starts. A project whose last-used checkout is on a cloud machine reads as Cloud too, and still starts a new machine.

Tested against [demo/cloud.html](../demo/cloud.html): real `dray-serve`s, one for This Mac and the rest spare machines handed to tasks as they start, with the control plane faked in the page and a panel to stop a machine or fail the next start.
