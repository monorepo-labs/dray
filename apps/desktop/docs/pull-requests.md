# Pull requests

**A session's PR is a tab in the right pane** ([PrPanel](../src/components/PrPanel.tsx)), rendering readiness, checks, comments and the merge action.

**`gh`, not the REST API** — it already holds auth, enterprise host config and token refresh. Cost: the feature is absent where `gh` is missing or logged out, surfaced as one readable line. Resolved through [binpath.rs](../src-tauri/src/binpath.rs), returning `Option` rather than a bare-name fallback.

**A missing `gh` keeps the tab and is drawn as a setup pane, and that reverses the older rule** (DRA-258). Hiding it made the feature invisible on a machine that never had the CLI — the marks fail silently and the handoff row's Create PR only fails inside the agent's turn, so nothing anywhere said that one `brew install` puts pull requests on this screen. **The exception is exactly two states**, `no_cli` and `not_authenticated`: everything else follows the rows, so a *refresh* that failed still draws its sentence under pull requests already on screen while an error with no rows takes the tab away rather than leaving one that can only say "this went wrong".

Without `gh` **every** directory answers `NoCli`, since the first call fails before anything has looked at the checkout — so `prs_for_branch` asks `git::has_github_remote` and answers `NoRemote` where there is none, or a gh-less machine grows a PR tab on every session it has. Any remote counts, and the match is on the URL's **host** — a remote *named* `github.com-mirror` and the host `github.com.example.net` both pass a contains-check over `remote -v`, the trap `is_upload` documents next door. Hand-rolled rather than `url::Url`, which refuses `git@github.com:owner/repo` outright. An enterprise host is not `github.com` and reads as no GitHub remote, costing a prompt to somebody already on a GitHub this app cannot name.

**The pane copies and never runs.** macOS lets no app put text on another's prompt without an Accessibility grant, so the honest pair is the command with a copy on it and a terminal opened at the session's `cwd` to paste into — where a button that ran an install would be Dray deciding what to execute in the reader's shell. The terminal is `OpenInButton` wearing a third hat, `TERMINAL_OPENER`: terminals alone, its own stored pick (`ade.runInTerminal` — the dir opener's holds editors and Finder too), and `Opener` gains `label`/`hint` so a control standing alone in an empty state can name the app on its face instead of in a tooltip. It needs nothing new in Rust, `open -a <terminal> <dir>` being the shape [apps.rs](../src-tauri/src/apps.rs)'s table already promises.

**`binpath`'s `gh` slot is therefore an `RwLock`, not a `OnceLock`** — it is the one cached answer here that caches an *absence* the reader is being asked to fix, and `recheck_gh` throws it away, so an install made on that pane's say-so is found without restarting the app. **A generation rides that**, the issue caches' own bargain: a probe already running when the reader installs `gh` would otherwise finish and publish its miss back over the answer, undoing the recheck with a reading older than it. It still answers its own caller — who asked before the install — and only the cache refuses it. The pane says so when it still finds nothing: a button that redraws the same screen reads as broken, which is the one thing a pane asking for an install cannot look like. The logged-out half has no such answer to give — `gh` has not moved, and only GitHub knows whether the login took — so it re-asks and leans on `loading` for the same promise made quieter.

**One `gh api graphql` carries the whole panel, and avatars are why it is not `gh pr list --json`.** The rollup `gh` hands back has no image on it, and `github.com/<login>.png` **404s for exactly the accounts that matter** — a GitHub App's real login ends in `[bot]` and `gh` strips it.

- **GraphQL fails with 200 and zero exit** (`{"data":null,"errors":[…]}`), so check `errors` before `data`, or "could not resolve repository" reads as a branch having no PR.
- **The rollup is heterogeneous** — `StatusContext` names itself on `context` and reports on `state`; `CheckRun` on `name` / `status`+`conclusion`, image at `checkSuite.app.logoUrl`. Tagged on `__typename` with `#[serde(other)]`. A running check has **null** conclusion where `gh` sent an empty string.
- **Every connection's `nodes` is nullable.** `Option` is load-bearing: a PR with no comments otherwise fails the whole response.
- **One branch can carry several PRs, so the backend answers with a list**, open-first then newest.
- **Inline comments live in `reviewThreads` alone** and join to reviews on `pullRequestReview{id}`. A review's `body` is top-level text only, so an empty envelope holding threads is **kept** — it is the only row naming who left them — while an empty one holding nothing is dropped unless it approves.

**Readiness is three overlapping fields read in one fixed order** ([pr.ts](../src/lib/pr.ts)): `state`, `mergeable`, `mergeStateStatus`. The order is the whole logic — a closed PR's merge state is stale, conflict outranks failing checks, and `UNKNOWN` means GitHub hasn't worked it out rather than no. A pure function with its own tests, not JSX conditionals.

**Polling**: 15s while something is in flight, 60s otherwise, gated on `active`, cached per `cwd + branch` for 30s. Gate on *any open PR on screen*, never *any check running* — a check that hasn't registered yet leaves the rollup empty exactly like a repo with no CI, so the tighter read polls zero times during the only window that matters. `active` is read off the stored **pick**, not `activeTab`, which derives from this hook's own answer. **Nothing polls while the window is in the background** — this poll, the sidebar marks and the browser pane's local-server list all gate on `useWindowFocused` ([focus.ts](../src/lib/focus.ts)) and read again on return. The marks' return read is forced only on the return itself, since a forced read beside `load(false)` on a repo change queues a second `gh`.

**A PR appearing means a turn ending, and nothing else could see it**: the tab is hidden exactly while the answer is "no PR", so it could never self-heal. Refetch on the **falling edge of `busy`** in `App`, with the session id riding along in that ref since `busy` is the *selected* session's. Appearance also opens the pane once, through `onOpened` fired inside `load` — only the fetch knows the previous answer, and that is the whole guard. Key-guarded, so a read landing after a session switch cannot pull the pane onto a branch the reader left. **Claude Code also says so mid-turn** (v2.1.310): `code_change_published` (PR created, pushed, readied, commented) and `vcs_state_changed` (commit, push, merge, rebase) map to one unpersisted `repo_changed` event, and `App` re-reads on it through `repoChanged` in [prSync.ts](../src/lib/prSync.ts) — marks for any session, the panel and the handoff row for the selected one. Measured: 10s to 15 minutes ahead of the turn ending. The falling edge stays, since the other harnesses send nothing.

**Every write refetches**, and reaches past the pane: `onChanged` fires `prMarks.refresh`, and unlike every other write there it is **not** key-guarded, since a repo-wide answer is true whether or not the reader is still looking. **A merge that fails is checked against the PR before being reported** — `gh pr merge` can fail with the merge already through, so `merge_pr` re-reads `state` and answers `Ok` only where it comes back `MERGED`.

**No Close, and no `--delete-branch`.** Abandoning a PR happens on GitHub. Delete-branch: a worktree session has that branch checked out, so `git branch -D` refuses it and cleanup fails after the merge already landed.

**Branch name read first, rebuilt only as fallback.** `sessionBranch` takes `observed` (`work_status.branch`, git's HEAD) and it wins wherever the session still has a checkout of its own. Everything else is a **guess made at creation** and never re-read, so a `git checkout` inside the tree leaves both naming the wrong branch and the PR tab fails **closed**. `observed` null is a resting state. **`worktreeRemoved` is the one case `observed` loses** — a relocated session's checkout is shared, so HEAD there never answers "where does this session's work land"; `relocate_session_to_project` sets that flag beside clearing `worktree_name`. One function, and `SessionHeader` takes the result as a **prop**. Sidebar rows still read the guess, deliberately: marks are one `gh` per repo, where a per-row branch read is one `git` spawn per row.

**The hook lives in `App`, not the panel** — the tab row must know whether an open PR exists *before* that tab is shown, so its first read is **not** gated on `active`; only the poll is. The sidebar's mark stands in while the panel's own read is out (`hasPrTab = prTabVisible(…) || (loading && mark)`), and once the read answers the panel's answer governs.

**Sidebar marks** ([usePrMarks](../src/hooks/usePrMarks.ts)) ask `pr_marks` once per **distinct repo** among visible sessions, since `gh` costs better part of a second. `QUERY_MARKS` carries `number headRefName isDraft`, the tip commit's rollup **state**, and `mergeable mergeStateStatus` on the open half for the ready-to-merge notice — nothing else, since a row draws one glyph.

- **`PrChecksState` folds GitHub's five-way `StatusState` into `Running` / `Failing` / `Clear`**, unrecognised words reading as `Clear` — the safe direction. Running is a spinner in the timestamp slot; failing turns the PR glyph red and `prStateLabel` says so too, since red-green is what this palette can least afford to make load-bearing. **Passing draws nothing.** Red only while open or draft. The field is `checks_state`, since `checks` is already the list of individual `PrCheck`. The glyph table is shared with the panel ([PrStateIcon](../src/components/PrStateIcon.tsx)).
- **Matching lives in the frontend** — the backend answers a list, not a map, because which branch a session lands on is the frontend's own rule.

**The marks cache is module-level per repo, fresh 120s, and a failed read changes nothing — no row written, no stamp.** Not writing keeps the last good mark on screen; not stamping stops a failed read re-certifying an answer a write just invalidated. A module `generation` counter is what makes `refreshAfterWrite`'s clear stick, since a read issued before the clear must not put its stale answer back; `inFlight` carries it too, because "a read is running" is not "a read will answer for me". The poll reads only repos holding an open PR, or a directory `gh` can never answer for takes a failing spawn every 30s forever. The archived view asks for no repos and therefore draws no check spinner — a stale glyph is an accepted trade, a stale spinner animates a claim about now.

**Marks and panel tell each other what they learned, signal only — never data** ([prSync.ts](../src/lib/prSync.ts)), since two caches with nothing joining them left a "Ready to merge" card on a panel still saying checks not passing. Marks emit `branchChanged` carrying **repo and branch**; the panel emits `panelRead` and the marks side asks `markDisagrees`, comparing checks *loosely* since neither fold can fill the other. A panel-triggered marks read **echoes nothing back for the branch that triggered it**, or the pair spawn `gh` at each other forever.
