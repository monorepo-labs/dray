# Pull requests

**A session's PR is a tab in the right pane** ([PrPanel](../src/components/PrPanel.tsx)), rendering readiness, checks, comments and the merge action.

**`gh`, not the REST API** — it already holds auth, enterprise host config and token refresh. Cost: the feature is absent where `gh` is missing or logged out, surfaced as one readable line. Resolved through [binpath.rs](../src-tauri/src/binpath.rs), returning `Option` rather than a bare-name fallback.

**A missing `gh` keeps the tab and is drawn as a setup pane, and that reverses the older rule** (DRA-258). Hiding it made the feature invisible on a machine that never had the CLI — the marks fail silently and the handoff row's Create PR only fails inside the agent's turn, so nothing anywhere said that one `brew install` puts pull requests on this screen. **The exception is exactly two states**, `no_cli` and `not_authenticated`: everything else follows the rows, so a *refresh* that failed still draws its sentence under pull requests already on screen while an error with no rows takes the tab away rather than leaving one that can only say "this went wrong".

Without `gh` **every** directory answers `NoCli`, since the first call fails before anything has looked at the checkout — so `prs_for_branch` asks `git::has_github_remote` and answers `NoRemote` where there is none, or a gh-less machine grows a PR tab on every session it has. Any remote counts, and the match is on the URL's **host** — a remote *named* `github.com-mirror` and the host `github.com.example.net` both pass a contains-check over `remote -v`, the trap `is_upload` documents next door. Hand-rolled rather than `url::Url`, which refuses `git@github.com:owner/repo` outright. An enterprise host is not `github.com` and reads as no GitHub remote, costing a prompt to somebody already on a GitHub this app cannot name.

**The pane copies and never runs.** macOS lets no app put text on another's prompt without an Accessibility grant, so the honest pair is the command with a copy on it and a terminal opened at the session's `cwd` to paste into — where a button that ran an install would be Dray deciding what to execute in the reader's shell. The terminal is `OpenInButton` wearing a third hat, `TERMINAL_OPENER`: terminals alone, its own stored pick (`ade.runInTerminal` — the dir opener's holds editors and Finder too), and `Opener` gains `label`/`hint` so a control standing alone in an empty state can name the app on its face instead of in a tooltip. It needs nothing new in Rust, `open -a <terminal> <dir>` being the shape [apps.rs](../src-tauri/src/apps.rs)'s table already promises.

**`binpath`'s `gh` slot is therefore an `RwLock`, not a `OnceLock`** — it is the one cached answer here that caches an *absence* the reader is being asked to fix, and `recheck_gh` throws it away, so an install made on that pane's say-so is found without restarting the app. **A generation rides that**, the issue caches' own bargain: a probe already running when the reader installs `gh` would otherwise finish and publish its miss back over the answer, undoing the recheck with a reading older than it. It still answers its own caller — who asked before the install — and only the cache refuses it. The pane says so when it still finds nothing: a button that redraws the same screen reads as broken, which is the one thing a pane asking for an install cannot look like. The logged-out half has no such answer to give — `gh` has not moved, and only GitHub knows whether the login took — so it re-asks and leans on `loading` for the same promise made quieter.

**One `gh api graphql` carries the whole panel, and avatars are why it is not `gh pr list --json`.** The rollup `gh` hands back has no image on it, and `github.com/<login>.png` **404s for exactly the accounts that matter** — a GitHub App's real login ends in `[bot]` and `gh` strips it.

- **GraphQL fails with 200 and zero exit** (`{"data":null,"errors":[…]}`), so check `errors` before `data`, or "could not resolve repository" reads as a branch having no PR.
- **The rollup is heterogeneous** — `StatusContext` names itself on `context` and reports on `state`; `CheckRun` on `name` / `status`+`conclusion`, image at `checkSuite.app.logoUrl`. Tagged on `__typename` with `#[serde(other)]`. A running check has **null** conclusion where `gh` sent an empty string.
- **Every connection's `nodes` is nullable.** `Option` is load-bearing: a PR with no comments otherwise fails the whole response.
- **One branch can carry several PRs, so the backend answers with a list**, open-first then newest.
- **Inline comments live in `reviewThreads` alone** and join to reviews on `pullRequestReview{id}`. A review's `body` is top-level text only, so an empty envelope holding threads is **kept** — it is the only row naming who left them — while an empty one holding nothing is dropped unless it approves.

**Readiness is three overlapping fields read in one fixed order** ([pr.ts](../src/lib/pr.ts)): `state`, `mergeable`, `mergeStateStatus`. The order is the whole logic — a closed PR's merge state is stale, conflict outranks failing checks, and `UNKNOWN` means GitHub hasn't worked it out rather than no. A pure function with its own tests, not JSX conditionals.

**Polling**: 15s while something is in flight, 60s otherwise, gated on `active`, cached per `cwd + branch` for 30s. Gate on *any open PR on screen*, never *any check running* — a check that hasn't registered yet leaves the rollup empty exactly like a repo with no CI, so the tighter read polls zero times during the only window that matters. `active` is read off the stored **pick**, not `activeTab`, which derives from this hook's own answer. **Nothing polls while the window is in the background** — this poll, the sidebar marks and the browser pane's local-server list all gate on `useWindowFocused` ([focus.ts](../src/lib/focus.ts)) and read again on return. The marks' return read is forced only on the return itself, since a forced read beside `load(false)` on a repo change queues a second `gh`.

**A PR appearing means a turn ending, and nothing else could see it**: the tab is hidden exactly while the answer is "no PR", so it could never self-heal. Refetch on the **falling edge of `busy`** in `App`, with the session id riding along in that ref since `busy` is the *selected* session's. Appearance no longer opens the pane (#913): a merge card goes in the chat that started the task once the PR is ready (#953, see orchestration.md), and the pane opens by hand. **Claude Code also says so mid-turn** (v2.1.310): `code_change_published` (PR created, pushed, readied, commented) and `vcs_state_changed` (commit, push, merge, rebase) map to one unpersisted `repo_changed` event, and `App` re-reads on it through `repoChanged` in [prSync.ts](../src/lib/prSync.ts) — marks for any session, the panel and the handoff row for the selected one. Measured: 10s to 15 minutes ahead of the turn ending. The falling edge stays, since the other harnesses send nothing.

**Every write refetches**, and reaches past the pane: `onChanged` fires `prMarks.refresh`, and unlike every other write there it is **not** key-guarded, since a repo-wide answer is true whether or not the reader is still looking. **A merge that fails is checked against the PR before being reported** — `gh pr merge` can fail with the merge already through, so `merge_pr` re-reads `state` and answers `Ok` only where it comes back `MERGED`.

**No Close, and no `--delete-branch`.** Abandoning a PR happens on GitHub. Delete-branch: a worktree session has that branch checked out, so `git branch -D` refuses it and cleanup fails after the merge already landed.

**Branch name read first, rebuilt only as fallback.** `sessionBranch` takes `observed` (`work_status.branch`, git's HEAD) and it wins wherever the session still has a checkout of its own. Everything else is a **guess made at creation** and never re-read, so a `git checkout` inside the tree leaves both naming the wrong branch and the PR tab fails **closed**. `observed` null is a resting state. **`worktreeRemoved` is the one case `observed` loses** — a relocated session's checkout is shared, so HEAD there never answers "where does this session's work land"; `relocate_session_to_project` sets that flag beside clearing `worktree_name`. One function, and `ViewTabs` and `PrPanel` take the result as a **prop**. Sidebar rows still read the guess, deliberately: marks are one `gh` per repo, where a per-row branch read is one `git` spawn per row.

**The hook lives in `App`, not the panel** — the tab row must know whether an open PR exists *before* that tab is shown, so its first read is **not** gated on `active`; only the poll is. The sidebar's mark stands in while the panel's own read is out (`hasPrTab = prTabVisible(…) || (loading && mark)`), and once the read answers the panel's answer governs.

**Sidebar marks** ([usePrMarks](../src/hooks/usePrMarks.ts)) ask `pr_marks` once per **distinct repo** among visible sessions, since `gh` costs better part of a second. `QUERY_MARKS` carries `number headRefName isDraft`, the tip commit's rollup **state** and check **count**, `headRefOid`, and `mergeable mergeStateStatus` on the open half for the ready-to-merge notice — nothing else, since a row draws one glyph.

- **`PrChecksState` folds GitHub's five-way `StatusState` into `Running` / `Failing` / `Clear`**, unrecognised words reading as `Clear` — the safe direction. Running is a spinner in the timestamp slot; failing turns the PR glyph red and `prStateLabel` says so too, since red-green is what this palette can least afford to make load-bearing. **Passing draws nothing.** Red only while open or draft. The field is `checks_state`, since `checks` is already the list of individual `PrCheck`. The glyph table is shared with the panel ([PrStateIcon](../src/components/PrStateIcon.tsx)).
- **Matching lives in the frontend** — the backend answers a list, not a map, because which branch a session lands on is the frontend's own rule.

**The marks cache is module-level per repo, fresh 120s, and a failed read changes nothing — no row written, no stamp.** Not writing keeps the last good mark on screen; not stamping stops a failed read re-certifying an answer a write just invalidated. A module `clock` numbers reads as they start and changes as they are reported (`allChangedAt` for a write, `changedAt` per repo for an agent's report), and is what makes a clear stick, since a read issued before the change must not put its stale answer back; `inFlight` carries each read's start too, because "a read is running" is not "a read will answer for me". The poll reads only repos holding an open PR, or a directory `gh` can never answer for takes a failing spawn every 30s forever. The archived view asks for no repos and therefore draws no check spinner — a stale glyph is an accepted trade, a stale spinner animates a claim about now.

**A failed read is retried until one lands** (#1077), 15s doubling to 10 minutes, on the polls' terms: everything on screen while focused, a bot's repos while not. The poll alone could not: a repo whose reads all failed holds no open mark, so it was never polled, and a PR opened while GitHub's hourly limit was spent never showed — no Tasks-tab mark, no merge card, a stall saying "waiting on the user". `no_cli` and `no_remote` are not retried; logged out is, since logging in mends it.

**One read per GitHub repo, however many keys name it.** One repo has a key per machine — this Mac's checkout, `dray://<boat>/home/user/dray` on each Boat, a merge card's `github:` slug — and each was read on its own every 30s, against one budget. `marksRepo` learns a key's repo off its PRs' URLs, `load` reads one key per repo, the least-failing first and the next if it fails (a stopped Boat answers nothing), and the answer is written to every key sharing it. Each key also keeps `answeredAt`, the start of the read its answer came from, so a slow read through one machine landing after a newer one through another is dropped; and each attempt is waited on 20s before the next key is tried, since neither `gh` nor the socket has a deadline. A `repo_changed` re-reads that session's repo only (`refreshRepo`): it used to re-read every repo on screen, once per agent push or PR comment on any machine.

**Marks and panel tell each other what they learned, signal only — never data** ([prSync.ts](../src/lib/prSync.ts)), since two caches with nothing joining them left a "Ready to merge" card on a panel still saying checks not passing. Marks emit `branchChanged` carrying **repo and branch**; the panel emits `panelRead` and the marks side asks `markDisagrees`, comparing checks *loosely* since neither fold can fill the other. A panel-triggered marks read **echoes nothing back for the branch that triggered it**, or the pair spawn `gh` at each other forever.

## The pull requests page

**A sidebar row under Issues, a main-column page like the issues page** (#1337, [PullsView](../src/components/PullsView.tsx), rules in [prInbox.ts](../src/lib/prInbox.ts), plan in [PR-INBOX-PLAN.md](../PR-INBOX-PLAN.md)). `App` holds one `page` state, `"issues" | "pulls" | null`; `pageOpen` answers "does a page cover the session" for every guard that means any page, and `goToSession` sets it to null.

**"Involving me", the default, is one GitHub search across every repo** (`pr_search`, `usePrSearch`): `is:pr is:open involves:@me archived:false`, a hundred newest, narrowed by the Owner menu to `org:` or `user:`. Measured at 1 point with `rateLimit{cost}` whatever it covers, against a point per repo read one by one; read on open, on an owner pick, on ↻, and every 60s while the window has focus, so 60 points an hour. Each answer is a mark with its listing plus the repo, so no checkout is needed to list a PR. A row's key is the attached checkout whose git remote names the repo (`repo_checkouts`, local git, no network) or the repo's `github:` slug, which the pane reads through and Start Task clones from. The Owner menu holds the reader, every owner a search turned up, and their orgs; the Repository menu narrows the rows on screen. **"This space" is the marks read below**, every open PR in the space's projects, not only the reader's.

**The list is the sidebar's marks, not a third cache.** `QUERY_MARKS`'s open half carries a `PrListing` — title, author, size, comment counts, `viewerDidAuthor`, `viewerLatestReviewRequest` — measured still 1 point, but only for the repos the page lists (`pr_marks`'s `listing`, `usePrMarks`' `listedPaths`): the sidebar's 30s poll and the phone's reads would otherwise carry it for nothing. A listed key whose cached answer has no listings counts as stale. While the page is up its repos join `usePrMarks`' read: the active space's projects (or every project, under All spaces) and every bot task's repo, whatever space it sits in, the `inBotTree` exemption. The page's ↻ re-reads its own repos alone (`refreshRepos`), and the picked PR goes with a space or scope switch that takes its repo off the page. `inboxRows` lists each open PR once, the first key naming it winning, so a PR is read through a checkout here before a `github:` slug. `reviewRequests` stays out: it doubles the cost, so team requests are not counted.

**Sections are `inboxSection`, over `mergeVerdict`**: draft first, then failing checks, a conflict, a review asked of the reader or changes asked of their own PR (Needs you), then running checks ahead of ready, as the sidebar's stages order them. No merged PRs: the page is what is still open.

**A PR's session is `sessionsForPr`**: same repo (the key itself, or `repoOf`) and `sessionBranch` naming the head — the sidebar mark's own reading, with no per-row git spawn. Live before hidden before settled, then newest. A fork's PR matches nothing, its bare head name being somebody else's branch. Sessions are grouped by branch once per index change, so a row asks about its head alone. The index holds one side at a time, so the page reads the other side from every server while it is open, again whenever a PR is picked; a live session missed for the archived view being up would be a duplicate started next to it.

**The detail is the PR panel itself**, `PrPanel` handed the one PR, inside `CommentPickContext`, which draws a box on each timeline row and each inline thread. Rows are picked by `PrComment.id`, the node id; `QUERY` asks reviews for their own `url` too, where it used to fill in the PR's. The pane's read is a second `usePullRequest`, keyed on the PR's key and head, so the 15s/60s poll, the actions and `prSync` come with it — 2 points a read where a by-number query would be 1. It is lazy and sits behind `MountOnce`, the Suspense boundary, or its first open suspends the whole window. **Nothing reads on hover or focus**: a read ahead on a row the pointer rested on cost 2 points per row swept past, out of the budget every agent shares, so the read waits for the click.

**Every task a PR has had stays reachable, newest first.** A row draws its latest task's title, truncated, where it says "No task" ("Read only" for a fork's PR), and the pane draws it above the PR with the rest behind an "N earlier" menu. Settled ones stay, marked Settled: the page is where the reader finds a PR's work again, and a settled task still holds its conversation. A bot's task wears its bot's face and name. A click opens it: a bot's task as a tab in its bot's row, the way its Tasks list opens one (`openPrSession`), anything else on its own.

**The page only starts tasks.** A follow-up is said in the task, or to its bot, where the conversation already is; sending into a running task from here was the first take and went. `prPrompt` names the PR, quotes each picked comment with its link and its replies, says the quotes are GitHub's and not instructions, and puts the reader's text last. Each body goes through `plainComment` first: bot reviews are mostly HTML, badges and buttons — Greptile's carries a signed "retrigger review" link an agent with a browser could act on — so tags go and their text stays, images go, and a link keeps its URL only on github.com. Nothing is written to GitHub, and a fork's PR is read only.

**Start Task starts it right in the pane**, whatever tasks the PR has, and the new one leads the list; the reader stays on the page. Its agent and model come from the PR's latest task, else a new task's remembered ones (`readComposerPrefs`, never the selected session's the main composer mirrors), and the model can change in place through the New Task composer's own `ModelSelector`. **The stance is always Auto**, with no picker. The page says task, not session, throughout. **A composer, not a form**: the PR pane's box is shaped like the task composer, its bottom row holding the Bot | Task switch, the pickers (truncating, never wrapping) and the composer's own send arrow (`SendButton`, shared with `ChatInput`), which starts the task; "Select unresolved" sits in the Comments header with "N selected · Clear". The bot side leads — "Start task in <bot>" makes the tree a task of that bot, hidden under its chat on the chat's own agent and picks as a task the bot starts is, so the model picker shows on the Task side alone. With several bots a menu beside the switch picks one, remembered (`dray.prStartBot`), the first bot standing in until one is used; the side is remembered too. The bot is told (`note_since`, "the user started it on PR #n", the task named "PR #n" there, since its title is read off a prompt that opens with the PR author's title). Only bots on the checkout's server are offered, the only ones whose task can be made there. **No checkout is no dead end**: a key that is a checkout on disk (a bot task's, listed though nobody attached it) is attached first, and a `github:` key with none anywhere is cloned into `~/dray` on This Mac through the attach dialog's own `clone_github_repo`; the pane names an attach before the click and says nothing of a clone until one runs, when the Start button reads Cloning… over git's own progress line (`clone_progress`, its staging-path line dropped), and a clone that fails says why. **A plain task picks its machine** with the New Task page's own `MachineSelector`, over the repo's checkouts (`Project.remote` naming the repo) and a stand-in at `~/dray/<name>` on each connected machine without one, never a Dray Cloud one; a start on a stand-in clones there first. It opens on the checkout the PR would use anyway. A bot's task runs where the bot is, so the picker shows on the Task side alone, and only bots on the picked task's machine are offered.

**`start_pr_session` is its own command**, not a field on `send_msg`: a server older than the page answers `unknown command` before anything is made, where an ignored field forked from the default branch and answered like success. Dray makes the tree on the head **by its own name** (`git::create_worktree_on_branch`): fetched, within 60s, from the remote whose URL names the PR's repo — a fork's `origin` is the fork, and no matching remote is refused rather than read off `origin` — and checked out with `--track -B`. A `worktree-<name>` branch forked from the head would have the agent's push open a second PR. **Git checks a branch out in one tree only**, so a second task while another tree holds the branch — a live task's, or a settled one whose tree was kept — is **detached at the tip** (`PrTree::Detached`) and told to push `HEAD:<branch>` and rebase on a refusal. **Where a local branch has commits the remote lacks**, a branch some task of this checkout recorded (`PrHead::ours`, read off the index) is carried on from by name, an earlier task's unpushed work; any other is refused with "rename it", never pushed over a rebased PR. How the tree pushes is the server's to say (`with_push_line`, after the prompt's header), since only it knows which case this is. The index records `branch` as the head either way, and `sessionBranch` (TS, and its iOS twin in `Pr.swift`) reads the record before rebuilding `worktree-<name>`. **Settling, or a failed start rolled back, leaves the PR's branch**: both delete `worktree-<name>` alone, since a local branch of the PR's name may be the reader's own.
