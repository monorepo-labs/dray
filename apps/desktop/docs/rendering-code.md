# Rendering code

Every surface showing code — `Edit` diffs, ranged `Read` slices, markdown fences — go through **one** Shiki highlighter, the shared instance inside `@pierre/diffs`: [DiffView](../src/components/chat/DiffView.tsx), [CodeView](../src/components/chat/CodeView.tsx), and [codePlugin.ts](../src/lib/codePlugin.ts) replacing `@streamdown/code`'s runtime. Sharing is not just deduplication: the stock Streamdown plugin build a *second* Shiki with its own registries, which cannot see `pierre-*` at all.

**Themes are `{light, dark}` pairs, never one name** ([codeTheme.ts](../src/lib/codeTheme.ts)) — the app's mode can change under a mounted view. **The shipped default is `auto`, which mean the app theme, so `codeThemePair` take one** — resolving without it drew every palette's code in Pierre's colours and switched on mode alone (DRA-183). `AUTO_THEMES` hold the map; a palette with no Shiki counterpart take the nearest, never a grey. [useCodeTheme](../src/hooks/useCodeTheme.ts) is `useSyncExternalStore`, not `useLocalStorage`, because several diffs are mounted at once and per-component state desync them.

Three failure modes, all presenting as _code that renders but is blank or grey_ rather than as an error:

- **A view must not mount before _its own_ language and theme are attached.** `FileDiff`/`File` kick off their own load when they hydrate without one, then drop the promise and never re-render. [useHighlighter](../src/hooks/useHighlighter.ts) is the single gate both views use, asking `getHighlighterIfLoaded({ theme: pair, lang })`, which answers only once that pair and that language are attached. **Do not gate on `isHighlighterLoaded()`** — it only report that an *instance* exists, so a view whose grammar is still loading mount the moment any other view warmed the highlighter.
- **Themes and grammars load independently.** Tokenizing with a theme unattached return every token with an empty style; with a *grammar* unattached it silently yield one plain-text token per line. `codePlugin` check both and report not-ready rather than caching either result — caching the plain-text fallback is what left blocks permanently grey.
- **A fence's info string is a language id, not a filename.** `getFiletypeFromFileName` map *extensions*, so it turn `typescript` and `rust` into `text` while only `ts` happens to work. Use it for paths, never a fence tag.

**Streamdown's link hardening write into prose, so we replace its rehype list** ([markdownPlugins.ts](../src/lib/markdownPlugins.ts)). `rehype-harden` drop an href it cannot resolve — right — then leave a literal ` [blocked]` beside the link, which lands in the reader's text as if the agent typed it. `linkBlockPolicy`/`imageBlockPolicy` = `text-only` unwrap instead. Streamdown expose no option, so the whole `rehypePlugins` list is passed, with **harden's own function taken back out of `defaultRehypePlugins`** rather than from a direct dep, which pin it to the version Streamdown itself runs.

`File` number files from 1 and expose no starting-line option, so `CodeView` rewrite the gutter in `onPostRender`, which hand back the *host* element whose rows live in its shadow root.

**Every diff side carry a content-derived `cacheKey`** (`diffSide` in [diff.ts](../src/lib/diff.ts)). The library fall back to the file *name* as the key and the worker pool cache highlighted lines on the key alone — so a second `Edit` to one file, or `index.ts` from another dir, reuse the first one's tokenized result and a longer diff walk off its end ("deletionLine and additionLine are null", thrown mid-render). Key = full path + length + FNV-1a of the text. **Never hand `parseDiffFromFile` a bare `{name, contents}`.**

**`+N -M` come from the library's hunks, not a hand-rolled scan.** `countChanges` sum `hunk.additionLines`/`deletionLines`, so a collapsed row can never disagree with the diff it opens. A prefix/suffix scan looks equivalent and isn't: `Edit` fragments usually arrive without a trailing newline, so the algorithm treat the boundary line as changed on both sides. Group headers carry the same figure summed over their calls, memoized on call count rather than on `calls`. These are *region* counts, not file counts.

**Where time goes, and the engine is the whole answer.** Every Shiki instance here — the shared main-thread one and each pool worker — run on **WASM Oniguruma** (`HIGHLIGHT_ENGINE` in [useHighlighter.ts](../src/hooks/useHighlighter.ts)), never the library's default JavaScript regex engine. `getSharedHighlighter` read the engine on first creation only, so **every creation site name it** — `warmHighlighter`, `useHighlighter`, `codePlugin`, `DiffWorkerPool` — or whichever run first decide for the rest. Measured in Safari 26.5 (the WKWebView's JavaScriptCore) through this app's own components, the JS engine tokenized at ~1ms/line (2237 lines of TS = 2.2s, a full-file diff twice that) and translated each grammar's regexes lazily on first use — ~1.9s for TypeScript, paid **separately** by the main thread and by each worker — so a small Edit waited 1.0s, a small Read 1.8s and a 2000-line full-file diff 5.8s (DRA-235). Same code on WASM: 230ms for those lines, 150ms cold, 110ms → 1.4s for the same three. V8 hide the gap (3x, not 10x), which is why a Chromium head never showed it; **measure code rendering in Safari or the app, never in the session browser.** The binary is base64-inlined in `shiki/wasm`, so nothing is fetched. Grammar *attach* is the cheap half (~25ms for the whole `COMMON_LANGS` set) and is per language and one-off; *tokenizing* is per file and scales with the whole file, not the change. `warmHighlighter` preload a **named list** — keep it that way. Anything absent still load lazily and render *unhighlighted but readable* meanwhile. **A `File` input want a `cacheKey` like a diff side does** (`diffSide`), or the pool cache nothing for it and every remount tokenize again.

**Diff highlighting run in a worker pool** ([DiffWorkerPool.tsx](../src/components/DiffWorkerPool.tsx)) — without one, whole-file tokenizes ran on the main thread and expanding a row froze the app for up to a second. `FileDiff`/`File` pick the pool out of `WorkerPoolContext` themselves and fall back to the main-thread path (`isWorkingPool`) rather than erroring. Three wiring facts: the worker is built by Vite's `?worker` import (the library take a factory because it cannot know the host's bundler); `worker.format: "es"` in [vite.config.ts](../vite.config.ts) keep the worker's conditional `import("shiki/wasm")` from being inlined as ~600KB; and the pool's theme **override** each view's `theme` option, so `PoolThemeSync` push pair changes via `setRenderOptions`. Pool size 2, not the default 8. Markdown fences still tokenize on the main thread.

**A long session open on its newest turns and backfill the rest.** Opening an 11MB, 61-turn log measured ~700ms, and bytes were not why — what cost was mounting every collapsed turn's answer through Streamdown at once. So [Chat.tsx](../src/components/Chat.tsx) draw the newest `FIRST_MOUNT` turns on the first commit and mount older ones above in `MOUNT_STEP` chunks, one per macrotask ([turnWindow.ts](../src/lib/turnWindow.ts)). Each step grow content *above* what the reader is looking at: pinned, the bottom is re-taken; unpinned, the oldest mounted turn's node is anchored before the step and `scrollTop` moved by exactly what it moved — a height diff is wrong there, since a delta landing below the anchor would count as backfill. Not virtualised: backfill finish in well under a second and then the transcript is ordinary DOM.

**The data follows the same shape: a switch reads the newest `FIRST_MOUNT` turns, and pages the rest in above them.** At 21MB the webview's `JSON.parse` of the whole log was the dear half — ~250–550ms in JSC against ~5–55ms for its 1.8MB tail. `get_session_by_id` takes `turns` and reads the log **backwards** from the end, parsing only what it returns; `older_before` is the byte offset the rest ends at, valid for the file's life since it is only appended to. Once every held turn is mounted, `Chat` asks `loadOlder` ([olderPages.ts](../src/lib/olderPages.ts), a module slot) for the next 16, and each page lands as more to backfill. Three rules hold it together. **A page is prepended in log order, never sorted by `seq`** — a Claude Code subagent numbers its own events from 0. **The mount window is the oldest mounted turn's *key*, not its index**, or a page landing above it shifts the index onto the page and mounts it whole. **The cut is `buildTranscript`'s**: a main-thread `user_message` that is not queued, so a page never splits a turn. Whole-log readers were checked against a tail and all but one read the newest turn only; the todo list's seed in `App` re-seeds silently whenever `olderBefore` moves, since an older page carrying a list would otherwise read as a new one and drag the panel open.
