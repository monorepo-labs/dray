# Rendering code

Every surface showing code — `Edit` diffs, ranged `Read` slices, markdown fences — go through **one** Shiki highlighter, the shared instance inside `@pierre/diffs`: [DiffView](../src/components/chat/DiffView.tsx), [CodeView](../src/components/chat/CodeView.tsx), and [codePlugin.ts](../src/lib/codePlugin.ts) replacing `@streamdown/code`'s runtime. Sharing is not just deduplication: the stock Streamdown plugin build a *second* Shiki with its own registries, which cannot see `pierre-*` at all.

**Themes are `{light, dark}` pairs, never one name** ([codeTheme.ts](../src/lib/codeTheme.ts)) — the app's mode can change under a mounted view. **The shipped default is `auto`, which mean the app theme, so `codeThemePair` take one** — resolving without it drew every palette's code in Pierre's colours and switched on mode alone (DRA-183). `AUTO_THEMES` hold the map; a palette with no Shiki counterpart take the nearest, never a grey. [useCodeTheme](../src/hooks/useCodeTheme.ts) is `useSyncExternalStore`, not `useLocalStorage`, because several diffs are mounted at once and per-component state desync them.

Three failure modes, all presenting as _code that renders but is blank or grey_ rather than as an error:

- **A view must not mount before _its own_ language and theme are attached.** `FileDiff`/`File` kick off their own load when they hydrate without one, then drop the promise and never re-render. [useHighlighter](../src/hooks/useHighlighter.ts) is the single gate both views use, asking `getHighlighterIfLoaded({ theme: pair, lang })`, which answers only once that pair and that language are attached. **Do not gate on `isHighlighterLoaded()`** — it only report that an *instance* exists, so a view whose grammar is still loading mount the moment any other view warmed the highlighter.
- **Themes and grammars load independently.** Tokenizing with a theme unattached return every token with an empty style; with a *grammar* unattached it silently yield one plain-text token per line. `codePlugin` check both and report not-ready rather than caching either result — caching the plain-text fallback is what left blocks permanently grey.
- **A fence's info string is a language id, not a filename.** `getFiletypeFromFileName` map *extensions*, so it turn `typescript` and `rust` into `text` while only `ts` happens to work. Use it for paths, never a fence tag.

**Streamdown's link hardening write into prose, so we replace its rehype list** ([markdownPlugins.ts](../src/lib/markdownPlugins.ts)). `rehype-harden` drop an href it cannot resolve — right — then leave a literal ` [blocked]` beside the link, which lands in the reader's text as if the agent typed it. `linkBlockPolicy`/`imageBlockPolicy` = `text-only` unwrap instead. Streamdown expose no option, so the whole `rehypePlugins` list is passed, with **harden's own function taken back out of `defaultRehypePlugins`** rather than from a direct dep, which pin it to the version Streamdown itself runs.

`File` number files from 1 and expose no starting-line option, so `CodeView` rewrite the gutter in `onPostRender`, which hand back the *host* element whose rows live in its shadow root.

**Every diff side carry a content-derived `cacheKey`** (`diffSide` in [diff.ts](../src/lib/diff.ts)). The library fall back to the file *name* as the key and the worker pool cache highlighted lines on the key alone — so a second `Edit` to one file, or `index.ts` from another dir, reuse the first one's tokenized result and a longer diff walk off its end ("deletionLine and additionLine are null", thrown mid-render). Key = full path + length + FNV-1a of the text. **Never hand `parseDiffFromFile` a bare `{name, contents}`.**

**`+N -M` come from the library's hunks, not a hand-rolled scan.** `countChanges` sum `hunk.additionLines`/`deletionLines`, so a collapsed row can never disagree with the diff it opens. A prefix/suffix scan looks equivalent and isn't: `Edit` fragments usually arrive without a trailing newline, so the algorithm treat the boundary line as changed on both sides. Group headers carry the same figure summed over their calls, memoized on call count rather than on `calls`. These are *region* counts, not file counts.

**Where time goes, and the engine is the whole answer.** Every Shiki instance here — the shared main-thread one and each pool worker — run on **WASM Oniguruma** (`HIGHLIGHT_ENGINE` in [useHighlighter.ts](../src/hooks/useHighlighter.ts)), never the library's default JavaScript regex engine. `getSharedHighlighter` read the engine on first creation only, so **every creation site name it** — `warmHighlighter`, `useHighlighter`, `codePlugin`, `DiffWorkerPool` — or whichever run first decide for the rest. Measured in Safari 26.5 (the WKWebView's JavaScriptCore) through this app's own components, the JS engine tokenized at ~1ms/line (2237 lines of TS = 2.2s, a full-file diff twice that) and translated each grammar's regexes lazily on first use — ~1.9s for TypeScript, paid **separately** by the main thread and by each worker — so a small Edit waited 1.0s, a small Read 1.8s and a 2000-line full-file diff 5.8s (DRA-235). Same code on WASM: 230ms for those lines, 150ms cold, 110ms → 1.4s for the same three. V8 hide the gap (3x, not 10x), which is why a Chromium head never showed it; **measure code rendering in Safari or the app, never in the session browser.** The binary is base64-inlined in `shiki/wasm`, so nothing is fetched. Grammar *attach* is the cheap half (~25ms for the whole `COMMON_LANGS` set) and is per language and one-off; *tokenizing* is per file and scales with the whole file, not the change. `warmHighlighter` preload a **named list** — keep it that way. Anything absent still load lazily and render *unhighlighted but readable* meanwhile. **A `File` input want a `cacheKey` like a diff side does** (`diffSide`), or the pool cache nothing for it and every remount tokenize again.

**Diff highlighting run in a worker pool** ([DiffWorkerPool.tsx](../src/components/DiffWorkerPool.tsx)) — without one, whole-file tokenizes ran on the main thread and expanding a row froze the app for up to a second. `FileDiff`/`File` pick the pool out of `WorkerPoolContext` themselves and fall back to the main-thread path (`isWorkingPool`) rather than erroring. Three wiring facts: the worker is built by Vite's `?worker` import (the library take a factory because it cannot know the host's bundler); `worker.format: "es"` in [vite.config.ts](../vite.config.ts) keep the worker's conditional `import("shiki/wasm")` from being inlined as ~600KB; and the pool's theme **override** each view's `theme` option, so `PoolThemeSync` push pair changes via `setRenderOptions`. Pool size 2, not the default 8. Markdown fences still tokenize on the main thread.

**A transcript opens on its tail, reads back only as the reader scrolls, and draws a window** (#1155, the bot chat's mechanism from #968 and #998, now one code path in [Chat.tsx](../src/components/Chat.tsx) for both). Opening an 11MB, 61-turn log measured ~700ms, and bytes were not why — what cost was mounting every collapsed turn's answer through Streamdown at once. Tasks used to read the tail and then page the whole log in, because the checkpoint rail listed every turn; the rail is gone, so nothing needs the whole history. While the reader follows the bottom the chat draws its last 24 turns (`lastTurns`) and slides as turns land. Scrolled up, the top holds on an event; within a screen of it the window grows 16 held turns (`earlierTurns`), and once everything held is drawn the next page is read (`loadOlder`). When a page lands above, the row at the top of the view is put back where it was (`noteAnchor`). Back at the bottom the window slides again and the pages read above it are let go (`dropOlder`). Not virtualised: the window keeps the DOM small, and what is drawn is ordinary DOM.

**The data follows the same shape.** At 21MB the webview's `JSON.parse` of the whole log was the dear half — ~250–550ms in JSC against ~5–55ms for its 1.8MB tail. `get_session_by_id` takes `turns` (`FIRST_MOUNT`, [turnWindow.ts](../src/lib/turnWindow.ts)) and reads the log **backwards** from the end, parsing only what it returns; `older_before` is the byte offset the rest ends at, valid for the file's life since it is only appended to. Three rules hold it together. **A page is prepended in log order, never sorted by `seq`** — a Claude Code subagent numbers its own events from 0. **The window is held as an event id, not an index**, or a page landing above it shifts the index onto the page. **The cut is `buildTranscript`'s**: a main-thread `user_message` that is not queued, so a page never splits a turn and a window always starts on a turn's prompt. `buildTranscript` still runs over every held event, never the window, so a call drawn in the window finds a result that landed later and a card can wait longer than 24 turns. **The Changes panel reads back on its own** (`useOlderWrites`): its last writing turn can sit far above the tail, so where the held turns found fewer than two it reads pages above them and keeps only the ranges, never the events. Only while the panel is on the Changes tab, as `useChanges` reads only then, and only where held prompts record snapshots, since a plain directory has nothing up there; a failed read is retried, backing off to every 30s, while the panel shows it. **The More tab sees what is loaded** — subagents, pictures and the todo list are read off held events, so a long task shows its recent ones until the reader scrolls up; the todo list's seed in `App` re-seeds silently whenever `olderBefore` moves, since an older page carrying a list would otherwise read as a new one and drag the panel open.

**A remote transcript opens on a first frame, and reads the rest only when something drawn needs it** (#1236). The tail is megabytes of tool output a collapsed transcript never draws — 836KB of JSON, 52KB deflated, for a 100-call turn — and it was all read, sent, inflated and parsed twice before the newest screen could paint. A finished turn draws its prompt, a count of its work and its answer, so `get_session_by_id` takes `lite` and [thin.rs](../src-tauri/src/thin.rs) answers the same page with tool arguments and results cut to 256 bytes, then whole turns dropped from the old end until the rest deflates to 11KB — ten TCP segments is the most a sender opens with, so that crosses in one flight. **Never part of a turn**: its header counts its calls, and a count of some of them is wrong where no count is merely absent, so the newest turn is kept whatever it weighs. A cut body carries `_cut` (in the call's `input`, the result's `structured`), reasoning and reported diffs are left whole, and every event kept is its logged self under the same id. `olderBefore` is the page's either way.

The client holds that frame as `SessionSnapshot.lite` and asks for the whole page (`fill` in [useSessions.ts](../src/hooks/useSessions.ts), merged over it by id, live events kept) on three cues and no other: the reader within a screen of the top, which is the chat's own paging rule and `loadOlder`'s first step; a row whose body was cut being drawn ([ToolCall](../src/components/chat/ToolCall.tsx), which shows no figure counted from a fragment and opens onto nothing until then); and the side panel opening, whose tabs read the transcript's events. So a transcript shorter than two screens completes at once and a long one never does unless read back. The todo seed in `App` treats that completion like an older page landing. An older server ignores the argument and answers whole; This Mac is never asked, its disk being milliseconds away; a bot's chat is read its own way, below. **iOS asks for the first frame and then the whole page straight behind it** (`Store.reload`), never caching a first frame: loading on demand there is not built. Measured to a real sandbox over OpenTunnel, 195ms a round trip, 100-call turn: first frame 13KB and 230ms on the wire against 52KB and 350–390ms; first open in the dev app 537ms whole, 453ms thin, 210–290ms local (medians).

**A bot's chat is read as what it draws, on every server** (#1236). It shows the conversation and the tasks the bot started and never the work between, yet it was read like a task's transcript: a real bot's log was 135 events and 1.01MB, 100 of them tool calls holding 97% of the bytes, against 18 messages in 9KB. `get_session_by_id` and `get_session_page` take `bot`, and `thin::chat` drops every tool call with its result bar three kinds — a `dray … new` or `dray … send`, which `botItems` reads for a task or a message, kept whole with 4KB of output; and a call still open, which the orb line names — along with reasoning, reported edits and anything a subagent did. Everything else stays, so an event a later build adds still reaches a chat that draws it. That is all the client ever holds of a bot's session, older pages included (`readAs`, `loadOlder`), so it is not `lite` and nothing follows it; live events arrive whole as before and draw nothing. Same sandbox: 28 events and 5KB in 198ms on the wire against 212KB in 323ms, first open 462–658ms against 844–968ms. iOS still reads a bot's chat whole.

**What is left is the round trip itself, and only a read made before the click removes it.** `warm` reads a first frame into [keptTranscripts.ts](../src/lib/keptTranscripts.ts), where evicted remote transcripts already wait, and the open is `loadTail`'s copy path: drawn at once, completed and caught up behind — 146–180ms on that same link. Two triggers: a server's index read warms its six newest rows (`warmPicks`), one at a time, 12KB each; and a turn finishing re-reads that session, since the row that just went green is the next one opened. A read-ahead still out when the click lands becomes that click's read. Never This Mac, never a row mid-turn, hidden or set aside.

**Keeping the connection warm buys nothing, measured.** Through OpenTunnel a 52KB frame takes ~250ms after ten idle seconds, after ten seconds of pings, and back to back alike; only the first on a fresh connection is slow (386ms). The sender facing the client is the tunnel's edge, so neither a server's `tcp_slow_start_after_idle` nor traffic from here reaches it. A direct or SSH-forwarded connection does fall back to slow start after idle (480ms against 170ms at 150ms RTT, on a netem rig), which is the case the 11KB budget is for.
