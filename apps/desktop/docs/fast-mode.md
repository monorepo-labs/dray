# Fast mode

**Three harnesses have one, each reached a different way, and `Capabilities::fast_mode` is the one statement of that** — a two-armed enum rather than a bool, since "offered" and "changeable" would spell combinations nothing has. Stated twice, in [fastMode.ts](../src/lib/fastMode.ts) too, for the same reason `stanceFor` is. It is a **bool** on the index entry and on the wire, never an enum: every one of them is two-valued, and a variant an older build cannot spell fails the line and reads the whole index as no sessions.

- **Claude Code — in place.** `--settings '{"fastMode":true}'` at spawn, `apply_flag_settings` with the same `flagSettings` layer on a running child, both verified against v2.1.270. **The SDK has to opt in and nothing else turns it on**: without it the CLI reports `fast_mode_state: "off"` with `fast_mode_disabled_reason: "sdk_opt_in_required"` however the reader's own settings files are written. The flag rides *every* spawn, resume included — `flagSettings` is per process, so a respawn would silently drop back to standard speed. Opus alone, which is the CLI's own gate on the resolved model naming `opus-5` or `opus-4-8`.
- **Codex — on the next turn.** `serviceTier: "priority"` (the tier's id from `serviceTiers`, not `fast` from `additionalSpeedTiers`; `thread/start` takes either and answers `priority`). It rides **both** `thread/start` and every `turn/start`, and is **always sent** where `effort` is omitted when unset: a tier set on a turn sticks to the thread, so omitting it means "keep what you have" and `"default"` is what puts it back — and that stickiness is why a switch rides the next `turn/start` rather than a respawn. `thread/resume` ignores the field. **An unknown tier is accepted with no error at all** and runs the turn at ordinary speed, which is why `supports_fast` follows the wire and absent reads as *no* — the opposite of `accepts_images` beside it.
- **fx — in place, since 0.0.14.** `session/set_config_option fast` with `"true"`/`"false"`, measured: it writes nothing to `~/.fx/settings.json`, survives a `session/resume` in a fresh process and a model switch on the codex provider. Refused mid-prompt like every fx config change, so a mid-turn pick rides `DeferredControls`. A reply with no `fast` option — an older fx, or a model with no fast lane — reads as `None`, and asking such a session for fast mode is refused in Dray's own sentence, drawn in the transcript, never fatal. This replaced writing `fast_mode` into fx's global settings before `session/new`, which raced fx's own TUI writing the same key; an fx before 0.0.14 now simply runs at ordinary speed.
- **pi — none.** `serviceTier` is plumbed through its provider layer and populated from nowhere: no flag, no settings key, and `set_model`/`set_session_name` are its RPC's only setters.

**The control is a row in the model picker, because fast mode is per *model* on every harness that has one.** `Model.supports_fast` is what draws it — the Codex list reads it off the wire, Claude's table names Opus alone, and **fx's gateway rows say so outright** — `fx models --json` carries `fast` per row since 0.0.14. Where a row does not (codex and grok rows, or an older fx), **the Vercel gateway's fast tier is a model of its own**, a separate id with `-fast` on the end, so a gateway model has fast mode where its twin is in `Listing.ids`. The twins are **kept out of the picker** — the same model twice, once as a model and once as a mode, gives fast speed with an inert toggle beside it — and a `-fast` id takes no toggle **because it is the fast tier**, not for want of a twin of its own, which is its own arm in `supports_fast` rather than left to the lookup answering right by accident. codex offers fast mode and lists no `-fast` id, so its hardcoded `true` is correct and measured; grok is **untested** and keeps `true` for codex's reason rather than on a reading of its own. Applied globally the twin rule would mark every codex and grok model as having none. **Hidden is never unrunnable**: `list` filters, `find` reads the unfiltered list, or a session recorded on a `-fast` id would resolve to nothing, spawn with no `--model` at all and record its own model as unset — silent on screen and in the log. Codex's hidden rows (`gpt-reserve`, `codex-auto-review`) make the same bargain. The pick itself is **one preference, not one per model**, unlike effort: a level means different things on each ladder where fast mode means one thing everywhere, so switching to a model without one keeps the pick and simply doesn't honour it. `fastFor` narrows it at the send and `send_msg` clamps by harness again, so what reaches the index is always what the child was told. **It sits straight under the models.** **A real switch, not a tick, and the row holds the menu open** — every other row there is a pick out of a set where this one is on or off, and a switch that vanishes on the press never shows which way it went. The row is the control and the `Switch` is its picture (`pointer-events-none`, with `role="switch"` on the item), or the two would fire side by side and toggle twice. The trigger says **Fast** beside the effort and drawn exactly like it: its presence is what says the mode is on, so a colour would be a second way to say one thing — and an accent there competes with the yellow the sidebar spends on sessions wanting the reader. A glyph was the other try; among two words it read as a badge stuck on the label.

**A refusal is drawn as the harness's own sentence under the row, and nothing moves the switch.** Claude Code says it on `system`/`notification`, keyed rather than typed — `fast-mode-overage-rejected` / "Fast mode disabled · usage credits exhausted", captured in [fast_mode_refused.jsonl](../src-tauri/src/harness/claude_code/fixtures/fast_mode_refused.jsonl), where it used to land in `parse_failures.jsonl` as `unknown_subtype`. The mapper reads the whole `fast-mode-` prefix and drops every other key to `None`, since the payload carries the sentence untouched and anything said under that prefix is news about fast mode. **Not `fast_mode_state` on `init`, which is not the weaker source but a lying one** — measured: through both turns of the captured session it reported `on` while the CLI was refusing fast mode outright, so a reader believing it is told the opposite of what happened. That retires reconciling anything from it as a question: it was already refused on `permissionMode`'s grounds, which is that these fields report what the CLI is *doing* rather than what was asked for, so a cooldown would read as the reader turning fast mode off — and a field that also reports the wrong thing about what the CLI is doing has nothing left to offer. The notice is the only honest source, and the switch stays the reader's alone.

**The notice is scoped to the newest turn, and that is what clears it.** `fastNotice` in [fastMode.ts](../src/lib/fastMode.ts) walks the session's own log back and stops at `turn_started`, so a turn that runs fast says nothing and the sentence goes; the CLI says it once per **turn** it refuses rather than once per session, which is what makes that reading safe — two lines 8s apart in one captured session, and the whole of why the walk stops where it does. Read from the log rather than tracked in a map, the same bargain the context ring makes, so a reopened session reads what it read live. Drawn only while the switch is **on** — it is there to explain a lit control that changed nothing, and beside an off one it is a stale complaint about a setting already left. Codex and fx report nothing at all, so there is nothing to draw for those two either way.
