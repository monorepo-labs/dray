# Harnesses

- **Codex runs, over `codex app-server`, and it is partial.** Session spawn, stream, resume and Stop; the transcript draws messages, reasoning, shell calls and file diffs; the context ring fills. **Approval is wired**, and the options are the server's own — Codex sends `availableDecisions` and each button carries one back untouched. A real capture offers *no* refusal at all, so `decline` is added where the server names none. Codex splits stance into two settings where Claude has one (`approvalPolicy` = when it asks, `sandbox` = what a command may touch, OS-enforced), so Dray's mode widens into a pair and the composer hides Plan there. `acceptEdits` was removed from Dray outright, Claude included; `#[serde(alias)]` keeps old index entries loading as `auto`. Forks through `thread/fork`. Images go as `localImage` input items naming the archived copy. **Model, effort, stance and fast mode ride the next `turn/start`**, every one an override that sticks to the thread (measured on 0.164) — the sandbox as a `sandboxPolicy` object, sent only once the stance moves, since restating one every turn would overwrite what `config.toml` made of the mode; going back sends the policy `thread/start` resolved. Mid-turn they stay locked: a steered `turn/start` ignores them. **Its slash commands are its skills and nothing else** — the rest of Codex's own `/` menu is TUI actions Dray already owns in its chrome — and unlike Claude Code they are *not* prompt text: `/caveman` sent as text is four literal words to the model, so `turn/start` carries `{"type":"skill","name":…,"path":…}` as its own input item, both fields required and a skill accepted with no text beside it. The picker asks a throwaway app-server (`skills/list`, cached per directory); the send path asks the session's own live client, so there is no second spawn and no cwd to go stale. Worktrees work by the other route, since Codex has no `-w`. **Read [CODEX.md](../CODEX.md) first** — it carries four things that bite: `tokenUsage.last` is occupancy where `total` is cumulative; a stale `codex` on PATH with no `app-server` subcommand answers nothing for 30s; `turn/interrupt` refuses without `turnId`, so Stop must track the running turn; and `thread/start` drops `effort` in silence, so it rides every `turn/start` instead. Design and staging in [CODEX-PLAN.md](../CODEX-PLAN.md).
- **fx (Vercel) runs over `fx acp`** — ACP, newline JSON-RPC like Codex's app-server, and the framing *is* Codex's `rpc.rs`. Streams text and thoughts, draws tool calls off ACP's `kind` — **with `subagent` and `glob_files` the two names that outrank it**, since ACP spells both `other`/`read` and each wrong reading costs the row something: a run of subagents collapsed into a count that hid the tasks, and a glob typed as a read took the whole-file-read dead end and drew its matches nowhere. Raises the permission card from `session/request_permission` with the server's own options carried back whole, cancels with a notification, resumes by the id fx minted (`thread_id`), and fills the context ring from `usage_update` — an occupancy, not a cumulative. **A prompt is a request that blocks for the whole turn**: `session/prompt` answers with `stopReason` minutes later, so it is sent with `request_detached` and the read loop settles the turn on that id itself. **So the held queue goes over as one turn, not one turn each** — every message keeps its own bubble and its own `user_message` line, and `flush_fx` joins their prepared text with a blank line into the one prompt fx takes. Drained one at a time it was the reader's second sentence waiting out a whole turn answering their first. **Now** under the newest bubble is the reader's way out of that wait, and it is `interrupt` and nothing else: a cancelled prompt answers `cancelled`, which is a `turn_completed`, which reserves and flushes. Drawn on fx alone — every other harness hands its queue over at the next tool boundary, seconds away, where stopping the turn costs more than the wait. **⌘⏎ is its chord** (`queue.send`), drawn beside the words as plain text rather than as keycaps — a `Kbd` is chrome, and this is one muted sentence under a dimmed bubble — with Return as lucide's `CornerDownLeft` rather than `keyLabel`'s `⏎`, since the hint under the empty composer already draws that icon a few pixels away and two spellings of one key is one too many (the registry keeps the character, for the Settings tab's text chips) — and bound in `QueuedMessages` off the `onSendNow` prop rather than off the harness name, so it exists exactly where the button does — and the composer gives it up: `ChatInput`'s Enter-sends branch now reads the modifier, which it never did, so ⌘⏎ used to send the draft by accident and would otherwise fire both. **Model, effort and stance apply in place** — the one harness whose effort change is a request, not a respawn — and the model rides the spawn as `--model`, which fx saves nowhere. **fx titled its own sessions and no longer does** (DRA-250). It titles with a *second model call* and its ACP server holds the `session/prompt` reply until that lands — measured through `fx acp --log-file` as `prompt_finish`, then 5.9s of `title_generation`, then the reply — so the reader watched a finished answer under a working orb for seconds. Nothing on the wire says the answer is done (`prompt_finish` is log-only), and nothing can be squeezed into the gap either: a prompt sent there is refused `-32600 Prompt already in progress`, so fx holds the whole **session**, not merely the reply. Only the first turn pays it, since fx restates the stored title afterwards rather than deriving it again — which is the whole of why the stall looked like the first message being special. So `session_titles: false` goes into `~/.fx/settings.json` at creation beside `fast_mode` and under the same guard (0.16s after), and `session_info_update` is **dropped**: with generation off it carries the raw first prompt, which is what the index already holds, and fx restates it every later turn, so honouring it would write the prompt back over [title.rs](../src-tauri/src/title.rs)'s generated title mid-session. fx's **global** setting, so it moves the reader's own TUI default too, and their TUI is a second writer that can undo it — a lost write costs the stall back, never the session. The proper cure is fx's: send the title as the notification it already is instead of holding the response. **The title child takes `FX_SOUND=off`, and that is not tidiness** (DRA-251): `fx ask` plays fx's own completion chime on finishing — `/usr/bin/afplay …/fx-success.m4a`, measured at 13 `ps` sightings against **0** with the variable set — and since the child starts at session creation and takes a few seconds, the sound landed about where the first turn ended. So Dray appeared to have grown a chime on every fx turn, over a child the reader never asked for. Models are *discovered* through `fx models --json`, never `fx acp`: a promptless `session/new` is still persisted, and a probe there litters `fx sessions`. **The effort ladder is per model, and three things answer it in order — the guess, the row, a live session.** fx 0.0.14's `fx models --json` carries `name`, `efforts`, `fast` and `ultrafast` on every gateway row, authenticated, so a reader's private models are in it too; that retired the anonymous AI Gateway catalog fetch (DRA-252) that stood in for it. An empty `efforts` is an answer — no effort control — and `none`/`minimal` have no rung. Codex and grok rows still carry `{id, source}` alone, and keep the guess. **A level a session actually took still outranks it**, since that is the only source that has watched this model rather than been told about it. **Over-offering stays the chosen direction where nothing better answered**: a picker with no effort control until after the first send is a control the reader cannot find when they are choosing what to send. So a level fx refuses is drawn, asked for, refused, and the refusal is **reported in the transcript alone** — see the composer's error slot, which that sentence deliberately does not reach. **A result lives in the closing update, and the stream is the fallback** — the reverse of what the shell alone suggested. `web_fetch` streams `Fetching …` / `Converting …` as progress and answers at the close, so preferring the stream drew the chatter and dropped the page; a shell is the other way round and its closing update carries only fx's replay blob, which is what the blob sniff is still for. **fx caps ACP tool content at 200 characters** and hands the model a `full_output_handle` to query through `read_tool_result` — nothing on the wire carries the rest, `rawOutput` included, so a long result is 200 characters in the transcript however it is read. That cap is why two rows read the result rather than drawing it. **A `web_fetch` row does not expand at all**: the page is context the agent pulled in rather than something it is showing the reader, the same reading a whole-file `Read` takes, and expanding offered 200 characters of somebody else's page. Name-keyed, since a web *search* answers with the results themselves; Claude's `WebFetch` is deliberately untouched, answering with a model's summary written for the reader. And **a subagent's report is unwrapped out of `{"ok":true,"result":"…"}` by shape, never by parsing** — the cut usually lands mid-string, so the envelope is invalid JSON exactly when it carries something worth reading, and the row drew the brace and the escapes.

**A delegated run is Dray's own, minted from the call that spawned it.** fx sends no subagent lifecycle and nothing about a child streams at all, so the panel listed nothing however many times a session delegated; the mapper mints `SubagentStarted`/`SubagentCompleted` around the `subagent` call instead, enveloped on that call's id, which is what the transcript correlates a run on. Two things follow. **`agent_id` is empty, deliberately** — it is the handle a stop names and fx publishes none, so `transcript.ts` reads an empty one as *no handle* and the panel withholds a Stop button whose request fx could not take. And **`SubagentRun.inline` keeps the chat row a tool row**: the spawning call is the whole run here, so a row that only navigated would send the reader to a panel holding what they were already looking at. It is keyed on the harness rather than on "has this run filed any events yet", which is true of every run for its first frame and would flip the row out from under a Claude subagent the moment it started working. The row carries the orb, and `request.model`/`request.effort` sit on it beside the task where the agent chose them for the child — the work went somewhere else, which should not need a click to find out. **The brief is the row's own text, and opening the row un-clamps it in place** — one line collapsed like every other row, the whole thing wrapped when open. Drawn as a block under a truncated summary it put the task on screen twice in the chat and three times in the panel, whose row title is the task as well. It **wraps back under the label** rather than hanging off it, which is why the label, the settings and the summary become one inline flow for this row alone (`contents` on the wrapper leaves every other row's three flex items exactly as they were, and the flex gap becomes real spaces, or the accessible name reads `Delegatinggpt 5.6 luna high…`). **The panel draws that brief as text rather than the spawning call's row**, since a row brings a caret of its own — a second thing to open inside the pane just opened — along with a tool name and a report the header and the agent already cover. Every other harness still gets the row there, where it carries the prompt. **The report is not drawn at all**: a delegated run answers *the agent*, which says what it made of it in the next message, so the row would carry the child's answer a second time. A failure still shows, since the agent may carry on without mentioning it. `tools.jsonl`. Two more things measured, not read off fx's docs, both pinned by fixture:

  **`fx acp` reads no MCP config of its own, so Dray hands it the list** ([harness/fx/mcp.rs](../src-tauri/src/harness/fx/mcp.rs)), off `~/.fx/mcp.json` — the file `fx mcp path` names — on **both** `session/new` and `session/resume`, since fx keeps none of it across a connection (measured: resumed with an empty list, the tools are gone). `mcpServers: []` was not "use your own", it was "this session has none", and it is what left Dray's fx sessions with no tools while the same machine's `fx` shell had all of them (DRA-220). Shapes are fx's own validation, not ACP's prose: stdio is `{name, command, args, env:[{name,value}]}`, http/sse is `{type, name, url, headers:[{name,value}]}`, `headers` is **required** on every http server and must be that **array** — an object map is refused outright.

  **Dray forwards only what the reader already wrote into their own fx config** — a literal `headers`, or `header_env`/`bearer_token_env` resolved from the process environment and then the **login shell** (`$SHELL -l -c 'printenv NAME'`, the name interpolated only after `is_env_name` — a `$1` positional looked safer and is wrong on fish, which has no `$1`, so `printenv` dumps everything and the last line is some other variable sent as a token), since a Dock-launched bundle inherits launchd's environment and a token exported from `.zprofile` would otherwise read as absent — `binpath`'s trap again. **A bearer token has one spelling, `bearer_token_env`** — fx refuses a literal `Authorization` under `headers` or `header_env` (`McpConfigInvalidHeaders`, "so credentials do not become ordinary profile data"), so the key lives in the environment and `.zprofile` is where it has to be exported for a Dock launch. Verified: `bearer_token_env: "LINEAR_API_KEY"` gave an ACP session Linear's 66 tools with the variable scrubbed from Dray's own env. fx's OAuth store is never read: it **refuses to lend its own credentials** to an ACP-supplied server, answering "supply an Authorization header in the ACP MCP server configuration" even for a name it holds a live authenticated connection for — and to an *approved workspace* `.mcp.json` server too, which logs `McpAuthenticationRequired` in ACP and reads `auth=required` even natively after `fx mcp auth` (0.0.10); its docs: "ACP never inherits servers from `~/.fx/mcp.json`" and "ACP is noninteractive, so an ACP host must supply headers for a protected MCP server". A Dray-side reuse of the Issues panel's Linear key was built, flagged in review as spending a credential given for another purpose, and reverted — `bearer_token_env` makes it unnecessary. **A headerless HTTP server is two cases one config line cannot tell apart** — an endpoint wanting no auth takes `headers: []` and works, an OAuth-backed one takes the same list and fails the open — so `fx mcp list` (no `--connect`, no network) is asked: `auth=none` earns the empty list, anything else or a failed probe is a skip. Measured: the same entry reads `auth=none` under a home with nothing stored and `auth=authenticated` under the reader's, so it is fx's credential store answering, not the file. Run from home, so a project `.mcp.json` cannot answer for a profile server of the same name.

  **Every server on the ACP surface is *required*, and `open_with_servers` is what keeps that from being fatal.** fx's shell tolerates a dead entry under `policy=optional`; over ACP the same entry fails the whole `session/new` with `-32602 Required MCP server '<name>' failed to start`, so one stale command in `~/.fx/mcp.json` would make fx sessions uncreatable in Dray while working fine in a terminal. The named culprit is dropped and the open repeated — a refusal naming none sheds them all — and the child stays usable across a refused open, measured for both `session/new` and `session/resume`. Each drop is logged, since the reader's only other signal is a tool the agent cannot find. **Only an MCP refusal is retried** (`is_mcp_refusal`: the flattened error's `(code -32602)` plus fx's "MCP server" wording) — a timed-out open may already have persisted a session, and repeating it mints a second one nothing tracks. Project-scoped `.mcp.json` is deliberately unread — a repo-supplied server names a command to execute, and there is no trust prompt to put in front of that.

- **`effort` is simply absent** from the `configOptions` of a model that does no reasoning, and which models those are does not follow the vendor — on the gateway `anthropic/claude-opus-5` carries one and `anthropic/claude-sonnet-4` does not, `openai/gpt-5.4-nano` offers a `none` rung and `spacexai/grok-4.6` offers nothing at all. No table written here could name that. `effort_ladder.jsonl`.
- **The option list is the model's ladder unioned with the level the session is on**, and a model switch does not clamp that level, so a list can name a rung its model refuses and `session/resume` restates it: a session moved from `gpt-5.6-sol` at `ultra` onto `gpt-5.6-luna` reports `ultra` among luna's options and is still answered `-32602` for it. `effort_carryover.jsonl`.

So **what is remembered is narrower than what is used**. The session takes the list whole — fx judges its own session, and over-offering costs one reported refusal where withholding costs a rung fx would have taken — while the *model* list reads one reply as **two bounds** (`LadderReading`): `options` minus the current level is every rung proven, `options` whole is every rung still on offer. The subtraction is sound whatever the level is, since every survivor is one the model takes. `learn_ladder` keeps a rung where this reading proves it or an earlier one did **and fx still offers it**, which is what lets the level in use come back from the next reading instead of the menu shuffling one in and out, while a rung fx stops offering altogether is dropped rather than cached for the life of the process. **fx accepting a level is the third statement and the only proof the active model takes it** — no reply can say so, that being exactly the level subtracted out — so `set_effort`'s reply is read back with the accepted level put in. Without it, opening a session on a perfectly valid level teaches the picker that level is unsupported and `usableEffort` moves the reader off the effort their conversation has been running on. Trusting only a reading sitting on fx's `auto` was the rejected alternative: it is sound too, and does nothing at all for a reader whose fx default effort is not `auto`. A definitive "no effort option" replaces the lot. The rule is checked against every reply in every fixture by test, so a future fx widening the list some other way fails there first.

A refused effort is **never fatal and never silent**. Fatal is the half with teeth: the spawn used to `?` on it and kill the child, so a session resumed onto a model that had stopped taking its recorded level could not be opened *at all*. Now the level is dropped, the send keeps its prompt, the index records what is actually running, and the transcript draws **Dray's own sentence** naming the levels the model does take — fx has two refusals one word apart ("is unavailable" for a model with none, "is not available" for a rung too high) and neither says which level, what the model takes, or what the session ended on. `models_changed` is what carries a learned ladder to the composer, so the picker stops offering a control mid-session rather than at the next restart. Stances are three — `manual` → `ask`, `auto` → `auto`, `bypassPermissions` → `full-access` — since 0.0.14, which renamed ACP's `code` to `auto` and refuses the old name with `-32602 Unknown mode`. **A refused mode at spawn kills the child**, so a mode name fx drops is every fx session failing to open (#672). **`session/set_mode` also rewrites `permission_mode` in `~/.fx/settings.json`** (0.0.14, measured: one backup per call, `full-access` stored as `yolo`; `set_config_option mode` does the same), and fx's changelog says that is the design — ACP changes are remembered "for future CLI and ACP sessions". There is no session-only mode. A session opens in that saved mode, so a spawn skips `set_mode` where the open reply's `currentModeId` is already the stance asked for; only a pick that differs moves the reader's TUI default. **Provider is a composer control an existing session may still move, and the model is what carries it.** It writes `fx provider`, fx's global setting, because the picker's list is the *active* provider's and nothing else can make it follow. The session itself moves at the next send: `fx::set_model` sends `set_config_option provider` first where the model it is handed belongs elsewhere, since fx refuses a cross-provider model outright (`-32602`) — a `?` that used to fail the whole send and, on a resume, kill the child, so a session whose global provider had moved underneath it could not be opened at all. Safe because the switch is real: measured on 0.0.10, it moves the model with it and **persists onto fx's own session record**, so a `session/resume` in a fresh process comes back on it rather than on whatever the settings file names by then (`provider_switch.jsonl`, which leaves `settings.json` on the provider it started at throughout). **Disabled while the turn is in flight**, with the reason drawn under the row rather than hung off a tooltip a disabled button can never open. **Its slash commands are its skills**, walked off disk rather than asked for — `available_commands_update` is empty and nothing else on the wire answers — and sent as ordinary prompt text, which fx expands itself. Not in v1: fork (fx has none), images (0.0.14's codex provider took a 1×1 PNG, but `start_turn` sends text alone and fx refuses images per model, which no list here names). **Steering is advertised and does not work**: 0.0.14 answers `_meta.fx.steering: true` on `initialize`, yet a second `session/prompt` mid-turn — mid-tool and mid-stream, with or without a `_meta` opt-in, on codex and gateway — is refused `-32600 Prompt already in progress`, so the held queue and **Now** stay. **Read [FX-PLAN.md](../FX-PLAN.md)** for the captured wire and what the docs got wrong.

**Dray's rules ride `session/new` as `systemPrompt`** — `[{"type":"text","text":…}]` with `systemPromptMode: "append"`, sent only where `initialize` advertises `sessionCapabilities.systemPrompt` (0.0.14). fx stores it on its own session record, so a `session/resume` in a fresh process still carries it — measured with a codeword asked only after the resume (`fast_and_rules.jsonl`). [system_prompt.md](../src-tauri/src/harness/fx/system_prompt.md) is its own file rather than pi's, which names `~/.agents/skills` where fx reads `~/.claude/skills` among its global roots. The first-prompt append that stood in for this, and `title.rs`'s cut of it, are gone; an fx that does not advertise the capability gets no rules. Sessions made before keep the rules in their first prompt's history.
- **Grok Build runs over `grok agent --no-leader stdio`** — ACP again, so the framing is Codex's `rpc.rs` for the third time and the shape is fx's throughout. Spawn, stream, resume, cancel, permission cards, questions, subagents and the context ring. **Dray picks the session id**: `_meta.sessionId` on `session/new` is honoured, so the index id *is* the resume handle and `thread_id` stays `None` — the one thing here fx cannot do. Model and effort move in place through `session/set_config_option` (`model`, `reasoning_effort`), whose value is a **bare string**: the docs' `{value: …}` object form is refused outright. **Read [GROK-PLAN.md](../GROK-PLAN.md)** for the captured wire, which is where every claim below was measured rather than read.

  **A prompt sent mid-turn steers the turn, through `_x.ai/interject {sessionId, text}`** — pi's `Session::steer` path, not fx's hold. The model reads it at the next tool or model gap inside the same turn (measured: told mid-run to skip its remaining commands, it skipped them on one prompt id). A second `session/prompt` is the wrong way in: grok takes it but queues it behind the turn — its TUI's default `follow_up_behavior = "queue"` — and it replaces the id the read loop settles the turn on. **An interject landing after the turn ended opens a turn of grok's own** (`interject-fallback-…`) with no prompt answer coming, so the read loop closes any turn Dray did not open on grok's `turn_completed` — the one place that line is read. `text` is a required string; **images ride beside it under `content`**, an array of ACP image blocks — measured on 1.0.70, the model quoted the words of an image sent there with no tool call. An `images` field is the trap: accepted with no error and dropped, and the model went hunting the disk for "the attached image" and read another session's. `_x.ai/queue/interject` is the TUI's send-now, cancel-and-run, which Now already covers for fx and nothing needs here.

  **Two notification streams share one envelope, and a reader on ACP's alone is blind.** Kinds that exist in ACP arrive on `session/update`; grok's own — `subagent_*`, `background_tasks`, `turn_completed`, `pending_interaction`, `auto_compact_completed` — arrive on `_x.ai/session_notification` with the identical `{sessionId, update:{sessionUpdate,…}}` body. **Every one must be filtered on `params.sessionId`**, since a `spawn_subagent` child streams its *whole* transcript down the parent's pipe under the child's own id: 113 updates against the parent's 154 in the capture, thoughts and tool calls and all. Drop that filter and the child's thinking is painted into the parent's chat. Pinned by fixture, and deliberately not on a filename both sides say — the parent reports the child's findings back itself, so an assertion on one passes with the filter removed.

  **The envelope is camelCase and grok's own payloads inside it are snake, and `rawOutput` is where that bites.** A `rename_all` on [`RawOutput`](../src-tauri/src/harness/grok/parser.rs) costs no error and no failed line — every field reads `None` for ever, so a shell row silently loses its exit code and its text falls back to whatever the model wrote *about* the call. Caught by a fixture asserting `Some(0)`, which is the only thing that can keep it honest; everything else on the wire (`toolCallId`, `rawInput`, `multiSelect`, `stopReason`) really is camel, so the mixture is the trap rather than either casing.

  **`tool_call.title` is the tool *name* on the opening line and a sentence on the next**, so the row is keyed on `_meta["x.ai/tool"].name` and never on `title`; ACP's `kind` lands on the first update too, which is why `tool_type` reads grok's own before it.

  **A delegated run is filed under the spawning call's id, and nothing on the wire joins the two.** `subagent_spawned` names the *child* (`subagent_id`, which is also `child_session_id` and the id its own updates arrive under) and carries no `toolCallId`, where `buildTranscript` correlates a run on the call that asked for it — so filing under grok's handle left the chat drawing a plain tool row and the panel a run with no spawn behind it. The join is made in the mapper off the **brief**, which is the one field on both lines (`rawInput.description` and `subagent_spawned.description`), with arrival order as the fallback and the child's own id below that, since a run filed under a handle nothing correlates still lists where dropping it would lose the delegation. **`agent_id` is the child's `subagent_id`**, which is what `_x.ai/subagent/cancel {subagentId}` takes (1.0.70), so the panel's Stop ends that child alone: its spawning call fails "Subagent was cancelled" and the parent's turn carries on. `Session::stop_task` sends `_x.ai/task/kill` first and the cancel only where kill answered `not_found`, since one handle names both kinds of run and nothing on it says which; both answer `not_found` outright rather than failing. **The report is still not drawn**, the same call fx's makes: the parent says what it made of the child's findings in its very next message ("The explore subagent reported: **alpha.txt, beta.md**"), so `SubagentCompleted.summary` would be that answer a second time. It costs grok more than it costs fx — the child's stream is dropped on its session id, so the panel body is genuinely empty — and it is still the right way round.

  **Stance is a respawn where model and effort are not**, because `session/set_mode` is **inert** — it answers `{}` for every mode id, grok's own and invented alike — and `_meta.permissionMode` (Claude's enum) is swallowed. So the stance rides `_meta` as `autoMode` or `yoloMode`, `session/new` answers `modes: null`, and the index entry is the only record of it, the bargain `ApprovalPolicy` already makes for Claude Code's `default`. **It rides `session/resume` as well, and that is what makes moving one mean anything** — a respawn *is* a resume, so a stance sent on creation alone never reaches the child the reader just replaced, and they would move a session to auto and go on being asked for every write. Both directions measured rather than assumed: a session created without `autoMode` and resumed with it stopped raising the card, and one created *with* it and resumed under an empty `_meta` started raising it again. So **an omitted key reads as manual, not as "keep what you have"** — the opposite of Codex's service tier — which is why `stance_meta` answering `None` needs no `false` spelled out beside it. **`auto` raises no card at all and the stance row has to say so**: the classifier answers the *model*, not the client, so a blocked call is a failed tool carrying its reason and nothing reaches stdio — and it blocks an in-cwd `rm -rf` while letting an outside-cwd one, a `git push` and a `curl` POST straight through. There is no injectable allow rule on the ACP surface either, so `dray` itself raises a card under `manual` unless a rule sits in the repo or the user config.

  **Plan mode is the model's, not the composer's.** Nothing but a typed `/plan` enters it, so Plan stays off the stance picker and `HONOURED.grok` names the other three; `exit_plan_mode` arrives as `_x.ai/exit_plan_mode` and **only `{"outcome":"approved"}` approves** — seven other spellings and an outright error all read as revise — so the card is two buttons and abandoning is the reader's next prompt. A write asked for inside plan mode is held until approval and then made.

  **The plan itself rides the *request* and nowhere else, which is why it is drawn in a panel tab and held in memory.** `_x.ai/exit_plan_mode` carries `plan_content` where the `exit_plan_mode` tool call beside it carries `{}`, so the ask is the only copy — and a permission request is never persisted, so a restart honestly opens with no plan. **It rides `PermissionRequested.input` as `{"plan": …}` and deliberately not the held `PendingRequest`**, which looks like the natural home and is unreachable: that struct is only ever read to rebuild an *answer*, and a plan's answer is a fixed outcome that rebuilds nothing. The frontend reads the event, so putting it there alone cost the Plan tab, the View plan button and the markdown rendering all three, silently — caught in review on #253. [plan.ts](../src/lib/plan.ts) is the per-session store `Chat` copies it into, and the card draws **View plan** in place of its usual `<pre>`: a plan's identifying argument is pages of markdown, which is the one shape that slot cannot draw. **It is the one card whose description is rendered as markdown**, since a plan's description *is* the plan — headings, lists, fenced code — where every other card's is one sentence, and drawn as a `<p>` it arrived as one run-on paragraph with the `#` and `-` still in it. `onViewPlan`'s presence is what decides that, one question rather than two: a card carrying a plan is exactly the card whose description was written as one. It also takes `--shadow-card`, the user bubble's own token — the border alone drew the box and said nothing about height, which on the one question in the transcript that blocks the agent is the wrong way round. Keyed on the tool name (`exit_plan_mode`/`ExitPlanMode`) rather than on the input carrying a `plan` field, so a later tool taking an argument by that name is not adopted. The store outlives the card deliberately — approving a plan is the moment the reader most wants to go on reading it.

  **A task list is drawn as a checklist, outside the expander** ([TodoList](../src/components/chat/TodoList.tsx), read by [todos.ts](../src/lib/todos.ts)). It is the one tool body that is a progress report rather than an argument, so it says nothing from behind a caret. Claude Code's `TodoWrite` and grok's `todo_write` send the same array under the same key, so one reader serves both; an unrecognised `status` reads as pending, the safe direction, since drawing a row wrongly costs one line where dropping it hides work. `todos` and grok's `merge` go into the omitted-fields set and the result is suppressed, or the same list is on screen three times — as the checklist, as the arguments, and as the echo the tool answers with. Drawn at the transcript's own size and not the tool row's, since it is a list of sentences the reader tracks their work against rather than machine output read at a glance; the three states are one glyph filled three ways — outline, solid, ticked — and **nothing is struck through**, a rule across a sentence saying it was wrong rather than that it is done.

  **The live list is a section of the panel's catch-all tab, and the transcript is exactly where it stops being visible.** A turn collapses when it ends and consecutive `todo_write` calls group into one row, so the checklist vanished at the moment the work carried on. `currentTodos` reads the list **back out of the session's log** rather than tracking it as it arrives, the context ring's own bargain, so a reopened session shows what it showed live — **skipping any event carrying a `subagent`**, since a child runs its own context and keeps its own list, so folding its writes in lets a delegated run replace what the conversation is tracking and `startsNewList` then opens the pane on somebody else's work. The running item shimmers on the session being **mid-turn**, not on the list being the panel's: a finished list is kept, so a session that stopped mid-item would otherwise animate a claim about now over what is only history. **A finished list is kept**, not dropped — what the turn did is worth as much on screen as what is left of it. The section carries **no caret**: one the reader opened the tab to read is not one to make them open again, and the panel opening itself on a new list would otherwise answer with a heading. **Both sections are titled or neither is** — a heading over one list and none over the other reads as the second belonging to the first — and the in-progress item takes `shimmer-text`, the same mark a pending tool row wears. **Subagents is drawn only where there are runs**, not as an empty state: this tab is a catch-all whose sections come and go, and a heading over the words "no subagents" is two lines spent saying the reader has nothing to read.

  **`merge` is grok's, and reading it as an ordinary write lost the whole list.** A merge update names `id` and `status` and **no text at all**, so taken as a list in its own right it is rows with nothing to say — which is how a session that had ticked every box ended up drawing its raw JSON where the checklist had been. Two rules follow. The walk runs **forwards**, since a merge only means anything against the list it updates, where a backwards walk stopping at the newest call reads the last tick as the whole list. And **"is this a todo call" and "does this call draw a checklist" are two questions**, `isTodoCall` against `todoList`: the row drops its arguments on the first, or a merge expands onto the bare ids it carries. Matched on `id` alone, the only thing such an update has; an id the list has not met is appended where it brings words of its own and dropped where it does not.

  **The panel opens itself on a list the reader has not been shown, and on nothing else** ([MorePanel](../src/components/MorePanel.tsx), rule in `startsNewList`). Two borrowed rules make that safe. **Signal is transition, not state**, `readyTransitions`' own: the first reading of a session is recorded silently, so arriving at a session that already holds a list does not drag the pane over the transcript the reader came to read — and the seed waits on the *transcript*, not the id, since an empty event list reads as no list and would make the real one look like news. And the transition must be a **different list** rather than any change at all, or `todo_write` firing on every status tick would yank the pane several times a turn. The test is **no shared item text**: a tick keeps every line, adding a step keeps most, and replacing the work replaces all of them — cleaner than a threshold, and it needs nothing remembered beyond the previous list. A composer strip was built first and removed: it made the pane's discoverability problem disappear by never having it, at the price of the same list drawn in two places.

  **The three marks are drawn here rather than taken from lucide, because lucide cannot make them the same size.** Its circles are `r=10` in a 24 viewBox and the visible disc is the circle *plus its stroke*: `CircleCheck` strokes in the page colour to keep the tick legible, cutting the disc to `r=9`, where a plain `Circle` stroked in its own colour reads `r=11` — two discs 22% apart under one `size-4`. One viewBox of our own, `r=8` of 16, no stroke on the disc. **In progress is a half-filled disc in the page's ink, never the accent yellow**, which is what the sidebar spends on a session *wanting* the reader — an item merely being worked on wore the colour of a problem.

  **Both plan-mode tools have their result suppressed.** grok answers each with `Plan file: <path>` — the copy it wrote into its own session store, percent-encoded, in a directory the reader has no business in — so `enter_plan_mode` drew a caret over a path and nothing else. The plan is on the card and in the Plan tab; this is bookkeeping. The pair reads as the *state* rather than as a call, hence "Entering plan mode" / "Entered plan mode".

  **A namespaced tool id is drawn as two coloured halves.** `<server>__<method>` with no `mcp__` in front of it is what grok's `use_tool` carries as its `tool_name`, so `mcpCall` reads the bare form too and `namedParts` title-cases both halves for the row — the server dimmer than the method, since the server is *where* the tool lives and the method is what was done. The split is **strict**: the whole string must be two identifier runs joined by `__`, or a path or a command holding a double underscore gets half of it coloured as a server that does not exist.

  **Dray's rules ride `session/new._meta.rules`, which is the one thing easier here than on fx**: they persist onto grok's own session record, so a resume in a fresh process still carries them and there is no prompt to append to and nothing to strip on the way out. grok titles its own sessions on the wire too — `session_info_update` mid-turn, measured at 0.22–0.24s from the last token to the prompt's reply — so [title.rs](../src-tauri/src/title.rs) refuses grok outright rather than spending a second child on an answer already in hand. That is the whole of fx's six-second stall not happening again.

  **The ring reads `_meta.totalTokens` off the prompt reply, and the two figures beside it are traps.** `inputTokens`/`outputTokens` are per turn and the nested `_meta.usage` is session-cumulative — Claude's `result.usage` problem restated. A `/compact` turn answers `totalTokens: 0`, so the mapper drops a zero rather than publishing it and `auto_compact_completed` sets the occupancy to what compaction *left*.

  **A backgrounded task needs no pid tracking, and that corrects the plan.** It does outlive `session/cancel` and the agent process, and grok does hand its `pid` over where Claude Code never does — but measured under Dray it is an ordinary *descendant* of the child, so settle's existing `kill_tree` (SIGKILL every descendant, then the parent) already reaps it. Stop is the other half: it kills the foreground tool and leaves it **with no terminal update at all**, so the transcript's own `ABANDONED` stand-in settles that row, one rule for every harness. A sibling already running still lands its result, so "a cancelled turn answers nothing" is the wrong reading.

  **A backgrounded task is drawn as a run, and publishing the list alone was not enough.** `BackgroundTasksChanged` is what `BackgroundTasksIndicator` counts, and its click opens the **subagent panel** — which draws runs and knows nothing of that payload, so a grok session backgrounding a shell lit a count that opened an empty pane. Claude Code's backgrounded shells are rows there already (DRA-264's "Wait for…" list), so the mapper mints `SubagentStarted`/`SubagentCompleted` around each task rather than the panel growing a second kind of row. grok republishes the **whole set** on every change, and **a task stops being live when its `status` stops being `running`** — 1.0.70 keeps a finished task in the set marked `completed` or `failed` where 1.0.40 dropped it, so reading absence alone left every run open for good. `agent_id` is the `task_id`, which `_x.ai/task/kill {sessionId, taskId}` takes and which `BackgroundTasksChanged` lists, so the transcript keeps the run open while it lives. **A kill wakes the model** for a short turn of grok's own (`task-completed-…`), closed off `turn_completed` like an idle interject's. Hand-written test, since no capture backgrounds anything.

  **A failed open kills the whole tree, not the child.** `initialize` has already returned by the time `session/new` or `session/resume` can fail, and grok starts every MCP server the reader has configured off its own config — six on the machine this was measured on — so killing the parent alone reparents them to launchd, and an expired login repeats that leak on every send. No `Session` exists yet, so `Session::kill_tree` cannot serve; both now go through `local_servers::kill_descendants`, which is the walk stated once. The other three harnesses take `child.kill()` alone on this path and are a separate question — grok is the one measured starting a tree of its own.

  **Slash commands are the wire's and arrive too late to probe for.** `initialize._meta.availableCommands` carries grok's seven TUI built-ins, every one of them withheld; the real 64 arrive on `available_commands_update` *after* `session/new`, which persists a session. So [commands.rs](../src-tauri/src/harness/grok/commands.rs) caches per cwd from the read loop and answers `Err` until one has landed — which the picker reads as a probe that has not returned, so the menu stays shut rather than claiming grok has no commands. **Every ACP session grok opens is persisted under `~/.grok/sessions`, prompted or not**, which is exactly why a probe is not an option; an `initialize`-only spawn writes nothing and answers in 0.23s, so the model list is free.

  **The model list is `initialize._meta.modelState` with a four-row table behind it**, and the context window comes off the session's own reply rather than a constant per model — 256k on every model since 1.0.70. Each row also lists `contextWindows: [256000, 500000]`, but no config option reaches the larger, so a session always runs on the first. The effort ladder is closed at four — `low medium high xhigh`, case-sensitive — and is per model: 4.5 stops at `high`, and `minimal` and `ultra` both answer `unknown reasoning_effort value` without naming the legal set.

  **Fast mode is the twin id, and that is the whole mechanism.** grok publishes no fast flag and no settings key: `grok-4.7-build-fast` is a row in the same list as `grok-4.7`, so asking for fast speed *is* asking for another model — which grok takes on a running child, hence `FastMode::InPlace` and one setter rather than two (`grok::set_model` takes the switch, and `Session::set_fast` comes back through it). **The Vercel gateway's `-fast` ids are the same bargain and this follows it**: the twin is kept **out of the picker**, since the same model twice — once as a row, once as a mode — gives fast speed with an inert toggle beside it, and here it also spent one of Shift+Tab's two slots on a flip between a model and its own fast tier. `supports_fast` is a lookup *in* the set, so it is mapped over the whole list rather than per row; only 4.7 has a twin on this wire, so 4.6 and 4.5 draw no switch at all rather than one that would change nothing, and **a twin itself takes none because it *is* the fast tier** — its own arm, not the lookup happening to miss for want of a `…-build-fast-build-fast`. **Hidden is never unrunnable**: `list` filters and `find` reads the unfiltered `all`, or a session recorded on the twin would resolve to nothing, spawn with no `--model` at all and record its own model as unset. The suffix is `-build-fast` rather than `-fast`, which is grok's spelling rather than a shorter rule that happens to work. It rides **every** spawn including the resume, since a respawn that dropped it would come back at standard speed with the switch still lit — and the index records the **base** id beside `fast: true`, because the pick and the switch are two settings and collapsing them would read as the picker having moved itself.

  **⌘⇧F toggles it, and it is the one chord two ids share.** `SHARED_CHORDS` in [shortcuts.ts](../src/lib/shortcuts.ts) is where that is written down and what the registry test reads — a list of pairs rather than a flag on one entry, so adding another is a deliberate act naming both sides. `issues.search` holds ⌘⇧F on the issues page and `composer.fast` everywhere else, and the two are never on screen together; `IssuesView` already *released* the chord when its page is shut rather than leaving a binding standing, since `useHotkey` calls `preventDefault` on every match and would otherwise eat the key from whatever is on screen. The binding is gated on `offersFast`, the same question the switch in the picker asks — a chord that toggled a setting no control shows, on a model that would ignore it, is a key that silently moves the index and nothing else.

  **MCP needs nothing from Dray, which is the reverse of fx.** `mcpServers: []` goes over and grok merges its own `~/.grok`, `.claude` and `.cursor` config and runs OAuth itself — the same machine state its TUI sees, which is the right way round and means a broken MCP server in the reader's *Claude* config costs grok's startup grace here too (5s for six servers, measured). **Folder trust is never asked for over stdio**: the request type exists in the binary and no run ever sent one, so the folder is silently untrusted and `GROK_FOLDER_TRUST=0` is the only lever — `=1` does nothing. `GROK_DISABLE_AUTOUPDATER=1` rides every spawn, since `--no-auto-update` is TUI-only. `PATH` is **merged rather than replaced**, but grok prepends `~/.grok/bin` and the login shell's copy, so an injected directory lands mid-list and cannot shadow what the login shell already resolves — `agent_path`'s append-not-prepend rule holds here by construction.

  **Image prompts follow the handshake**: `agentCapabilities.promptCapabilities.image` was `false` through 1.0.40 and is `true` from 1.0.70, so `read_models` reads it into `accepts_images` on every row and an older grok never has the tray offering what it would refuse. They ride as ACP image blocks beside the text, and grok reads them natively — measured, it named the colour and the words of a rendered PNG with no tool call. **Fork ships, by Claude Code's lazy route over grok's eager call** — see _Forking a session_, which carries the whole reading. Plan stays out for its own reason above.
