# Forking a session

**A fork is one conversation carried on twice.** A sidebar row's right-click submenu: **Fork in new worktree** and **Fork here**. Both copy the whole conversation — `--fork-session` takes a session and nothing narrower — so the two differ only in *where* the copy runs. Claude Code, pi, grok and Codex fork; fx refuses in its own words. **Codex's is `thread/fork`, on the fork's first spawn** — grok's lazy route — naming the parent's `thread_id`, and a parent with none is refused at the press. Measured on 0.164: the fork carries the whole conversation and the parent's own `developerInstructions` (those sent on the fork are not read), and works with the parent loaded in another app-server.

**Fork is lazy, and that is the whole shape.** The app's half (copy the log, write an index entry) is instant; the CLI's half only happens on **spawn**. So `SessionManager::fork` writes the app's half now and leaves `fork_from` on the index entry as an instruction; the **first send** spawns `--resume <parent> --fork-session --session-id <new>` and clears it. The copied log is what the fork replays meanwhile. **`fork_from` is an instruction, not lineage**: cleared **after** spawn, so a child failing to start leaves it standing, and **before** the prompt goes out, since from there the CLI owns the session under this id. `#[serde(default)]`, or every existing session forks on its next send.

**`--fork-session` honours `--session-id`** (v2.1.246), which is what lets the frontend mint a fork's id the way it mints a new session's. Also verified: the CLI writes a fork a **complete standalone transcript** holding the parent's history, and `-w` combines with all three.

**grok's fork is the eager one and still rides the first send, and that is the whole of why it needed no new path.** `_x.ai/session/fork {sourceSessionId, sourceCwd, newCwd, newSessionId}` makes the copy *inside the request*, so unlike Claude Code's spawn flag it needs a child to make it on — and the child the first send was going to spawn anyway is that child, arriving on exactly the send that wants it. So grok is `fork_needs_cli` beside Claude Code rather than pi, and `open_session` sends it between `initialize` and `session/resume`. Forking when the reader *asks* is the shape the plan proposed and it costs a second child and its whole MCP tree per fork, for a row that may never be sent to. **Measured: 0.07s, on a child with no session open at all** — it reads the parent off grok's own store rather than out of a live session, including a parent whose child is alive in another process and finished a turn a moment earlier (11 messages copied, that turn recalled), and the parent goes on working afterwards. That is also what makes the `turn_in_flight` guard the right width here and not a wider one: what the call reads is what the parent has *finished*.

**`session/resume` after it, never `session/load`, and the difference is the transcript.** `load` replays the copied conversation back as `session/update`s — `user_message_chunk`, `agent_thought_chunk`, `agent_message_chunk`, measured — where `resume` sends nothing but `available_commands_update`. Dray's own copied log is what the fork's transcript draws and grok's copy is what the model remembers, so the two halves are wanted and a `load` would draw the parent's turns a second time on top of the log. Which is why the log copy stays for grok rather than being left to the CLI, the same division Claude Code makes.

**`sourceCwd` is required and `newCwd` is what the two menu items differ by.** grok files a session under `<GROK_HOME>/sessions/<cwd-encoded>/<id>/`, so the directory is half the address — and pointing `newCwd` at the tree `send_msg` made is the whole of forking into a worktree, since the call carries **no worktree flag**: `worktree`, `useWorktree`, `sessionKind` and `sourceWorkspaceDir` are every one of them swallowed with no error. The tree is Dray's by the Codex/pi route, grok having no usable `-w`. Nothing in the reply tells a key it understood from one it swallowed, so `fork_params` is pinned by test — a wrong name fails as `-32602 missing field` at the fork, on a send the reader has already made.

**Where grok filed a conversation is asked of grok's own store, never inferred from the index** (`stored_cwd`). The address is `<GROK_HOME>/sessions/<cwd-encoded>/<id>/`, so the directory holding `<id>` *is* the answer, and reading it back needs only percent-**decoding** — the unambiguous direction, where the encoder's character set is grok's to change. It is asked twice: at the press, so a conversation grok has genuinely lost is refused before the log is copied and a row appears holding work it can never carry on; and at the send, for the address itself, so a **settled session still forks** — its tree is gone but its conversation is not.

Two inferences were tried and both were wrong in a way the store simply is not. Reconstructing the old path from `branch` is a *guess*: that field is kept for the PR tab, so a branch renamed by hand makes it a **wrong** address rather than an absent one, and a wrong one fails exactly like a right one until the send. Refusing on `worktree_removed` **over-refuses**, since `mark_relocated` sets that flag from a shape whose own doc names the false positive — an ordinary project-root session on a `worktree-` branch, which never moved and which grok can still find.

**A store this build cannot read is not a refusal.** `Err` means no store or a layout that moved, and refusing on it would take Fork off every grok session at once the day grok rearranges its files, where letting it through costs at worst the late failure the press-time check is there to avoid. grok's alone throughout — Claude Code scans `~/.claude/projects` for `<id>.jsonl` and pi's handle is a file copied by id, so neither is addressed by directory.

**A lazy fork copies what the parent holds *then*, not what it held when the reader asked**, and Claude Code's has the same window. The app's half is taken at the press and the CLI's at the first send, so a parent prompted again in between is forked with that turn in it while the fork's transcript, copied earlier, does not show it. Named rather than fixed: closing it means forking eagerly, which is the child-per-fork this shape exists to avoid.

**Refused while the parent's *turn* is in flight, and nothing wider.** The CLI forks by *reading* the parent's transcript, which a live child is appending to mid-turn. An outstanding background task is not that case — it appends *after* a turn ended. The backend checks `turn_in_flight()` and the submenu disables on `in_progress`, the **same question** by construction, pinned by test. The guard was `has_outstanding_work()`, the safe-to-replace-the-child question — and since a `local_bash` task never ends, a session running a dev server could not be forked again for the rest of its life while the menu item stayed enabled. **Also refused where the parent has no conversation**, since an index entry is written before spawn.

**Fork in a new worktree is a resume whose tree doesn't exist yet**, so it needs creation's treatment inside `send_msg`: `-w`, the project root as spawn dir, `base_ref_tree` as baseline. The name is resolved against the **project**, not the parent's own. The item names the cost out loud: `claude -w` forks the *tree* from `origin/<default>`, so the copy can carry a whole conversation onto code that doesn't hold the work it was about. **A harness that makes no tree of its own takes the other arm of the same branch** — pi and grok — where `send_msg` runs `create_worktree` before the spawn and the baseline is an ordinary snapshot of a tree that is already on disk, which is the more exact of the two.

**Names are resolved against the index and every `worktree-*` branch, not disk alone.** A lazy fork's tree doesn't exist until its first send, so its name lives **only in the index** until then — anything else drawing a name takes one a pending fork holds, and that fork's `-w` then fails **permanently**, since the name is on its index entry and every retry redraws it. And a settled session frees its name everywhere but `origin`, where the branch its PR landed from stays — the PR tab and sidebar marks look a session up by that branch, so a redrawn name opened onto somebody else's merged PR. `worktree_branch_names` folds local and remote-tracking branches in with one `for-each-ref`; no fetch, since a push from a linked worktree writes the tracking ref in this same repo. `resolve_unclaimed_worktree_name` reads all three, and **both** call sites use it. The pool is 32³ and every landed PR retires a name for good.

**The copied log is repointed, twice, and both are about outliving the parent.** Every event carries `session_id` and the frontend routes live events by it, so a log left alone claims to be the parent's and then grows new events under its own id. And `ImageRef.path` names a file under `~/.dray/attachments/<session-id>/`, so a verbatim copy draws pictures out of the parent's directory and goes blank the moment the parent is deleted; the attachment directory is copied beside the log and the paths rewritten. Event `id`s are deliberately **not** re-minted. `repoint_events` is split out from the copy so the rule is testable with no `~/.dray` to write into.

**`parent_session_id` inherits, because a fork is a copy and a copy sits where the original sits.** The sidebar draws a fork **beside** its source under the same parent, and the depth cap counts it at the same depth. Resetting to `None` looks tidier and is a hole — a copy surfacing top-level is free to spawn where the session it copied could not. Pinned by test.

**`restoreSessionControls` takes an *item*, not an id.** A fork opens selected, but it can't go through `handleSelectSessionIndexItem`, which reads `sessionIndexItems` and won't hold the new row until the next render — without the split the fork opens under whatever model the composer last left on.
