# Deleting a worktree

**Nobody else cleans these up.** Sweep never removes worktrees created with `--worktree`, and `-p` runs have no exit prompt — and `-p` is exactly how Dray spawns.

**Unlocking is a required step, not a defensive one.** A `-p` run leaves its creation lock in place (v2.1.239: the tree still carries `locked claude session <name> (pid N start <date>)` and `git worktree remove --force` refuses it, exit 128). [remove_worktree](../src-tauri/src/git.rs) unlocks first, and that string is what the pid check parses. Reading the reason rather than unlocking blind is the point: a **live pid** means another session is working in that directory now, and it is the only thing that refuses this. `kill(pid, 0)` answers it, `EPERM` counting as alive. **Canonicalize both sides of the lock lookup** — git prints real paths, so `/var/…` comes back `/private/var/…` and a plain `==` finds no record, which reads as "not locked".

Order is load-bearing at both ends: unlock before remove because the lock refuses it, `branch -D` after remove because git refuses a branch some worktree has checked out. The path guard sits ahead of all of it and keys on **shape, not index** — a direct child of `<project>/.claude/worktrees/` or nothing, so an empty worktree name resolving to the project root can never reach a delete.

**Sessions survive.** Removal rewrites the index entry — `cwd` and `project_path` both to the project root, `worktree_name` cleared — and `cwd` is the load-bearing half, since `send_msg` reads it off the index. **The project root, not `project_path` as recorded**: an older `dray new` filed sessions under the *caller's* own worktree, so a flat `cwd = project_path` landed the session in a checkout another live session was working in — and the startup backfill could never heal that, since the result exists. `project_root_of` is the one statement of that rule and both paths take it. The CLI meets us there: it resumes in the directory Claude was launched from, and `--resume <id>` falls back to scanning `~/.claude/projects` for `<id>.jsonl`.

**`branch` stays and `worktree_removed` goes on, and that is what keeps the PR tab alive.** The field holds `worktree-<name>`, the branch the work landed on. Clearing it took the tab off every worktree session the moment the reader settled it; keeping it and nothing else still lost the tab, since `sessionBranch` prefers observed HEAD. So the flag decides which wins. `#[serde(default)]`, so an entry predating it reads as tree-still-there. Trees settled before the flag existed need `backfill_removed_worktrees`, one startup pass recognising relocation by its shape — **and the same pass repairs a `cwd` that is simply gone**, which the shape rule cannot see: a tree removed by anything but Dray's own delete leaves the entry pointing inside it, and every `git` and `gh` spawned there fails with ENOENT before the binary is reached. That is why the PR panel said "could not run gh" on a session whose sidebar mark, read in the project root, was fine. `surviving_root` moves both `cwd` and `project_path` to the first root on disk, and **a managed worktree is never that root even where it is the recorded project and still there** — `dray new` used to file a session under the *caller's* own worktree, and that caller is usually a live session, so believing `project_path` would put two sessions in one checkout. So the `/.claude/worktrees/` prefix of `project_path` is tried first, the recorded project only where it names no worktree, then the prefix of `cwd`. **`<name>` has to be a *direct* child there**, the same reading `is_managed_worktree` takes before deleting one — without it an ordinary repo sitting anywhere below such a segment reads as a worktree and its sessions get moved to an ancestor that is not their repo. **No surviving root means no rewrite**, since a project on an unmounted drive reads exactly like a deleted one. The backfill runs at launch, so `gh()` refuses a missing `cwd` in its own words before the spawn — a tree removed while the app is up has no pass coming until the next one.

**"Unpushed" means no other ref holds it, not "no remote holds it"** — `rev-list HEAD --not --remotes` reports a whole history at risk in a repo with no remote. Now `--not --exclude=<branch> --branches --remotes --tags`. Two spelling traps, both failing silently to zero: `--exclude` applies to the **next** ref-enumerating option only, and its glob is relative to `refs/heads`. A squash-merged PR still counts. Over-warning is the safe direction.

**Already-gone trees ask nothing** — disposition is read *before* deciding whether to ask. **Delete takes the tree with it, no second question**, folded into `SessionManager::delete` best-effort; a failed removal there orphans the tree, and `git worktree remove` by hand is the recovery.

**Settle and delete both stop the session, and the stop is the whole process tree** (`SessionManager::settle`): the child, everything it started, and its browser tabs. `child.kill()` alone signals the agent's pid, so a `run_in_background` Bash or a dev server survived a delete under launchd. The descendants are read with `local_servers::descendants` and signalled **before** the child dies, straight off the walk: a dead parent's children are reparented and the walk loses them, and a pid held across the parent's shutdown could be another process's by the time it is signalled. Tabs close whatever the kill answered. A respawn keeps `kill` alone: the dev server should survive an effort change. Settle is refused mid-turn by the sidebar for this reason. The log and index entry stay, and unsettle resumes as any idle session does.
