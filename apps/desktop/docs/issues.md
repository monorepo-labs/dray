# Issues

**The surface says "issue" and two trackers sit under it.** Vocabulary in [issues/issues.rs](../src-tauri/src/issues/issues.rs), wire in [linear.rs](../src-tauri/src/issues/linear.rs) and [github.rs](../src-tauri/src/issues/github.rs) — a tracker really was a module plus a variant on `IssueTracker`, which is why `IssueRef` has always carried one. The connection is workspace-wide — no project ↔ team mapping. **Every user-facing string is collected in [COPY-ISSUES.md](../COPY-ISSUES.md)**; reword there and here together.

**GitHub's credential is `gh`'s and Dray stores none**, so "connected" is `gh` resolving and `gh api user` answering, cached behind the same `RwLock` bargain `binpath::gh` makes and thrown away by `recheck_gh`. **Identifiers are `owner/repo#123`, always** — GitHub's own cross-repo spelling, and **a bare `#123` is refused on purpose**: a number alone means nothing without a repository and prose is full of them, so linking one would file a session under whichever repo was nearest, a wrong link that reads exactly like a right one. That shape is also what *routes*: `IssueTracker::of` reads the `#`, stated twice (Rust `parse_identifier`, [issue.ts](../src/lib/issue.ts)'s `parseIdentifier`) and tested twice, like the Linear rule beside it. Case is kept where Linear's is uppercased, since GitHub is case-insensitive on a slug and uppercasing one would leave the reader's own sentence disagreeing with the repository they typed. **The switch is drawn whether or not both are connected, and the issues page honours the pick outright.** It is the only surface in the app that says a second tracker exists, so gating it on having both put the pitch for one on a screen you reach only by having *neither*. A press landing on a disconnected half draws that tracker's own connect pane — Linear's key form, or GitHub's `gh auth login` with `brew install gh` under it — which is where the press was going anyway. **That pane carries a Check again button and has to**: `binpath::gh` caches an absent CLI and `issues::github` caches a logged-out one, both for the life of the process, so a sign-in that worked left the pane exactly as it was until the app was relaunched. `recheckGithub` throws both away and re-reads the integrations; it claims nothing about *which* half it fixed, the two being one state (`NotConnected`) on this surface. An earlier draft said "refresh this page" with no such control on it, which is the shape of the bug rather than a wording slip. That is why `effectiveTracker` is no longer read there: a switch whose press is silently undone is worse than no switch. The composer's `#` menu still asks `canSwitchTracker`, since inside a sentence being typed there is nowhere to put a connect pane and the chip could only produce a list that will not load. **Each pane asks for one tracker and offers the other only while it is missing too**, a line pitching something the reader already has being unreadable as anything but a bug. **Both trackers can be connected and a pick chooses one, never a merged list** — one workspace's priorities do not order another's issues — held in `ade.issueTracker` ([issueTracker.ts](../src/lib/issueTracker.ts)) and drawn as chips on the issues page *and* on the `#` menu's header, either moving both. **The settled read is Linear's alone.** `wantSettled` is sticky for the life of the page, so a reader who had once opened a Done group went on paying a second `gh` spawn behind every GitHub query — for a list GitHub never draws, its finished work being the state switch's other half. That budget is per *user* and every agent in every session spends it too. **`IssueQuery.team_id` is the repository slug under GitHub**, which is the one field name that lies about itself: the page reads one repo at a time from `ade.issueRepo` (no "all", since a number is only addressable within one) and the composer's picker reads the session's own, resolved through `github_repo(cwd)`. **Writes are status alone** — `open`/`completed` onto two `gh issue` subcommands — and priority is refused in Rust *and* undrawn in both surfaces, GitHub having no such field. **`NOT_PLANNED` is deliberately not a third state**: GitHub files it as a *reason* on the one closed state, so drawing it as one bought a permanent empty heading on the page plus a menu row for a distinction nothing else here reads. **A GitHub list is drawn flat under a two-way switch and takes no headings at all** — two states against the six `groupIssues` names, so a heading was the switch's own answer repeated over the rows it had already picked; `groupIssues` is therefore Linear's alone, and `query.settled` is what the switch moves. The switch is [Segmented](../src/components/Segmented.tsx), shared with the tracker chips: a `--surface-well` track with one thumb that *slides*, where `DiffPane`'s fills whichever segment is pressed — at this size a fill is two labels blinking, and a thumb that travels is what says the pair is one control with a position. **Labels are the GitHub half's one narrowing**, per repository, so `list_issue_filters` takes the repo and is re-read when the pick moves; they are drawn through `IssueLabelChip`, which puts every one through `readableStateColor` — a repository picks its label colours against GitHub's white background and half of them vanish on Dray's light palette. The plan and what was left out are in [GITHUB-ISSUES-PLAN.md](../GITHUB-ISSUES-PLAN.md).

## Credentials

**The key lives in `~/.dray/credentials.json` at `0600`, the account cache in `settings.json`.** Read together: credentials say whether a key exists, settings say whose it is, and a cached account with no key behind it reads as **disconnected** — the key *is* the connection.

- **Own file, not a field on `settings.json`**, for two reasons that both bite: settings are rewritten whole and read on a launch path where a parse failure falls back to defaults, which would silently *forget* the key; and a struct the frontend may be handed is no place for a credential.
- **Mode rides the *create*, on the temp file** — not set after the write, not on the final file after the rename. `fs::write` creates at the process umask, so every other order leaves a window where the key is world-readable, where `OpenOptions::mode` plus `create_new` leaves none. Pinned by test; the failure is otherwise silent.
- Keychain was tried and retreated from — macOS ties the grant to the exact binary, so every rebuild is a new authorization dialog. Cost: the key is readable by anything running as the user, in a directory that is `0700` and already holds every transcript.
- **Validated before saved**, and `verify` also answers identity. **A write to either side forgets every cached issue** (`forgetIssues()`), since every cached answer was read with the old key — the `not_connected` failure the empty state is drawn from included.

## Tags and links

**A tag carries the title itself** — `#DRA-53 Add issue tracker integration`, everywhere: picked from the composer's `#` menu, typed by hand, or appended by the CLI's `--issue` (`tag_text` in Rust, `issueTag` in [issue.ts](../src/lib/issue.ts), pinned both sides). The title being *in the text* is what makes the feature cheap, and it is what the composer's issue chip draws on its face. Descriptions are not injected: the agent has the tracker's own MCP server and can fetch what it wants, where a pasted description is stale the moment somebody edits the issue.

- **Resolution is best effort, always.** Unreachable Linear, a revoked key, an identifier that doesn't exist — all leave the tag as text, record no link, say nothing. A send must never fail because the tracker is down.
- **Best effort stops short of losing a named issue.** A tag the reader typed is already in the prompt; one arriving through `--issue` is not, and dropping it left the model with no mention of the work at all while **answering identically to success**. So a named issue that resolves to nothing is appended bare (`#DRA-53`) and linked bare.
- **A tag clicked in a prompt opens the issues page**, through a module slot ([`setIssueOpener`](../src/lib/issue.ts)) the way a transcript link reaches the browser. ⌘-click leaves for the tracker instead — the same thing the modifier means on an issue row and on a file link. `App` holds the picked issue as an `IssueRef` rather than a full `Issue` for this: a tag carries one of those and nothing more.
- **A tag in prose is a mention, and a mention links nothing.** `ExpandedTags` answers two lists: `mentioned` (rides `user_message`, so the tag draws as a button) and `linked` (written onto the session). Only a caller naming an issue outright — `dray new --issue`, `dray issue link` — puts anything in the second. Every `#DRA-53` used to link, so "this is unrelated to #DRA-53" filed the session under DRA-53 forever.
- **One tagging rule per side of the bridge.** Everything the app sends tags in prompt *text*, so `send_msg` always passes an empty issue list; the CLI's `--issue` names them outright. Both merge inside `expand_tags`.
- **Send answers with links as written, every path** — created, live, queued, resumed — as a whole list, not a delta, since re-tagging *replaces* an entry. Without it the Issue tab draws old links until reselect or restart.
- **A link made over the socket answers back on `issues_changed`**, the same inversion `session_created` and `session_title` are. `dray issue link` reaches Rust without the frontend asking, so with the send's answer as the only other channel a link sat invisible until the next prompt went out (#256). Whole list again, `link` and `unlink` alike, and the tab hides itself once the last one goes.
- **Tag shape is stated twice and tested twice.** Rust `issue_tags`/`parse_identifier` decide what gets *linked*; [issue.ts](../src/lib/issue.ts)'s `parseIdentifier`/`highlightSegments` decide what gets *painted*, and neither can call the other. Rule: team key plus number, `#` must open a word, bracketing punctuation counts as opening it. `#fff` and markdown headings stay prose, both directions pinned.
- **A link is a copy, not a pointer.** `IssueRef` holds identifier, title, url and tracker id, so the sidebar and prompt need no network call. It goes stale, which is the right way round; re-tagging **replaces** the entry rather than appending.
- **Link and unlink match on tracker id *or* identifier, within a tracker** — a resolved link carries Linear's UUID, a blind one carries the identifier itself. **Detail is read by UUID first, identifier as fallback**, since identifiers are not stable across a team move; not the other way round, because the identifier is the *only* thing a blind link carries (`is_stable_id`).
- **A fork inherits links; a relayed message carries none.**

**`dray issue link` writes down what it is given and asks the tracker nothing.** A link is a local record, so needing reachable Linear and a stored key meant it could fail for reasons unrelated to what it records — and the caller is an agent that just read the issue through the tracker's MCP, so it already holds the title and url. Hence `IssueInput { identifier, title?, url? }` and `--title`/`--url`. Absent metadata is ordinary. **Several identifiers plus `--title`/`--url` is a refusal**, since one title applied to all is a wrong link that reads exactly like a right one.

**The session id is optional, and `$DRAY_SESSION_ID` is why.** Claude Code's Bash guard refuses any command naming an env var inside a worktree-isolated session, **silently** — the agent reads the refusal, carries on, and the issue is never linked. So the CLI resolves the session itself off `parent_session_id()` and the documented call carries no `$` at all. Shape tells a session from an issue (uuid vs letter-leading team key), so positionals are **one `Vec`** split in one function — clap refuses a non-required positional above a required one. The old `<session> <ISSUE>...` form still parses and must, since it shipped.

## Reading Linear

**The panel reads Linear's API with the stored key. MCP is nowhere near it.** Two channels answering two questions: the key fills *this app's* screens, MCP lets the *agent* read the same issue in its own turn. That is why the connect form says MCP out loud, once. A live `claude mcp list` check existed in the panel and was removed — readers open that panel to read the issue, not audit their tooling.

**Caching** ([issue.ts](../src/lib/issue.ts)). Lists are cached module-level on the whole query, capped at 12, 60s freshness; opened issues separately by identifier, capped at 24. A failed read changes nothing. One **generation counter** over every issue cache, bumped whenever the answer to "who are we, what may we read" changes; a read that started under an older generation is refused rather than written, since the damaging half is not a stale row but a **stamp** that suppresses the read which would correct it. `useSyncExternalStore`d, so a hook holding an answer read under an old key re-reads. Refresh **forgets then bumps** — bumping alone must never gate the cache, or every later visit refetches for the rest of the session. Cached answers are picked **during render**, not in an effect, or one frame of the previous issue's description sits under the new issue's title. A cache short-circuit must clear `loading` itself, since a cancelled read never reaches its own `finally`.

**The composer's `#` picker reads that same cache, and the sharing is what makes it quick.** It asks the question the issues page opens with — `assigned`, unsettled — so a second `#` inside the freshness window opens with no round trip at all. Two rules hold it together. **It reads to `ISSUE_LIST_LIMIT`, not to the 25 rows it draws**, since the key is the *query* and carries no depth: a shallower read would file a truncated answer under the key the page paints from, so the cap is applied at the `slice` and nowhere else. And **a keystroke paints before it reads** — `filterIssues` narrows the cached assigned list locally so the menu moves on the frame the character lands in, with the server's answer replacing it when it arrives. That local match is deliberately weaker than Linear's, which reads descriptions too, so it is only ever allowed to under-match: a row it misses appears a moment late rather than going missing.

**A cold `#` draws placeholder rows rather than nothing**, since with no cache and no index there is a round trip between the keypress and the first row — the state the other two pickers never sit in. `PickerMenu` takes `loading` and reads it **only where it holds no rows**: a list already painted from cache is what the reader wants, not placeholders over it. The composer's key block follows the **rows** rather than the menu being drawn — `% rowCount` is a division by zero on an empty list, and Enter would otherwise be swallowed by a pick that can only land on nothing, so Enter sends while placeholders are up. The empty state's "Press ⏎ to send" legend still follows the **menu**, and deliberately: the legend would be true there, but a send hint under an open picker reads as belonging to the list.

## Uploads

Linear puts uploads *in* the description's markdown, pointing at `uploads.linear.app`, so there is no attachment list to build — override `img` and `a` on that one `Markdown` and leave every other link alone. They sit behind the same auth the API does, so the webview cannot fetch them: `<img src>` resolves to 401 and the browser draws its own broken box. `fetch_issue_asset` puts the key on that request and hands back a `data:` URL.

- **Host checked exactly, and scheme with it.** A description is text somebody else wrote and it names the URL this fetch is handed, so without the check an issue could name any host and have the app post the credential to it. Compared on **parsed host**, never a prefix — `uploads.linear.app.evil.test` passes `starts_with`. Wrong scheme is rejected, not upgraded. Stated twice (Rust `is_upload` decides where the key goes, [IssuePanel](../src/components/IssuePanel.tsx) what is drawn as an asset), pinned on the Rust side.
- **Size capped before the body is read, and the body streamed to that cap.** `content_length` is a courtesy — a server may send none or lie — and `.bytes()` drains the whole body first, so the chunk loop is what actually enforces the cap.

## The issues page

**A sidebar row under New task, a main-column view — not a session.** Opening it **keeps selection** but drops the sidebar *highlight*, since a lit row would name a session nowhere on screen. The page hides rather than unmounts, so filters and scroll survive the trip. The row is drawn whether or not a tracker is connected: the page's empty state is where connecting is offered, and disconnect lives in settings, whose row only draws when something is connected.

- **The right pane is hidden while the page is up, and the preference kept**: `panelShown = panelOpen && !issuesOpen`. Everything that draws or reads reads `panelShown`; `panelOpen` stays the standing preference.
- **`SessionHeader` takes `standIn`** and `App` passes `"Issues"`, or the header sits at "New session" over a list of issues.
- **Clicking a row opens it in the pane beside the list**, off the same key the list was read with, in the same `RightPanel` frame. The picked issue is held as a whole row, not an identifier, so the pane is complete before its own detail read lands. `useSessionIssues` serves both, since a page pick is a one-element link list.
- **Every route to a session goes through `goToSession`**, which closes the page then navigates. Two buttons closed the page and the chords beside them did not, which made ⌘N and ⌘⇧↑/↓ read as inert.
- **⌘E only ever closes there**, and the guard lives on the chord, not only in `handleTogglePanel` — ⌘E binds **raw** `togglePanel`, so a guard in that function alone lets the chord sail past into a pane not on screen. Same for the view chords.
- **Panel tab `issue`, hidden with no link.** Rows are drawn from the session's own `IssueRef`s, so the tab exists the moment something links one. **Linking is the agent's**, through `dray issue link`. The description is drawn here where the PR panel leaves the PR body out, and the difference is who wrote it.
- **No Start button** — it would create a session, so it must name a project, and the page is workspace-wide. Tagging with `#` in the composer already starts work against an issue from a place that knows the project.

**Both lists are ordered by when the issue was filed, newest first**, since
that is the date the row draws. `gh issue list` has no sort flag, so it rides a
`sort:created-desc` **search qualifier** — which moves the read onto the search
API while still honouring `--assignee`, `--label` and `--state` and still
carrying `closedByPullRequestsReferences` (measured); a reader's own `sort:` is
left alone rather than fought with. Linear takes `orderBy:createdAt`, and its
priority sort still outranks it *within* a state group, which is what the
headings are for.

**A row says whether anybody has started, and both trackers answer it
narrowly.** `Issue.pull_requests` is linked PR *numbers* and nothing else, since
that is what the chip says. GitHub's are `closedByPullRequestsReferences` — its
own sidebar's Development list, the PRs that would close the issue — not every
PR that mentions it. Linear's are the issue's attachments filtered by **URL** to
`github.com/<owner>/<repo>/pull/<n>`, never by `sourceType`: that is Linear's
own word for where an attachment came from, a different undocumented string per
integration, where the URL is GitHub's own shape and is what the GitHub half
already reads a number out of. Both sorted and deduplicated, or one attachment
added twice reorders the row between reads. The URL reading wants a **non-empty**
owner and repo — `github.com///pull/7` splits into the right number of segments
and is no pull request — and Linear's attachments are read `first:20` with no
paging, so a PR attached after twenty other things is missed; a chip is not worth
a cursor loop. The `sort:` guard beside it is a **whole-word** test for the same
family of reason: `contains` read `resort:x` as a qualifier and silently dropped
the created-order the list promises. The chip is **inert** — a single
number could open its PR and a count could not, and a chip that links on some
rows and not others is worse than one that never does.

**Dray writes exactly two fields, and only from the opened issue's header** — status and priority, through `update_issue` over Linear's `issueUpdate`. Nothing else: no comment, no attachment, no assignee, no label. **The `dray` CLI writes nothing at all**, and [SKILL.md](../../cli/skill/SKILL.md) says so out loud, because an agent assuming otherwise tells the user their issue moved when nothing of the sort happened.

The two menus live on `IssueRow`'s header in [IssuePanel](../src/components/IssuePanel.tsx), so the session's Issue tab and the Issues page get them from one component. **A status menu is drawn from `IssueDetail.states`, the issue's own *team* workflow, which rides the read the panel already makes** — a menu that has to fetch before it can open is a menu that opens empty. Sorted by kind and *then* `position`: Linear only makes position meaningful within one state type, so a single sort on it lists Done above Todo. No states means no menu, just the glyph.

**`None` means leave it and `Some(None)` means clear it**, which is why priority crosses as `Option<IssuePriority>` rather than a number — "no priority" is a level a reader can pick and it goes down the wire as `0`. **`issueUpdate` answers `success: false` at 200 with no `errors`** for a write it understood and refused, so that field is checked; without it the panel re-reads, finds nothing moved, and silently redraws what was already there. The mutation's own `issue` echo is deliberately unread — the panel draws a whole `IssueDetail`, and asking for that field set back would be a fourth copy of it in `linear.rs`.

**A write is the one moment every cached answer about issues stops being true**, so `update` calls `forgetIssues()` and then puts the freshly-read detail back — *after* the generation bump, or the guard that makes the clearing stick refuses it. `useIssueList` subscribes to that generation for the same reason: without it the row beside the panel keeps saying "Backlog" under a heading the issue has just left. Failure reports through the panel's existing banner; nothing is optimistic.

**⌘-click on an issue row opens it in the tracker**, on the panel's rows and the page's list alike — the same modifier a transcript link uses to mean "out there, not here". A shortcut, not the affordance: the row's own button is that.
