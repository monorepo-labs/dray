# Orchestration

**One agent can fan work out into several sessions**, each with its own worktree and sidebar row. Three commands: create, list, send.

**This is the first inbound channel into the app.** Every other command travels frontend → Rust; this one travels agent → Rust → frontend, so the frontend learns about a session from an *event* rather than a return value. That inversion is the whole of what [orchestration.rs](../src-tauri/src/orchestration.rs) adds. The work goes through `SessionManager::send_msg`, the same function the composer reaches, so a session created this way is not a second kind of session.

**Three shipped pieces, one line of glue.** The app serves a unix socket (on a Mac, its background server does — see _The Mac's background server_); `dray` is a standalone CLI in its own crate; a skill documents it; one line in [system_prompt.md](../src-tauri/src/harness/claude_code/system_prompt.md) names the capability plus install command. **The app installs nothing** — it informs, the agent does. It only *updates* a CLI already there; see below.

**Commands are `noun verb` — `session`, `server` (this machine), `machine` (the app's list), `draft`, `issue`, `share` — and every spelling that shipped before stays a hidden alias** (`new`, `ls`, `send`, `setup`, `serve`, `service`, `tunnel`, `share <port>`, `--from`, `--install`). Not courtesy: the app's SSH connect runs `dray service start` and `dray setup --install` on remote boxes, and a tunnel's systemd unit runs `dray tunnel`, against whatever CLI that box has — so the app keeps calling the old names, which every CLI answers. A bare group prints its help rather than acting (clig.dev).

**The CLI is deliberately not part of the app** — it has to run on Linux later, where no Dray app exists. Own crate, own `cli-v*` tag, `curl -fsSL https://www.drayhq.com/install.sh | sh`. It links neither the app nor tokio: one connect, one write, one read, exit. **Wire types live in a third crate**, `crates/dray-proto`, compiled into both sides so request shapes cannot drift — a drifted shape fails with no error and the command simply stops working. No root Cargo workspace, and this adds none: `src-tauri` has its own `.cargo/config.toml` carrying the ts-rs export path, and a workspace moves the target dir out from under it.

## Install and versioning

**`install.sh` resolves the newest `cli-v*` tag itself, and `dray update` re-runs it.** The Tauri updater swaps the `.app` bundle only, so **the app runs the installed CLI's own `dray update` on the first launch of each new app version** (`sync_cli` in [updater.rs](../src-tauri/src/updater.rs)) — an app that bumped `PROTOCOL_VERSION` otherwise leaves every agent's `dray` call refused until somebody updates by hand. `dray update` judges what is newer, so nothing compares versions; the version is recorded in `~/.dray/cli-synced` only once the run succeeded or found no CLI, so an offline launch retries — its own file, since `settings.json` is rewritten whole and a second instance writing a marker from a stale read would undo the reader's settings. A `dray` that doesn't answer `--version` as `dray …` is not run, and the update is killed as a tree after 5 minutes. Silent, and skipped under `tauri dev` and debug builds, since the CLI on disk belongs to the release app. `/releases/latest/download/` is unusable because app and CLI publish into the same repo, so that URL belongs to whichever released last. Instead ask the releases API (`?per_page=100`) and take the first `tag_name` starting `cli-v`; the API answers newest-first, and `sort -V` is not portable. `DRAY_VERSION` is a literal-tag override. **Failed resolution refuses, never falls back** — a rate-limited API quietly installing something ancient is the exact failure being removed. **The channel is the tag's shape, never GitHub's `prerelease` flag**: a `-` after the version (`cli-v0.12.0-beta.1`) is a beta, stable (`DRAY_CHANNEL` unset) skips those, and beta takes the newer of the newest of each — a beta sorting below its own release, so a stable hotfix cut after a newer beta never moves a beta install back. `dray update` reads its channel off its own version, so a beta binary stays on beta and no setting can drift from it; `--channel` moves it. **The app's sync hands over the app's own channel**, so the CLI follows the switch at the next app update and not before — started from `check_update`, since the channel lives in the frontend's local storage and `setup` cannot see it. `--channel` from CLI 0.12, `DRAY_CHANNEL` below that, where the flag is refused but the variable reaches the installer. **Leaving beta downgrades nothing**: `install.sh` stops unless the resolved tag is *newer* than `DRAY_CURRENT_VERSION`, so a beta CLI on the stable channel stays until a stable release passes it, the app's own updater's rule. That check lives in the installer alone. The flag on the release is a label for people and nothing reads it.

**The protocol version is checked before the request is even looked at**, and the refusal **names which half is behind** — `envelope.v < OLDEST_SPOKEN` means the CLI is behind, say `dray update`; `>` means the app is behind, say update the app. Naming the wrong half is worse than naming neither, since only one cure is runnable from an agent. **The envelope must still parse at a version the app no longer speaks** — the check is a layer *above* parse, or a v1 line answers "could not parse the request" where it should answer "run `dray update`". Both pinned by test.

**Bump rule: bump when the default the old side falls back to is undetectable.** An old app ignoring `model` runs on its own default, which the caller can see and judge; an old app ignoring `from` starts the worktree at `origin/<default>` and answers *identically to success*, so a session spawned to review unpushed work reviews none of it and reports everything fine. Wrong work that looks like right work is what earns a bump. Currently **v12**: v2 = `from`, v3 = `issues` and `LinkIssues`, v4 = `LinkIssues.identifiers` → `issues` (renamed, not extended, so two shapes cannot be confused), v5 = `Browser`, v6 = `fast` — an old app ignores it and runs at ordinary speed, which answers identically to success since nothing in the transcript says which tier served the turn, v7 = the `dray draft` requests, which an older app reads as a broken CLI rather than as an app to update, v8 = `dray share`, for the same reason, v9 = the server list (now `dray machine`), v10 = the session verbs, `share ls` across sessions, and `from` renamed `base` — a create or draft naming a base goes out as v10 and nothing else does, since an older app ignores `base` and starts at `origin/<default>`, v11 = `set_remote_access`, v12 = `on_machine`, since an app that ignored the machine would run the request on the Mac. **The app answers every version from `OLDEST_SPOKEN` up to its own, and the CLI stamps each request with the oldest version that carries it whole** (`Request::version`), so a bump breaks only the requests that need it — a v7 CLI runs everything but `dray draft` against a v6 app, and that one is refused naming the app. `OLDEST_SPOKEN` moves only for a rename, never for an addition.

## The socket

**Unix socket, not an HTTP port.** `~/.dray/dray.sock` — nothing on the network reaches it, no port to collide on. Stale sockets are unlinked at bind. **Dev builds listen on `dray-dev.sock`**, under `~/.dray-dev` since #456, which is what makes unlinking safe: one path for both builds means whichever starts last owns the channel, silently, since neither app reads a socket it no longer owns. **The child gets `DRAY_ENDPOINT` injected** rather than left to the CLI's default, or a dev app's agent files its session into the release app's sidebar. That one value is also what lets the app move to a server later — a `.sock` path today, an HTTPS URL and token in a cloud build.

**The boundary is the directory's `0700`, not the socket's `0600`.** `bind` applies the process umask, so a socket lands world-writable under a permissive one and stays that way until a chmod runs a moment later — a window another local account can connect through and reach session creation unauthenticated. A directory cannot have that window, since connecting needs search permission on every dir in the path. `~/.dray` was `0755`, which also made every transcript readable by any local account. **Narrowing is best-effort, so `serve` checks rather than assumes**: a dir still group- or world-reachable → refuse to bind, naming `chmod 700`. Cost a feature, never the app — as does any `serve` error, logged and dropped in `setup()`.

**Connect fails three ways, and only one of them is about the app being up.** `NotFound` and `ConnectionRefused` are the two shapes a closed app leaves and are named outright rather than used as a fallback — a full listen backlog, an interrupted call and a timeout are all this connect failing with the app very much alive. `PermissionDenied` is its own answer and deliberately **not** stated flatly as a sandbox: the kind covers `EACCES` as well as `EPERM`, and `connect(2)` returns it for search permission on a path component too, neither of which escalation fixes. That hedge is pinned by test, and the cure is named in three places — the error, [SKILL.md](../../cli/skill/SKILL.md) and [developer_instructions.md](../src-tauri/src/harness/codex/developer_instructions.md) — reword them together, since rewording the error alone leaves both docs answering a sentence nothing emits. (A Codex-side unix-socket allowlist was looked for and is not reachable: the only config surface is a `[permissions.<name>]` profile, and any custom profile aborts with SIGABRT on `codex-cli 0.151.0-alpha.7.1`.)

## Sharing `~/.dray` between builds

**An older build doesn't merely lose a write, it downgrades the schema.** The index is rewritten whole, so a build reading it round-trips every entry through *its own* struct and silently drops every field it cannot represent — a released build beside a dev one erased `thread_id` from every Codex session, and resume then answered "this session has no Codex thread" for work still perfectly alive. A file lock fixes none of this. `SessionIndexItem.unknown` (`#[serde(flatten)]`) is what fixes it, and it protects only versions carrying it, so it goes in **before** the field it saves, never after.

**An unknown *variant* is a different failure, and flatten covers none of it.** A value serde cannot spell fails the line, and the index parses as one `Vec`, so a failed line is the whole file — a dev build writing `"harness":"pi"` made a released app read 256 real sessions as none. **`Harness` is fixed by carrying the spelling**: `Harness::Other(&'static str)` holds the name verbatim and `wire_name` writes it back unchanged. A placeholder would be **worse than a crash** — it parses fine, then silently rewrites the harness of every session it doesn't recognise. `Harness::ALL` excludes it and `names_a_cli()` answers false. **`ApprovalPolicy` and `SessionStatus` stay unfixed, deliberately**: neither can carry a string, since both must resolve to something real to spawn with, and `ApprovalPolicy` falling back to `Auto` makes a session **freer than the reader asked**. Per-entry tolerance is no good either, since "fail its own entry" can only mean *drop* it, and a dropped entry is a **deleted** one on the next whole-file write.

## Creating sessions

**Spawned sessions always take a worktree, and no flag turns it off** — three issues in one checkout overwrite each other. `--no-worktree` and `--worktree-name` both existed and were removed; the agent has no basis for picking a name and a supplied one is one more thing that collides.

**`--from` moves where the tree starts, not who owns it.** `-w` forks from `origin/<default>` whatever is checked out, so a spawned session could not see the work of the session that spawned it — which put the obvious use, *a second model reviewing what the first just did*, out of reach. `--from <session-id | branch | ref>` still makes a new worktree, based at that point. Sharing a live checkout stays out of scope.

- **Mechanism: Dray makes the tree itself.** [create_worktree](../src-tauri/src/git.rs) runs `git worktree add --no-track -B worktree-<name> <path> <base>` and the child spawns **into** that directory with no `-w` at all. So the tree exists before the child does — a real `snapshot_tree` baseline rather than `base_ref_tree`'s approximation — and carries no lock.
- **Session ids resolve through [`session_branch`](../src-tauri/src/store.rs), the same reading `sessionBranch` in [pr.ts](../src/lib/pr.ts) takes.** Two readers, neither can call the other, so the rule is stated and tested twice; what it must not become is two *different* rules. Id is tried before ref, since a v7 uuid is no branch name anybody types.

**Model, effort, harness and permission mode inherit from the parent**, each overridable by flag. No parent means Rust's own default, since the composer's remembered pick lives in frontend localStorage; `ModelId::default()` cannot serve, being `Unknown`.

- **Model and effort both stop at the harness boundary.** The model half is obvious; the effort half is not — the two ladders share every name (`low`…`max`) and Codex accepts whatever is passed, so a Claude parent's `high` lands silently on a Codex child whose own default is `medium`.
- **Whether to inherit at all is the agent's question and lives in [SKILL.md](../../cli/skill/SKILL.md) alone.** A parent on Fable, or above its harness's own default effort, wants the user's answer before fanning out. Restating it in `system_prompt.md` would be a second copy on the app's release train.

**Depth cap 2, walked not stored.** A spawned session may spawn; its children may not. Walk `parent_session_id` up the index at create time with a cycle guard, rather than storing a `depth` free to disagree with the chain it describes.

**The CLI resolves the project as the main worktree, and `--show-toplevel` cannot do it** — the caller is almost always an agent standing *inside* a linked worktree, where that command answers the tree, not the repo, and the app rightly takes the caller's value over its own guess. The result was sessions whose Changes, commits and PR all read a directory that doesn't exist. The first record of `git worktree list --porcelain` is the main worktree wherever you run it; a bare repo answers `None`. Not `-z`, which wants git 2.36. **Projects are deliberately not attached**, since `add_project` bumps `last_selected` and would let an agent's call quietly change the project the app reopens. **Project order is the reader's**, set by dragging in Settings and kept on the device (`ade.projectOrder`, `orderProjects` in [space.ts](../src/lib/space.ts)) — each server's `projects.json` holds only its own share and the merge puts local first, so a remote project dragged among local ones snapped back to the end. The owning server still takes the move within its share. `last_selected` answers only which project launch reopens.

**`dray` raises no consent card, and that is one flag**: `--allowedTools "Bash(dray:*)"`, additive, with everything else still routed through `can_use_tool`. Verified against v2.1.241, not assumed — a pattern that fails to match fails *silently*, as an unexpected card. **Test with a command that mutates**: a read-only one like `echo` is auto-allowed whatever the rule says, so it reports success for a pattern matching nothing.

**The child gets `PATH` put back.** A bundled `.app` inherits launchd's `PATH`, so `dray` installed to `~/.local/bin` is not there for the agent — the same trap [binpath.rs](../src-tauri/src/binpath.rs) solves for `claude`. Appended, not prepended.

## Skills

**The skill is embedded in the binary and written by `dray skill install`** — downloading it separately is how a skill ends up describing a different version of the CLI than the one installed. Global at `~/.claude/skills/dray/` **and** `~/.codex/skills/dray/`, both written every install, since the CLI cannot know which agent the user runs.

**Freshness rides the CLI, never the app, and the chain closes on its own.** `include_str!` binds the skill to the binary at compile time; `install.sh` runs `dray skill install`; `dray update` re-runs `install.sh`. So every CLI update rewrites the skill and an **app update does nothing to it**, which is the right way round. The skill and `PROTOCOL_VERSION` travel in the *same binary*, so a skill describing the wrong protocol is impossible without the CLI also being wrong. **The skill teaches how to cure a refusal, never which flag needs which version** — enumerating those ages badly and the agent cannot check versions anyway.

**Codex gets Dray's rules as `developerInstructions`** on `thread/start` *and* `thread/resume` (a rollout carries none across). `baseInstructions` beside it is the wrong field — it *replaces* Codex's built-in prompt, tool docs included. Its own file ([developer_instructions.md](../src-tauri/src/harness/codex/developer_instructions.md)), since Claude's names `AskUserQuestion` and the Agent tool, neither of which exist on Codex. Both pinned by test.

## Other machines

**`--machine <name>` runs a request on a machine the app connects to, and trust runs one way: the machine that added another may reach it, never the reverse** (#740). The Mac app already drives every server it added and none of them can call back in; `dray` follows the same rule, so a prompt-injected agent on a VPS has no path into the Mac's sessions. A remote child therefore cannot report to its parent, and its relayed prompt says so (`attribute`); the parent reads it with `ls --machine`.

- **The path is the app's connection.** The agent's `dray` reaches the Mac's server, which holds no remote connections; it wraps the request in `Request::OnMachine` (v12) and asks the app through `host_call` (`forward`), and the app calls the remote's serve command `orchestrate` over `servers.rs`. A server from before #740 answers `unknown command`, which is reworded to "update it". The app closed means no remote reach at all.
- **What only the Mac's index knows travels whole** (`Forward`): the calling session's row and its depth (`Caller`), so the remote inherits model, effort, harness, stance and fast without looking up an id it has never seen, and checks the depth cap against the carried number; and the sender as a `MessageSender` with `machine` set to the Mac's `ComputerName`. The remote takes both as given — it trusts its token holder already.
- **The project is matched on `origin`** (`git::origin`, host and path, lowercased, `.git` and scheme dropped), since the CLI fills `--project` with a Mac path. Failing that a path that exists there is taken as named; else the refusal lists that machine's projects.
- **A session id routes itself on a miss.** `route` looks locally first and only an id this index has never heard of is asked of every connected machine at once (`session_index_item`), so an ordinary call costs nothing. Only the socket's entry routes; a forwarded request is answered where it lands, so nothing bounces on.
- **`ls --machine all`** lists here and every connected machine, each remote row carrying `SessionSummary.machine`. A machine that fails to answer is skipped unsaid.
- **Machine and server verbs never cross** (`this_machine_only`), checked on both sides.

## Relaying messages

**`dray send` goes both ways, and that is one command not two.** A child reporting up and a parent handing a child context are the same operation. The message arrives as an ordinary prompt and *starts a turn*, so it wakes an idle agent; a target mid-turn queues it. Unrestricted to parent/child pairs on purpose — an id is an address. **Send passes the target's own recorded model/effort/permission back in**, which is what makes it inert: `send_msg` finds no change, so nothing respawns. A message must not reconfigure the session it arrives at.

**A relayed message names its sender twice, and neither copy does the other's job.** `user_message.from` = `MessageSender { session_id, title }`, set only by `send_message` and persisted so attribution survives replay; the prompt text carries `[message from the Dray session "title" (id)]` as well. Both are built from one lookup in `attribute`, so the two cannot name different sessions.

**The transcript has no business parsing it back out.** Not for forgery — `from_session_id` comes from `DRAY_SESSION_ID` in the child env, so the **field is no more authentic than the prose**. Refused because a parse *fails silently*: a title holding a bracket, a reworded prefix or another harness's shape each break the regex and leave a relayed message drawn as the user's own. The bubble instead **rebuilds** the exact string `attribute` builds ([stripSenderPrefix](../src/lib/relay.ts)) and drops it only on `startsWith`, so drift fails by leaving the line **drawn**, never by eating the sentence after it. The log is untouched.

**A sender can outlive the session it names, so selection rolls back on an empty read.** Leaving a dead id selected looks harmless and isn't: `selectedSession` goes null while `selectedSessionId` still holds it, and `centered`/`isNewTask` both derive from that null — so the reader gets a *new task* composer while `handleSendMsg` still finds the id and resumes a session that is gone. `handleSelectSessionIndexItem` restores the previous pick and says "Session not found", which also covers a stale sidebar row.

**Two refs, answering different questions.** `selectedSessionIdRef` mirrors state, so it is a **render behind** and a read landing in that gap still sees itself as current. `selectionRequestRef` is written at *call* time and claimed at every site selection moves, and the rollback fires only where it still names this read. The rollback target likewise cannot be "whatever is selected", since selection is optimistic until its own read lands — hence `restorable` is the previous pick *only if loaded in `sessions`*, else `null`. Validity is judged **at rollback, not at capture, off `sessionsRef`**, since the closure's `sessions` is the render's copy and the rollback runs after an `await`. General rule: **state read across an await must come from a ref, not a closure.**
