# The sidebar

**`session_created` carries an index item, never a `SessionSnapshot`.** The frontend's `agent_event` listener writes into sessions it already holds and *drops* events for ids it doesn't, so a snapshot would start a transcript in memory that later events could miss. An index item leaves the transcript unread until the row is clicked. `session_status` and `session_title` still land, since both write by id into maps the sidebar reads. **The row appears and is deliberately not selected** — the user is mid-conversation in the session that spawned it. The listener sits in a `[]` effect, so it needs `showArchivedRef`.

**Nesting is `sortSessions`** in [Sidebar.tsx](../src/components/Sidebar.tsx), exported and shared with ⌘⇧↑/↓ so the order stepped is the order drawn. **Walk depth-first, not one pass over roots** — the depth cap allows a spawned session to spawn, and a single pass emitted neither the grandchild nor anything below it, so rows vanished. A `seen` set means a cycle costs a strange order rather than a hung sidebar.

**The live list is stages, workspace-wide, and draws no project headings** (#516) — needs you, unread, idle, unread with an open PR, open or draft PR (ready to merge included), checks running, merged, set aside. Needs you wins whatever the PR says, running checks outrank a running turn, and a row mid-turn otherwise sits where it would rest. Draw order is also strength, so a nest takes whichever of its rows sits highest. This reverses the older rule of states *under* each project: past three sessions, the answer to "what wants me" was scattered under every heading. The PR stages read the sidebar's own marks, so they cost no `gh` call; a merged PR holds its session unread or working, so follow-up on landed work stays together, and failing checks stay in the open-PR stage, the red glyph saying the rest. Checks running sits near the bottom on purpose, since nothing is asked of the reader until CI answers. **Mid-turn is not a state of its own**: the row already says so where its timestamp would be, and a run for it moved a row twice for one piece of work, out on send and back on the turn ending. **A nest takes the strongest state anything in it holds**, so a child blocked on a question carries its parent up rather than the run that says "these want you" missing the only session in it that does. `asking` is read ahead of the backend's status, which still says `in_progress` and is right to. Live status falls back to the item's own field, which is what carries a `completed` across a restart. **The settled list passes no live reading at all** and collapses back to one run per project — it is a history, not a worklist — and **draws no Pinned group either**, since a pin is what the reader keeps in reach while they work and every row over there is done with. **Neighbouring single-row stages share one break**, within two families — needs you with unread, and the four PR stages — since a run of one row between two breaks reads as a heading rather than as a row, and each row's own mark tells them apart. An empty stage is skipped, its neighbours touching on screen; a stage of two rows cuts the run. **A list under three rows is not split at all** (`STATE_SPLIT_MIN`) — the split earns its break by making a long list quicker to scan, and there is nothing to scan in two rows. Rows, not nests: the count is what the reader sees down the left edge.

**No run names itself.** The state is already on every row in it — the yellow rail mark, the green one, the working indicator — so a heading is a second copy of what the rows say, and eight of them turn a list of sessions into a list of headings. The break between runs is what says one ended, which makes that spacer the whole signal — and **it needs `shrink-0`**, since a bare height in a flex column collapses to nothing once the list overflows, i.e. on exactly the long sidebar it exists for. Every row beside it is held up by its own `min-h`. `sortSessions` takes the same reading as the render, or ⌘⇧↑/↓ steps rows where they used to be.

**One remote is one project, wherever it runs** (#782, [projectGroups.ts](../src/lib/projectGroups.ts)). A project is still server plus path everywhere it is stored; grouping is a reading of that list, keyed on `Project.remote ?? path`, so a server too old to report a remote and a repo with no remote both stay per path. `remote` is read off git on every list and never saved. A remote that is a path is not one (`git::shared_remote`): `/srv/x.git` here says nothing about `/srv/x.git` there. Two clones on one machine merge too, with no exception, so the machine dropdown names a path only where a machine holds two.

**Session rows do not change.** What merges is the settled and drafts headings and the filter with its chords, each under `leadPath`, the group's first checkout. A heading names a machine only where the project has just one, and dims only when all of them are gone. `projectFilter` still stores a path, compared through `sameProject`, so a filter set before grouping keeps working.

**`&` lists the project's tasks on every machine an agent there can reach** (#784, `composerSessions` in `App`). A tag is text an agent acts on with `dray session send`, so a row nothing can deliver is a dead end. This Mac's server reads the app's own machine list, so a task here lists every connected machine. A task on a remote lists that machine's tasks, plus whatever it answers to `reachable_sessions`: the ids it can reach through links of its own, asked only when the picker opens. They are ids, not machines, since the remote and the app name one machine differently. A server too old to answer reaches only itself.

**A new task lands on the last machine used**: the newest `lastSelected` among checkouts still reachable. Picking the project takes it, and [MachineSelector](../src/components/composer/MachineSelector.tsx), a dropdown beside the project, changes it. A project only on This Mac draws none, one checkout on a server draws it disabled, and several draw it live, two clones on This Mac included, since the second is otherwise unreachable. It is the one place This Mac is named, being a choice that needs a label. `handleSelectProject` stamps the list in memory as well as on the server, since the list is only read again on connect. **Every way into a project goes through this** (the selector, a heading's click, the filter, `project.next`) except opening a session or draft, which names its exact checkout. **The tab names the machine and never names This Mac**: no name is what says local. It sits beside the label rather than in it, since a long title is cut and the name must not be.

# The crew

**The crew is cards, not a list** (#807, [Crew.tsx](../src/components/Crew.tsx), rules in [crew.ts](../src/lib/crew.ts)). Drawn **only while** a session the selected one started — at any depth — is waiting on a permission or question card. One card per session, under its title, answered in place. The title is a label: answering is a reply sent by id, never a move into that session. It used to be a standing list of every child, each expandable into a live transcript, with ⌘⇧C to hide it and an anchor that held the main column on the parent while a child was selected. All of that went: the sidebar already lists the sessions, and a second copy spent 320px on every fan-out whether or not anything wanted the reader. The main column always draws the selection now.

**Every depth, not direct children.** A hidden parent is never the selection, so a grandchild's card would otherwise be answerable nowhere. `crewRows` walks depth-first, each level newest first by `created` — `modified` moves on every turn ending — with a `seen` set so a cycle costs a short list rather than a hung render. Archived sessions drop with everything under them.

**A hidden session surfaces only through its cards.** It has no row in the sidebar and no list anywhere else; the bots/projects mode is where a list of them belongs, if anywhere.

**No column beside a split**, on the issues page, or behind another view tab. A card raised there announces instead.

**`setCrewSeen` is every row, never filtered by `asking`** (`crewSeen`). `announce` reads it to withhold a card's notice where the column would draw the card itself, and `asking` is set by the very event being announced — so a set filtered by it is one render behind, and a child raised a notice *and* drew its card (DRA-277). The sound still plays; only the notice card is withheld. `setOnScreen`'s set is narrower — the asking rows of a drawn column, since a card needs its session's log loaded. **A `useLayoutEffect`**, since a stale reading here suppresses a notice: an ordinary effect lands after paint, and a render-time write may describe a render React threw away.

**The card scrolls itself into view**, `scrollIntoView({ block: "nearest" })` keyed on the request id, which is what makes that suppression honest on a column with more cards than fit.

**Above the composer, one card at a time.** Several cards at once was a wall of questions over the conversation the reader is in, so the crew draws the first and steps through the rest with arrows and a `1/3` count. The pick is held by session id, so an answered card leaving drops the reader on the first one rather than on whichever took its index. The count is the only sign a second ask arrived: `crewSeen` names every row, so it raises no notice card.

**The side column is off, not gone** (`CREW_BESIDE` in [Crew.tsx](../src/components/Crew.tsx)). With it on, the cards stand in a 420px column beside the chat where the minimums fit — chat floor + 420 + sidebar (drawn width, floored at its minimum) + panel floor while the panel shows — and stack above the composer otherwise, and up to 1512px whenever the panel is open (`CREW_STACK_WITH_PANEL_W`). The chat column's floor takes the crew's width ([ResizeHandle](../src/components/ResizeHandle.tsx)), since the column never gives width back. Its edge is a `border-image` ramp in `--border`'s colour, full at the composer's end and gone by the top, since a flat border reads as a split between two places to work.

**Number keys and Return reach one waiting card, wherever focus is — unless it is in a text field** ([cardKeys.ts](../src/lib/cardKeys.ts)). The composer keeps what is typed into it; anywhere else, a digit picks and Return sends. A window capture listener answers before `typeIntoComposer`, which would otherwise pull the key into the composer. The conversation's own card outranks the crew's, since it blocks the turn the reader is in; a click on a card makes it the one until it goes, and while two are up the one with the keys is ringed. A question card is handed the key on its active choice, so the questionnaire picks, steps or submits as it would for a key pressed there. A permission card has Allow once picked from the start, so Return alone allows once; digits move the pick.
