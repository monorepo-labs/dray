# CLAUDE.md

File give Claude Code (claude.ai/code) guidance for work with code in this repo.

## Working practices

**Product work = Linear issue, before first edit.** Feature, bug fix, UX change, refactor. Plan freely without one; create through Linear MCP before code land. Existing issue = use that one.

**Housekeeping take no issue.** CLAUDE.md, plan note, tooling config — thing changing how we work, not what ship. Issue there = noise.

**Minor update take no issue either.** Tooltip wording, copy tweak, one-line prompt change. Several small thing landing in one PR = one issue at most, never one each.

**Description over ~1000 character open with `## TLDR for human`, closed by `---`.** One line per thing worked on, even when only one. Shorter description need none.

**Status:** start → `In Progress`. After that, leave it — GitHub integration move issue to `In Review` on PR open and `Done` on merge. **Exception: work pushed straight to `main`.** No PR = nothing for integration to read, so set `Done` yourself.

**PR carry issue id so Linear link itself.** Body (`Fixes DRA-123`) or branch name — integration read both. Worktree branch = `worktree-<name>` minted by CLI, so body = reliable slot. Id = what arm the whole status rule above; PR without one leave issue sitting `In Progress` forever.

**PR nobody need review carry `no-review` label.** Copy tweak, doc, prompt wording, config. Add at open (`gh pr create --label no-review`), since review fire on open. Anything touching behaviour = no label.

**Default road = work → PR → stop.** Greptile review every PR on open, so spawn no reviewer session. Open ready, not draft — Greptile skip draft, so a draft sit unreviewed till somebody ping `@greptile review` by hand.

**One team, `Dray`. Prefix `DRA-`. Assign every issue to `yogesh`.**

Linear MCP not connected → say so, then carry on with the work. Tell reader at the end which issue still want creating.

**Don't commit unprompted.** Stage + describe change, then wait — even when finished and passing. Asked = approval for that commit only, not ones after. Same for `git push`, branches, anything rewriting history.

**Always write commit message with `caveman-commit` skill.** Invoke it, don't imitate — skill carry format and it can change under you. Every commit here, amend included.

**Comment sparingly.** ~10% of lines, only where code cannot speak for itself:

- Write _why_, not _what_. `// bump seq` on `self.seq += 1` = noise; "the session layer must number synthesized events through this same counter or seq develops gaps" = not noise.
- Good reasons: non-obvious wire-format fact, invariant future edit could silently break, why simpler-looking alternative rejected, deliberate omission.
- No restate type signature, no banner separators (`// ---- helpers ----`), no doc comment on every field of obvious struct.
- One dense sentence beat three-paragraph doc comment.

**Write plainly.** Everywhere — chat replies, comments, docs, commit messages, plan files. Short sentences, active voice, no clutter, no over-explain, no under-explain where detail matter. Skip fancy words. Cut any word doing no work.

**Stay out of files being actively edited.** User say they work on something → review and advise, don't rewrite. `todo!()` or missing match arm = work in progress, not defect.

**`///` doc comments show on hover, so add one to every `pub fn` and any non-obvious private fn** — one line, same "why not what" bar. Skip trivial helpers/getters where name say all.

## What this is

`Dray` = Tauri 2 desktop app wrapping coding-agent CLIs in chat UI. Spawn `claude` binary as child process, speak stream-json over its stdin/stdout, parse each output line into typed Rust enum, forward to React frontend as Tauri event.

## Repo layout

pnpm workspace, two apps, no shared package yet.

```
apps/desktop/   the Tauri app — everything below this section describe it
apps/web/       marketing site: Next.js App Router, Tailwind 4, deploy Vercel
```

Root `package.json` carry **no dependencies** — name, `packageManager`, `pnpm --filter` aliases only. Keep it that way: dep at root install into root `node_modules`, which both apps resolve through, so version drift there show up as one app mysteriously working.

Two things repo-wide on purpose. Release pipeline = desktop's alone but live in root `.github/workflows`, so paths carry `apps/desktop/` prefix and `tauri-action` need `projectPath`. And `pnpm-lock.yaml` single for whole workspace, why `pnpm install` run at root and nowhere else.

`apps/web` share design language with app but **no code** — no build step reach across, no import cross line. First component genuinely wanted in both = reason to create `packages/ui`, nothing before.

## Design direction

Dray keep to one visual language — one radius scale, one yellow, filled buttons carry shadow and chrome don't, shortcuts live in real tooltips and never on `title`. Window is glass (macOS vibrancy) with body's fill the only hole in it, and the titlebar row is what user drag window by.

**Rules, rejected alternatives and the reasoning all live in [DESIGN.md](apps/desktop/DESIGN.md)** — read it before restyling anything, changing window chrome, or reworking a panel, card, row or button. Two things there fail *silently* and cost an afternoon each: vibrancy's `body` specificity, and window drag needing both an explicit capability and `data-tauri-drag-region="deep"`.

## Commands

Use **pnpm**, not npm. `tauri.conf.json` hardcode `pnpm dev` / `pnpm build` as before-commands.

**Every app command run from its own package dir.** Workspace root hold no deps, only thin `pnpm --filter` aliases (`pnpm app`, `pnpm web`). Anything else — `cargo`, `vitest`, `tauri build` — want real cwd, because relative paths in `tauri.conf.json`, `.cargo/config.toml` and `install.sh` all resolve against it.

```bash
cd apps/desktop && pnpm tauri dev
```

That = real entry point. `pnpm tauri` = shim ([scripts/tauri.mjs](apps/desktop/scripts/tauri.mjs)) merging `tauri.dev.conf.json` into `dev` subcommand only, so dev app carry own name and icon and `build` untouched.

**Shim also pick dev port, and it only side that can.** Vite and Tauri have to agree on one, and both start from here — so shim ask the OS for a free one (`listen(0)`), hand it to Vite as `DRAY_DEV_PORT` and to Tauri as second `--config` carrying `build.devUrl`. Fixed 1420 was hard failure before, which = one worktree's dev build refusing to start because another's already running. `strictPort: true` **stay** on Vite side: port already known free, and Vite wandering off it leave Tauri loading URL nothing serve.

- `pnpm dev` — frontend only, port 1420 unless `DRAY_DEV_PORT` say otherwise. `invoke` do nothing in plain browser, so only useful for pure-CSS/layout work.
- `pnpm build` — `tsc && vite build`. `pnpm tauri build` for bundled app.
- `cd apps/desktop/src-tauri && cargo test` — Rust tests (parser + mapper + event-model compatibility, plus git and file index). Single test: `cargo test parses_complex_fixture`.
- `cd apps/desktop/src-tauri && cargo check` — fast type check, no linking whole app.
- `pnpm test` — frontend tests (vitest, node environment, no DOM). Scoped to pure logic where being wrong invisible on screen: [streaming.ts](apps/desktop/src/lib/streaming.ts), which read same committed fixtures Rust tests do; composer's caret arithmetic ([slash.ts](apps/desktop/src/lib/slash.ts), [mention.ts](apps/desktop/src/lib/mention.ts), [highlight.ts](apps/desktop/src/lib/highlight.ts)); and [theme.ts](apps/desktop/src/lib/theme.ts)'s coercion. Components not tested — no DOM here.

## Architecture: the event pipeline

Messages flow one way out to CLI and one way back in; return path = what most Rust code exist to serve.

1. **`useSessions`** ([useSessions.ts](apps/desktop/src/hooks/useSessions.ts)) call `invoke("send_msg", {...})` with camelCase keys (`sessionId`, `isNewSession`); Tauri map them onto snake_case params in [lib.rs](apps/desktop/src-tauri/src/lib.rs). Frontend mint session UUID with `crypto.randomUUID()` — Claude Code adopt id chosen by app, not other way round.
2. **`SessionManager`** ([session.rs](apps/desktop/src-tauri/src/session.rs)) own `Mutex<HashMap<String, Session>>`. On send: spawn process for new session, reuse live one when present, re-init from `--resume` when id known but process gone. New sessions written to index before spawn, so one failing to start still visible, and created `SessionIndexItem` returned to frontend — `Some` on creation, `None` on resume.
3. **`claude_code::init`** ([claude_code.rs](apps/desktop/src-tauri/src/harness/claude_code/claude_code.rs)) spawn `claude -p --input-format stream-json --output-format stream-json --verbose --include-partial-messages`, add `--session-id` for new sessions or `--resume` for existing, and `-w <name>` on creation for worktree session.
4. Two `tokio::spawn` tasks drain stdout and stderr. Each non-empty stdout line go through `parser::parse_line` → `Mapper::map` → `app.emit("agent_event", &agent_event)`, with copy pushed onto `Session.events` and appended to session's JSONL.
5. **`useSessions`** listen for `"agent_event"`, route deltas into `streamingContentBlock` and everything else onto session's `events`. `Chat.tsx` render both.

**Finding the binary.** [binpath.rs](apps/desktop/src-tauri/src/binpath.rs) resolve `claude` to absolute path, cached in `OnceLock`; both spawn sites go through it. Never go back to `Command::new("claude")` — bundled `.app` launched from Finder or Dock inherit launchd's `PATH` (`/usr/bin:/bin:/usr/sbin:/sbin`), which hold no `claude` however globally installed, so bare name work under `pnpm tauri dev` and fail in bundle with no events arriving at all. Resolution escalate by cost: inherited `PATH`, then known install dirs (`~/.local/bin`, `~/.claude/local`, `~/.bun/bin`, `~/.npm-global/bin`, Homebrew, globbed nvm version dirs), then `$SHELL -l -c 'command -v claude'`. `-l` load-bearing — without it zsh read `.zshrc` only and miss `PATH` exported from `.zprofile`. `git` need none of this.

**Worktrees.** `claude -w <name>` put tree at `<project>/.claude/worktrees/<name>` on branch `worktree-<name>`. Child must spawn at **project root** — directory not existing yet can't be `chdir`ed into, and CLI create tree and move itself in after launch. So spawn dir and session's recorded `cwd` differ for worktree sessions, only latter point at tree.

## The normalized event model

Both harnesses map onto one vocabulary in [events/events.rs](apps/desktop/src-tauri/src/events/events.rs), so the frontend and on-disk log never see raw wire format. Adding a harness = writing one mapper. Per-harness code sits under `harness/<name>/` with a seam: `parser.rs` (wire → typed events), `mapper.rs` (those → `AgentEvent`). Module entry files are named after their directory (`events/events.rs`), not `mod.rs`, declared with `#[path]`.

Two rules the whole design rests on:

- **`seq` is the ordering key, not `ts`.** Most Claude Code lines have no timestamp. One counter per session, and events the app synthesizes itself (the user's own prompt, which the CLI never echoes back) must be numbered through it too.
- **Deltas are a preview; the committed event wins.** Absent deltas are the common case — Codex sends none, Claude Code sends none for subagent output — so consumers must render correctly without them. Deltas match on `BlockRef`; tool calls join on **tool_use id**.

Prompts go the other way as one JSON line on the child's stdin ([session.rs](apps/desktop/src-tauri/src/session.rs)), sharing the pipe with `control_request` lines ([control.rs](apps/desktop/src-tauri/src/harness/claude_code/control.rs)). `set_model` and `set_permission_mode` switch a running child in place. **`set_effort` does not exist** and `effort` on `set_model` is accepted and ignored, so effort changes need a respawn.

**`interrupt` stops a turn, `stop_task` stops a task** (v2.1.232). `stop_task` takes `task_id`, not the spawning `tool_use_id`, and `not_found`/`not_running` also answer success — so a wrong id looks exactly like success, and only lifecycle events' `agent_id` carry the right one. **Stop = interrupt alone.** It fanned `stop_task` out over every outstanding id back when a task held the session `in_progress`; status follow the turn alone now, so the fan-out only killed dev servers and subagents the reader still wanted. `StatusTracker` hold ids rather than a count for the panel's per-task stop and the stranded-task report, not for Stop.

**What can change mid-session.** Model and permission mode apply in place; effort kills and resumes; project, branch and worktree are creation-time only and the composer hides them once a session exists. That rule keeps `git checkout` from ever running under a live child.

### Fast mode

**Three harnesses have one, each reached a different way, and `Capabilities::fast_mode` is the one statement of that** — a four-armed enum rather than a pair of bools, since "offered" and "changeable" would spell combinations nothing has. Stated twice, in [fastMode.ts](apps/desktop/src/lib/fastMode.ts) too, for the same reason `stanceFor` is. It is a **bool** on the index entry and on the wire, never an enum: every one of them is two-valued, and a variant an older build cannot spell fails the line and reads the whole index as no sessions.

- **Claude Code — in place.** `--settings '{"fastMode":true}'` at spawn, `apply_flag_settings` with the same `flagSettings` layer on a running child, both verified against v2.1.270. **The SDK has to opt in and nothing else turns it on**: without it the CLI reports `fast_mode_state: "off"` with `fast_mode_disabled_reason: "sdk_opt_in_required"` however the reader's own settings files are written. The flag rides *every* spawn, resume included — `flagSettings` is per process, so a respawn would silently drop back to standard speed. Opus alone, which is the CLI's own gate on the resolved model naming `opus-5` or `opus-4-8`.
- **Codex — on the spawn.** `serviceTier: "priority"` (the tier's id from `serviceTiers`, not `fast` from `additionalSpeedTiers`; `thread/start` takes either and answers `priority`). It rides **both** `thread/start` and every `turn/start`, and is **always sent** where `effort` is omitted when unset: a tier set on a turn sticks to the thread, so omitting it means "keep what you have" and `"default"` is what puts it back. `thread/resume` ignores the field. **An unknown tier is accepted with no error at all** and runs the turn at ordinary speed, which is why `supports_fast` follows the wire and absent reads as *no* — the opposite of `accepts_images` beside it.
- **fx — at creation, and unreachable after.** ACP's `configOptions` are provider, model, mode and effort and nothing else (0.0.10), `fx acp` takes `--model` and `--log-file`, and no `FX_*` variable names it — so `~/.fx/settings.json`'s `fast_mode` is the only surface, written through the same read-modify-rename `fx provider` already uses. fx reads it at `session/new` and **stamps it onto its own session record**, which a resume then honours whatever the file says since — so a respawn would not move it and the composer draws the row on a new session alone. fx's global setting, so it moves the reader's own TUI default too; the row says so.
- **pi — none.** `serviceTier` is plumbed through its provider layer and populated from nowhere: no flag, no settings key, and `set_model`/`set_session_name` are its RPC's only setters.

**The control is a row in the model picker, because fast mode is per *model* on every harness that has one.** `Model.supports_fast` is what draws it — the Codex list reads it off the wire, Claude's table names Opus alone, and **fx's is per provider**, since only one of its providers publishes the answer. **The Vercel gateway names a fast tier as a model of its own**, a separate id with `-fast` on the end, 25 of its 247 — so a gateway model has fast mode exactly where its twin is in `Listing.ids`, the list `probe` already reads. No new call, no wire surface, and nothing to learn from a live session the way the effort ladder next door is: the list *is* the answer, so there is no `models_changed` to emit here. The twins are **kept out of the picker** — the same model twice, once as a model and once as a mode, gives fast speed with an inert toggle beside it — and a `-fast` id takes no toggle **because it is the fast tier**, not for want of a twin of its own, which is its own arm in `supports_fast` rather than left to the lookup answering right by accident. codex offers fast mode and lists no `-fast` id, so its hardcoded `true` is correct and measured; grok is **untested** and keeps `true` for codex's reason rather than on a reading of its own. Applied globally the twin rule would mark every codex and grok model as having none. **Hidden is never unrunnable**: `list` filters, `find` reads the unfiltered list, or a session recorded on a `-fast` id would resolve to nothing, spawn with no `--model` at all and record its own model as unset — silent on screen and in the log. Codex's hidden rows (`gpt-reserve`, `codex-auto-review`) make the same bargain. The pick itself is **one preference, not one per model**, unlike effort: a level means different things on each ladder where fast mode means one thing everywhere, so switching to a model without one keeps the pick and simply doesn't honour it. `fastFor` narrows it at the send and `send_msg` clamps by harness again, so what reaches the index is always what the child was told. **It sits under the models and above "More models"**, which is a fold of the same list rather than a category beside it. **A real switch, not a tick, and the row holds the menu open** — every other row there is a pick out of a set where this one is on or off, and a switch that vanishes on the press never shows which way it went. The row is the control and the `Switch` is its picture (`pointer-events-none`, with `role="switch"` on the item), or the two would fire side by side and toggle twice. The trigger says **Fast** beside the effort and drawn exactly like it: its presence is what says the mode is on, so a colour would be a second way to say one thing — and an accent there competes with the yellow the sidebar spends on sessions wanting the reader. A glyph was the other try; among two words it read as a badge stuck on the label.

**A refusal is drawn as the harness's own sentence under the row, and nothing moves the switch.** Claude Code says it on `system`/`notification`, keyed rather than typed — `fast-mode-overage-rejected` / "Fast mode disabled · usage credits exhausted", captured in [fast_mode_refused.jsonl](apps/desktop/src-tauri/src/harness/claude_code/fixtures/fast_mode_refused.jsonl), where it used to land in `parse_failures.jsonl` as `unknown_subtype`. The mapper reads the whole `fast-mode-` prefix and drops every other key to `None`, since the payload carries the sentence untouched and anything said under that prefix is news about fast mode. **Not `fast_mode_state` on `init`, which is not the weaker source but a lying one** — measured: through both turns of the captured session it reported `on` while the CLI was refusing fast mode outright, so a reader believing it is told the opposite of what happened. That retires reconciling anything from it as a question: it was already refused on `permissionMode`'s grounds, which is that these fields report what the CLI is *doing* rather than what was asked for, so a cooldown would read as the reader turning fast mode off — and a field that also reports the wrong thing about what the CLI is doing has nothing left to offer. The notice is the only honest source, and the switch stays the reader's alone.

**The notice is scoped to the newest turn, and that is what clears it.** `fastNotice` in [fastMode.ts](apps/desktop/src/lib/fastMode.ts) walks the session's own log back and stops at `turn_started`, so a turn that runs fast says nothing and the sentence goes; the CLI says it once per **turn** it refuses rather than once per session, which is what makes that reading safe — two lines 8s apart in one captured session, and the whole of why the walk stops where it does. Read from the log rather than tracked in a map, the same bargain the context ring makes, so a reopened session reads what it read live. Drawn only while the switch is **on** — it is there to explain a lit control that changed nothing, and beside an off one it is a stale complaint about a setting already left. Codex and fx report nothing at all, so there is nothing to draw for those two either way.

### Permissions

**`ApprovalPolicy` is what `--permission-mode` accepts; `PermissionMode` is what `system/init` reports**, and they differ (v2.1.224): `plan`, `acceptEdits`, `bypassPermissions`, `dontAsk` report themselves, but both `auto` and `manual` report `default`. So `ApprovalPolicy` must never regain a `Default` variant, and session state must never be reconciled *from* the init event — `auto` and `manual` are indistinguishable there.

**Nothing is ever asked without `--permission-prompt-tool stdio` on spawn.** The literal `stdio` is a special case, undocumented in `--help`. Without it the CLI auto-denies and reports `system`/`permission_denied`.

A held call arrives as `control_request`/`can_use_tool`, the only line travelling *into* the app expecting an answer, and the CLI blocks its turn until a `control_response` with that `request_id` comes back. Silence stalls the session, so [permissions.rs](apps/desktop/src-tauri/src/harness/claude_code/permissions.rs) guarantees a reply and an unmodelled subtype is refused from inside `read_stdout` — hence `Session.stdin` is an `Arc<Mutex<ChildStdin>>` shared with the read loop. The reply double-wraps:

```json
{"type":"control_response","response":{"subtype":"success","request_id":"…",
 "response":{"behavior":"allow","updatedInput":{…},"toolUseID":"…",
             "updatedPermissions":[…]}}}
```

`deny` takes `message` and an optional `interrupt`. **A wrongly shaped reply is ignored silently**, so a regression here presents as a hung turn, not an error.

- Options are the CLI's — `permission_suggestions` carry pre-composed rules and `build_options` turns each into a button. **The rule never leaves Rust**; the frontend answers with an option id alone.
- The request is always main-thread even when a subagent asked, since subagent events are filtered out of chat and `agent_id` is the harness's handle, not the `tool_use_id` this app correlates subagents by.
- The card renders outside the turn stack from `buildTranscript`'s `pendingAsks`. Neither `permission_requested` nor `questions_asked` belong in `RENDERS` — they draw no row, so counting one miscounts collapse.
- `control_cancel_request` is the CLI taking a question back: drop the entry, mint `PermissionDecided { automatic: true }`, **write no reply**. It names an inbound id and carries v4 where `ControlLine::new` mints v7.
- **Never persisted** — request, decision and questions alike. Only the child that asked can answer and no child survives a restart, so a replayed one is a card whose buttons cannot work.

**`AskUserQuestion` rides the same channel and is not permission.** It arrives as `can_use_tool` with `requires_user_interaction: true`, and the answer travels back inside *allow*: `updatedInput` is the tool's own input with an `answers` map added, keyed by each question's verbatim text. Allowing with nothing filled in is what produces "The user did not answer the questions", so the mapper branches on tool name into `QuestionsAsked` and the card carries no Allow/Deny. Three answer shapes (v2.1.226): an option's **label** is the answer, multi-select is one **comma-separated string**, free text is any string. An absent question is skipped, so Skip is a real answer.

[QuestionRequest](apps/desktop/src/components/chat/QuestionRequest.tsx) is a `<form>`, and that is what reads answers back: each item's `name` is the question's text, so `FormData` is already keyed the way the CLI matches. `items` must carry `choices` (numbers come from that array, not markup), and the card **takes focus on mount** onto the first choice, since Enter only fires when the event target is a choice. The free-text box is not optional — the CLI promises the user one and tells the model not to add an "Other" option because of it.

**Two denials mean different things.** `PermissionRequested` → `PermissionDecided` is a question the user answered; `PermissionDenied` is `system`/`permission_denied`, refused with no question possible. Both render as nothing — approval is visible in the tool running, refusal in its error.

**A tool call with no result is only _pending_ while something could still produce one.** `buildTranscript` takes `live` (session `busy`) and files an `ABANDONED` stand-in into `resultByCallId` for every call the log leaves open, so collapsed row, group header and shimmer all read pending-ness from one map. `user_message` also abandons everything open before it. Marks are applied after the walk and only where no real result exists, since a background subagent can report back after its turn. It works only because `handleSelectSessionIndexItem` returns early for a session already in memory — make it always refetch and an open card disappears mid-flight with the agent still blocked behind it. **Loaded transcripts are evicted** (`evictSessions` in [useSessions.ts](apps/desktop/src/hooks/useSessions.ts)) on archive, on settle, and after ten minutes unviewed — never the selected session, never one mid-turn, never one holding a card, for that same reason.

### Streaming and previews

**A tool call is drawn before its arguments arrive.** `Write`'s arguments *are* the file, so the committed row lands only once the whole content has streamed (39.5s on a 12KB file). Split = **header from stream, body from committed event**; a half-arrived diff is worse than none, so the preview row never expands. It is retired on `tool_call_started`, not `block_stop`, which lands later and draws both rows for a frame.

[streaming.ts](apps/desktop/src/lib/streaming.ts) reads the accumulated `input_json_delta` prefix rather than parsing it and holds no state between frames, so a dropped fragment cannot corrupt a running parse. Two lookup strategies sit side by side and the difference is load-bearing: **target keys are field-keyed** (`file_path`, `command`, `pattern`…), safe on MCP tools nobody enumerated, while the **line-count key is tool-keyed**, because `content` only means *file* content on a tool that writes one (`TodoWrite` carries `content` inside every todo). Within target keys, `command` is checked before `description`.

### The changes panel

**Diff two snapshots, not the working tree.** `git diff` reports everything uncommitted, including what was already dirty. `snapshot_tree` captures the tree at send time and the panel diffs that against the turn's **closing snapshot**, frozen onto `turn_completed.head` by `read_stdout`. Freezing the end is as load-bearing as snapshotting the start — head left at "now" and an idle session absorbs whatever later touches the checkout. A frozen pair also diffs to one immutable answer, which lets `useChanges` treat that cache entry as final.

Snapshot = **temp-index `write-tree`**: copy the index to a temp file, `git add -A` through `GIT_INDEX_FILE`, `write-tree`. Real index, working tree and stash untouched, and copying rather than starting empty keeps it at ~18ms since the copy carries git's stat cache. `--git-path index` finds it, which is not `.git/index` for a worktree session.

Comparing *content* rather than replaying edits is why `Bash` moves and reformats show up, several `Edit`s collapse into one diff, and a mid-turn commit is invisible — `Edit` carries only the fragment it replaced and `Write` never reports what it overwrote. Cost: the snapshot describes the *tree*, so anything else writing during the turn is attributed to it.

The baseline rides on `user_message.baseline`, the closing head on `turn_completed.head`. `changeRange` pairs the newest baseline with the newest head *after* it, and leaves head open only while nothing closed the turn, so a turn that never closed degrades to diff-against-now. **Only the newest prompt's snapshot is ever used.** `None` is ordinary and reads as nothing to show. **A worktree session's first prompt is the exception** — no tree yet, so the baseline comes from `base_ref_tree`.

- **Panes hide, they don't unmount.** The `active` prop is the other half: a hidden `ChangesPanel` must not keep snapshotting on every event, and `active`'s place in the effect deps triggers the catch-up read on reopen.
- **Reads are cached across mounts, keyed by tree id** ([useChanges](apps/desktop/src/hooks/useChanges.ts)) — a new snapshot is a new key, so an entry can only be stale by being unreachable and eviction is a size cap, not invalidation. Change sets are counted (12); file contents are budgeted by **bytes**, or a turn touching more files than the cap evicts rows while they are still mounted. A fresh read whose `base`/`head` match keeps the **old object**, which is what lets `FileRow`'s `memo` survive a re-render on every session event.
- **Two `cat-file` passes per file, and the split is about memory.** `--batch` is one spawn but drains stdout whole, so a 2GB blob is read in before `MAX_BLOB` could reject it; `--batch-check` returns headers only. Input is NUL-delimited (`-z`), since a rev embeds a path and a path may contain a newline. Both parsers always answer exactly as many entries as asked for, or one file's contents render under another's name.
- **Every `git diff` here ends in `--`**, or a working-tree file *named* like a sha makes it die with "ambiguous argument". Covered by test.

**Filtering `cargo test` rewrites generated TS.** ts-rs regenerates `src/types/events.ts` from whatever exports ran, so `cargo test git::` leaves only git's types and breaks the frontend build. **Always follow a filtered run with a bare `cargo test`.**

### Indicators and failed turns

- **Thinking blocks arrive empty** — `thinking_delta` carries `thinking: ""` and the committed block is empty too. `reasoning` must not be counted in `RENDERS`, or the working indicator stays suppressed for the rest of the turn. No fixture carries one.
- **A failed turn draws the harness's own sentence, never `stop_reason`.** Aborts are already suppressed, leaving `stop_sequence` — a wire token that says nothing, drawn instead of the `final_text` beside it that usually carries the cure. `Turn failed` is the fallback for an errored turn with no text.
- **The harness sends that sentence twice, and the red row wins.** The builder drops the assistant block rather than the renderer skipping it, since three surfaces could draw it. Written to under-match: the block must be the turn's last rendered row and **equal** the sentence whole, never contain it. `drawsFailure` is exported from [transcript.ts](apps/desktop/src/lib/transcript.ts) and shared with [EventRow](apps/desktop/src/components/chat/EventRow.tsx), since an aborted turn draws no red row and dropping the block there would take the agent's last words off screen.
- **The working indicator is driven by `model_request_started`**, not "this turn has drawn nothing yet", which only ever described the turn's first wait. Three exits clear it, all needed: a `block_start` that is not thinking, `turn_completed`, and any `session_status` off `in_progress` — the last covers interrupt or a dead child. Per-session and nowhere else, since both driving events are unpersisted.
- **Retry takes the indicator over.** `system`/`api_retry` draws its own row with the working one suppressed; the mapper drops `error: "unknown"` on the way in. There is no closing event, so it clears on "`api_retry` is the newest event", gated on `busy`.

**Git.** [git.rs](apps/desktop/src-tauri/src/git.rs) and [github.rs](apps/desktop/src-tauri/src/github.rs) are the only places the app shells out to anything but `claude`. `checkout_branch` validates the name against branches git just listed — injection is not the risk, but a name starting with `-` parses as a flag. It runs when the user picks a branch, not at send, and `dirty` is re-read at pick time.

**`-w` worktrees do not fork from the checked-out branch.** The CLI resolves the repo's default branch, fetches `origin/<it>` and passes that to `git worktree add --no-track -B`, so the fork point is `origin/main` whatever is checked out, and a failed fetch falls back to local `HEAD`. The `-w` flag surface exposes no base ref, hence the composer hides the branch picker in worktree mode and shows the resolved base.

**Models.** [models/models.rs](apps/desktop/src-tauri/src/models/models.rs) name Claude Code's list and **Codex's fallback** one; the frontend build its picker from `list_models`. **Codex's real list is asked of Codex** ([harness/codex/models.rs](apps/desktop/src-tauri/src/harness/codex/models.rs)), so a model OpenAI ship is pickable with no Dray release — the table behind it is what a missing or broken `codex` leave the picker drawing. Haiku has no effort levels — the CLI ignores `--effort` there, so omitting it keeps the persisted value honest.

**The ladder is six rung and `ultra` is per *model*, never per family.** Codex report it on Sol and Terra, stop Luna at `max`, and stop the older generation at `xhigh` — so a family-wide list would put a level on the wire the model refuse. **`ultra` is not a louder `max`**: Codex describe `max` as maximum reasoning *depth* and `ultra` as maximum reasoning **with automatic task delegation**, and offer both on one model. Claude Code's own list stop at `max`; its `ultracode` is a **session boolean** pairing xhigh with dynamic-workflow orchestration, set through `--settings` or `apply_flag_settings`, so it is no rung and belong nowhere in [`Effort`] — see DRA-140, which also carry the finding that `apply_flag_settings` take `effortLevel` and so may retire the effort respawn under _Known issues_.

**A rung is a persisted enum, and `ultra` never reach disk as itself.** An older build reading a level it cannot spell fail that line, and the index parse as one `Vec` — so one `ultra` session read as **no sessions at all** in a release build sharing `~/.dray`. Measured, not feared. `encode_effort`/`decode_effort` in [store.rs](apps/desktop/src-tauri/src/store.rs) are the only two places that know: `ultra` go down as **`max`** — a real level that build can run, one rung below — with the truth beside it in `effortAbove`, which its `unknown` flatten carry back untouched. Decode honour that field **only while `effort` is still `max`**, since an older build rewriting the entry write its own level there and leave the forward field standing; reading it then would put the session back on a level the reader just left. Same bargain `Harness::Other` make, same ordering rule — protection ship *before* the value, never after, which is why the stand-in has to be a level already shipped rather than a new spelling of "unknown".

**`effort_above` is a `String` and must stay one.** Typed as `Effort` it recreate the very bug it fix, one build later: the next rung a newer Dray write there fail *this* build's line and take the index down. A string hold a level nobody here has heard of, so `carries_unreadable_level` **carry it through whole** — stand-in kept runnable, forward field handed back untouched, exactly how `unknown` treat a field it never heard of. It is dropped only when the reader move the effort off the stand-in, since that is them asking for the level they moved to.

**Codex's list is the wire's, with Dray's ids kept.** A row Dray already name keep the table's **id and label** — an index entry hold `gpt56_sol` where the wire say `gpt-5.6-sol`, and minting the wire spelling would leave every running Codex session naming a model the picker no longer list, which read as the composer moving it to the default. Only a model this build never heard of is minted from the wire, id and all. Everything else is the row's own: ladder and image support. **Effort default stay Dray's — Medium**, never the row's `defaultReasoningEffort` (Codex say `low` on its top two today): which model exist is Codex's answer, how hard Dray set one working is Dray's, and a CLI setting must not arrive through the back door of a list read for something else. Reader's own pick override it and persist, as before. **Tier is position** — the first two visible rows are the top level and the cycle, the rest fold into "More models" — since Codex list its newest first, so a new flagship land at the top of the chord the day it ship. Hidden rows (`gpt-reserve`, `codex-auto-review`) are asked for and dropped. The probe is a throwaway app-server ([probe.rs](apps/desktop/src-tauri/src/harness/codex/probe.rs), shared with the skill picker), cached for the life of the process, and an answer this build cannot read fall back to the table rather than to an empty picker. **`nextCursor` is followed**, capped at ten pages — the server take `limit` and refuse a bogus cursor outright, so paging is real and a first page read as the whole list would drop models silently. **A model neither list name is taken as written** — pi's rule, pi's reason: a *discovered* model is one no table here hold, so a restart whose probe fail would otherwise leave a live session's own model unnameable and report "not a Codex model" about a model Dray itself offered. The id **is** the alias, the stand-in carry no ladder (so that spawn omit `--effort`), and a Codex that cannot run it say so in its own words. It must not make everything runnable, so another harness's alias still answer `None` — `find_model` is what ask that, holding both harnesses. Cost, stated: `runs_on` cannot judge a model newer than the build, so `send_msg` ask "did the lookup find it" for Codex instead, and `dray new` read its **alias and its default off the same list** — a model named here that the installed Codex do not list is a create failing at the spawn for a choice nobody made.

**The frontend hold one model list per harness, never one list plus a note saying whose it is** (`modelsByHarness` in [useSessions.ts](apps/desktop/src/hooks/useSessions.ts)). A single list carry the *previous* harness's answer until the next land, which draw Claude's models under pi's mark for the second pi's read spawn a child for; blanking it instead only move the flaw, since every switch then empty the menu for the frame an `invoke` take and the two table-backed harnesses start flickering too. Keyed, a harness already visited answer on the same frame the toggle move — and `setHarness` repair the pick against that entry in the **same commit**, so the trigger never name a model one frame before the fetch correct it. Only a first visit to a harness whose list is a genuine read draw the waiting row, which there is the truth rather than a stutter.

**The fx list on screen follows the pick, never fx's global provider alone** (`fxListFor` in [model.ts](apps/desktop/src/lib/model.ts)). `modelsByHarness.fx` holds what the global provider last answered; what is drawn is the cached list of the provider serving `modelId`, falling to that slot only where no cached list names it. The provider is one setting for the whole machine, so drawn from the slot alone a switch in session A put A's new provider under every other fx session's picker — its thumb, its rows, ⇧⇥'s cycle — and a list landing after the reader had moved on repaired B's model onto A's provider's pick (DRA-254). Hence the landing repair keeps any pick the cache can name a provider for, and a seed with nothing cached still moves the pick off the old provider, or the derived list would keep following it and the switch would read as inert.

**fx's pick is repaired per provider at every seed, and `handleNewSession` is a seed.** `repairFxModel` — `usableFxModel` over the reader's last model per provider (`ade.fxModelPick`) — is what every fx site must use, never `usableModel`, whose fallback for fx is the unset sentinel. The two disagree in the ordinary state after a provider switch: the reload repairs the on-screen pick through the raw setter, so `prefs.modelByHarness.fx` keeps naming the model of the provider *left*, and a seed judging that against the list on screen throws it away. From another fx session the harness has not changed, so no fetch follows to put it back, and the trigger says "Select Model" over a pick the reader made an hour ago.

**Shift+Tab cycle exactly what the picker draw at its top level, and that is one function** — `topLevel` in [starredModels.ts](apps/desktop/src/lib/starredModels.ts), read by both. A chord landing on a model the menu never offered is the bug sharing prevent, and pi had it: the menu drew the reader's shortlist while the chord walked every model every logged-in provider serve. `cycledModels` is the same answer for `App`, reading the stars through `readLocalStorage` **at the press** rather than holding them — a second `useLocalStorage` copy there would drift from the picker's the first time the library dialog wrote one.

Each harness bound that list its own way. pi bound an unbounded *discovered* list by what the reader starred; Claude Code and Codex bound a *written* one by **`secondary`**, which fold a row into the "More models" submenu and out of the cycle together. Claude Code cycle two (Fable 5.1, Opus 5) and keep Fable 5, Sonnet, Haiku below, in that order. The flag decide where a row is **drawn**, never what may be run: a session on a secondary model spawn like any other, and enter the cycle at its start.

**Top-level ids are bare aliases (`opus`) so sessions follow the latest model; a pinned id (`claude-fable-5`) live under `secondary` only.** An alias follow the latest — `fable` resolve to `claude-fable-5-1` today, per the CLI's own alias table — which is what the top level want and exactly what somebody pinning a previous generation ask *not* to happen.

A pinned id is the only way to reach a previous generation, since **the CLI list none**: its own picker say "for other/previous model names, specify with `--model`". Its current list is *served*, not compiled in — the picker build rows from a fetched catalog plus a `tengu-model-error-overrides` config, each row carrying its own `selectable`, which is how a model land in the picker disabled with "update Claude Code to use it". The `initialize` control reply carry that resolved list as `models` (`displayName`, `description`, `supportsEffort`, `supportedEffortLevels`, optional `disabled`), so a Dray release stop being needed the day [commands.rs](apps/desktop/src-tauri/src/harness/claude_code/commands.rs) read that field instead of discarding it. Codex answer the same question through `model/list` on app-server, and **that half is read** — Claude Code's is not, see DRA-137.

## Pull requests

**A session's PR is a tab in the right pane** ([PrPanel](apps/desktop/src/components/PrPanel.tsx)), rendering readiness, checks, comments and the merge action.

**`gh`, not the REST API** — it already holds auth, enterprise host config and token refresh. Cost: the feature is absent where `gh` is missing or logged out, surfaced as one readable line. Resolved through [binpath.rs](apps/desktop/src-tauri/src/binpath.rs), returning `Option` rather than a bare-name fallback.

**A missing `gh` keeps the tab and is drawn as a setup pane, and that reverses the older rule** (DRA-258). Hiding it made the feature invisible on a machine that never had the CLI — the marks fail silently and the handoff row's Create PR only fails inside the agent's turn, so nothing anywhere said that one `brew install` puts pull requests on this screen. **The exception is exactly two states**, `no_cli` and `not_authenticated`: everything else follows the rows, so a *refresh* that failed still draws its sentence under pull requests already on screen while an error with no rows takes the tab away rather than leaving one that can only say "this went wrong".

Without `gh` **every** directory answers `NoCli`, since the first call fails before anything has looked at the checkout — so `prs_for_branch` asks `git::has_github_remote` and answers `NoRemote` where there is none, or a gh-less machine grows a PR tab on every session it has. Any remote counts, and the match is on the URL's **host** — a remote *named* `github.com-mirror` and the host `github.com.example.net` both pass a contains-check over `remote -v`, the trap `is_upload` documents next door. Hand-rolled rather than `url::Url`, which refuses `git@github.com:owner/repo` outright. An enterprise host is not `github.com` and reads as no GitHub remote, costing a prompt to somebody already on a GitHub this app cannot name.

**The pane copies and never runs.** macOS lets no app put text on another's prompt without an Accessibility grant, so the honest pair is the command with a copy on it and a terminal opened at the session's `cwd` to paste into — where a button that ran an install would be Dray deciding what to execute in the reader's shell. The terminal is `OpenInButton` wearing a third hat, `TERMINAL_OPENER`: terminals alone, its own stored pick (`ade.runInTerminal` — the dir opener's holds editors and Finder too), and `Opener` gains `label`/`hint` so a control standing alone in an empty state can name the app on its face instead of in a tooltip. It needs nothing new in Rust, `open -a <terminal> <dir>` being the shape [apps.rs](apps/desktop/src-tauri/src/apps.rs)'s table already promises.

**`binpath`'s `gh` slot is therefore an `RwLock`, not a `OnceLock`** — it is the one cached answer here that caches an *absence* the reader is being asked to fix, and `recheck_gh` throws it away, so an install made on that pane's say-so is found without restarting the app. **A generation rides that**, the issue caches' own bargain: a probe already running when the reader installs `gh` would otherwise finish and publish its miss back over the answer, undoing the recheck with a reading older than it. It still answers its own caller — who asked before the install — and only the cache refuses it. The pane says so when it still finds nothing: a button that redraws the same screen reads as broken, which is the one thing a pane asking for an install cannot look like. The logged-out half has no such answer to give — `gh` has not moved, and only GitHub knows whether the login took — so it re-asks and leans on `loading` for the same promise made quieter.

**One `gh api graphql` carries the whole panel, and avatars are why it is not `gh pr list --json`.** The rollup `gh` hands back has no image on it, and `github.com/<login>.png` **404s for exactly the accounts that matter** — a GitHub App's real login ends in `[bot]` and `gh` strips it.

- **GraphQL fails with 200 and zero exit** (`{"data":null,"errors":[…]}`), so check `errors` before `data`, or "could not resolve repository" reads as a branch having no PR.
- **The rollup is heterogeneous** — `StatusContext` names itself on `context` and reports on `state`; `CheckRun` on `name` / `status`+`conclusion`, image at `checkSuite.app.logoUrl`. Tagged on `__typename` with `#[serde(other)]`. A running check has **null** conclusion where `gh` sent an empty string.
- **Every connection's `nodes` is nullable.** `Option` is load-bearing: a PR with no comments otherwise fails the whole response.
- **One branch can carry several PRs, so the backend answers with a list**, open-first then newest.
- **Inline comments live in `reviewThreads` alone** and join to reviews on `pullRequestReview{id}`. A review's `body` is top-level text only, so an empty envelope holding threads is **kept** — it is the only row naming who left them — while an empty one holding nothing is dropped unless it approves.

**Readiness is three overlapping fields read in one fixed order** ([pr.ts](apps/desktop/src/lib/pr.ts)): `state`, `mergeable`, `mergeStateStatus`. The order is the whole logic — a closed PR's merge state is stale, conflict outranks failing checks, and `UNKNOWN` means GitHub hasn't worked it out rather than no. A pure function with its own tests, not JSX conditionals.

**Polling**: 15s while something is in flight, 60s otherwise, gated on `active`, cached per `cwd + branch` for 30s. Gate on *any open PR on screen*, never *any check running* — a check that hasn't registered yet leaves the rollup empty exactly like a repo with no CI, so the tighter read polls zero times during the only window that matters. `active` is read off the stored **pick**, not `activeTab`, which derives from this hook's own answer.

**A PR appearing means a turn ending, and nothing else could see it**: the tab is hidden exactly while the answer is "no PR", so it could never self-heal. Refetch on the **falling edge of `busy`** in `App`, with the session id riding along in that ref since `busy` is the *selected* session's. Appearance also opens the pane once, through `onOpened` fired inside `load` — only the fetch knows the previous answer, and that is the whole guard. Key-guarded, so a read landing after a session switch cannot pull the pane onto a branch the reader left.

**Every write refetches**, and reaches past the pane: `onChanged` fires `prMarks.refresh`, and unlike every other write there it is **not** key-guarded, since a repo-wide answer is true whether or not the reader is still looking. **A merge that fails is checked against the PR before being reported** — `gh pr merge` can fail with the merge already through, so `merge_pr` re-reads `state` and answers `Ok` only where it comes back `MERGED`.

**No Close, and no `--delete-branch`.** Abandoning a PR happens on GitHub. Delete-branch: a worktree session has that branch checked out, so `git branch -D` refuses it and cleanup fails after the merge already landed.

**Branch name read first, rebuilt only as fallback.** `sessionBranch` takes `observed` (`work_status.branch`, git's HEAD) and it wins wherever the session still has a checkout of its own. Everything else is a **guess made at creation** and never re-read, so a `git checkout` inside the tree leaves both naming the wrong branch and the PR tab fails **closed**. `observed` null is a resting state. **`worktreeRemoved` is the one case `observed` loses** — a relocated session's checkout is shared, so HEAD there never answers "where does this session's work land"; `relocate_session_to_project` sets that flag beside clearing `worktree_name`. One function, and `SessionHeader` takes the result as a **prop**. Sidebar rows still read the guess, deliberately: marks are one `gh` per repo, where a per-row branch read is one `git` spawn per row.

**The hook lives in `App`, not the panel** — the tab row must know whether an open PR exists *before* that tab is shown, so its first read is **not** gated on `active`; only the poll is. The sidebar's mark stands in while the panel's own read is out (`hasPrTab = prTabVisible(…) || (loading && mark)`), and once the read answers the panel's answer governs.

**Sidebar marks** ([usePrMarks](apps/desktop/src/hooks/usePrMarks.ts)) ask `pr_marks` once per **distinct repo** among visible sessions, since `gh` costs better part of a second. `QUERY_MARKS` carries `number headRefName isDraft`, the tip commit's rollup **state**, and `mergeable mergeStateStatus` on the open half for the ready-to-merge notice — nothing else, since a row draws one glyph.

- **`PrChecksState` folds GitHub's five-way `StatusState` into `Running` / `Failing` / `Clear`**, unrecognised words reading as `Clear` — the safe direction. Running is a spinner in the timestamp slot; failing turns the PR glyph red and `prStateLabel` says so too, since red-green is what this palette can least afford to make load-bearing. **Passing draws nothing.** Red only while open or draft. The field is `checks_state`, since `checks` is already the list of individual `PrCheck`. The glyph table is shared with the panel ([PrStateIcon](apps/desktop/src/components/PrStateIcon.tsx)).
- **Matching lives in the frontend** — the backend answers a list, not a map, because which branch a session lands on is the frontend's own rule.

**The marks cache is module-level per repo, fresh 120s, and a failed read changes nothing — no row written, no stamp.** Not writing keeps the last good mark on screen; not stamping stops a failed read re-certifying an answer a write just invalidated. A module `generation` counter is what makes `refreshAfterWrite`'s clear stick, since a read issued before the clear must not put its stale answer back; `inFlight` carries it too, because "a read is running" is not "a read will answer for me". The poll reads only repos holding an open PR, or a directory `gh` can never answer for takes a failing spawn every 30s forever. The archived view asks for no repos and therefore draws no check spinner — a stale glyph is an accepted trade, a stale spinner animates a claim about now.

**Marks and panel tell each other what they learned, signal only — never data** ([prSync.ts](apps/desktop/src/lib/prSync.ts)), since two caches with nothing joining them left a "Ready to merge" card on a panel still saying checks not passing. Marks emit `branchChanged` carrying **repo and branch**; the panel emits `panelRead` and the marks side asks `markDisagrees`, comparing checks *loosely* since neither fold can fill the other. A panel-triggered marks read **echoes nothing back for the branch that triggered it**, or the pair spawn `gh` at each other forever.

## The repo view

**The main column has tabs, and Chat is one of them.** [ViewTabs](apps/desktop/src/components/layout/ViewTabs.tsx); `VIEW_TABS` is set *and* order, so Terminal later is one array entry plus one body plus one shortcut id — accelerators (⌘⌥1 through ⌘⌥4) are named per *view* rather than per slot, since a rebinding names the view and not its position in the row. The bare ⌘ digits belong to the split view's panes. Bodies use `TabBody`, so the transcript **hides, not unmounts** — scroll position, follow pin and highlighted diffs survive the flip. The tab is per session and **not persisted**. The composer is hidden off Chat, safe to unmount because `useDraft`/`useAttachments` are module-level.

The right panel's Changes tab stays and answers a different question: the panel is "what did this turn do", the view is the whole repository.

- **`head_tree` answers `None` for one thing only: not a repository.** A repo with an **unborn** branch answers the **empty tree** instead, the honest baseline there. `null` alone still says two things — "no repo" and "not asked yet" — so `useHeadTree` carries `settled` and the empty state waits on it.
- **The uncommitted list is the HEAD tree against a live snapshot** (`changes_since(cwd, headTree, None)`). A commit moves HEAD → a new tree id → the cache key rolls onto the new baseline by itself. **Nothing invalidates anything.**
- **Commit SHAs pass `is_tree_id` and every diff path takes them unchanged** (≤64 hex), so a commit's own diff is `useChanges(cwd, commit.parent ?? EMPTY_TREE, commit.sha)`. A root commit's parent is `None` and `EMPTY_TREE` (`4b825dc…`) stands in, so the first commit in history opens like any other.
- **The selected file is derived, never stored** (`find(path) ?? files[0]`), so a file that stops being changed can't leave the pane pointing at nothing.

**The view reads, never writes — and that is not "not yet".** The conversation next door is where work gets made and committed, so a second place to write commits is a second way to do what the reader is already asking the agent for. No checkbox, no message box, no push button, no discard.

## The files view

**A fourth tab beside Chat, Diff and Browser, and it reads for the same reason the repo view does.** A tree down one side, an editor's tab strip and a code pane down the other. No editing: the Docs panel edits markdown because a doc is the *reader's*, where code is the agent's and this view's whole promise is that it changes nothing. Design and what was left out are in [FILES-PLAN.md](apps/desktop/FILES-PLAN.md).

**Two commands and one generalisation.** `list_dir` and `read_file` join `files.rs` beside the `@` picker's index, and `watch_docs` takes a **scope**.

- **Order is VS Code's** — directories first, then case-insensitive by name. `.git`, `.svn`, `.hg`, `.DS_Store` and `Thumbs.db` are dropped, which is VS Code's `files.exclude` defaults and nothing else: `node_modules` and `target` list like any directory, **dimmed rather than hidden**, since a tree that hides what is on disk is lying about it.
- **`ignored` is `git check-ignore --stdin -z`, one spawn per listing.** Nested `.gitignore`s, `info/exclude` and the user's global ignore in one answer, which the `ignore` crate already in the lock file cannot give. Exit 1 means "none of them" and is an answer; only a non-repository or a git that will not run leaves every flag down. **The input is written from its own task** — git streams its answer as it reads, so filling both pipes before draining stdout is a deadlock on a big enough directory.
- **`isDir` is read off the link's *target*.** A symlinked directory expands like any other; a broken link lists as a file rather than as a folder that answers nothing.
- **`read_file` is `read_doc`'s three checks at a 4MB cap**, with images answered first as a `data:` URL — the asset protocol is scoped to the attachments directory and stays so, so a file anywhere else has no URL the webview can fetch. The cap is four times the doc panel's because a lockfile is the file most likely opened here and the renderer already goes plain text past 100KB, so a big one costs scrolling, not freezing. SVG is an image here though `attachments.rs`'s table calls it a file: that table is the *model's*, and the API refusing an SVG says nothing about a webview.
- **`watch_docs` takes a scope and `WATCH` is a map.** The Docs panel passes `"docs"` and this view `"files"`. Without it the two silently take each other's watch away on every open, since the command replaces a scope's set outright; `doc_changed` stays shared, each listener already filtering on its own open set. It is also now **`#[tauri::command(async)]` over a synchronous body**: a plain command runs on the **main thread**, and this one builds an FSEvents watcher and drops the scope's previous one, a drop that joins that watcher's thread. Re-arming is every session switch since this view arrived, so the freeze it bought was one met while doing nothing unusual.

**`useOpenFiles` is `useDocs` without the draft half** — per session, module-level, `useSyncExternalStore`d, in memory only. The `opened` counter is what `App` flips the view on, for the docs panel's reason: reopening a file already on screen leaves the list unchanged, so only a count of clicks can say the reader asked. **`reveal` is a second counter and it is not redundant** — `line` alone cannot scroll, since clicking one link twice asks to be taken back to a line the pane is already sitting on.

- **The store speaks absolute paths, the tree relative ones.** A chat link can open a file from outside `cwd` entirely; the tree stays rooted at the session's directory and the header draws an outside file's path whole.
- **Reads adopt the file silently, always.** Nothing is compared and nothing can be lost, because nothing here edits — so an agent rewriting what the reader is looking at should move the text under them. `doc_changed`, the turn ending and the header's refresh all land in one function.

**The tree relists on the turn ending, and nothing polls.** Every *expanded* directory, one `list_dir` each, gated on the view being the one on screen. Expanding caches until that relist, so collapsing and reopening is free. **Rows are `flattenTree`'s flat list** ([fileTree.ts](apps/desktop/src/lib/fileTree.ts), pure and tested) because the keyboard works on a list: ↑/↓ are one step through an array where a nested render would have to walk a shape the DOM only implies.

**Every row is `memo`ized and the click handler is one stable function, and that pair is load-bearing.** This view re-renders on every session event — a streaming turn is one per delta — so a tree with a few hundred rows open otherwise reconciles all of them at the speed an agent types, which is how a view that only *reads* manages to freeze the window. An inline arrow per row defeats the memo entirely, so `activate` is a `useCallback` and `FilesView`'s `openRelative` above it is too. Both change only when the reader expands something or a relist lands, which is when the rows have to be reconciled anyway. **The cursor takes real focus with it**, which is what makes Enter honest — every row is a button, so the browser activates the focused one, and a cursor drawn beside a focus that stayed behind would open whichever row was clicked last. Enter is therefore **absent** from the key handler: handling it there too toggles a directory open and shut in one press. Not virtualised, deliberately — a tree that large is the reader's own doing and the Diff view's list draws the same way.

**The filter box is the `@` picker's index, so it is already built and already watched.** An empty box draws the **tree**, never a ranked list of everything — that is what an empty filter means here. The tree is **hidden, not unmounted**, while a query is up: the expanded set is what the reader built and clearing the box has to give it back. Escape clears and puts focus back on the tree **next frame**, since the tree is `display: none` until the clear commits and focusing that does nothing at all, silently.

**Two tabs with one basename get their parent appended** (`index.ts — changes`), computed in `tabLabels` over the whole list — a name only stops being unambiguous when a second file arrives, and the tab that has to change is the one already on screen. Closing the active tab activates its left-hand neighbour, or the right-hand one at the start. ⌘⇧←/→ step the strip, `skipInTextField` for the filter box; ⌘W closes the active tab, through `tab.close` in `App` rather than a binding here — see _Closing with ⌘W_.

**The viewer is `CodeView`'s `File`, full height, inside the library's `Virtualizer`.** Same shared Shiki, same worker pool, same `useHighlighter` gate with a plain `<pre>` meanwhile. The `Virtualizer` is the scroll container and its presence alone is what makes `File` a `VirtualizedFile` (`useFileInstance` reads the context), so only the rows in and around the viewport exist — measured on an 8452-line lockfile in Safari, 400 rows in the DOM against 16904, and a tab switch painting in ~56ms where it took 480–900ms (DRA-238). `overflow: "scroll"` is load-bearing there: it is the library's uniform-row path, nothing measured per line, and the default 20px metric is exactly the `--diffs-line-height` its rows draw at — set that variable anywhere and `metrics.lineHeight` must follow. **A line a link named may not be in the DOM yet**, so the mark scrolls the pane through `getLinePosition` when its row is absent, and the post-render that follows marks it; the plain `scrollIntoView` still serves a row already drawn. **The line a link named is marked through `onPostRender` plus `unsafeCSS`** — `[data-line-index="line-1"]` inside the host's shadow root, scrolled to centre once and given `data-target`, painted from the library's own `unsafe` layer the way `DiffPane` overrides its gutter. Zero-based on the wire, one-based to the reader; a line past the end marks nothing, which is the right answer for a stale reference.

**A chat link no longer leaves the app.** `openPath` sends markdown to the Docs panel and everything else here; **⌘-click is what still reaches the reader's own editor**, line and all — the same "out there, not here" the issue rows and the link dialog already mean by it. `ChangesView`'s file rows are left alone: a diff and a file are different answers.

**One row, not two: the Open button rides the tab strip and there is no filename header.** The tabs already name the file, so a header under them said it twice — the reading the Docs panel's chip strip takes. **A tab carries no `title` either**: the full path on one drew a native tooltip, which is the app's own rule broken (chrome is a real tooltip or nothing) and read as a directory hanging off the cursor on a tab the reader was passing over. `tabLabels` appends the parent where a basename stops being unambiguous, which was the only moment the rest of the path was worth saying. The close cross keeps a real tooltip, and names ⌘W on the **active** tab alone — the chord closes whichever tab is active, so a background cross naming it would promise a key that closes a different file. **The button is `OpenInButton` wearing a second hat.** The split button the right panel hands a *directory* to now takes an [`Opener`](apps/desktop/src/lib/openWith.ts) — the key a pick is stored under, which apps are listed, which one stands in for a missing pick, and what opening even *means*. Directory and file differ on all four, and Finder most of all: it **reveals** a file and opens a directory. One control for both, or the reader would have two places to say which editor they use and they would disagree — and the file half has to resolve exactly as `openFile` does, or the button names one app while a ⌘-click in the transcript reaches another.

**The list's side and width are the reader's, in local storage** (`ade.filesListSide`, `ade.filesListWidth`). **It opens on the right**, against every other list in the app: the sidebar already holds the left edge, so a tree there puts two lists back to back with the code squeezed between them. The switch is one icon button beside the filter; the width is a drag handle, the first in the app, and it **writes on pointerup alone** — the value moves on every frame and only the last one is a preference. `setPointerCapture` is load-bearing: without it the pointer leaves the strip on the first frame and every move after that is delivered to the code pane.

## Spaces

**Membership is a tag on the project and that is the whole record** — `Project.space` in [projects.rs](apps/desktop/src-tauri/src/projects.rs), no spaces file, no id, no ordering. `#[serde(default)]` is load-bearing: the projects file is rewritten whole, so an entry written before the field existed failing to parse is *every* project gone.

**A space nobody has filled yet has nowhere to live in `projects.json`, so existence is a union.** A made space is declared in local storage (`SPACE_LIST_KEY`) and `spaceNames` reads the two together — the reader's list plus every name a project carries. A tag whose name was never declared still counts, or a project filed on another machine would read as filed nowhere. Rename writes both halves and the reader's own pick; remove takes the name out of the list and clears the tag from its projects, which is why it asks first. **Projects and sessions are untouched either way** — a space is a way of looking at them, so losing one costs the view and never the work.

**Switching space narrows what is drawn and nothing else.** Every session in every space keeps running; one finishing elsewhere simply says nothing until the reader comes back. The rules are [space.ts](apps/desktop/src/lib/space.ts), pure and tested, and the narrowing lands in **one place** — `visibleSessions` in [App.tsx](apps/desktop/src/App.tsx), which is what the sidebar draws, what ⌘⇧↑/↓ walks and what the PR marks and the ready notice read — so a hidden session cannot come back through a side door.

**What is *on screen* is reconciled by one effect, never at the switch.** The sidebar filters itself, but the composer's project and the open transcript do not — and switching is only one of the ways a session leaves the space it was in: filing a project elsewhere, detaching it, or a stale notification opening a session move the same boundary. So `App` states the invariant once — what is showing must be in the space — rather than listing the ways it stops being, each of which was its own bug. The project is judged first and independently, since **a space holding nothing is ordinary** and a stale pick still sends: the picker draws "Attach project" while `send_msg` runs happily in the project the reader walked away from, hence `handleSelectProject(null)`. A session whose project neither the index nor the loaded snapshot can name is **left alone** — that is "cannot tell", not "elsewhere". It is a `useLayoutEffect`: an ordinary one runs after paint, so a switch drew one frame of the transcript being switched away from, which is nothing to the reader and everything to the room watching them share the screen. Notices are the one thing dropped at the switch itself, since a card raised a moment earlier opens a transcript the reader just put away — and they are dropped by the *announce* rule, not the screen one.

**Rename and remove are one Rust call, `retag_space`.** The declared list and the tags are two records of one fact, so a loop of per-project writes with the list updated up front left half-renamed tags beside a list claiming otherwise. One read, one edit, one write under the lock; the local record follows only once it lands. Retagging a space no project carries writes **nothing** — that is the ordinary path for renaming one nobody has filled.

**Notifications answer to the space; the dock badge does not.** `announce` drops both channels for a session filed elsewhere, since both name the session out loud and a personal one named over a shared screen is what spaces exist to stop. The badge counts every session deliberately: it names nothing, and a number that lies about work waiting is worse than one that admits another space exists.

**Every card asks `canAnnounce` first, not just `announce`.** The two worktree notices are raised outside it, land after an `await`, and carry the session's **title** — so the reader can be in another space by the time one arrives. The dialog route beside them is deliberately unguarded: the reader pressed a button and is owed its answer. `usePrReady` needs no guard, reading `visibleSessions`, which is already narrowed.

**A session that cannot be attributed is refused while a space is up**, not let through — `allowedInSpace`, shared by `announce` and by the notice sweep, since a card and a banner say the same sentence out loud. The index holds one side of the archived split at a time and a new session's entry lands after its first events, so "not in the index" is not "not filed elsewhere"; the loaded snapshot is the only other place a `projectPath` can come from. Cost, stated: a settled session in the *active* space stays quiet while the reader is on the live list. **The opposite direction governs the screen**, above — refusing to announce costs a notice, refusing to draw costs a transcript already open.

**The active space is read at the event, never held.** `announce` runs from a listener registered once, so a captured copy would be the space the app launched in for the rest of the run — hence `SPACE_KEY` and `readLocalStorage`, the same bargain `cycledModels` makes with the starred list.

**Switching takes the screen with it**: the project filter resets, the composer moves to a project the new space holds, and a transcript from outside it is closed. Each only where it actually falls outside — a space holding both changes nothing but the list.

**The switcher sits in the sidebar's titlebar strip and is drawn whether or not a space exists** — it is the one place in the app that says spaces are a thing, and a control appearing only once you have found the setting can only be found by someone who did not need it. Its **New space** item opens Settings' Spaces tab with the field already up rather than growing a second way to make one.

**That tab is two lists, and the split is what each is for**: the projects list files a project into a space it already has, and the spaces list is where one is made, renamed or removed. Creating from inside a project's picker put the one thing that changes every other row inside the row least likely to be opened. The projects list draws **every** project whatever space is up — narrowed by the active space it would hide exactly the rows somebody opens it to move.

## Issues

**The surface says "issue", the implementation says Linear.** Vocabulary in [issues/issues.rs](apps/desktop/src-tauri/src/issues/issues.rs), wire in [linear.rs](apps/desktop/src-tauri/src/issues/linear.rs). A second tracker is a module plus a variant on `IssueTracker`, which is why `IssueRef` carries a tracker while there is only one. The connection is workspace-wide — no project ↔ team mapping. **Every user-facing string is collected in [COPY-ISSUES.md](apps/desktop/COPY-ISSUES.md)**; reword there and here together.

### Credentials

**The key lives in `~/.dray/credentials.json` at `0600`, the account cache in `settings.json`.** Read together: credentials say whether a key exists, settings say whose it is, and a cached account with no key behind it reads as **disconnected** — the key *is* the connection.

- **Own file, not a field on `settings.json`**, for two reasons that both bite: settings are rewritten by every toggle and read on a launch path where a parse failure falls back to defaults, which would silently *forget* the key; and `get_settings` hands that struct to the frontend, which a credential must never ride along with.
- **Mode rides the *create*, on the temp file** — not set after the write, not on the final file after the rename. `fs::write` creates at the process umask, so every other order leaves a window where the key is world-readable, where `OpenOptions::mode` plus `create_new` leaves none. Pinned by test; the failure is otherwise silent.
- Keychain was tried and retreated from — macOS ties the grant to the exact binary, so every rebuild is a new authorization dialog. Cost: the key is readable by anything running as the user, in a directory that is `0700` and already holds every transcript.
- **Validated before saved**, and `verify` also answers identity. **A write to either side forgets every cached issue** (`forgetIssues()`), since every cached answer was read with the old key — the `not_connected` failure the empty state is drawn from included.

### Tags and links

**A tag carries the title itself** — `#DRA-53 Add issue tracker integration`, everywhere: picked from the composer's `#` menu, typed by hand, or appended by the CLI's `--issue` (`tag_text` in Rust, `issueTag` in [issue.ts](apps/desktop/src/lib/issue.ts), pinned both sides). The title being *in the text* is what makes the feature cheap, and it is what the composer's issue chip draws on its face. Descriptions are not injected: the agent has the tracker's own MCP server and can fetch what it wants, where a pasted description is stale the moment somebody edits the issue.

- **Resolution is best effort, always.** Unreachable Linear, a revoked key, an identifier that doesn't exist — all leave the tag as text, record no link, say nothing. A send must never fail because the tracker is down.
- **Best effort stops short of losing a named issue.** A tag the reader typed is already in the prompt; one arriving through `--issue` is not, and dropping it left the model with no mention of the work at all while **answering identically to success**. So a named issue that resolves to nothing is appended bare (`#DRA-53`) and linked bare.
- **A tag clicked in a prompt opens the issues page**, through a module slot ([`setIssueOpener`](apps/desktop/src/lib/issue.ts)) the way a transcript link reaches the browser. ⌘-click leaves for the tracker instead — the same thing the modifier means on an issue row and on a file link. `App` holds the picked issue as an `IssueRef` rather than a full `Issue` for this: a tag carries one of those and nothing more.
- **A tag in prose is a mention, and a mention links nothing.** `ExpandedTags` answers two lists: `mentioned` (rides `user_message`, so the tag draws as a button) and `linked` (written onto the session). Only a caller naming an issue outright — `dray new --issue`, `dray issue link` — puts anything in the second. Every `#DRA-53` used to link, so "this is unrelated to #DRA-53" filed the session under DRA-53 forever.
- **One tagging rule per side of the bridge.** Everything the app sends tags in prompt *text*, so `send_msg` always passes an empty issue list; the CLI's `--issue` names them outright. Both merge inside `expand_tags`.
- **Send answers with links as written, every path** — created, live, queued, resumed — as a whole list, not a delta, since re-tagging *replaces* an entry. Without it the Issue tab draws old links until reselect or restart.
- **Tag shape is stated twice and tested twice.** Rust `issue_tags`/`parse_identifier` decide what gets *linked*; [issue.ts](apps/desktop/src/lib/issue.ts)'s `parseIdentifier`/`highlightSegments` decide what gets *painted*, and neither can call the other. Rule: team key plus number, `#` must open a word, bracketing punctuation counts as opening it. `#fff` and markdown headings stay prose, both directions pinned.
- **A link is a copy, not a pointer.** `IssueRef` holds identifier, title, url and tracker id, so the sidebar and prompt need no network call. It goes stale, which is the right way round; re-tagging **replaces** the entry rather than appending.
- **Link and unlink match on tracker id *or* identifier, within a tracker** — a resolved link carries Linear's UUID, a blind one carries the identifier itself. **Detail is read by UUID first, identifier as fallback**, since identifiers are not stable across a team move; not the other way round, because the identifier is the *only* thing a blind link carries (`is_stable_id`).
- **A fork inherits links; a relayed message carries none.**

**`dray issue link` writes down what it is given and asks the tracker nothing.** A link is a local record, so needing reachable Linear and a stored key meant it could fail for reasons unrelated to what it records — and the caller is an agent that just read the issue through the tracker's MCP, so it already holds the title and url. Hence `IssueInput { identifier, title?, url? }` and `--title`/`--url`. Absent metadata is ordinary. **Several identifiers plus `--title`/`--url` is a refusal**, since one title applied to all is a wrong link that reads exactly like a right one.

**The session id is optional, and `$DRAY_SESSION_ID` is why.** Claude Code's Bash guard refuses any command naming an env var inside a worktree-isolated session, **silently** — the agent reads the refusal, carries on, and the issue is never linked. So the CLI resolves the session itself off `parent_session_id()` and the documented call carries no `$` at all. Shape tells a session from an issue (uuid vs letter-leading team key), so positionals are **one `Vec`** split in one function — clap refuses a non-required positional above a required one. The old `<session> <ISSUE>...` form still parses and must, since it shipped.

### Reading Linear

**The panel reads Linear's API with the stored key. MCP is nowhere near it.** Two channels answering two questions: the key fills *this app's* screens, MCP lets the *agent* read the same issue in its own turn. That is why the connect form says MCP out loud, once. A live `claude mcp list` check existed in the panel and was removed — readers open that panel to read the issue, not audit their tooling.

**Caching** ([issue.ts](apps/desktop/src/lib/issue.ts)). Lists are cached module-level on the whole query, capped at 12, 60s freshness; opened issues separately by identifier, capped at 24. A failed read changes nothing. One **generation counter** over every issue cache, bumped whenever the answer to "who are we, what may we read" changes; a read that started under an older generation is refused rather than written, since the damaging half is not a stale row but a **stamp** that suppresses the read which would correct it. `useSyncExternalStore`d, so a hook holding an answer read under an old key re-reads. Refresh **forgets then bumps** — bumping alone must never gate the cache, or every later visit refetches for the rest of the session. Cached answers are picked **during render**, not in an effect, or one frame of the previous issue's description sits under the new issue's title. A cache short-circuit must clear `loading` itself, since a cancelled read never reaches its own `finally`.

**The composer's `#` picker reads that same cache, and the sharing is what makes it quick.** It asks the question the issues page opens with — `assigned`, unsettled — so a second `#` inside the freshness window opens with no round trip at all. Two rules hold it together. **It reads to `ISSUE_LIST_LIMIT`, not to the 25 rows it draws**, since the key is the *query* and carries no depth: a shallower read would file a truncated answer under the key the page paints from, so the cap is applied at the `slice` and nowhere else. And **a keystroke paints before it reads** — `filterIssues` narrows the cached assigned list locally so the menu moves on the frame the character lands in, with the server's answer replacing it when it arrives. That local match is deliberately weaker than Linear's, which reads descriptions too, so it is only ever allowed to under-match: a row it misses appears a moment late rather than going missing.

**A cold `#` draws placeholder rows rather than nothing**, since with no cache and no index there is a round trip between the keypress and the first row — the state the other two pickers never sit in. `PickerMenu` takes `loading` and reads it **only where it holds no rows**: a list already painted from cache is what the reader wants, not placeholders over it. The composer's key block follows the **rows** rather than the menu being drawn — `% rowCount` is a division by zero on an empty list, and Enter would otherwise be swallowed by a pick that can only land on nothing, so Enter sends while placeholders are up. The empty state's "Press ⏎ to send" legend still follows the **menu**, and deliberately: the legend would be true there, but a send hint under an open picker reads as belonging to the list.

### Uploads

Linear puts uploads *in* the description's markdown, pointing at `uploads.linear.app`, so there is no attachment list to build — override `img` and `a` on that one `Markdown` and leave every other link alone. They sit behind the same auth the API does, so the webview cannot fetch them: `<img src>` resolves to 401 and the browser draws its own broken box. `fetch_issue_asset` puts the key on that request and hands back a `data:` URL.

- **Host checked exactly, and scheme with it.** A description is text somebody else wrote and it names the URL this fetch is handed, so without the check an issue could name any host and have the app post the credential to it. Compared on **parsed host**, never a prefix — `uploads.linear.app.evil.test` passes `starts_with`. Wrong scheme is rejected, not upgraded. Stated twice (Rust `is_upload` decides where the key goes, [IssuePanel](apps/desktop/src/components/IssuePanel.tsx) what is drawn as an asset), pinned on the Rust side.
- **Size capped before the body is read, and the body streamed to that cap.** `content_length` is a courtesy — a server may send none or lie — and `.bytes()` drains the whole body first, so the chunk loop is what actually enforces the cap.

### The issues page

**A sidebar row under New task, a main-column view — not a session.** Opening it **keeps selection** but drops the sidebar *highlight*, since a lit row would name a session nowhere on screen. The page hides rather than unmounts, so filters and scroll survive the trip. The row is drawn whether or not a tracker is connected: the page's empty state is where connecting is offered, and disconnect lives in settings, whose row only draws when something is connected.

- **The right pane is hidden while the page is up, and the preference kept**: `panelShown = panelOpen && !issuesOpen`. Everything that draws or reads reads `panelShown`; `panelOpen` stays the standing preference.
- **`SessionHeader` takes `standIn`** and `App` passes `"Issues"`, or the header sits at "New session" over a list of issues.
- **Clicking a row opens it in the pane beside the list**, off the same key the list was read with, in the same `RightPanel` frame. The picked issue is held as a whole row, not an identifier, so the pane is complete before its own detail read lands. `useSessionIssues` serves both, since a page pick is a one-element link list.
- **Every route to a session goes through `goToSession`**, which closes the page then navigates. Two buttons closed the page and the chords beside them did not, which made ⌘N and ⌘⇧↑/↓ read as inert.
- **⌘E only ever closes there**, and the guard lives on the chord, not only in `handleTogglePanel` — ⌘E binds **raw** `togglePanel`, so a guard in that function alone lets the chord sail past into a pane not on screen. Same for ⌘⌥1/⌘⌥2.
- **Panel tab `issue`, hidden with no link.** Rows are drawn from the session's own `IssueRef`s, so the tab exists the moment something links one. **Linking is the agent's**, through `dray issue link`. The description is drawn here where the PR panel leaves the PR body out, and the difference is who wrote it.
- **No Start button** — it would create a session, so it must name a project, and the page is workspace-wide. Tagging with `#` in the composer already starts work against an issue from a place that knows the project.

**Dray writes exactly two fields, and only from the opened issue's header** — status and priority, through `update_issue` over Linear's `issueUpdate`. Nothing else: no comment, no attachment, no assignee, no label. **The `dray` CLI writes nothing at all**, and [SKILL.md](apps/cli/skill/SKILL.md) says so out loud, because an agent assuming otherwise tells the user their issue moved when nothing of the sort happened.

The two menus live on `IssueRow`'s header in [IssuePanel](apps/desktop/src/components/IssuePanel.tsx), so the session's Issue tab and the Issues page get them from one component. **A status menu is drawn from `IssueDetail.states`, the issue's own *team* workflow, which rides the read the panel already makes** — a menu that has to fetch before it can open is a menu that opens empty. Sorted by kind and *then* `position`: Linear only makes position meaningful within one state type, so a single sort on it lists Done above Todo. No states means no menu, just the glyph.

**`None` means leave it and `Some(None)` means clear it**, which is why priority crosses as `Option<IssuePriority>` rather than a number — "no priority" is a level a reader can pick and it goes down the wire as `0`. **`issueUpdate` answers `success: false` at 200 with no `errors`** for a write it understood and refused, so that field is checked; without it the panel re-reads, finds nothing moved, and silently redraws what was already there. The mutation's own `issue` echo is deliberately unread — the panel draws a whole `IssueDetail`, and asking for that field set back would be a fourth copy of it in `linear.rs`.

**A write is the one moment every cached answer about issues stops being true**, so `update` calls `forgetIssues()` and then puts the freshly-read detail back — *after* the generation bump, or the guard that makes the clearing stick refuses it. `useIssueList` subscribes to that generation for the same reason: without it the row beside the panel keeps saying "Backlog" under a heading the issue has just left. Failure reports through the panel's existing banner; nothing is optimistic.

**⌘-click on an issue row opens it in the tracker**, on the panel's rows and the page's list alike — the same modifier the transcript's link dialog uses to mean "out there, not here". A shortcut, not the affordance: the row's own button is that.

## Opening the working directory

**A split button in the right panel's tab row** ([OpenInButton](apps/desktop/src/components/OpenInButton.tsx)) hands the session's `cwd` to an installed app; the left half opens in the app picked last, the chevron changes it. Detection is [apps.rs](apps/desktop/src-tauri/src/apps.rs), macOS only — everything else answers an empty list. It sits in the tab row because the directory belongs to the *session*, not to one tab's answer about it.

- **Detection is `read_dir` over known dirs, matched on bundle file name exactly.** `/Applications`, `/Applications/Utilities`, `/Applications/Setapp`, `/System/Applications`, `/System/Applications/Utilities`, `~/Applications`; first dir wins, so a machine-wide install outranks a user's copy. **Exact, never substring** — `Cloudflare WARP.app` is not `Warp.app`, and a contains-check lists it as a terminal that then ignores the directory handed to it. `resolve` is split from `detect` so order is testable with nothing spawned.
- **The table is the guarantee, not `CFBundleDocumentTypes`.** `open -a` names the app outright rather than asking Launch Services to rank a handler, so it reaches apps declaring nothing — MacVim declares no folder type and opens one fine.
- **Address is the bundle path, never the bundle id.** `open -b` hands the id to Launch Services, which picks whichever copy it indexed. Names are no good either, since two builds of one editor differ by path alone.
- **Finder is the file default, and it *reveals*.** Every failure lands there too, so the worst a click does is what the link did before the setting existed. `pickFileOpener` therefore falls back to Finder, not the first editor — a transcript row has nowhere to put an error sentence, so a failure must be a working link.

### File links

**Three surfaces, one component.** [FileLink](apps/desktop/src/components/chat/FileLink.tsx) draws a tool row's filename, the reader's own `@mention`, and an absolute path an agent wrote into a sentence. The last is drawn the way the mention is — `@name:12` in mention colour, full path on the tooltip (`FilePathSpan` in [Markdown.tsx](apps/desktop/src/components/chat/Markdown.tsx)) — where a link the agent *wrote* as `[label](/path)` keeps its label and Streamdown's anchor look. It is a span with `role="link"`, never a button or anchor, because the tool row's copy sits *inside* the row's expand button — a second interactive element there is invalid markup and a click toggles the row instead. `stopPropagation` on click **and** on key.

**Mentions resolve against the session cwd**, joined in [filePath.ts](apps/desktop/src/lib/filePath.ts) onto [ChatCwdContext](apps/desktop/src/hooks/useChatCwd.ts)'s value — context, not a prop, since the only reader is four components below `Chat`. No cwd means the mention stays inert coloured text; resolving against wherever the app happens to run opens the *wrong* file. **A fork records the parent's cwd on every copied prompt** for the same reason — a fork carries the conversation into a *different* tree. `repoint_events` sets `user_message.cwd` with `get_or_insert`, not a plain set, so a fork of a fork keeps the *first* ancestor to record one.

**Paths in prose are a rehype pass, after sanitize and before harden** (`rehypeFilePaths` in [markdownPlugins.ts](apps/desktop/src/lib/markdownPlugins.ts)). After sanitize or it strips what the pass adds; before harden or the href is already rewritten. **Second plugin list, not a flag** — an issue description or PR comment names paths from somebody else's checkout, so `linkFilePaths` is on `AssistantMessage` alone.

- **Relative paths are marked too, as written, and resolved in `FilePathSpan` against the chat session's cwd** — the pass has no working directory, and resolving against wherever the app runs opens the wrong file. Same `findPromptPaths` the bubble reads, so the two surfaces link the same words; no cwd leaves the run inert mention-coloured text, a mention's own resting state.
- **A markdown link whose href names a file, absolute or relative, is *converted*, not descended into** (`anchorToFile`), keeping the anchor's children, and checked **before** `NOT_PROSE` — a link that is not converted is left whole, so a path inside a real link's label stays plain rather than nesting two links.

**The match rule is written to under-match** ([findFilePaths](apps/desktop/src/lib/filePath.ts)). A path must *open* a word, hold two segments, and carry no `//` — the letter-then-slash rule keeps `https://host/a/b` and `and/or` out, the two-segment rule keeps `/compact` out. `pre` and `a` are skipped in the walk. Nothing asks whether the file exists, so an over-match costs a dead click, not an error.

- **A path holding a space is dropped, not halved** — a half is a *real* path that can exist and open the wrong directory. The read runs forward to **end of line**, not one word.
- **"Whitespace" is the same set on both sides**: the match stops on `\s`, the forward read resumes on `[^\S\r\n]`, so tabs and non-breaking spaces break a path exactly as spaces do (`&nbsp;` in agent HTML is ordinary input).
- **Trailing `:12`, `:12:5`, `:L12`, `#L12` are stripped from the *path* before it is judged, and kept on the *match*.** The app's own harness prompt asks for `file_path:line_number`, so the whole reference is one link — a link stopping at the filename with `:12` dangling beside it in plain text read as half-converted (DRA-180). After punctuation stripping, before `isFilePath`, so `/a:12` is still refused rather than conjured into a path. The line rides `FilePathMatch.line` → `Segment.line` / `data-line` → `FileLink` → `openFile`, where `lineUrl` in [openWith.ts](apps/desktop/src/lib/openWith.ts) asks a known editor through its own URL scheme (`open -a <bundle> -- vscode://file/…:12`, verified against Cursor). An editor with no known scheme opens the file as before; Finder reveals and a line means nothing there.
- **The word straight after a break decides it wherever it can**: one holding a slash means the match was a truncation, one *opening* with a slash is a path of its own. Only past that word does the shape of the match matter — a match whose last segment holds a dot stops reading at one word, one without reads to end of line. The dot is a **guess**, so it only ever stops the read early, never accepts a match outright.

## Transcription

**Dictation is local, and the engine is somebody else's.** [transcribe-cpp](https://crates.io/crates/transcribe-cpp) run the GGUF model, `cpal` capture, `rubato` resample. **The engine is not Handy** and the two must not be credited as one thing: `transcribe-cpp`/`transcribe-cpp-sys` live at `handy-computer/transcribe.cpp` under their own notice (`Copyright (c) 2026 The transcribe.cpp authors`), where the [Handy](https://github.com/cjpais/Handy) app is `cjpais/Handy` under `Copyright (c) 2025 CJ Pais`. Two entries in [THIRD-PARTY-LICENSES.md](THIRD-PARTY-LICENSES.md), and a claim that one notice covers both name the wrong holder. **The only Handy files in this tree are the two dictation sounds.** Nothing tracks Handy releases because nothing is vendored from it; the engine update through Cargo like any dep. Handy's *app* code deliberately not taken: global hotkey, text injection, tray, history — Dray own the composer, so the words have nowhere to travel.

**No model ship with the app, and first press download nothing.** Weight is 218MB–886MB; pulling that on a press meant to start talking = not a thing to do to somebody. `start_transcription` answer `false` where no model ready, `stop_transcription` answer `NeedsModel`, and frontend open Settings on the Transcription tab. That the whole first-run flow.

**Backend is a *build-time* choice.** `Cargo.toml` turn `metal` on under `cfg(target_os = "macos")` and off elsewhere, so `Backend::Auto` resolve to GPU on Apple Silicon and CPU everywhere else. Nothing at runtime can change it — why there is no accelerator setting. **cmake is now a build dependency**; `transcribe-cpp` drive it through the `cmake` crate.

**Weights come from HuggingFace, pinned to a revision.** [catalog.rs](apps/desktop/src-tauri/src/transcription/catalog.rs) = the list, compiled in. Not `blob.handy.computer`, which is Handy's own CDN — same files, but their bandwidth is not ours to spend. `resolve/<revision>`, never `resolve/main`, or the bytes move out from under the `sha256` and every download fail verification at once. Catalog change = manual edit; nothing tell us when a better model land.

**Recommendation read the arch, where Handy's is editorial.** Their `recommended_rank` is a static catalog field and nothing there probe hardware. `recommended()` answer Parakeet Unified EN on Apple Silicon and Canary 180M elsewhere. Suggestion only — every model stay selectable.

- **Installed = present at the catalog's exact size.** Hash is checked once, before a fresh download is renamed into place, never on the settings read — hashing 700MB every open is felt. A truncated GGUF **load far enough to produce garbage** rather than erroring, which is the failure the size check exist for.
- **Download land via `.part` + rename**, so the real path only ever hold a file that already passed verification. A killed process leave a `.part` and nothing [`is_installed`] would believe.
- **Progress is an event, not a return value** — a download outlive the dialog that started it, so closing settings must not cancel it and reopening must find it running. Emitted every ~4MB; one event per chunk = thousands of round trips for a bar that redraw at screen resolution.
- **The loaded `Session` is cached across dictations** and dropped on model switch or delete. Loading is seconds; a session dropped per recording put that on every press. `Session` is owned and `Send` (hold `Arc<ModelInner>`), so it cache directly with no self-referential struct.
- **The load start on the press and the model leave after ten idle minutes.** `warm_selected` run from `start_transcription` alone — the reader talk for the whole load, so it usually land before they press stop. It used to run at launch and on every model change too, which kept 731MB of Parakeet resident for a reader who never dictated (measured: the main process sat at 819MB). `Engine::touch` on every warm and transcribe bump a use counter and spawn a sleeper for `IDLE_UNLOAD`; a sleeper waking to a moved counter exit, one waking to its own empty the slot. **Check and clear under the `loaded` lock, and no `generation` bump**: split, a press slip between the two; bumped, a transcribe that took its token a moment earlier refuse to load and bail with "model changed", where an empty slot under a live token just reload. So the first dictation after a quiet spell may wait on a load, and every one inside the window is instant. **A warm load run with the lock released and install under a generation token, taken by `warm_selected` before it spawn**, and **one loader mutex both warm and transcribe queue on**, or a press and its stop a second later pull the same several hundred megabytes twice. `unload` take neither, so switch and delete stay instant while a load run. — held across the load it would stall the `unload` a switch or delete is waiting on, and installed blind it would put a deleted model back after that unload cleared it.
- **Device is stored by *name*, never cpal's enumeration index.** Handy store the index; it shift on USB replug and silently start naming a different device. An unplugged stored device fall back to the system default rather than refusing to record.
- **Audio must be 16kHz mono `f32`.** No device offer that. Convert once at the end, never per callback — the audio callback is a realtime thread where allocating risk a dropout, and a dropout is a word the reader has to notice is missing. Stereo **average** both sides rather than taking channel 0, since a mic wired to one side alone record silence otherwise.
- **A denied microphone is *silence*, not an error, and that cost a whole round.** macOS open the stream, fire every callback and fill each one with zeros. First build transcribed those zeros to `""` and did nothing — reading exactly like a broken model, with no log line anywhere. Two things fix it and **both** are needed: `tauri-plugin-macos-permissions` raise the real prompt on `start_transcription`, and `Recording::finish` answer `None` where every sample is under `SILENCE_PEAK`. Verified by probe: 192000 samples, peak `0.000000`.
- **Every way dictation can fail is a *message*.** `TranscribeOutcome` carry `NoAudio`, `Empty` and `Failed` beside `Text`/`NeedsModel` precisely so none of them can collapse back into "nothing happened". A silent failure here is indistinguishable from the feature not existing. `Failed` was an `Err(String)` and is the one that escaped the rule; its message is `{:#}`, since `to_string` on an `anyhow` chain print the outermost context alone and every model failure read as the bare words "transcription failed".
- **The audio outlive the run, and that is what make a failure survivable.** Samples used to go into the engine **by value**, so a failed run drop them and the only cure was saying the whole thing again — ten minutes of speech gone to a model that could not load. Every stop now park a 16-bit WAV in `~/.dray/recordings/` ([recordings.rs](apps/desktop/src-tauri/src/transcription/recordings.rs)) *before* the model is even resolved, at any length, and the file is deleted the moment the model answer. `Failed` and `NeedsModel` carry the path, `retry_transcription` read it back through the **same** `transcribe_audio` a stop use, and `DictateControl` draw Retry and Show beside the mic while one is held.
  - **Deletion is on the model answering, not on words arriving.** `Empty` is a verdict — the model read the audio and found nothing in it — so it clear the file like `Text` do. Only a run that could not answer keeps one.
  - **Saving is best effort and the path is `Option`.** A full disk must not take down a dictation that would otherwise work, so a failed write log and carry on; `audio_path: None` is the one failure with nothing to retry, and the message say so.
  - **`recordings::read` refuse any path outside the directory.** The path arrive from the frontend and this command open a file and feed it to a model, so the directory is the only thing saying which files it may.
  - **16-bit PCM, not the captured `f32`.** Half the size of something reaching hundreds of megabytes, playable by anything the reader open it with, and the quantization sit ~96dB below what an ASR model read. Chunks are walked rather than a 44-byte header assumed: a header read at the wrong offset yield audio that transcribe to *nonsense* instead of failing.
  - Unclaimed recordings are pruned after 7 days, on write — the one moment something is definitely being added. Nothing else sweep them.
- **Struct-variant fields need `rename_all` on the *variant*.** The container's rename name variants; a struct variant's own fields stay snake case without it and cross the bridge as `audio_path`, which read as `undefined` and fail nothing.
- **Two files gate the mic, and each fail differently.** `NSMicrophoneUsageDescription` in [Info.plist](apps/desktop/src-tauri/Info.plist): macOS **kill** a process reaching for the mic without one rather than refusing it, so its absence present as the app vanishing on first press. `com.apple.security.device.audio-input` in [Entitlements.plist](apps/desktop/src-tauri/Entitlements.plist): Tauri's bundler sign **every** build with the hardened runtime, ad-hoc `-` included, and under it TCC refuse before the prompt stage — no dialog, no row in Privacy & Security, `check_microphone_permission` just answer false. The plist key being present prove nothing about this one; `codesign -d --entitlements - Dray.app` is what to read. `tauri-build` embed that file into the dev binary's `__TEXT,__info_plist` section too, so the string *is* there under `tauri dev` — read it with `otool -X -s __TEXT __info_plist`, remembering the words come out little-endian.
- **Dictation cannot raise its permission prompt under `pnpm tauri dev`, and the reason is not the plist.** The dev binary is a bare Mach-O, not a bundle, so TCC attribute its request to the nearest **responsible ancestor** — walk `ppid` and it land on whichever GUI app started the chain. Running Claude Code inside Dray, that is `/Applications/Dray.app`, whose *shipped* plist carry no microphone key, so the request is refused **silently, no prompt**. Two ways it break: a detached launch (`nohup`, `&`) reparent to `launchd` and leave **no** responsible app at all; an attached one inherit an app that may not declare the key. **Test dictation from a bundle** — `pnpm tauri build --debug --bundles app` — which is its own responsible process and prompt properly. Same shape as the notification banner's `is_dev()` guard, different mechanism.
- **Engine is fine; suspect capture first.** Parakeet transcribed a `say`-generated WAV word-perfect on the first try. When dictation "doesn't work", probe the microphone before the model — a standalone `cargo run` reading `/tmp/tts.wav` settle it in a minute.
- **The mic hear the speakers, so recording mute them.** One toggle, `muteWhileRecording`, on by default. Moved through `osascript`'s `set volume output muted`, since that is the documented way at the *system* output where CoreAudio want a device lookup plus a property write per channel. Four thing it rest on: the prior mute state live in a **module static**, not on the `Recording`, since a recording dropped rather than stopped must still put the sound back; a second mute **keep the first reading**, or the machine get restored to our own `true` and stay silent for good; restore put back **what it found**, never a flat unmute, since a reader already muted before they spoke stay that way; and restore **clear the record only once the machine is actually back**, since taking it first mean one failed `osascript` drop the only thing that know what to restore and every later stop find nothing to do. Quit is the other end of that record's life, so `RunEvent::Exit` in [lib.rs](apps/desktop/src-tauri/src/lib.rs) restore synchronously — quitting mid-recording is otherwise the one ordinary way to leave a machine silent. Best effort throughout — no output device answer `missing value`, which fail the parse and leave the machine alone. Mute land **after** `Recording::start`, so a refusal never touch it, and restore land the moment the mic close, not once the model finish. **The start tone is swallowed while muted and that is deliberate** — a reader asking for silence while they talk get it, and the visualizer appearing is what say the mic is live. **Lower-the-volume was built and cut**: a three-way picker where the honest answer is one switch.
- **The composer take focus when the words land** ([composerFocus.ts](apps/desktop/src/lib/composerFocus.ts)). One module-level element registered by `ChatInput`'s own `ref`, same gap `useDraft` name and same fix: the recorder live in `App` and the mic button live in `ComposerToolbar`, so neither can reach the editor through props. Only where the reader is still on the session they spoke into — a dictation outlive the screen it began on, and focusing a composer holding somebody else's draft is worse than not focusing. The caret is **left where it was**, since a draft grow at the end.
- **Transcript append to the draft, so `useDraft` is now a `useSyncExternalStore`.** The controls reach `ChatInput` as an opaque `ReactNode` — same gap `useAttachments` name, same fix. `appendToDraft` join with a space unless the draft already end in whitespace, so dictating after typing continue the sentence and never eat it.
- **The destination session is pinned when recording *starts*, never read at the end.** The recorder is app-wide and a recording outlives the screen it began on, so handing `onText` the live `selectedSessionId` filed the words under whichever session happened to be selected when the model finished — dictate in A, switch to B, the sentence lands in B's draft, silently. `useRecorder` take a `target` and copy it on `start`. Switching away therefore **does not** cancel: the recording run on and the text is waiting in the draft it was spoken into.
- **One recorder, process-wide.** `TranscriptionState.recording` is a single `Mutex<Option<Recording>>` and `start_transcription` replace whatever is there, so two live streams cannot exist — both would fill buffers and only one could be read. The frontend state is global too, so a second session show the *same* recording rather than offering a new one.
- **Transcribing redraw the stop button, spinner in place of the tick.** Same filled circle, same place — the state after a press should say the app is working on what was asked, not that the control went away. A `span` carrying `buttonVariants`, not a disabled `Button`, since `disabled` dim the fill to half for a state lasting under a second.
- **Dictation is two sounds: Handy's own marimba pair**, copied under its MIT licence to `src/assets/dictate-{start,stop}.wav` and played frontend-side ([sound.ts](apps/desktop/src/lib/sound.ts), one `play(url)` shared with the notification and celebration clips) — no `rodio`, no Tauri resource, since the recorder's state already live there. `start` play **after** the refusals, or the tone announce a microphone that was never opened. `stop` play when the **words land**, not when the microphone close: the wait between the two is what the reader is listening for the end of. Only on `Text` — the other outcomes say their own piece, and the tone would be claiming something arrived. **Cancel is silent**, matching Handy, which ship no third sound. The elements are kept and rewound rather than rebuilt, since a fresh `Audio` decode on first play and put the tone behind the press.
- **Stop and cancel are two controls, never one.** They mean opposite things about the words just spoken. Handy get away with one key because it type into whatever window has focus; here the transcript land in a draft the reader can see, so throwing it away has to be deliberate. Escape also cancel, **ahead of every other Escape** in `ChatInput`, since recording is the only state holding a device open.
- **Send moved out of the text row onto the control row.** It spanned the whole card height beside the text before, which left nowhere for dictation. Now: text take the card's full width, and one row under it carry the toolbar left, dictate and send right.
- **The level is polled, not pushed** — `transcription_level` answer the loudest sample since it was last asked, ~20fps. A level is only interesting *now*, so a missed reading should be a dropped frame rather than a queued event arriving late. Written from the audio thread as an `AtomicU32` holding `f32` bits, never a lock the realtime callback could block on.
- **The visualizer is an envelope, not a spectrum.** One float cross the bridge and a fixed centre-weighted shape spread it across nine bars. Handy draw a real FFT, which want the whole buffer frontend-side; this tell the reader the one thing they need, which is that the mic is hearing them. **No `Loader2` anywhere here.** Its glyph is not centred in its own box, so rotating it trace a small orbit and read as a wobble at 14px. [Spinner](apps/desktop/src/components/ui/spinner.tsx) is ours: one circle concentric with the viewBox, `pathLength`-normalized so the gap is a share of the ring rather than `2πr` recomputed per size, and `animate-spin` on the **`svg`** — an SVG child's `transform-origin` resolve against the viewport, so a spin on the `circle` swing it around the top-left corner. Downloading draw its percentage over the bar it already has.
- **⌘D alone dictate**, through `useHotkey`'s `platformOnly`. `meta` normally accept either accelerator, which cost nothing for a chord no platform assign — but ⌃D is delete-forward in every macOS text field, including the composer this shortcut is for.
- **A finished download select itself where nothing is selected**, never replacing a working choice — a reader adding a second model to compare has not asked to switch to it. **A *cancelled* one select nothing at all**, and that need saying because a cancel answer `Ok` like a success: `download` return `Downloaded::{Installed,Cancelled}` so the caller can tell them apart. Without it a cancel pointed the setting at a file never written — the tab drew a tick beside a model the composer kept refusing to dictate with.
- **Deleting a model is confirmed in the row, not in a dialog** — a modal take the whole window over a file Download get back. **The actions sit on the bars' row, not the title's, and that is what make the confirmation cheap.** Beside the title they shared a line with prose that had to give up width for them, so anything wider than an icon re-wrapped the description and moved every row below — which forced an absolutely-drawn question over an `invisible` bin, and before that a reserved slot spending the widest state's width in all four. The bars are fixed-width and give up nothing, so the buttons grow into the gap and the whole problem go away. One `confirming` id in the parent, never a flag per row, or two rows ask at once where one press was made; picking any row clear it.
- **Dictation cannot be looked at under `tauri dev` at all**, so a composer demo page carried the controls for a while and was deleted once it had answered — see _Demo pages_ for the shape to rebuild it in. Testing the real thing want a bundle: `pnpm tauri build --debug --bundles app`.
- **The model list is a `radiogroup` and the whole row is the control.** A "Use" button beside a row that already look selectable was two ways to do one thing. Only an *installed, unselected* row is clickable — a row that look clickable and answer nothing is worse than a plain one, and a several-hundred-megabyte download is too big to trigger by clicking a row, so Download keep its own button. Buttons inside the row `stopPropagation`, or deleting a model select it on the way down.
- **`languages` is a phrase, not a count.** "4 languages" tell a French speaker nothing about whether the model is for them, so few languages get **named** (Canary's four) and twenty-eight or a hundred stay a number. Compiled into the catalog, since that is where the judgement belong. **A counted phrase link to the model's Hugging Face page; a named one link nowhere** — which-28 is a question only a count leave open, and "English, German, Spanish, French" have nowhere to send anybody. The row tell the two apart with `/^\d+ languages$/` rather than a second catalog field free to disagree with the first. Expanding the list in the row was the rejected alternative: long, and stale the moment the model gain a language.
- **`speed` and `accuracy` are Handy's catalog scores, copied not measured**, 1–100 and relative to each other — no benchmark was run here, and numbers that look measured would be worse than none. Drawn as bars for that reason: a figure invite a precision that is not there. (Handy's own UI draw neither today; the fields are in its `catalog.json`.)
- **Dropping a catalog entry orphan its file.** `installed_ids` only answer for ids the catalog still name, so a downloaded model whose entry is removed become several hundred megabytes with no row to delete it from. Nothing sweep the models directory.
- **Download cancel is cooperative, checked between chunks.** Aborting the task would drop a half-written file and a live hasher mid-flight; between chunks is the one place it can delete its own `.part` on the way out. The cancelled id live in a module `HashSet` and is **removed** rather than set false, so "cancelled" and "running" are one question. A cancel emit a closing progress event with **no** error, since it is what the reader asked for.

## Handing work back

**The composer hides a row of canned prompts behind itself.** [HandoffRow](apps/desktop/src/components/composer/HandoffRow.tsx) sits above the composer card, clipped to a sliver, open on hover: Commit, Create PR, Run server.

**Every button sends a prompt** through `handleSendMsg`, so there is no confirm dialog and no error surface — whatever goes wrong reports in the transcript like any other tool failure. The agent is not deterministic, so every button is a **suggestion, not a command**.

**Prompts are a few words** — `"commit your changes"`, `"create a PR"`. A longer prompt is a spec competing with the repo's own instructions. Pinned by test (≤5 words). **`RUN_SERVER_PROMPT` is the one exception** ([handoff.ts](apps/desktop/src/lib/handoff.ts)): `"start the dev server in the background"`, where **"in the background" is load-bearing** — a bare "run server" makes the CLI run `pnpm dev` in a *foreground* Bash, which blocks until that tool's timeout and takes the server down with it. The length test skips it by id and pins that clause instead, not dodged by leaving `hasSession` default.

**Hidden, not contextually visible, and that is the whole shape.** A turn touching files is most turns, so a row drawn on "there are changes" is a row drawn always. Hiding is also what lets Run server be offered unconditionally, since nothing tracks whether a server is up.

**Which buttons exist is [handoff.ts](apps/desktop/src/lib/handoff.ts), pure and tested.** Dirty tree → Commit. Create PR is hidden on the default branch, where no remote resolves one, where the branch already has a PR (from `usePrMarks.prFor`, not a fourth git call), and where it holds nothing new. That last check reads `ahead_of_base`, **not** `ahead`: `ahead` counts against *upstream*, so a fully pushed branch reads zero — the exact state a branch is in when its PR gets opened. `ahead_of_base` counts `origin/<default>..HEAD`, since a local `main` can be stale or absent in a worktree. `None` means "couldn't tell" and counts as something, since over-offering costs one click where under-offering removes the action.

**One backend command, not three stitched.** `work_status` = `dirty`, `branch`, `upstream`, `ahead`, `default_branch`, `ahead_of_base`, so the row can't draw one button from one snapshot beside another from a different one. `default_branch` arrives **stripped of remote**. Infallible: a non-repo answers defaults. **Read on the falling edge of a turn and on arriving at a session, nothing else** — polling for an editor in another window is several `git` spawns a second to catch something rare.

## Deleting a worktree

**Nobody else cleans these up.** Sweep never removes worktrees created with `--worktree`, and `-p` runs have no exit prompt — and `-p` is exactly how Dray spawns.

**Unlocking is a required step, not a defensive one.** A `-p` run leaves its creation lock in place (v2.1.239: the tree still carries `locked claude session <name> (pid N start <date>)` and `git worktree remove --force` refuses it, exit 128). [remove_worktree](apps/desktop/src-tauri/src/git.rs) unlocks first, and that string is what the pid check parses. Reading the reason rather than unlocking blind is the point: a **live pid** means another session is working in that directory now, and it is the only thing that refuses this. `kill(pid, 0)` answers it, `EPERM` counting as alive. **Canonicalize both sides of the lock lookup** — git prints real paths, so `/var/…` comes back `/private/var/…` and a plain `==` finds no record, which reads as "not locked".

Order is load-bearing at both ends: unlock before remove because the lock refuses it, `branch -D` after remove because git refuses a branch some worktree has checked out. The path guard sits ahead of all of it and keys on **shape, not index** — a direct child of `<project>/.claude/worktrees/` or nothing, so an empty worktree name resolving to the project root can never reach a delete.

**Sessions survive.** Removal rewrites the index entry — `cwd` and `project_path` both to the project root, `worktree_name` cleared — and `cwd` is the load-bearing half, since `send_msg` reads it off the index. **The project root, not `project_path` as recorded**: an older `dray new` filed sessions under the *caller's* own worktree, so a flat `cwd = project_path` landed the session in a checkout another live session was working in — and the startup backfill could never heal that, since the result exists. `project_root_of` is the one statement of that rule and both paths take it. The CLI meets us there: it resumes in the directory Claude was launched from, and `--resume <id>` falls back to scanning `~/.claude/projects` for `<id>.jsonl`.

**`branch` stays and `worktree_removed` goes on, and that is what keeps the PR tab alive.** The field holds `worktree-<name>`, the branch the work landed on. Clearing it took the tab off every worktree session the moment the reader settled it; keeping it and nothing else still lost the tab, since `sessionBranch` prefers observed HEAD. So the flag decides which wins. `#[serde(default)]`, so an entry predating it reads as tree-still-there. Trees settled before the flag existed need `backfill_removed_worktrees`, one startup pass recognising relocation by its shape — **and the same pass repairs a `cwd` that is simply gone**, which the shape rule cannot see: a tree removed by anything but Dray's own delete leaves the entry pointing inside it, and every `git` and `gh` spawned there fails with ENOENT before the binary is reached. That is why the PR panel said "could not run gh" on a session whose sidebar mark, read in the project root, was fine. `surviving_root` moves both `cwd` and `project_path` to the first root on disk, and **a managed worktree is never that root even where it is the recorded project and still there** — `dray new` used to file a session under the *caller's* own worktree, and that caller is usually a live session, so believing `project_path` would put two sessions in one checkout. So the `/.claude/worktrees/` prefix of `project_path` is tried first, the recorded project only where it names no worktree, then the prefix of `cwd`. **`<name>` has to be a *direct* child there**, the same reading `is_managed_worktree` takes before deleting one — without it an ordinary repo sitting anywhere below such a segment reads as a worktree and its sessions get moved to an ancestor that is not their repo. **No surviving root means no rewrite**, since a project on an unmounted drive reads exactly like a deleted one. The backfill runs at launch, so `gh()` refuses a missing `cwd` in its own words before the spawn — a tree removed while the app is up has no pass coming until the next one.

**"Unpushed" means no other ref holds it, not "no remote holds it"** — `rev-list HEAD --not --remotes` reports a whole history at risk in a repo with no remote. Now `--not --exclude=<branch> --branches --remotes --tags`. Two spelling traps, both failing silently to zero: `--exclude` applies to the **next** ref-enumerating option only, and its glob is relative to `refs/heads`. A squash-merged PR still counts. Over-warning is the safe direction.

**Already-gone trees ask nothing** — disposition is read *before* deciding whether to ask. **Delete takes the tree with it, no second question**, folded into `SessionManager::delete` best-effort; a failed removal there orphans the tree, and `git worktree remove` by hand is the recovery.

**Settle and delete both stop the session, and the stop is the whole process tree** (`SessionManager::settle`): the child, everything it started, and its browser tabs. `child.kill()` alone signals the agent's pid, so a `run_in_background` Bash or a dev server survived a delete under launchd. The descendants are read with `local_servers::descendants` and signalled **before** the child dies, straight off the walk: a dead parent's children are reparented and the walk loses them, and a pid held across the parent's shutdown could be another process's by the time it is signalled. Tabs close whatever the kill answered. A respawn keeps `kill` alone: the dev server should survive an effort change. Settle is refused mid-turn by the sidebar for this reason. The log and index entry stay, and unsettle resumes as any idle session does.

## Orchestration

**One agent can fan work out into several sessions**, each with its own worktree and sidebar row. Three commands: create, list, send.

**This is the first inbound channel into the app.** Every other command travels frontend → Rust; this one travels agent → Rust → frontend, so the frontend learns about a session from an *event* rather than a return value. That inversion is the whole of what [orchestration.rs](apps/desktop/src-tauri/src/orchestration.rs) adds. The work goes through `SessionManager::send_msg`, the same function the composer reaches, so a session created this way is not a second kind of session.

**Three shipped pieces, one line of glue.** The app serves a unix socket; `dray` is a standalone CLI in its own crate; a skill documents it; one line in [system_prompt.md](apps/desktop/src-tauri/src/harness/claude_code/system_prompt.md) names the capability plus install command. **The app installs nothing** — it informs, the agent does.

**The CLI is deliberately not part of the app** — it has to run on Linux later, where no Dray app exists. Own crate, own `cli-v*` tag, `curl -fsSL https://www.drayhq.com/install.sh | sh`. It links neither the app nor tokio: one connect, one write, one read, exit. **Wire types live in a third crate**, `crates/dray-proto`, compiled into both sides so request shapes cannot drift — a drifted shape fails with no error and the command simply stops working. No root Cargo workspace, and this adds none: `src-tauri` has its own `.cargo/config.toml` carrying the ts-rs export path, and a workspace moves the target dir out from under it.

### Install and versioning

**`install.sh` resolves the newest `cli-v*` tag itself, and `dray update` re-runs it.** The app cannot push a CLI update — the Tauri updater swaps the `.app` bundle only. `/releases/latest/download/` is unusable because app and CLI publish into the same repo, so that URL belongs to whichever released last. Instead ask the releases API (`?per_page=100`) and take the first `tag_name` starting `cli-v`; the API answers newest-first, and `sort -V` is not portable. `DRAY_VERSION` is a literal-tag override. **Failed resolution refuses, never falls back** — a rate-limited API quietly installing something ancient is the exact failure being removed. **`prerelease: false` is hard-coded in [release-cli.yml](.github/workflows/release-cli.yml)**, which is what keeps the resolver honest.

**The protocol version is checked before the request is even looked at**, and the refusal **names which half is behind** — `envelope.v < PROTOCOL_VERSION` means the CLI is behind, say `dray update`; `>` means the app is behind, say update the app. Naming the wrong half is worse than naming neither, since only one cure is runnable from an agent. **The envelope must still parse at a version the app no longer speaks** — the check is a layer *above* parse, or a v1 line answers "could not parse the request" where it should answer "run `dray update`". Both pinned by test.

**Bump rule: bump when the default the old side falls back to is undetectable.** An old app ignoring `model` runs on its own default, which the caller can see and judge; an old app ignoring `from` starts the worktree at `origin/<default>` and answers *identically to success*, so a session spawned to review unpushed work reviews none of it and reports everything fine. Wrong work that looks like right work is what earns a bump. Currently **v6**: v2 = `from`, v3 = `issues` and `LinkIssues`, v4 = `LinkIssues.identifiers` → `issues` (renamed, not extended, so two shapes cannot be confused), v5 = `Browser`, v6 = `fast` — an old app ignores it and runs at ordinary speed, which answers identically to success since nothing in the transcript says which tier served the turn.

### The socket

**Unix socket, not an HTTP port.** `~/.dray/dray.sock` — nothing on the network reaches it, no port to collide on. Stale sockets are unlinked at bind. **Dev builds listen on `dray-dev.sock`**, which is what makes unlinking safe: one path for both builds means whichever starts last owns the channel, silently, since neither app reads a socket it no longer owns. **The child gets `DRAY_ENDPOINT` injected** rather than left to the CLI's default, or a dev app's agent files its session into the release app's sidebar. That one value is also what lets the app move to a server later — a `.sock` path today, an HTTPS URL and token in a cloud build.

**The boundary is the directory's `0700`, not the socket's `0600`.** `bind` applies the process umask, so a socket lands world-writable under a permissive one and stays that way until a chmod runs a moment later — a window another local account can connect through and reach session creation unauthenticated. A directory cannot have that window, since connecting needs search permission on every dir in the path. `~/.dray` was `0755`, which also made every transcript readable by any local account. **Narrowing is best-effort, so `serve` checks rather than assumes**: a dir still group- or world-reachable → refuse to bind, naming `chmod 700`. Cost a feature, never the app — as does any `serve` error, logged and dropped in `setup()`.

**Connect fails three ways, and only one of them is about the app being up.** `NotFound` and `ConnectionRefused` are the two shapes a closed app leaves and are named outright rather than used as a fallback — a full listen backlog, an interrupted call and a timeout are all this connect failing with the app very much alive. `PermissionDenied` is its own answer and deliberately **not** stated flatly as a sandbox: the kind covers `EACCES` as well as `EPERM`, and `connect(2)` returns it for search permission on a path component too, neither of which escalation fixes. That hedge is pinned by test, and the cure is named in three places — the error, [SKILL.md](apps/cli/skill/SKILL.md) and [developer_instructions.md](apps/desktop/src-tauri/src/harness/codex/developer_instructions.md) — reword them together, since rewording the error alone leaves both docs answering a sentence nothing emits. (A Codex-side unix-socket allowlist was looked for and is not reachable: the only config surface is a `[permissions.<name>]` profile, and any custom profile aborts with SIGABRT on `codex-cli 0.151.0-alpha.7.1`.)

### Sharing `~/.dray` between builds

**An older build doesn't merely lose a write, it downgrades the schema.** The index is rewritten whole, so a build reading it round-trips every entry through *its own* struct and silently drops every field it cannot represent — a released build beside a dev one erased `thread_id` from every Codex session, and resume then answered "this session has no Codex thread" for work still perfectly alive. A file lock fixes none of this. `SessionIndexItem.unknown` (`#[serde(flatten)]`) is what fixes it, and it protects only versions carrying it, so it goes in **before** the field it saves, never after.

**An unknown *variant* is a different failure, and flatten covers none of it.** A value serde cannot spell fails the line, and the index parses as one `Vec`, so a failed line is the whole file — a dev build writing `"harness":"pi"` made a released app read 256 real sessions as none. **`Harness` is fixed by carrying the spelling**: `Harness::Other(&'static str)` holds the name verbatim and `wire_name` writes it back unchanged. A placeholder would be **worse than a crash** — it parses fine, then silently rewrites the harness of every session it doesn't recognise. `Harness::ALL` excludes it and `names_a_cli()` answers false. **`ApprovalPolicy` and `SessionStatus` stay unfixed, deliberately**: neither can carry a string, since both must resolve to something real to spawn with, and `ApprovalPolicy` falling back to `Auto` makes a session **freer than the reader asked**. Per-entry tolerance is no good either, since "fail its own entry" can only mean *drop* it, and a dropped entry is a **deleted** one on the next whole-file write.

### Creating sessions

**Spawned sessions always take a worktree, and no flag turns it off** — three issues in one checkout overwrite each other. `--no-worktree` and `--worktree-name` both existed and were removed; the agent has no basis for picking a name and a supplied one is one more thing that collides.

**`--from` moves where the tree starts, not who owns it.** `-w` forks from `origin/<default>` whatever is checked out, so a spawned session could not see the work of the session that spawned it — which put the obvious use, *a second model reviewing what the first just did*, out of reach. `--from <session-id | branch | ref>` still makes a new worktree, based at that point. Sharing a live checkout stays out of scope.

- **Mechanism: Dray makes the tree itself.** [create_worktree](apps/desktop/src-tauri/src/git.rs) runs `git worktree add --no-track -B worktree-<name> <path> <base>` and the child spawns **into** that directory with no `-w` at all. So the tree exists before the child does — a real `snapshot_tree` baseline rather than `base_ref_tree`'s approximation — and carries no lock.
- **Session ids resolve through [`session_branch`](apps/desktop/src-tauri/src/store.rs), the same reading `sessionBranch` in [pr.ts](apps/desktop/src/lib/pr.ts) takes.** Two readers, neither can call the other, so the rule is stated and tested twice; what it must not become is two *different* rules. Id is tried before ref, since a v7 uuid is no branch name anybody types.

**Model, effort, harness and permission mode inherit from the parent**, each overridable by flag. No parent means Rust's own default, since the composer's remembered pick lives in frontend localStorage; `ModelId::default()` cannot serve, being `Unknown`.

- **Model and effort both stop at the harness boundary.** The model half is obvious; the effort half is not — the two ladders share every name (`low`…`max`) and Codex accepts whatever is passed, so a Claude parent's `high` lands silently on a Codex child whose own default is `medium`.
- **Whether to inherit at all is the agent's question and lives in [SKILL.md](apps/cli/skill/SKILL.md) alone.** A parent on Fable, or above its harness's own default effort, wants the user's answer before fanning out. Restating it in `system_prompt.md` would be a second copy on the app's release train.

**Depth cap 2, walked not stored.** A spawned session may spawn; its children may not. Walk `parent_session_id` up the index at create time with a cycle guard, rather than storing a `depth` free to disagree with the chain it describes.

**The CLI resolves the project as the main worktree, and `--show-toplevel` cannot do it** — the caller is almost always an agent standing *inside* a linked worktree, where that command answers the tree, not the repo, and the app rightly takes the caller's value over its own guess. The result was sessions whose Changes, commits and PR all read a directory that doesn't exist. The first record of `git worktree list --porcelain` is the main worktree wherever you run it; a bare repo answers `None`. Not `-z`, which wants git 2.36. **Projects are deliberately not attached**, since `add_project` bumps `last_selected` and would let an agent's call quietly reorder the user's project picker.

**`dray` raises no consent card, and that is one flag**: `--allowedTools "Bash(dray:*)"`, additive, with everything else still routed through `can_use_tool`. Verified against v2.1.241, not assumed — a pattern that fails to match fails *silently*, as an unexpected card. **Test with a command that mutates**: a read-only one like `echo` is auto-allowed whatever the rule says, so it reports success for a pattern matching nothing.

**The child gets `PATH` put back.** A bundled `.app` inherits launchd's `PATH`, so `dray` installed to `~/.local/bin` is not there for the agent — the same trap [binpath.rs](apps/desktop/src-tauri/src/binpath.rs) solves for `claude`. Appended, not prepended.

### Skills

**The skill is embedded in the binary and written by `dray skill install`** — downloading it separately is how a skill ends up describing a different version of the CLI than the one installed. Global at `~/.claude/skills/dray/` **and** `~/.codex/skills/dray/`, both written every install, since the CLI cannot know which agent the user runs.

**Freshness rides the CLI, never the app, and the chain closes on its own.** `include_str!` binds the skill to the binary at compile time; `install.sh` runs `dray skill install`; `dray update` re-runs `install.sh`. So every CLI update rewrites the skill and an **app update does nothing to it**, which is the right way round. The skill and `PROTOCOL_VERSION` travel in the *same binary*, so a skill describing the wrong protocol is impossible without the CLI also being wrong. **The skill teaches how to cure a refusal, never which flag needs which version** — enumerating those ages badly and the agent cannot check versions anyway.

**Codex gets Dray's rules as `developerInstructions`** on `thread/start` *and* `thread/resume` (a rollout carries none across). `baseInstructions` beside it is the wrong field — it *replaces* Codex's built-in prompt, tool docs included. Its own file ([developer_instructions.md](apps/desktop/src-tauri/src/harness/codex/developer_instructions.md)), since Claude's names `AskUserQuestion` and the Agent tool, neither of which exist on Codex. Both pinned by test.

### Relaying messages

**`dray send` goes both ways, and that is one command not two.** A child reporting up and a parent handing a child context are the same operation. The message arrives as an ordinary prompt and *starts a turn*, so it wakes an idle agent; a target mid-turn queues it. Unrestricted to parent/child pairs on purpose — an id is an address. **Send passes the target's own recorded model/effort/permission back in**, which is what makes it inert: `send_msg` finds no change, so nothing respawns. A message must not reconfigure the session it arrives at.

**A relayed message names its sender twice, and neither copy does the other's job.** `user_message.from` = `MessageSender { session_id, title }`, set only by `send_message` and persisted so attribution survives replay; the prompt text carries `[message from the Dray session "title" (id)]` as well. Both are built from one lookup in `attribute`, so the two cannot name different sessions.

**The transcript has no business parsing it back out.** Not for forgery — `from_session_id` comes from `DRAY_SESSION_ID` in the child env, so the **field is no more authentic than the prose**. Refused because a parse *fails silently*: a title holding a bracket, a reworded prefix or another harness's shape each break the regex and leave a relayed message drawn as the user's own. The bubble instead **rebuilds** the exact string `attribute` builds ([stripSenderPrefix](apps/desktop/src/lib/relay.ts)) and drops it only on `startsWith`, so drift fails by leaving the line **drawn**, never by eating the sentence after it. The log is untouched.

**A sender can outlive the session it names, so selection rolls back on an empty read.** Leaving a dead id selected looks harmless and isn't: `selectedSession` goes null while `selectedSessionId` still holds it, and `centered`/`isNewTask` both derive from that null — so the reader gets a *new task* composer while `handleSendMsg` still finds the id and resumes a session that is gone. `handleSelectSessionIndexItem` restores the previous pick and says "Session not found", which also covers a stale sidebar row.

**Two refs, answering different questions.** `selectedSessionIdRef` mirrors state, so it is a **render behind** and a read landing in that gap still sees itself as current. `selectionRequestRef` is written at *call* time and claimed at every site selection moves, and the rollback fires only where it still names this read. The rollback target likewise cannot be "whatever is selected", since selection is optimistic until its own read lands — hence `restorable` is the previous pick *only if loaded in `sessions`*, else `null`. Validity is judged **at rollback, not at capture, off `sessionsRef`**, since the closure's `sessions` is the render's copy and the rollback runs after an `await`. General rule: **state read across an await must come from a ref, not a closure.**

### The sidebar

**`session_created` carries an index item, never a `SessionSnapshot`.** The frontend's `agent_event` listener writes into sessions it already holds and *drops* events for ids it doesn't, so a snapshot would start a transcript in memory that later events could miss. An index item leaves the transcript unread until the row is clicked. `session_status` and `session_title` still land, since both write by id into maps the sidebar reads. **The row appears and is deliberately not selected** — the user is mid-conversation in the session that spawned it. The listener sits in a `[]` effect, so it needs `showArchivedRef`.

**Nesting is `sortSessions`** in [Sidebar.tsx](apps/desktop/src/components/Sidebar.tsx), exported and shared with ⌘⇧↑/↓ so the order stepped is the order drawn. **Walk depth-first, not one pass over roots** — the depth cap allows a spawned session to spawn, and a single pass emitted neither the grandchild nor anything below it, so rows vanished. A `seen` set means a cycle costs a strange order rather than a hung sidebar.

**Each project's run splits again by state** — Needs attention, Completed, Idle, in that order. **Mid-turn is not a state of its own**: the row already says so where its timestamp would be, and a run for it moved a row twice for one piece of work, out on send and back on the turn ending. Under the project heading, never over it: "what is happening" is asked of one repo at a time, and a workspace-wide attention run would leave every project heading below it describing only what is left. **A nest takes the strongest state anything in it holds**, so a child blocked on a question carries its parent up rather than the run that says "these want you" missing the only session in it that does. `asking` is read ahead of the backend's status, which still says `in_progress` and is right to. Live status falls back to the item's own field, which is what carries a `completed` across a restart. **The settled list passes no live reading at all** and collapses back to one run per project — it is a history, not a worklist — and **draws no Pinned group either**, since a pin is what the reader keeps in reach while they work and every row over there is done with. **Where both marked runs are a single row they share one break** — a run of one row between two breaks reads as a heading rather than as a row, and the pair says "these want you" either way, with yellow against green telling them apart. **A project under three rows is not split at all** (`STATE_SPLIT_MIN`) — the split earns its break by making a long list quicker to scan, and there is nothing to scan in two rows. Rows, not nests: the count is what the reader sees down the left edge.

**No run names itself.** The state is already on every row in it — the yellow rail mark, the green one, the working indicator — so a heading is a second copy of what the rows say, and three of them turn a list of sessions into a list of headings. Only the project heading is drawn, on the first of its runs; the break between runs is what says one ended, which makes that spacer the whole signal — and **it needs `shrink-0`**, since a bare height in a flex column collapses to nothing once the list overflows, i.e. on exactly the long sidebar it exists for. Every row beside it is held up by its own `min-h`. `sortSessions` takes the same reading as the render, or ⌘⇧↑/↓ steps rows where they used to be.

## The browser

**Chromium embedded through CEF (cef-rs), behind the `cef` cargo feature, macOS only.** [cef.rs](apps/desktop/src-tauri/src/cef/cef.rs) owns the tabs; [automation.rs](apps/desktop/src-tauri/src/cef/automation.rs) is `dray browser`. Design and the rejected routes (screencast, WKWebView) are in DRA-155. Dev: `pnpm tauri dev --features cef` with `CEF_PATH` pointing at the framework, after `scripts/cef-dev-bundle.sh` has laid the helpers beside the debug binary — nothing runs it for you, and a cleaned `target/` takes it away. **A dev build's profile root is `~/.dray/browser-dev`**, the same split the socket makes: Chromium holds a singleton lock on the root, so a dev build sharing the release app's failed to initialize and *exited the process* (DRA-172).

**The bundle ships the five helper apps and never the framework.** Chromium is ~330MB unpacked, and in the bundle it would ride every download and every update. [chromium.rs](apps/desktop/src-tauri/src/chromium.rs) fetches it a few seconds after the window first opens — no prompt, no opt-out — from Spotify's CDN (`cef-builds.spotifycdn.com`, the minimal tarball, arch by `consts::ARCH`), pinned to the `cef` crate's CEF version with size and sha256 of each tarball beside it. Same shape as the transcription models: tarball to `.part`, size and hash checked, only `Release/<framework>` unpacked by `/usr/bin/tar` into `<version>.part/`, renamed to `~/.dray/cef/<version>/`, everything else in that directory swept. Progress is a `chromium_status` event every 4MB; the settings row (Integrations) and the Browser tab's empty state draw `describeChromium`'s one sentence. Failure backs off through four retries and Retry wakes the wait rather than starting a second loop.

- **`paths()` finds the helpers in the bundle and the framework wherever it is** — beside them only in the dev layout, else the download. `create_tab` checks `paths()` *before* `ensure_started`, since that one remembers a failure for the life of the process: a tab asked for mid-download must answer "Chromium is still downloading (n%)", not write CEF off. `dray browser` gets the same sentence through `browser_open`.
- **The helper reads `--framework-dir-path` off its own argv.** CEF forwards the browser's `framework_dir_path` to every child under that switch, and the bundle-relative `../../..` the wrapper's loader assumes does not hold once the framework lives in `~/.dray`.
- **Signing is two halves and the bundler does one.** Tauri signs the app with no `--deep` and signs nothing `bundle.macOS.files` copied, and codesign refuses an app whose nested bundles carry no signature — so [cef-helpers.sh](apps/desktop/scripts/cef-helpers.sh) signs the helpers first, with their own [HelperEntitlements.plist](apps/desktop/src-tauri/HelperEntitlements.plist) (library validation off for the ad-hoc-signed framework, JIT for V8), and the app's [Entitlements.plist](apps/desktop/src-tauri/Entitlements.plist) carries library validation off too. [tauri.cef.conf.json](apps/desktop/src-tauri/tauri.cef.conf.json) is the overlay putting them in `Contents/Frameworks` and running that script as `beforeBundleCommand`; release.yml verifies both entitlements and the framework's *absence* after the build. Compiling the bindings needs the CEF SDK in `CEF_PATH` plus cmake and ninja, and nothing copies its framework out.
- **The hook builds nothing, and that is what keeps a release at one compile.** `tauri build --bins` already compiles `dray-helper` per target, with `MACOSX_DEPLOYMENT_TARGET` set from `minimumSystemVersion` and `custom-protocol` on — and every crate `cc` compiles fingerprints that variable, so a cargo build under any other env reruns those build scripts and rebuilds the tree above them, twice over once the CLI's build follows. That was 28 of a 31-minute release, with the cache restored and unusable.
- **To try the download route under dev**, remove the framework symlink `cef-dev-bundle.sh` leaves in `target/debug/cef/Dray.app/Contents/Frameworks`; the helpers stay and the app fetches its own. **To try a signed bundle**, `pnpm tauri build --debug --features cef --bundles app --config src-tauri/tauri.cef.conf.json` — ad-hoc, but the hardened runtime and both entitlement files are real. **That bundle is not a dev build to the socket**: `is_dev()` is `tauri dev` alone, so it binds `~/.dray/dray.sock` and takes the channel from the release app until that is relaunched. Quit the release app first, or test through `dray.sock` and relaunch it after.

**Each session has its own tabs and its own profile** — `RequestContext` with `cache_path` a *direct child* of `root_cache_path` (`~/.dray/browser/<session-id>`), or CEF refuses the profile. The native view sits above the webview, so nothing in the DOM can draw over it: modals hide it (a body `pointer-events: none` observer) **only where something open lands on it** (`judgeOcclusion`: popper wrappers and dialog overlays measured against the view's rect, two frames on so the popper is placed) and **behind a JPEG of the page** captured first and drawn in its place (`browser_snapshot`, `useBrowserSnapshot`) — Radix sets that style for every menu too, a bare hide left the pane a hole for as long as any dropdown was open, and the swap to a 1x picture is visible on its own, so a menu opened elsewhere touches nothing; tooltips open `side="top"`, and a "new tab" is *pending* with no browser behind it so the pane can draw an empty state.

- **Chromium's init resets SIGCHLD to `SIG_DFL`, and `execute_process` and `initialize` both run inside `keeping_signal` for it.** That reset wipes the handler tokio reaps children through, so every later `git` spawn waited forever — and `send_msg` awaits one under the sessions lock, which made one tab opened leave every session unsendable and unstoppable until restart (DRA-166). Diagnosed by a `<defunct>` `git` under the app in `ps`; that is the shape to look for if a child wait ever hangs again.
- **Never hold the `TABS` lock across a call into CEF.** `load_url` fires `on_loading_state_change` before it returns, and that handler takes the lock. Clone the `Browser` out (`browser_of`), drop the guard, then call.
- **`do_close` returns 1 and removes the `NSView` itself.** CEF's default sends `performClose:` to the top-level window, which is Dray's quit prompt, and returning 1 alone destroys nothing.
- **A hidden `NSView` drops input.** Chromium marks the widget hidden and every mouse and key event dispatched to it goes nowhere, measured with a page listener. `reveal` unhides the view off-screen for an input verb and `apply_layout` puts it back. Screenshots and `eval` work hidden; only input needs this. **The same drop takes the app's own chords when the view is hidden with focus still inside it** — hiding does not resign first responder, so ⌘E closed the panel and nothing reopened it until a click. `apply_layout` hands focus back to the `WKWebView` before hiding a view that holds it.
- `Target.createTarget` over the debug port is refused by CEF, so tabs are created through `browser_host_create_browser` only.
- **A popup is CEF's, not a tab made beside it.** `on_before_popup` rewrites the window info and client to ours and returns 0, so `window.open` answers a real window that OAuth flows post back through; cancelling and opening the URL as a fresh tab returned `null` to the page.
- **CEF can hand over a replacement browser under an id it has not closed yet**, so `on_after_created` replaces a same-id entry and `on_before_close` removes only the instance it holds (`is_same`, called with the lock released).
- **The picker's console channel is gated per tab and typed.** Any page can log the prefix; only a tab whose picker this app started is listened to, once, and only a payload shaped like `PickedElement`. A render-process binding would be the trusted channel.

**`dray browser` is agent-browser's grammar on Dray's own tabs — no agent-browser binary, no MCP, no debug port.** Each browser gets a DevTools channel of its own (`send_dev_tools_message` in, a `DevToolsMessageObserver` out), so an action is a few CDP calls on the session's active tab and the session id is the only address: an agent can reach no other session's pages by construction. Pointer and key verbs use `Input.dispatch*`, since that is what a person's click does; locators and reads are one page-side script, `HELPERS_JS`, shared by `snapshot` and `find` so the two name the same element.

- **Protocol v5.** `Request::Browser` fails to parse on an older app, which reads as a broken CLI rather than an app with no browser; the bump makes it "update the Dray app". **Do not install a v5 `dray` over `~/.local/bin` while the release app is what reviewers run on** — every `dray send` there is refused. Test through the dev socket: a wrapper setting `DRAY_ENDPOINT=~/.dray/dray-dev.sock` in front of `apps/cli/target/debug/dray`.
- **`wait_loaded` watches for loading to *begin* before waiting for it to end.** A click's CDP reply lands before the renderer has left the page, so "not loading" answered at once is the old page, and the next verb reads the old URL. 600ms window, then assume no navigation.
- **`scroll` is `window.scrollBy`, not `mouseWheel`.** The wheel event never answers on a page with nothing to scroll, and hangs the verb for the full timeout.
- **`press Enter` carries `unmodifiedText` beside `text`.** With `text` alone the key types and does not submit a form.
- **A shot hides the view and draws the page's own still in its place, with nothing on top of it** (`browser_shooting` → `shooting` in [browser.ts](apps/desktop/src/lib/browser.ts), `Snapshot` in [BrowserPane](apps/desktop/src/components/browser/BrowserPane.tsx)). The capture lays the page out at the asked-for size and the widget doing that is the one the reader is watching, so a screenshot was a visible reflow and a snap back. It rides the **same hide and the same still** a modal uses, one more reason in `present()` rather than a second path, and only for the session being photographed. **The shutter opens before the override lands**, so what is photographed is the page as the reader last saw it and the swap is invisible. **A scrim and a camera sat on that still for a while and were deleted**: the still is the page pixel for pixel, so the freeze cannot be seen and anything drawn over it is a flash where there was none — which read as the very flicker the cover exists to remove. A screenshot is not an event the reader must be told about; they asked for it. **`SETTLE` is spent at all three edges** — after the hide, after the override goes on, after it comes off — each one a frame where the wrong thing would otherwise be on screen. And **the ack is queued on the main thread**, which is the whole of it being true: `browser_layout` hands `apply_layout` to `run_on_main_thread` and returns at once, so the pane's "the hide landed" was really "the hide was asked for" — it acked, the override went on, and the reader watched the page reflow in a view still on screen. `hiding()` is one predicate because the still, the paint callback and the layout call must agree: asked separately, a shot drew a still nothing would hide behind.
- **`browser_snapshot` is let past `CAPTURING` while the shutter is open, and that exception is what makes the cover the page rather than a blank.** The lock is held for the whole shot, so the cover asked for *inside* one would be refused — and the cover is the thing the shot hides behind. Safe exactly there: `SHUTTER_OPEN` is true only between the shutter opening and the override going on, which is the window where the page still reads the way the reader sees it. Closed before `capture`, never after, or the cover would be a picture of the very reflow being hidden.
- **The shot waits for the pane to say it is covered, and never guesses.** `browser_shutter_ready` → `SHUTTER_READY`. **An ack names the shot it is for, and a bare `Notify` was not enough**: one shot is answered twice where the pane has nothing to cover — once outright, once when the hide it asked for lands — so the spare notification sat as a stored permit and released the *next* shot before its own still was painted, putting the reflow back on screen every other capture (caught in review on #204). `SHUTTER_ACK` carries how far the pane has got and the `Notify` only wakes the waiter to look, so a late ack is a number too small to release anything; the frontend captures the number where the answer is *promised*, not where it arrives. **A pane with nothing of that session on screen answers at once**, or every screenshot taken with the browser tab shut would sit out the whole timeout for a cover it never needed. `SHUTTER` is the cap alone (700ms), and reaching it shoots anyway — which is exactly what the verb did before it covered anything. The shutter closes on the failing path too, beside the metrics override, or a timed-out capture leaves the page frozen for good.
- **`set device` names live in `DEVICES` and in `VIEWPORT_PRESETS` both**; a test holds them together. **The agent's size is capture-only and never reaches the pane** — `Emulation.setDeviceMetricsOverride` lays the page out for the capture alone, and the widget keeps the pane's size. It used to ride a `browser_viewport` event into the pane's own store so the device bar could show what the agent set; that store is what puts the stage into device-preview layout, so one sized screenshot left the reader's page centred and padded inside the pane for the rest of the session, with the bar that explains it closed by default and nothing clearing it (DRA-233). The bar is the reader's alone, and their pick still letterboxes, that being what they asked for.
- `console`/`errors` drain a per-tab buffer fed from `on_console_message`; the picker's own lines are kept out of it.

**A link in the transcript asks first.** Both the assistant's markdown links and a URL in the user's own bubble go through `openLink`, which raises [LinkDialog](apps/desktop/src/components/chat/LinkDialog.tsx): Return opens in Dray, a second button opens the system browser, ⌘-click skips the question and leaves the app. One dialog for the whole app, fed by a module store, since the anchors are rendered several components below anything that could hold the state. URLs in user text are a `url` segment from `highlightSegments`, `http(s)://` only, with the sentence's trailing punctuation left outside.

## Forking a session

**A fork is one conversation carried on twice.** A sidebar row's right-click submenu: **Fork in new worktree** and **Fork here**. Both copy the whole conversation — `--fork-session` takes a session and nothing narrower — so the two differ only in *where* the copy runs.

**Fork is lazy, and that is the whole shape.** The app's half (copy the log, write an index entry) is instant; the CLI's half only happens on **spawn**. So `SessionManager::fork` writes the app's half now and leaves `fork_from` on the index entry as an instruction; the **first send** spawns `--resume <parent> --fork-session --session-id <new>` and clears it. The copied log is what the fork replays meanwhile. **`fork_from` is an instruction, not lineage**: cleared **after** spawn, so a child failing to start leaves it standing, and **before** the prompt goes out, since from there the CLI owns the session under this id. `#[serde(default)]`, or every existing session forks on its next send.

**`--fork-session` honours `--session-id`** (v2.1.246), which is what lets the frontend mint a fork's id the way it mints a new session's. Also verified: the CLI writes a fork a **complete standalone transcript** holding the parent's history, and `-w` combines with all three.

**Refused while the parent's *turn* is in flight, and nothing wider.** The CLI forks by *reading* the parent's transcript, which a live child is appending to mid-turn. An outstanding background task is not that case — it appends *after* a turn ended. The backend checks `turn_in_flight()` and the submenu disables on `in_progress`, the **same question** by construction, pinned by test. The guard was `has_outstanding_work()`, the safe-to-replace-the-child question — and since a `local_bash` task never ends, a session running a dev server could not be forked again for the rest of its life while the menu item stayed enabled. **Also refused where the parent has no conversation**, since an index entry is written before spawn.

**Fork in a new worktree is a resume whose tree doesn't exist yet**, so it needs creation's treatment inside `send_msg`: `-w`, the project root as spawn dir, `base_ref_tree` as baseline. The name is resolved against the **project**, not the parent's own. The item names the cost out loud: `claude -w` forks the *tree* from `origin/<default>`, so the copy can carry a whole conversation onto code that doesn't hold the work it was about.

**Names are resolved against the index and every `worktree-*` branch, not disk alone.** A lazy fork's tree doesn't exist until its first send, so its name lives **only in the index** until then — anything else drawing a name takes one a pending fork holds, and that fork's `-w` then fails **permanently**, since the name is on its index entry and every retry redraws it. And a settled session frees its name everywhere but `origin`, where the branch its PR landed from stays — the PR tab and sidebar marks look a session up by that branch, so a redrawn name opened onto somebody else's merged PR. `worktree_branch_names` folds local and remote-tracking branches in with one `for-each-ref`; no fetch, since a push from a linked worktree writes the tracking ref in this same repo. `resolve_unclaimed_worktree_name` reads all three, and **both** call sites use it. The pool is 32³ and every landed PR retires a name for good.

**The copied log is repointed, twice, and both are about outliving the parent.** Every event carries `session_id` and the frontend routes live events by it, so a log left alone claims to be the parent's and then grows new events under its own id. And `ImageRef.path` names a file under `~/.dray/attachments/<session-id>/`, so a verbatim copy draws pictures out of the parent's directory and goes blank the moment the parent is deleted; the attachment directory is copied beside the log and the paths rewritten. Event `id`s are deliberately **not** re-minted. `repoint_events` is split out from the copy so the rule is testable with no `~/.dray` to write into.

**`parent_session_id` inherits, because a fork is a copy and a copy sits where the original sits.** The sidebar draws a fork **beside** its source under the same parent, and the depth cap counts it at the same depth. Resetting to `None` looks tidier and is a hole — a copy surfacing top-level is free to spawn where the session it copied could not. Pinned by test.

**`restoreSessionControls` takes an *item*, not an id.** A fork opens selected, but it can't go through `handleSelectSessionIndexItem`, which reads `sessionIndexItems` and won't hold the new row until the next render — without the split the fork opens under whatever model the composer last left on.

## A missing agent CLI

**Answered before the reader writes a prompt, and refused before a session exists.** `agent_availability` reports which harnesses can run here; the picker reads it on mount and marks the one that can't, and `send_msg` checks again under `if is_new_session`.

That ordering is the whole feature. The index entry lands **before** spawn on purpose, so a session failing for an unpredicted reason stays visible — but a missing CLI is predictable, and through that path it leaves an empty row pointing at an agent that can never start. Refusing earlier means nothing to delete and no retry choreography: the composer never unmounts, `useDraft` still holds the text, and retry is pressing send again.

**"Is it installed" is read off the cached path, not probed again.** `binpath::agent_available` calls the ordinary resolver and asks `is_absolute()` — a successful resolution is always absolute, and the bare-name fallback is the only relative answer either resolver can give. Free after the first call, which matters because the *failing* call is the expensive one. For Codex it covers a stale binary for free: one with no `app-server` subcommand never satisfies `speaks_app_server`, so it falls through to the bare name exactly like an absent one.

**Dray installs nothing** — it names the command and links the page, using each vendor's own install script. Known cost: `binpath`'s cache never invalidates, so a CLI installed while the app runs still reads as missing until restart.

Check what is here before adding one; an entry named `demo.html` is already taken.

## Persistence

Everything lives under `~/.dray/` ([store.rs](apps/desktop/src-tauri/src/store.rs), [projects.rs](apps/desktop/src-tauri/src/projects.rs)).

- **`sessions/<session-id>.jsonl`** — one mapped `AgentEvent` per line, append-only. Single writer per file, so `O_APPEND` alone is enough; no lock. On resume, `next_seq_by_session_id` tail-read the last line to continue the counter.
- **`sessions/index.json`** — one `SessionIndexItem` per session, holding both `cwd` (where the agent runs) and `project_path` (repo root, the grouping key, so worktree sessions still list under their project). Rewritten whole, so it take a process-wide lock and land via write-temp + `rename`.
- **`attachments/<session-id>/`** — a copy of every image sent from that session, deleted with the session. Only images: non-image attachments are referenced by original path and never copied.
- **`projects.json`** — attached projects and which was last selected. Own file, own lock. Paths canonicalized at attach time, or `/x/proj` and `/x/proj/` become two projects and split the sidebar's grouping.

The asymmetry is the point: appending to a private file is atomic, rewriting a shared one is not. **`cwd` on the index is authoritative on resume** — `send_msg` read it rather than trusting the caller's argument, since the project picker make the two able to disagree and resuming in the wrong directory is silent.

## Updates

**Shipping one = `apps/desktop/RELEASING.md` (gitignored, local only)** — follow it rather than reconstructing it from here. It says what to type and, more important, what to *check* after: a green tick proves nothing, since the bundler only warn when notarization fails.

**Two signatures, and conflating them is the first mistake to avoid.** The minisign keypair is the updater's own integrity check — public half in `plugins.updater.pubkey`, private half a build-time env var, and a bundle built without it is refused by every client. Apple's Developer ID signature is a different question: it is what stops macOS blocking the download, and says nothing about whether the payload is one this app published. Both set in [release.yml](.github/workflows/release.yml); only the first is needed for a local build.

**A tag's shape pick the channel**, semver does the rest. `v0.3.0` stable, `v0.3.0-beta.1` beta, and because `0.3.0-beta.1` sort *below* `0.3.0`, beta users are offered a stable release the moment it ships with no logic reproducing that rule. What the release job encode is the other half: a stable release write both manifests, a beta release only `beta.json`, so beta is a superset, not a fork.

**Manifests only ever move forward** (`promote` in [release.yml](.github/workflows/release.yml)). The beta line run *ahead* of stable for its whole life, so an unconditional `cp` let a stable hotfix overwrite `beta.json` with an older version. The guard is the same semver comparison the plugin makes, prerelease rules included, in inline node — **not `sort -V`**, which put `0.9.4-beta.2` *above* `0.9.4`. Equal versions rewrite; a missing manifest is written, never an error; a release moving nothing skip the commit.

**The channel is chosen per check, in Rust** ([updater.rs](apps/desktop/src-tauri/src/updater.rs)), so switching channels need no rebuild. It is owned by [useUpdater](apps/desktop/src/hooks/useUpdater.ts) and handed down as a prop — `useLocalStorage` is per-component, so a second copy in the dialog write a value the hook never sees, and `channel` is what re-arm the checking effect.

**Install is blocked while any session is mid-turn**, and the button waits rather than warning, since swapping the bundle relaunch the app. The check is `statusBySession` and is complete on its own, as no child survive a restart. It lives at the button, not in `install_update`.

**The last step is a launch this app make itself, never `AppHandle::restart`.** `install_update` run off the main thread, where `restart` only ask the event loop to exit and relaunch from inside Tauri's own `RunEvent::Exit` arm — *after* the callback in [lib.rs](apps/desktop/src-tauri/src/lib.rs), which end in `libc::_exit(0)` to dodge ggml-metal's atexit abort. So the relaunch was never reached and Install read as a quit that never come back (DRA-160). Nothing here may call `restart` again while that `_exit` stand.

**Launch first, exit second, and that ordering is the whole of the reporting.** `relaunch` run `open -n <bundle>` — Launch Services, so the new instance is registered, and a refusal come back as a non-zero status carrying a sentence rather than as a process already gone. Only then `app.exit(0)`. A rejected `invoke` is therefore a real answer the UI can draw, where a diverging call left nothing running to say anything at all. `-n` is load-bearing: this app is still up, and without it `open` merely activate it. **Environment survive** — `open(1)` state that an opened app inherit it "just as if you had launched the application directly through its full path" — where `argv` do not, absent `--args`, and nothing here read any. Success only mean Launch Services took the request; an instance that start and then die look identical from here.

**The two failures are tagged, never told apart by their message.** `InstallError` carry `stage`, because the cures are opposite: a swap that did not complete leave nothing to open, so the button beside the sentence is the answer, where a *relaunch* that failed left the new bundle on disk and only opening it finish the job. Telling a reader to quit and reopen for a swap that never landed send them to do nothing. **Not "changed nothing"** — the plugin move the old bundle to a temp backup before unpacking and a final rename that fail return `Err` without putting it back, so the weaker claim is the true one. An unshaped rejection read as `install`, the safe half. The sentence itself is `updateFailure` and both surfaces call it — the sidebar row **and** the Settings row, since Settings cover the sidebar and a reader who pressed the button there would otherwise get no answer at all.

**Except when the user asks.** "Check for Updates…" is a question, so it is answered either way and both answers retire after 4s. The menu item **emit to the frontend** rather than checking in Rust, because the channel lives in frontend local storage; that also mean a manual check reuse the scheduled path and its in-flight guard. The verdict is read off `check_update` resolving with no `update_status` having arrived.

## Settings

**One dialog, seven groups down a rail** ([SettingsDialog.tsx](apps/desktop/src/components/SettingsDialog.tsx)), gear in the sidebar's titlebar strip, ⌘, from anywhere. Appearance, Spaces, Accounts, Transcription, Integrations, Shortcuts, About. `SETTINGS_TABS` is set *and* order.

**The rail reverses this dialog's own first shape, and the reason is that the dialog moved.** A row across the top was right at 28rem, where a rail would have taken a third of the width from prose already breaking over three lines — that reasoning is still sound and is why the row lasted six groups. At 34rem with seven it was the *row* that broke, wrapping onto a second line, which reads as two rows of tabs rather than as one list. A rail is a column and grows down; a row can only grow into the panel. The dialog is 44rem now, since the rail takes 8rem before the prose starts and 34rem-minus-a-rail put the analytics sentence back on three lines — the measure the width was set by in the first place. `useRovingGroup` needed nothing: it already answered both axes. Two things the panel needs beside it: `min-w-0`, since a flex child's `auto` refuses to go narrower than its content and one long command string would otherwise widen the whole dialog, and the fixed height it already had.

**The title heads the rail, and the dialog has no header row at all.** One was a whole line spent on one word at the left and the close cross at the right, with the groups starting under all of it — dead band across the middle of a dialog whose two columns both wanted the top. Over the rail the word names the list it sits on (`px-2`, the tab buttons' own padding, so it lines up with the labels) and the panel starts at the dialog's top edge. `DialogContent` takes `gap-0`, since it holds one child now. **The close cross is then drawn over the panel's own top corner, and the gutter for it is one row's, never the panel's.** A `pr-7` on the panel was 28px of empty column down the whole dialog to clear a 16px glyph, and it showed: everything in every tab sat short of the right edge. Only the *first row of one tab* ever reaches that corner — Spaces' New space — so it carries the padding itself. Header actions dodge it by the other route below.

**A tab can hang one control up there, through a portal** ([headerAction.tsx](apps/desktop/src/components/settings/headerAction.tsx)). `SettingsTabs` draws the slot over the panel's top-right and *outside* its scroll box, at `right-6` so the corner stays the close cross's, and `h-4` — the cross's own height — is what it aligns to, since a button is taller than its glyph and at `top-0` hung half a row low. A portal rather than a prop, because the state behind such a control lives in the tab's own component — Accounts' Refresh is its hook's `refresh` and `busy` — and lifting that to the dialog would spawn four child processes on every settings open whichever tab was wanted; bodies being switched rather than hidden is what empties the slot again. The slot is `useState`, not a ref, since a portal needs the node during render. Accounts' Refresh is **a glyph, not a word**: it acts on the whole tab rather than on the rows nearest it, and a row of its own pushed every account down the page and scrolled away exactly when the reader went looking for it. Its name lives in a real tooltip and in `aria-label`.

**The strip spans the panel so a tab can put something at either end**, and the sign-in form takes it over: a **back arrow** leading it (`mr-auto`), level with the close cross, where a reader already looks to get out of something. A cross inside the card said "close" a few pixels from the one that closes the dialog, and Refresh has nothing to re-read while a credential is being written. The strip itself takes **no pointer events** and its children take them back, or an empty 16px band over the panel would swallow clicks meant for the first row under it. The card below it keeps an `mt-6`, since the strip is drawn over its corner rather than above it.

**Font size is three px rows writing the `--fs-*` hooks App.css already exposed** ([fontSize.ts](apps/desktop/src/lib/fontSize.ts), store in [useFontSizes.ts](apps/desktop/src/hooks/useFontSizes.ts)) — chat, code, interface; tool output and the composer are left at their own size on purpose, their hooks unwritten. Stored under `ade.fontSizes` and applied pre-paint by the same `index.html` script the theme uses, so a stored size never flashes the default. Each field keeps a draft while focused and clamps on blur, since a controlled number input clamped on change turns a typed `15` into `105`.

**Every chord has an id, and the id is what `useHotkey` takes** ([shortcuts.ts](apps/desktop/src/lib/shortcuts.ts) is the registry, [useShortcuts.ts](apps/desktop/src/hooks/useShortcuts.ts) the overrides). Keycaps draw through [ShortcutKeys](apps/desktop/src/components/ShortcutKeys.tsx) off the same store, so a tooltip cannot name a chord the key no longer fires. A test refuses two ids sharing a default; one action bound from two components under different `enabled` gates is one id (`subtab.prev`), never two. The Shortcuts tab records the next keystroke on the row, refuses a chord another id holds with that id's name, and stops the event at the button — every `useHotkey` listens on `document`, so without that the chord being recorded would also fire. A bare printable key is refused as a chord, shifted or not. Known ceiling: inside the browser pane CEF forwards a fixed key set (`cef_key` in [cef.rs](apps/desktop/src-tauri/src/cef/cef.rs)), so a chord rebound onto anything outside it works everywhere but there.

**The tab panel is a fixed 512px capped at `60vh`, scrolling, not a floor.** A floor was enough while every tab was within a line or two of the others, and stopped being the moment Transcription arrive carrying a list of models — the dialog then double in height on the way in and halve on the way out, which read as the window jumping rather than the content changing. Raising the floor to the tallest tab instead spend that height on About, which is four lines. The cap keep the invariant, since it is one number per window rather than per tab. Two things the fixed height need: `shrink-0` on the sections, since a column flex item shrink toward its content before the container agree to scroll, and a negative margin, since `overflow-y` clip the other axis too and take the outer edge off a focus ring drawn at the panel's edge.

**Mounted in `App`, not beside the gear that opens it** — the sidebar unmount whole when collapsed, and ⌘, is the one route into settings that survive that. Open state is not persisted and the tab pick resets on close. **Bodies are switched, not hidden**, against the right panel's own bargain: there is no scroll position to keep, and mounting all three would run the external-app scan on every open.

**Row shape = `SettingRow`**, label and control on the top line, reason full width beneath. Two rules it encodes: a description is **not optional**, since it is where "why is this off by default" lives; and a setting that cannot apply on this platform is **disabled, not hidden**, since a row that vanishes reads as a setting the app forgot and the sentence under it is the only place the reason can be said.

### Accounts

**Which account each agent runs as, asked of the CLIs themselves** ([accounts.rs](apps/desktop/src-tauri/src/accounts.rs), [AccountsSettings.tsx](apps/desktop/src/components/settings/AccountsSettings.tsx)). The same facts already reach the composer as [LoginExpiredNotice](apps/desktop/src/components/composer/LoginExpiredNotice.tsx), but only *after* a turn has failed on auth and never for a session that is working — so "who is this running as" had nowhere to be asked.

**Dray stores no agent credential and this adds none.** Each CLI keeps its own store and each answers a status question on the command line, so the tab is four probes and a row each. **No CLI here has a headless OAuth flow** — `claude auth login`, `codex login`, `fx login` and pi's `/login` are every one of them interactive — so the tab reports, and the reader signs in. Stated out loud so a later reader does not go hunting for the flow this declined to build.

**Rows read; one form writes.** The four differ in what can be done without a terminal, and letting each row wear its own capability made four differently-shaped blocks out of one list — a key field on one, a sign-out on another, three verbs across them. So every row is dot, name, identity and auth type, and every way *in* is the one form, which asks the same questions and changes its answers underneath. **Add an account is pi's alone** (`MULTI_ACCOUNT`), and the question it answers is whether the providers can be *listed* rather than how many credentials the CLI holds: Claude and Codex hold one each, so signing in again *replaces* it, which is "change sign-in method" and not an addition; fx holds three and every one is already a row, so Add opened a form to reach a provider the reader could sign into from the row in front of them. pi publishes no provider list at all, which is what leaves a name only the reader can supply.

**A signed-in row ends in the ⋯ menu; every other row ends in a Sign in button.** `can_sign_out` follows being signed in on all four, so a signed-out row's menu was one item behind a caret — a button with a step in front of it. The menu stays where there are genuinely two things to pick between.

**Dray runs the sign-in command, and that reverses this tab's first shape.** Showing the string beside a terminal opened at the directory was the careful reading — macOS lets no app type into another's prompt without an Accessibility grant — but what it asked of somebody who had just pressed Sign in was to copy a command, find the window that had opened and paste it. The `.command` script route needs no such grant, so the caution was about a permission that was never involved. `run_agent_login` composes nothing: it takes the same closed set `add_agent_account` does — harness, provider, option id — and looks the string up in `auth_options`, where **every command is a literal**, so a frontend can ask for a flow this build offered and nothing else. `apps::run_in_terminal` is the one place a shell script is built, shared with the composer's notice, and it states that the caller owns what is in that line.

The cost, stated: a `.command` handed to `open` is run by **Terminal.app alone** — measured, with Ghostty and Warp accepting the open and running nothing — so the terminal picked next door is not honoured here. That pick still stands for opening a *directory*, which is all [the table behind it](apps/desktop/src-tauri/src/apps.rs) promises, and the command keeps a copy button for anybody who wants it elsewhere. The `cd` is omitted where there is no directory, since `cd ''` fails and would take the command with it.

- **claude** — `claude auth status --json`, the richest of the four: `loggedIn`, `email`, `orgName`, `subscriptionType`, `authMethod`. One row, and `authMethod` becomes the row's auth type rather than part of its identity line, since it is what the menu offers to change. Both its methods are browser flows (`--claudeai`, `--console`) and neither takes a key; they are listed as two anyway, because they bill differently.
- **codex** — `codex login status`, prose and no `--json` (measured: the flag is refused). **The sentence is on stderr and stdout is empty**, which is why `run` hands back both streams: a reader of stdout alone gets a correct yes/no and no identity at all. Signed-in is the exit code **and** the words together — either alone broke one of the two captures — and the pair buys a third state: a non-zero exit that does not say "not logged in" is **`Unknown`, never signed out**, since a config error would otherwise report a good account as missing and send the reader to replace it. The **auth type comes off disk**, `~/.codex/auth.json`'s `auth_mode`, since that is the field a saved key moves.
- **pi** — one row per provider, from the model list Dray already reads plus whatever its own store holds, with `pi auth check --provider <p> --json` adding the auth type. `--no-refresh` is load-bearing, or looking at the page silently renews the reader's token.
- **fx** — three rows, `FX_PROVIDERS`, and the providers **are** nameable (`fx login [vercel|codex|grok]`), so all three draw whether connected or not. Each is spelled twice and neither spelling derives from the other: `fx login`/`fx logout` take the short name, `fx status --json` reports the long one in `connected_providers`. Its `auth` field is prose about the *active* provider alone, matched loosely and drawn on the one row it names.

**pi's methods are per provider, and getting that wrong was the first draft's worst bug.** It offered OAuth and a key on every pi row; in fact **six of pi's providers have OAuth** and the rest do not, and `openai-codex` has OAuth and *no* key. Both halves are a control the reader can pick that ends in a refusal. `PI_PROVIDERS` is now a table of 39 read out of pi's own provider definitions (`auth:{apiKey:…,oauth:…}`) carrying `oauth`/`api_key` per row. Four of them — Bedrock, Vertex, both Cloudflares — take a *structured* credential rather than a key, so `providers_of` drops them from the offer while `pi_label` still names them, since a row for one can arrive from pi's model list.

**That table is a seed, never an authority.** pi publishes no provider list — `get_available_models` names only what is configured and its rpc has no providers method — so the reader can **type past it** and `pi auth check` decides, answering `provider_not_found` for a name pi does not know. The first draft guessed twelve names and got `moonshot` wrong (it is `moonshotai`), which is exactly why the validator rather than the list is what refuses. A provider this build has no entry for is offered **both** methods: over-offering costs a refusal from pi, where under-offering makes a provider added after this build unreachable.

**pi's keys are written into pi's own store**, `~/.pi/agent/auth.json`, as `{"type":"api_key","key":…}` beside the `oauth` entries `/login` writes — a shape read out of pi's bundle rather than a document pi published, so it is checked by `pi auth check` afterwards rather than trusted. Read-modify-write under a temp file and a rename, at `0600` **on the create**, the same reading the tracker key's own write records. pi's sign-out is removing that record, offered only where the store actually holds the provider.

**Both writers go through `pi_edit_store`, and what it guards is the rest of the file.** It is rewritten whole, so a read that answered "no credentials" for any reason but the file being *absent* would replace every OAuth entry `/login` put there with one key. So a writer takes `pi_auth_strict`, where unreadable and unparseable are both errors — the opposite of `settings::update`, and for the opposite reason: bytes that cannot be parsed cannot be preserved, and what is lost here is credentials rather than preferences. The tolerant `pi_auth` stays for *reading*, where the worst case is a row saying a provider is not configured. A process-wide lock is held across read, edit and rename; it cannot lock against **pi**, which is a second writer with no lock to take, and removing this process racing itself is all it claims.

**The key field is Codex's and pi's, and nothing else's.** `codex login --with-api-key` reads a key off **stdin** and pi's store is a file; Claude's login has no key form and `fx setup` is interactive, so both of those are commands. Nothing pasted is kept by Dray. **Sign-out is non-interactive on three of the four** — `claude auth logout`, `codex logout`, `fx logout <provider>` — with pi's being the store edit above, and **it asks first, in the row**: a modal over the whole window is more than the question is worth, the transcription rows' own reading, and the `confirming` id lives in the parent so one press leaves one question on screen. It earns the step where Reauthorize beside it does not: that one is undoable and this one is a credential gone on a slip.

**Every subprocess here is bounded, mutations included.** The probes always were; `codex login --with-api-key` and the three logouts were not, so a CLI that decided to prompt instead of answering would hold the page busy — Refresh and every row's menu disabled — until the app restarted. `PROBE_TIMEOUT` plus `kill_on_drop`, which is what makes the bound real rather than a future that stops being polled.

**The form opens on the method already in use.** `authIdOf` joins the row's label back to the option id, which are stated separately on purpose: a row says what the *CLI* calls its credential, the form picks by an id `add_account` accepts. An unrecognised label answers `null` and costs the preselection and nothing else. Picking the method already in use makes the submit read **Reauthorize** rather than Sign in, since a CLI holding one credential cannot be signed into twice.

**Three states, not two.** A probe that could not run must not read as *signed out*, which would send the reader to fix a login that was never broken — so `AccountState::Unknown` draws its own colour, the sidebar rail's `accent-command` beside `accent-add`.

**Every probe runs in the session's own directory**, the one the sign-in terminal opens in. A CLI resolves its config against the directory it is started in, so "who is this agent running as" has to be asked where the agent runs, or the read and the write disagree about which project is being signed into. Only where it is still there: a settled session keeps a `cwd` whose worktree is gone, and spawning into a missing directory fails with ENOENT before the binary is reached — `binpath`'s own trap — so the process directory stands in. `add_account`'s `pi auth check` is deliberately the exception, reading whether pi knows a *name*, which no directory moves.

**Nothing is cached and nothing polls.** The reader is on this page because they are about to change a login, so a cached answer would be stale exactly where it is read, and all four probes measure under 250ms. Mounting is the gate — the dialog switches tab bodies rather than hiding them, so `useAgentAccounts` takes no `enabled` flag. A terminal sign-in sends nothing back, so Refresh is how the page learns; four children on a timer to catch a browser round trip would be worse than a button. `what_the_installed_agents_answer` is the `#[ignore]`d live test every parser here was written against — run it when a CLI changes what it says.

### Closing with ⌘W

**The macOS Window menu ships no Close Window item, and that absence is the whole feature** ([quit.rs](apps/desktop/src-tauri/src/quit.rs)). The predefined one carries ⌘W built in, and a menu key equivalent is matched before the responder chain — so the key never reached the webview and closed the app's only window instead, which arrives as `CloseRequested` and raises the quit dialog. There is one window and quitting is already confirmed, so the item buys nothing the red traffic light does not; dropping it hands ⌘W to the app. `RESERVED` in [shortcuts.ts](apps/desktop/src/lib/shortcuts.ts) no longer holds it, and a test refuses any default that list would make unrebindable.

**One id, `tab.close`, and one binding in `App`** — never a `useHotkey` per tab strip. The views are mutually exclusive, so the chain is an *ordering*: the Files view's active file, then the Browser view's active tab, then a split pane on Chat, then the panel's browser where none of those apply. Split across the components that own each strip it would be several ids on one chord, which the registry test refuses, or several bindings of one id firing together — and `enabled` cannot arbitrate the last arm, where the browser sits beside a chat grid and both could answer. It is bound only where something is actually closable, since `useHotkey` claims every chord it matches. It replaced `pane.close`'s ⌘⌥W outright rather than sitting beside it: two close chords is one more than the reader has to learn.

### Theme

Full rules, rejected alternatives and the swatch/mode UI reasoning are in [DESIGN.md](apps/desktop/DESIGN.md). What must not be broken:

- **Colour is three layers, and which layer a token lives on is the whole filing system.** `:root` hold what neither theme nor mode changes, plus every **alias**; `[data-mode]` hold the ramp; `[data-theme][data-mode]` hold the palette. Aliases keep the third layer honest — `--card`, `--popover` and `--composer` all resolve to `var(--surface-card)`, so a theme cannot set one and forget another.
- **The ramp lives on `[data-mode]`, never `:root`** — the two have the same specificity, so a light document matching both would take any dark token the light block happens to miss.
- **Rules go on `body`, never on `html`.** Palette blocks are `[data-theme][data-mode]`, two attributes, so they out-specify any `html[…]` aimed at the same element and the override lose **silently**. Every new attribute hits this again.
- **An alias resolve where it is declared.** `:root { --backdrop-top: var(--background) }` resolve *at `:root`*, so a **descendant** setting its own `--background` still paint the document's — which is why `.theme-swatch` must re-declare both backdrop stops. A theme setting its own stop still wins, since palette blocks are unlayered.
- **A swatch carry its own mode, not the document's** (`hasLightMode(name) ? resolvedMode : "dark"`), or a dark-only theme in light mode match no palette block and draw something clicking it doesn't give.
- **`useTheme` is a module store, and that is not tidiness.** `useGlass` read the theme, so a per-hook copy meant the dialog set a theme its own copy knew about while the window kept the old one's behaviour, and the stale copy's `watchSystemMode` callback re-applied the old palette on the next OS colour-scheme change. One store, one watcher.
- **Transparency is a token set and vibrancy nests inside it.** Windowed is always on; fullscreen is answered by the **palette**, never the reader, since nothing sits behind a fullscreen window. [useGlass](apps/desktop/src/hooks/useGlass.ts) own both attributes and guarantee vibrancy ⊆ transparency. Neither is persisted.
- **The material blur inherit the appearance it is *given***, so a light palette on a Mac set to Dark composite over dark blur and go grey. `setTheme` fix it, app-wide — traffic lights, menu bar and native dialogs follow Dray's mode. Wants `core:window:allow-set-theme` in [capabilities](apps/desktop/src-tauri/capabilities/default.json), with the same silent ACL refusal `set-badge-count` documents. **Passing `resolvedMode` unconditionally break System**, since pinning the appearance also pin what the webview report for `prefers-color-scheme` — the only thing `watchSystemMode` reads.
- **`coerceTheme` reject unknown ids and fall back to `DEFAULT_THEME`**; nothing migrate stored values. Pinned by test, and that test is what should fail if the default ever stops being that palette.

## Analytics

**Five events, hosted PostHog** ([analytics.rs](apps/desktop/src-tauri/src/analytics.rs)): `app_started`, `active_day`, `session_started`, `feature_used` and `error`. Nothing about *what the reader writes* is measured — no prompt, no path, no title. `session_started` carry harness, model, effort, permission mode and whether the session is a worktree or was spawned, read off the index entry rather than `send_msg`'s arguments, and reported **after** the index write, since everything before it can still fail and a session counted before its row exists is a start that never happened.

**`app_started` is the install and version signal, never the activity one.** People leave this app open for days, so launches undercount use badly. What a launch uniquely answer is which build is in the wild.

**`active_day` is the activity one, and nothing else answer it.** PostHog compute actives off *any* event, but the events beside this one only fire where they fire: `app_started` want a launch and `session_started` want a session being **created**, so somebody working all day in one resumed session used to fire nothing at all and the most engaged reader read as churned. Three call sites, each covering a hole the others leave. **Launch**, beside `app_started` in `setup`, is the only one guaranteed to fire — [focus.ts](apps/desktop/src/lib/focus.ts) seed itself from `document.hasFocus()` and report *changes* alone, so a window coming up already frontmost never report gaining focus and somebody who open Dray, work and quit without switching app would go uncounted. **Focus gained**, through that same module's subscription and the `track_active_day` command beside `track_feature`, catch coming back to check on a session an agent is running — no prompt, and real use of an app about parallel agents. **The `send_msg` command** cover a reader who leave the app open and frontmost across a date boundary. All three share one key, so whichever get there first claim the day and the other two are no-ops — which is why none of them ask what the others did: "report this only if nothing reported today" is what the claim already is.

**The send site is the Tauri *command*, never `SessionManager::send_msg` one call down**, and that is the whole gate. The orchestration socket reach the manager directly for both of its jobs — relaying a `dray send` and starting a session `dray new` ask for — so an agent finishing at 3am would mark the day active with nobody in the room. A gate on `from.is_none()` catch only the relay half and read as if it caught both. A Tauri command is reachable from the webview alone, so getting there already mean somebody pressed send.

**`track_daily` throttle it, and it is deliberately *not* persisted.** At most one report per local day per key, per process, over a `Mutex<BTreeMap<String, String>>` of key → date. **The day is claimed inside `send`, *after* consent is read** — never at the spawn. Claiming up front look equivalent and is the shape DRA-199 already got caught by: an install launching opted **out** claim the day, send nothing, then silence itself for the rest of that day if the reader turn reporting back on. Process state consent have to remember to clear is a second place for consent to be wrong; claiming after it is asked leave nothing to clear. PostHog count distinct people per day, so one install reporting three times is still one active user — a restart re-reporting cost one event and move no number, where remembering across runs cost a file, a lock and a corruption path on the launch path. `claim_day` is split out so the throttle test need no clock and no request. Known wrinkle nobody is fixing: local date and the PostHog project's timezone disagree at the edges.

**`source` separate the two populations reporting into one project** — `"app"` in `base_properties`, `"site"` registered on the web SDK. The app carry a stable install uuid where the site is cookieless per visit, so an unfiltered "unique users" figure is the sum of two things that mean different things. `$lib` half-separate them already, but a dashboard built on a property's *absence* break the day something else stop setting one. **The one thing here that cannot be backfilled.** The site register it from `init`'s `loaded` callback rather than after `init` return, since the first pageview is captured inside `init` and a super property only ride captures made after it.

**Screen views were cut, not deferred** — which tab is open is not a question being asked, and `$pageview` would be the wrong name for it anyway: that event drive PostHog's Web Analytics product, which is clean and site-only today.

**`feature_used` is one event with the feature as a property, never an event per feature.** PostHog break one insight down by property, where a name each is a chart each to keep in step, and a feature added later then show up in the existing breakdown with no dashboard change. Reported on the feature *working*, not the control being pressed — **with one stated exception, the handoff row**, which report on the press. `handleSendMsg` catch its own failures and resolve either way, so awaiting it report identically on success and failure, and a real fix mean changing that function's contract, which the main composer path share. The question that number answer is whether a row parked behind the composer get *found*, which the press is the signal for; a send failing past there is the agent failing, and the transcript is where that show. Every other one sit at the **chokepoint every route pass through** — `transcribe_audio` rather than the two dictation commands, so a retry that finally produced words count like a stop that did; `connect_linear` after both the key and the account are down, so it report a connection rather than an attempt.

Today: `dictation` — which carry the **model id** beside it, since nothing else say whether `recommended()` is a pick people keep or which catalog entries are worth carrying — plus `fork`, `pr_merged`, `linear_connected`, `space_created`, `worktree_deleted`, `settle` / `unsettle` / `pin` / `unpin`, and `handoff_commit` / `handoff_pr` / `handoff_runServer`.

**`error` report *where* it broke, never *what it said*, and that rule is the whole feature.** An error string or a stack frame carry file paths, and a path carry the project, the branch and the client's name — so a property may be a closed tag (a stage, a harness, a `file:line` of our own source) and never a `String` that came out of an error. Three kinds today, one event with `kind` as a property, the same bargain `feature_used` make. **Panics** ride a `set_hook` chained to the previous hook, so abort behaviour is unchanged, and carry location and thread name, **never the payload** — a panic message is arbitrary text and `expect` is routinely handed a path to explain itself with. A `Location` is a compile-time constant naming the *build* machine, and `trim_source_path` cut the rest: `trim-paths` is the proper cure and is **not stable on the toolchain the release workflow pin**, so a registry or git-checkout path keep the part naming the crate and anything else still absolute is cut to its file name. **Parse failures** report at `harness::record_failure` — the same chokepoint as `store::record_parse_failure` one call down, which cannot name the harness — carrying `stage` and harness alone; `raw` is the whole CLI line and `detail` a serde message free to embed the value, so neither leave the machine. **Once per `<harness>/<stage>` per run**, since a wire format that moved fail every line of a live session and the second failure say nothing the first did not. **Failed update installs** report `InstallError`'s tag, a closed set, from a single point `install_update` wrap its body for. Frontend uncaught errors are deliberately out — JS messages and stack frames carry paths, and scrubbing them is its own piece of work (DRA-200).

**The four flag actions come out of `set_session_flags`, which is both buttons' one chokepoint**, and they report only where the flag **changed**: the frontend send the value it wants rather than a toggle, so `pinned: true` on an already-pinned session is a no-op and not somebody pinning it. Collected before the fields move and reported *after* the write, so a failed write report nothing. Named in the reader's vocabulary, not the field's — the row say Settle where the index say `archived`, and the question asked of the number is about the button.

**`space_created` check for the name twice, and the duplicate is the point.** A space is declared in local storage, so the only chokepoint is a `setState` updater — and React may call one twice, which would count one space as two. The report therefore sit *outside* it, judged against `spaces`, the union: re-declaring a name some project already carry as a tag is no new space to the reader, whatever the declared half of the list say. **The browser is deliberately unmeasured** — its only honest chokepoint is `create_tab`, which a page's own `window.open` reach as well as the reader do, and what that should count is an open question rather than a missing line.

**`track_feature` is the one command the frontend report through**, for the handful whose chokepoint is a click handler — the handoff row, whose `action.id` is already a closed union, so a fourth button cannot arrive nameless. It take a `String` and validate nothing: the only caller is this app's own frontend, and a permitted list there would be a second copy of one the call sites already are. Consent and the install id are still read inside `track`, so the webview cannot report anything Rust would not. The frontend side ([analytics.ts](apps/desktop/src/lib/analytics.ts)) **swallow every failure**, since the one thing worse than a missing event is a feature failing because counting it did.

**A persistent install id, and it is minted only for an install that is opted in.** A uuid **v4** on `settings.json` — not the v7 used for session ids, which embed the moment they were minted, one more thing an identifier meant to say nothing would say. `set_analytics_enabled(false)` **clear** it, so opting back in read as a new person rather than the old one resurfacing.

**Consent and the id are one decision under one hold of the lock**, which is why `ensure_install_id` live in [settings.rs](apps/desktop/src-tauri/src/settings.rs) and not in `analytics`. Both halves of that were wrong first time and both were caught in review (DRA-199):

- **Nothing caches the id in-process.** A `OnceCell` held it, and nothing invalidated it when the switch moved — so disabling and re-enabling inside one run handed back the very id the opt-out had just forgotten. A cache here is a second place for consent to be wrong; the file read it saves is small and happens a few times a session.
- **`settings::update` is the only way to change a setting, and `write` is private so that is true rather than aspirational.** `read` take no lock, so a read-modify-write in two steps can be interleaved and lose the other's field. There was a `pub write` beside `read` and seven callers pairing them — the shape that fails, and it fails **across features, not within one**: the Linear account or a transcription pick read while analytics was on, then written back after the reader opted out, restoring `analytics_enabled: true` and the install id with it. So consent could be undone by a setting that have nothing to do with it. Fixing the analytics caller alone and leaving a comment saying "use `update`" was the first attempt and it missed all six others; taking the write away is what stop the next one.
- **`update` recover from a *malformed* file and never from an *unreadable* one**, and `is_malformed` — an anyhow downcast to `serde_json::Error`, which the context chain preserve — is what tell them apart. Bytes that cannot be parsed can never be preserved, and erroring there would block every settings write until somebody deleted the file by hand, which nothing on screen say to do. Bytes that cannot be *read* are the opposite: the file may be perfectly good and merely unreachable for a moment, so writing over it would erase the Linear account, the install id and every transcription pick to change one unrelated switch. Where it does recover the fallback is `opted_out`, never `Default` — recovering must not be a route back to reporting for somebody who turned it off.
- **A failed write answer `None`**, reversing what the cached version did. With no cache, an id that did not reach disk would be re-minted on the very next event and every event arrive as a different person — no events beat a fabricated population.

**No transport plugin, and no new dependency.** `reqwest` is already here for Linear, and PostHog's capture API is one POST, so an event is a request rather than a queue with a flush interval — at single figures per session, batching would buy nothing and cost a drain on the quit path. `tauri-plugin-aptabase` came out with 282 lines of `Cargo.lock`.

### Surveys, and the one thing the POST cannot do

**`posthog-js` is in the webview, and it is there for surveys alone** ([surveys.ts](apps/desktop/src/lib/surveys.ts)). A survey is fetched and drawn client-side by that SDK and by nothing else, so with the POST as the only surface there was nothing in this app a survey could appear *in* — and no amount of targeting fixes a window with nothing to draw it. The SDK captures nothing of its own: `autocapture`, `capture_pageview`, `capture_pageleave` and session recording are all off, and every event this app reports still goes out of `analytics.rs`. **It is not a second analytics client so much as a second surface of the same consent**, which is what decides everything below.

**Targeting reads *persons*, which is the half that had nothing behind it.** `source: "app"` rides every event as an *event* property, and a survey cannot be aimed with one — so the app's install-uuid persons carried nothing at all and `source` was simply absent from the survey UI's field list. `person_profiles: "always"` plus a `$set` of [`base_properties`] is the fix, and it is why `SurveyIdentity` carries that map rather than the frontend naming the fields again. Pinned by test: dropping one from `base_properties` costs a targeting option in PostHog's UI and says nothing whatever in this tree. `identified_only` is the *site's* setting, where every visit is a new cookieless id and there is deliberately no person; here it would leave nothing to target.

**The marketing site can never draw a survey however one is aimed**, since it loads `posthog-js/dist/module.slim` and surveys are one of the four things that build drops. So the app/site split costs nothing here beyond the filter being there when it is wanted.

**Consent is read in Rust, once, and `analytics_identity` is what keeps it that way.** It answers with a key, a host, the install id and the person properties together, or with `None` — and `None` is the refusal, on all three grounds: no key compiled in, `DRAY_NO_ANALYTICS`, or an install that opted out. The frontend initialises nothing on it and never reads `analytics_enabled` for itself, because **a second reader of consent is free to disagree with the first**, which is exactly what DRA-199 was already caught by once. Key and host ride along for the same reason rather than becoming a `VITE_POSTHOG_KEY` beside `POSTHOG_KEY`: two build-time variables for one project are two things that can drift, and the drift is silent.

- **`bootstrap`, never `identify`.** The POSTs have already made the install id a person; identifying into it would alias an anonymous id nobody ever used.
- **Started from [main.tsx](apps/desktop/src/main.tsx), not an effect**, the same bargain the focus subscription beside it makes — the SDK lives for the process, and StrictMode double-invokes a mount. Unconditional, since it refuses itself.
- **The settings toggle calls it again**, after the write and unconditionally: the SDK re-reads consent from Rust for itself, so the call only has to say the answer may have moved. Opting out clears the install id and opting back in mints a fresh one — a new person on purpose — so that is the one place the bootstrapped id goes stale, and it is the one place `identify` is right.

**`session_count` is on the identity, and it is what a survey is aimed with.** PostHog receives nothing that counts sessions; the index is the only place the answer lives, so `identity()` reads it. Added there rather than in `base_properties`, a `OnceLock` answering once for the life of the process where this moves with every session made. A failed read leaves the property absent, which a survey targeting a minimum reads as **not** matching — the safe direction, and the cure is opening the app again. The threshold is PostHog's to change, which is the point of it being a person property rather than a rule in this tree.

**PostHog draws the card, and Dray draws nothing.** A survey is written, targeted and reworded entirely in its UI with no Dray release. The cost, stated: the card is *theirs* — colours and radius are settable, the layout is not, and the byline only comes off on a paid plan, so it will not match [DESIGN.md](apps/desktop/DESIGN.md).

**A Dray-drawn card was built and reverted, and the reason is worth keeping.** `getActiveMatchingSurveys` hands the questions over, `disable_surveys_automatic_display` silences PostHog's own display loop, `capture("survey sent", …)` reports back and the answers still land in the survey results view — it works, and the whole of it is in the history of DRA-257 if the stock card ever grates. What it costs is a payload this tree has to build correctly: the response key is `$survey_response` for the first question and the question's **id** or index after that, `id` being optional on the wire, and which key the results view reads has moved between PostHog versions. A wrong one loses the answer silently. That is a real price to pay for a nicer card, and it is not worth paying until the stock one has actually been seen and disliked.

**Frontend uncaught errors are still out of scope.** The SDK arriving does not change that JS messages and stack frames carry paths and that scrubbing them is its own piece of work (DRA-200).

**Nothing is stamped for us.** Aptabase's plugin put `appVersion`, `osName` and friends on every envelope itself; PostHog do not, so `base_properties` build that set once — `app_version` (from `CARGO_PKG_VERSION`, which `tauri.conf.json` hold too), `os`, `arch`, `is_debug`. **OS version is deliberately absent**: nothing in the tree knows it, and reading it mean a new dependency or spawning `sw_vers` on the launch path for a figure nobody has asked a question of. Event properties are merged **over** the base set, so a call site can correct one.

**`track` is not `async` and take no `AppHandle`**, which is what let the feature sites call it — several are synchronous commands with no handle in reach, one of them on CEF's main thread. It spawn, and consent is read *inside* the spawned half on every call, so a new call site cannot forget to ask and cannot run ahead of the persisted answer. `app_started` therefore fire from `setup` as one line that returns immediately.

**An empty key = a build that sends nothing, and that is the ordinary state.** `API_KEY` come from `option_env!("POSTHOG_KEY")`, so every local build compile with none and `pnpm tauri dev` stay out of the numbers. Checked **before** the settings read, or every event cost a file read on a build that sends nothing. `build.rs` declare `rerun-if-env-changed` for it and for `POSTHOG_HOST`, since `option_env!` resolve at compile time.

**`POSTHOG_HOST` treat the empty string as unset, and that is not defensive.** [release.yml](.github/workflows/release.yml) pass it through from a repository **variable**, which expand to `""` when undefined rather than being absent — so `Some("")` is the ordinary case for every build that has not set one, and taking it literally would post every event to `/i/v0/e/` with no host in front of it. Pinned by test. Region is worth a knob at all because the wrong one is a key that authenticates nowhere: a 401, logged, and no events.

**A non-success status is logged, not dropped.** Best effort otherwise — analytics that surfaced an error would be worse than analytics that went missing — but the two ways this silently reports nothing, a wrong key and a wrong region, both land there.

**Opt-out is read off `settings.json` on every `track`.** No in-process copy: `enabled()` is `!env_opt_out() && settings::read().analytics_enabled`, so the settings command write the file and nothing else.

**The persisted answer lives in `~/.dray/settings.json`, not local storage, and timing is the whole reason** ([settings.rs](apps/desktop/src-tauri/src/settings.rs)): `app_started` send from `setup`, before the webview exists. **Anything the frontend can read for itself belongs there, not here**, or this becomes a second settings store free to disagree with the first. `DRAY_NO_ANALYTICS` win one direction only.

**`install_id` is `#[serde(default)]`, and that is load-bearing the way every field on that file is** — the settings file is rewritten whole and read on a launch path where a parse failure fall back to opted *out*, so an entry written before the field existed failing to parse would silently turn reporting off. Pinned by test.

**The read fail *closed*, and a missing file is not the same case as a broken one.** Missing or empty = fresh install, read as the default (opted in). Anything else — unparseable JSON, unreadable file, no home dir — read as opted **out**, since a file that exists and can't be understood far likelier belongs to someone who turned this off. Never an error either way: this sits on the launch path. Pinned by test, and the direction is the test worth having. `track` read consent itself before sending, so nothing can go out before the file is read.

**The marketing site report to the same project, and it is a different bargain.** [instrumentation-client.ts](apps/web/src/instrumentation-client.ts) — Next run it before hydration, which is why there is no provider and nothing mounted in the layout; a `<Script>` or a layout `useEffect` both start measuring a page view later than the page view happened. `@vercel/analytics` came out, so the site has one analytics tool rather than two that disagree.

- **Cookieless** (`persistence: "memory"`), which is what mean no consent banner — at the cost that every visit is a new person, so referrers and conversions answer and returning visitors do not. Autocapture, session recording and person profiles are all off.
- **Ingest is proxied** through `drayhq.com/ingest`, rewritten in [next.config.ts](apps/web/next.config.ts), so a content blocker see a first-party request. **Two rewrite rules, not one**: the SDK fetch its own assets from a *different* host to the one it post events to, so a single catch-all leave the script 404ing and nothing measured at all. `skipTrailingSlashRedirect` go with it, since PostHog's API care about the trailing slash Next would otherwise strip. `api_host: "/ingest"` is the other half — change one and the other stop working silently.
- **[lib/posthog.ts](apps/web/src/lib/posthog.ts) is the site's one import of the SDK, and that is not tidiness.** `posthog-js` export a default instance *per module record*, so a file importing `"posthog-js"` beside one importing the slim build get a second instance `init` was never called on, whose `capture` calls go nowhere **silently**. It also pin the slim path: 148KB against 309KB, 45KB off First Load JS, everything it drop already disabled. The deep path is no declared export, so a version bump move it — which fail as a build error rather than quietly, the acceptable direction.
- **The download click use `transport: "sendBeacon"`**, since the href is a plain off-site navigation and the default transport is a request the browser is free to cancel as the page goes.

**The dialog draw *effective* state, not stored state** — `get_settings` answer off `analytics::enabled()` with `analytics_locked` beside it, so with `DRAY_NO_ANALYTICS` set the row disable itself and name the env var instead of sitting at `on` while nothing is sent. `env_opt_out()` is read in one place.

## Notifications

Three events hand a session back to the reader — it finished, it wants permission, it asked a question — and each announce itself on **exactly one channel**, chosen by where the reader is. `announce` in [useSessions](apps/desktop/src/hooks/useSessions.ts) is that split, written once and shared:

| focused | on screen | outcome |
|---|---|---|
| no | either | desktop notification |
| yes | no | in-app notice |
| yes | yes | nothing — the transcript *is* the notification |

Channels are exclusive, not additive: a card drawn for something the OS already told the reader is a second interruption for one event, and an in-app card is invisible from another app anyway.

**A fourth event ignore that table entirely: a PR turning ready to merge.** [usePrReady](apps/desktop/src/hooks/usePrReady.ts) raise an in-app card **unconditionally** and post no banner. The table's question is "has the reader seen this happen", and for the other three the answer is on screen — the turn's own output is the notification. This one has no such moment: CI report on someone else's schedule, and the panel line going from "Checks not passing" to "Ready to merge" is a silent two-word swap, so *being on the PR tab ≠ having noticed*. Nothing retire it but its own clock — no read-marking, no rail mark.

**Signal = transition, not state.** The first reading of a session is recorded silently; only a change out of it is news, since the app cannot tell a PR that turned green a second ago from one green since last week. `readyTransitions` ([pr.ts](apps/desktop/src/lib/pr.ts)) own that rule and the pruning with it — a session that stops being watched is **forgotten**, so it comes back as a first sighting. Re-seeding costs an announcement never made, where remembering `false` across an absence raise one for a PR that was ready the whole time.

**Read off the sidebar's marks, not the panel's own fetch**, since the panel's poll gate on its tab being visible and active — exactly the case with nothing to announce. So `QUERY_MARKS` carry `mergeable mergeStateStatus` on the **open half only**: a merged PR cannot become ready, and `mergeStateStatus` is computed *on being asked*. `None` there read as **unknown, not ready**.

**One ordered rule, two presentations.** `mergeVerdict` is the order; `mergeReadiness` turn it into the panel's sentence and `readyToMerge` into the one question the notice turns on — three-valued, `null` where GitHub hasn't worked it out, so `readyTransitions` hold the last reading instead of writing false over it (a merge move the base, every other open PR read UNKNOWN for a window, and settling back would read as news).

**Notices key on session *and* kind.** Keyed on session alone rested on "a session cannot both be blocked on a question and have finished a turn", which is false for the fourth kind: CI report while the agent stands still waiting for permission. `ANSWERED_BY_OPENING` spell out the three kinds opening a session answers — `pr` absent, since selecting a session ≠ looking at its PR.

**⌘G take the card without reaching for it**, acting on the **oldest** — the top one, next to expire — which make the key repeatable. The binding lives in `NoticeStack`, not `App`, so it exists only while a card does, and the cap is drawn **on** the card it acts on, which is also how the stack says which one the key takes.

**The progress bar is the timer, not a picture of one.** The store hold no `setTimeout` at all: the bar's `animationend` call `dismissNotice`. One clock means hovering pause both, so a card cannot vanish under a cursor reaching for its button, and it can't expire while the window is occluded and the animation throttled. `completed` run 10s, `asking` 15s. **A card going away ≠ the signal going away** — the `asking` one leave the session still blocked, which is fine because the yellow rail mark stays lit until the request is answered.

**Reading requires looking, so a `completed` notice on the selected session is only retired when the window has focus.** The other half is a focus listener marking it read on return, without which a session finishing in the background stay unread forever.

**The sidebar rail carry both marks and they mean different things.** Green = *unread*: the turn is over, cleared when the row is viewed. Yellow = *waiting on you*: the turn is still open and only an answer clears it, so viewing the row leave it lit. Yellow wins where both apply. The waiting set is frontend-only (`asksBySession`, request ids so `permission_decided` retire the right one) and deliberately **not** folded into `SessionStatus` — the backend report these sessions `in_progress` and is right to. Cleared when status leaves `in_progress`, which is what stop a stranded request marking a dead session as waiting forever.

**Dock badge = that same pair, counted** ([attention.ts](apps/desktop/src/lib/attention.ts), [useDockBadge.ts](apps/desktop/src/hooks/useDockBadge.ts)) — one predicate shared with the rail (`asking || status === "completed"`), so the number is a promise about what opening the window shows. It needs no clearing path of its own, and `0` goes out as `undefined`, which is what removes the badge. Counting read three sources, each covering a hole the others leave: `statusBySession` is empty at launch where the index carry `completed` from last run; the index list hold one side of the archived split at a time; and `asksBySession` is in neither. Live status wins over persisted.

Two Tauri facts. `core:window:allow-set-badge-count` is **not** in `core:default`, so it is named in [capabilities/default.json](apps/desktop/src-tauri/capabilities/default.json) — with the same failure mode as `start-dragging`: the ACL refuse and report nothing. Unlike the desktop banner, this one **does** work under `pnpm tauri dev`.

**Focus is read imperatively, never as state** ([focus.ts](apps/desktop/src/lib/focus.ts)) — the one caller that matters sits inside a Tauri listener registered once with `[]` deps, where a state value is the mount-time one forever. The source is Tauri's `onFocusChanged`, not the DOM's `blur`: a webview blur whenever focus leaves the document, which a native menu or devtools do without the user leaving the app.

### The desktop banner

**Posted from Rust, not from `tauri-plugin-notification`** ([notifications.rs](apps/desktop/src-tauri/src/notifications.rs)). The plugin cannot deliver a click on desktop and no configuration makes it: its desktop path spawn `show()` and drop the returned handle, and its `onAction` listener is wired to an event only mobile backends emit. Worth knowing because it *looks* like it works — macOS raise the app on click by itself, so the window comes forward and then sits on whatever session was already open.

`notify_session` wait on the handle, and `"default"` (the body, against `"__closed"` that dismissal and expiry both report) raise the window and emit `notification_activated` with the session id. The wait block until the reader acts or the banner ages out, hence `spawn_blocking`. **Raising the window and selecting the session are separate and both needed.**

- **A banner with no sound is delivered silently**, wrong here since this channel only fires when the reader is in another app. notify-rust call `setSound` only when `sound_name` is set at all, and the value is a trap: `""` reads like "no sound" and is the opposite, being the name that resolves to the **system default**. `asking` get **Ping**, since a question left unanswered holds the session open; `completed` take the default.
- **`preview-macos-un` is not an optional feature here — without it nothing is delivered at all.** notify-rust's default macOS backend is the deprecated `NSUserNotificationCenter`, which current macOS does not deliver for an app: measured from inside the running app, every shape timed out at exactly 2.0s while the *same code* in a plain CLI process delivered a clickable banner. `tauri-plugin-notification` post the same way and would fail identically.
- **The banner cannot work under `tauri dev`, and the guard is `is_dev()`.** `UNUserNotificationCenter` reach for the process's bundle and raise an **uncaught** `NSInternalInconsistencyException` when there isn't one, aborting the app rather than returning an error. `check_bundle` is *not* the guard to reach for — it only ask whether a bundle *identifier* exists, and the embedded `Info.plist` satisfy it right up to the frame that killed the app.
- **The bundle need a signing identity or macOS refuse permission silently.** Tauri's bundler leave the app linker-signed under a generated identifier, and with that mismatch `request_auth` return `Ok(false)` with status `NotDetermined` and **no prompt ever shown**. `bundle.macOS.signingIdentity: "-"` in [tauri.conf.json](apps/desktop/src-tauri/tauri.conf.json) fix it. This is the floor below which notifications don't work at all.
- **Permission is asked once per process, on the first banner** (`request_auth_once`). The call **block until the reader answers**, so a per-banner ask park a thread per notification behind one prompt. Nothing branch on the result: denial is silent and permanent, and the in-app notice cover the reader either way.

## Parser conventions

[parser.rs](apps/desktop/src-tauri/src/harness/claude_code/parser.rs) is the file most likely to need extending, and it has firm conventions:

- `ClaudeCodeEvent` = externally-tagged enum on `type`. `SystemEvent` and `ResultEvent` nest a **second** tag on `subtype`. Adding a new CLI event = adding a variant at the correct level.
- `stream_event.event` is fully modelled as `StreamFrame`. Every stream enum carry a `#[serde(other)]` catch-all so one unknown frame type doesn't cost the whole line.
- Genuinely volatile payloads (`message`, `usage`) stay `serde_json::Value`.
- Fields the CLI may omit need `#[serde(default)]`. CamelCase wire fields need an explicit rename.
- **A field the CLI may send as `null` need `null_as_default` as well as `default`.** The two are not the same and the difference is invisible until it bites: `default` answer for a key that is *absent* and do nothing for one present and null, which then fail against any non-`Option` type. `usage.iterations` is the captured case — a **synthetic** message (`model: "<synthetic>"`, the reply to a built-in slash command) send it as null, which failed the whole line, so every built-in command silently produced an empty turn. Reach for `Option<T>` where absence is meaningful and `null_as_default` where it isn't.
- **Failures are swallowed per line and filed.** `read_stdout` log and continue, so a schema mismatch presents as a missing UI update, not an error. Every one lands in `~/.dray/parse_failures.jsonl` with the raw line. `stage` = `parse` (no variant matched), `map` (mapper errored), `unknown_subtype` (a catch-all arm caught it, so the line survived but we learned nothing), or `unsupported_request` (a control request we had to refuse to keep the turn moving — the only stage that changes what the agent does, so treat it as urgent). Read it after a session with `jq -r '.stage + " " + .detail' ~/.dray/parse_failures.jsonl | sort | uniq -c`.
- **A line worth no UI is still worth modelling, to keep that log a signal.** `tool_progress` is a 30s liveness ping and was a third of the whole failure file. Parsed and mapped to `None`. Apply the same reading to the next high-volume line that turns out to say nothing.
- `McpServer` and `ApprovalPolicy`/`PermissionMode` are defined once in `events` and re-exported. Don't reintroduce per-harness copies.

**Outbound lines are typed too** ([control.rs](apps/desktop/src-tauri/src/harness/claude_code/control.rs)) — `ControlRequest` tagged on `subtype`, `ControlLine` minting `request_id`. Typed despite nothing here failing at runtime, because a wrongly shaped request is not reported: the CLI answer what it recognises and stay quiet otherwise, so a drifted envelope presents as a control that silently stopped working.

## Rendering code

Every surface showing code — `Edit` diffs, ranged `Read` slices, markdown fences — go through **one** Shiki highlighter, the shared instance inside `@pierre/diffs`: [DiffView](apps/desktop/src/components/chat/DiffView.tsx), [CodeView](apps/desktop/src/components/chat/CodeView.tsx), and [codePlugin.ts](apps/desktop/src/lib/codePlugin.ts) replacing `@streamdown/code`'s runtime. Sharing is not just deduplication: the stock Streamdown plugin build a *second* Shiki with its own registries, which cannot see `pierre-*` at all.

**Themes are `{light, dark}` pairs, never one name** ([codeTheme.ts](apps/desktop/src/lib/codeTheme.ts)) — the app's mode can change under a mounted view. **The shipped default is `auto`, which mean the app theme, so `codeThemePair` take one** — resolving without it drew every palette's code in Pierre's colours and switched on mode alone (DRA-183). `AUTO_THEMES` hold the map; a palette with no Shiki counterpart take the nearest, never a grey. [useCodeTheme](apps/desktop/src/hooks/useCodeTheme.ts) is `useSyncExternalStore`, not `useLocalStorage`, because several diffs are mounted at once and per-component state desync them.

Three failure modes, all presenting as _code that renders but is blank or grey_ rather than as an error:

- **A view must not mount before _its own_ language and theme are attached.** `FileDiff`/`File` kick off their own load when they hydrate without one, then drop the promise and never re-render. [useHighlighter](apps/desktop/src/hooks/useHighlighter.ts) is the single gate both views use, checking `getLoadedThemes()`/`getLoadedLanguages()` for the specific pair and language. **Do not gate on `isHighlighterLoaded()`** — it only report that an *instance* exists, so a view whose grammar is still loading mount the moment any other view warmed the highlighter.
- **Themes and grammars load independently.** Tokenizing with a theme unattached return every token with an empty style; with a *grammar* unattached it silently yield one plain-text token per line. `codePlugin` check both and report not-ready rather than caching either result — caching the plain-text fallback is what left blocks permanently grey.
- **A fence's info string is a language id, not a filename.** `getFiletypeFromFileName` map *extensions*, so it turn `typescript` and `rust` into `text` while only `ts` happens to work. Use it for paths, never a fence tag.

**Streamdown's link hardening write into prose, so we replace its rehype list** ([markdownPlugins.ts](apps/desktop/src/lib/markdownPlugins.ts)). `rehype-harden` drop an href it cannot resolve — right — then leave a literal ` [blocked]` beside the link, which lands in the reader's text as if the agent typed it. `linkBlockPolicy`/`imageBlockPolicy` = `text-only` unwrap instead. Streamdown expose no option, so the whole `rehypePlugins` list is passed, with **harden's own function taken back out of `defaultRehypePlugins`** rather than from a direct dep, which pin it to the version Streamdown itself runs.

`File` number files from 1 and expose no starting-line option, so `CodeView` rewrite the gutter in `onPostRender`, which hand back the *host* element whose rows live in its shadow root.

**Every diff side carry a content-derived `cacheKey`** (`diffSide` in [diff.ts](apps/desktop/src/lib/diff.ts)). The library fall back to the file *name* as the key and the worker pool cache highlighted lines on the key alone — so a second `Edit` to one file, or `index.ts` from another dir, reuse the first one's tokenized result and a longer diff walk off its end ("deletionLine and additionLine are null", thrown mid-render). Key = full path + length + FNV-1a of the text. **Never hand `parseDiffFromFile` a bare `{name, contents}`.**

**`+N -M` come from the library's hunks, not a hand-rolled scan.** `countChanges` sum `hunk.additionLines`/`deletionLines`, so a collapsed row can never disagree with the diff it opens. A prefix/suffix scan looks equivalent and isn't: `Edit` fragments usually arrive without a trailing newline, so the algorithm treat the boundary line as changed on both sides. Group headers carry the same figure summed over their calls, memoized on call count rather than on `calls`. These are *region* counts, not file counts.

**Where time goes, and the engine is the whole answer.** Every Shiki instance here — the shared main-thread one and each pool worker — run on **WASM Oniguruma** (`HIGHLIGHT_ENGINE` in [useHighlighter.ts](apps/desktop/src/hooks/useHighlighter.ts)), never the library's default JavaScript regex engine. `getSharedHighlighter` read the engine on first creation only, so **every creation site name it** — `warmHighlighter`, `useHighlighter`, `codePlugin`, `DiffWorkerPool` — or whichever run first decide for the rest. Measured in Safari 26.5 (the WKWebView's JavaScriptCore) through this app's own components, the JS engine tokenized at ~1ms/line (2237 lines of TS = 2.2s, a full-file diff twice that) and translated each grammar's regexes lazily on first use — ~1.9s for TypeScript, paid **separately** by the main thread and by each worker — so a small Edit waited 1.0s, a small Read 1.8s and a 2000-line full-file diff 5.8s (DRA-235). Same code on WASM: 230ms for those lines, 150ms cold, 110ms → 1.4s for the same three. V8 hide the gap (3x, not 10x), which is why a Chromium head never showed it; **measure code rendering in Safari or the app, never in the session browser.** The binary is base64-inlined in `shiki/wasm`, so nothing is fetched. Grammar *attach* is the cheap half (~25ms for the whole `COMMON_LANGS` set) and is per language and one-off; *tokenizing* is per file and scales with the whole file, not the change. `warmHighlighter` preload a **named list** — keep it that way. Anything absent still load lazily and render *unhighlighted but readable* meanwhile. **A `File` input want a `cacheKey` like a diff side does** (`diffSide`), or the pool cache nothing for it and every remount tokenize again.

**Diff highlighting run in a worker pool** ([DiffWorkerPool.tsx](apps/desktop/src/components/DiffWorkerPool.tsx)) — without one, whole-file tokenizes ran on the main thread and expanding a row froze the app for up to a second. `FileDiff`/`File` pick the pool out of `WorkerPoolContext` themselves and fall back to the main-thread path (`isWorkingPool`) rather than erroring. Three wiring facts: the worker is built by Vite's `?worker` import (the library take a factory because it cannot know the host's bundler); `worker.format: "es"` in [vite.config.ts](apps/desktop/vite.config.ts) keep the worker's conditional `import("shiki/wasm")` from being inlined as ~600KB; and the pool's theme **override** each view's `theme` option, so `PoolThemeSync` push pair changes via `setRenderOptions`. Pool size 2, not the default 8. Markdown fences still tokenize on the main thread.

**A long session open on its newest turns and backfill the rest.** Opening an 11MB, 61-turn log measured ~700ms, and bytes were not why — what cost was mounting every collapsed turn's answer through Streamdown at once. So [Chat.tsx](apps/desktop/src/components/Chat.tsx) draw the newest `FIRST_MOUNT` turns on the first commit and mount older ones above in `MOUNT_STEP` chunks, one per macrotask ([turnWindow.ts](apps/desktop/src/lib/turnWindow.ts)). Each step grow content *above* what the reader is looking at: pinned, the bottom is re-taken; unpinned, the oldest mounted turn's node is anchored before the step and `scrollTop` moved by exactly what it moved — a height diff is wrong there, since a delta landing below the anchor would count as backfill. Not virtualised: backfill finish in well under a second and then the transcript is ordinary DOM.

## Composer

- **`isNewTask` is the composer's two presentations, not one flag per effect.** Before a session exists the composer stands alone mid-window, so [ChatInput](apps/desktop/src/components/ChatInput.tsx) drops the card's fill, border and padding, moves the toolbar above the input, swaps the placeholder, and replaces the send button with a "Press ⏎ to send" hint. Dropping the button is only safe because Enter-to-send lives in `onKeyDown` rather than in that button being the form's submitter — make it the submitter again and the empty state loses its send path.
- **The error slot reports the reader's own last action failing, and nothing else.** It is one `useState` for the whole app, so anything written there follows the reader to every other session and to the new-task composer. An agent `error` payload therefore is **not** mirrored into it: that error belongs to one session, is persisted, and `EventRow` already draws it as a red row in that session's transcript — mirroring it drew it twice and outlived the conversation it was about. One decision across every harness, not a patch per caller. What remains are `invoke` rejections, which the reader caused a moment ago, so both intentional selection moves (`handleNewSession`, `handleSelectSessionIndexItem`) clear the slot **on the way in** — never on the way out, since the session-not-found rollback writes its own sentence after moving the selection. **Clearing is half of it; `navGen` is the other half.** A send, an interrupt or a permission reply rejects seconds after the reader has moved on, and an unguarded catch writes the previous session's failure into the composer they moved to. So every **session-scoped** catch reports through `failUnlessLeft()`, taken at the start of the action: it captures the navigation generation and writes the slot only while no move has bumped it since. Four moves bump it — select, new task, a send minting a session, a fork opening selected — and the two that also start an action (select's read, send itself) take their `fail` *after* the bump, so their own failure still reports. **App-wide loads and actions stay on the raw setter** — the index, projects, branches, a checkout, a space retag: their failure is as true after a move as before it, and guarding them left a list stale or empty with nothing saying why.
- **A draft belongs to the session, not the composer.** [useDraft](apps/desktop/src/hooks/useDraft.ts) keys unsent text by session id, `null` for a new task. The store is **module-level, and a ref would not do**: `AppShell` renders the footer at a different position when `centered`, so moving between the empty state and a session unmounts `ChatInput` and mounts a fresh one — losing the draft on exactly the switch most likely to be made. Nothing is persisted. [useAttachments](apps/desktop/src/hooks/useAttachments.ts) is the same shape, and also because the `+` button lives in `ComposerToolbar`, which reaches `ChatInput` as an opaque `ReactNode`.

**Slash commands are prompts, not protocol.** Every one travels as ordinary prompt text and the CLI expands it, so sending one needed no new code and nothing new arrives on the wire. Two things follow: the transcript cannot tell a command from prose (the CLI never echoes the prompt back), so [UserMessage](apps/desktop/src/components/chat/UserMessage.tsx) re-parses the text with `parseSlashCommand` to draw the name as a chip; and the command *list* is the only part that needed a backend.

**The command list comes from the `initialize` control request, not from `init`.** `system/init`'s `slash_commands` arrives only once a turn is under way, so it cannot populate a picker for a composer with no session, and it carries bare names where the picker wants a description and argument hint. [commands.rs](apps/desktop/src-tauri/src/harness/claude_code/commands.rs) instead spawns a throwaway child, writes one `initialize` request, reads the reply and kills it: ~1.5s, no model call. Walking `~/.claude/commands` was the rejected alternative, since the CLI merges user, project, plugin and skill scopes and namespaces the results. Results are cached per directory on **both** sides and neither cache invalidates, so a plugin installed while the app is open needs a restart.

**Command source is inferred, and one half of it reads display text.** `commandSource` splits harness / plugin / user from the only two signals the payload carries: a plugin namespaces its name (`railway:deploy`), and a user- or project-scoped command has its scope appended to its *description* (`… (user)`). There is no scope field, so `harness` means "neither of those" and files the CLI's built-ins together with skills Anthropic ships beside them.

**fx's commands are its skills, and they are read off disk because nothing on the wire answers** ([harness/fx/commands.rs](apps/desktop/src-tauri/src/harness/fx/commands.rs)). Same reading Codex's picker takes — the rest of fx's own `/` menu (`/model`, `/clear`, `/login`, `/settings`) is TUI actions Dray already owns in its chrome. What is different is where the list comes from: `available_commands_update` is `[]` at `session/new`, still `[]` after a full turn, and still `[]` in a workspace holding a skill (fx 0.0.10), there is no `skills/list` to ask, no `fx skills` subcommand, and a promptless `session/new` is **persisted** — so an ACP probe would litter `~/.fx/sessions` and answer nothing anyway. So the roots are walked. `WORKSPACE_ROOTS`/`GLOBAL_ROOTS` are fx's own list verbatim, lifted from its `/skills` usage text, including the two asymmetries between the halves (`skills/` and `.opencode/skills` on the workspace side, `.config/opencode/skills` on the global one). First name wins, workspace before global, alphabetical within a root — `read_dir`'s order is stable nowhere and the picker draws what it is handed. Uncached, unlike every other harness's list: those pay seconds for a child where this is a dozen `read_dir`s, and a cache would buy milliseconds at the price Claude Code's and Codex's already pay, which is a skill installed while Dray is open needing a restart.

**The send path needs nothing, and that is the difference from Codex.** fx expands a leading `/name` itself — `/hello then also print DONE-8899` sent as ordinary prompt text ran the workspace's `hello` skill *and* honoured the words after it, verified live — so a pick travels as text the way Claude Code's does and there is no companion to `turn_input` here. **Over-listing is therefore the unsafe direction**: a row fx did not load sends `/name` to a model with no such skill. Hence a skill is a directory holding a *readable* `SKILL.md`, under a name that could be typed after a slash, and **`authorized` where it is a link** — fx refuses one it cannot resolve "to an authorized readable directory" and the two halves fail separately. Captured both ways: a skill linked to `/tmp/elsewhere` was absent from fx's catalog and the model went hunting with `glob_files` for the name it had been handed, where the same skill linked *inside* the workspace ran straight away. So the authorities are the workspace and home, canonicalized — `/tmp` resolves to `/private/tmp` and a plain `starts_with` on the written path finds nothing, the same trap the worktree lock lookup documents. A plain directory is never asked the question at all, or every skill under a symlinked home would drop out. `FX_SKILL_SYMLINK_AUTHORITIES` can add roots and is deliberately unread: its separator is documented nowhere, and a misread one costs a row rather than inventing a dead one. **Block scalars are read** (`description: >` with the sentence indented under it): that is how most skills in the wild are written, and skipping it left half the rows naming themselves and saying nothing. A YAML dependency for one scalar would be the largest thing in the file.

**A harness with no commands says so, and that is the `/` picker's one empty state.** `menuOpen` wants rows, so a list that is empty for good left the picker silent — and a `/` that does nothing reads as Dray broken rather than as this agent having none (DRA-217). One line is drawn instead of rows, naming no agent: a machine with no skills installed puts Codex and fx in the same state and the reader's question is the same either way. **Gated on the probe having answered**, which is what `useSlashCommands` returns `loading` for: Claude Code's ~1.5s cold read would otherwise flash "publishes no slash commands" over a list about to land. **A *failed* probe stays pending forever** rather than answering empty — an unreachable CLI is not a CLI with no commands, and saying the one in the other's words is a claim about the agent made out of a failure to reach it. The picker then simply never opens, which is what it did before there was anything to say. **The answer carries the key that produced it**, since `cwd` and `harness` move mid-render and state alone handed the previous harness's commands to the picker for the frame before the effect caught up — the same flaw `modelsByHarness` names, and the cache is read *during render* for the same reason the issue caches are. A query matching nothing still closes the picker quietly — that list is on screen, so its emptiness needs no narrating. `PickerMenu` takes the sentence as `emptyNote` beside `loading`, and drops `role="listbox"` where it is all there is, a box holding one unpickable line being no list.

**`@file` is the same bargain and needed even less.** The CLI parses `@path` out of the prompt itself, reads the file and injects it as a system reminder *before* the model turn — no tool call, no new event, nothing to map. A path that doesn't exist is ignored rather than failing the turn. Unlike a command, a mention is a word *inside* a sentence, so [mention.ts](apps/desktop/src/lib/mention.ts) finds the token around the caret rather than keying off position zero; the email guard falls out of that walk for free, since scanning back from the caret stops at whitespace, so landing on `@` proves it opens a word. A path containing a space can't be mentioned — the CLI's limit, not the picker's.

**The file list is an in-memory index, not a spawn per keystroke.** [files.rs](apps/desktop/src-tauri/src/files.rs) wraps [`fff-search`](https://github.com/dmtrKovalenko/fff), which walks the tree once on a background thread. Speed is not the only reason: typo tolerance, path-segment matching and git-status ranking come with it, and the last is what makes **an empty query the right thing to open on** — a bare `@` lists what the current turn has been touching. A filesystem watcher keeps the index current. Two limits are deliberate: `SharedFrecency::noop()`, since the crate's tracker is an LMDB store fed by a host editor's access log; and `MAX_INDEXES` capping live indexes at four. Everything touching the index goes through `spawn_blocking` — search holds a `parking_lot` read guard across the whole scoring pass, which must not be held across an await.

**Attachments are two features, because two kinds travel two ways.** [attachments.rs](apps/desktop/src-tauri/src/attachments.rs) decides which from extension *and* size together, so the composer's tile and the wire can't disagree. **Images** — png/jpeg/gif/webp under 5MB — become a base64 `image` content block alongside the prompt. Anything else becomes an `@/abs/path` mention appended to the prompt text, so it needs no wire surface at all; that cheapness is also why an oversized or unsupported image *degrades* to a mention rather than failing the send.

- **Only paths cross the bridge.** `read_attachments` hands the composer a thumbnail as a `data:` URL; `send_msg` takes back a path and re-reads the file.
- **Images are copied into `~/.dray/attachments/<session-id>/` before the path is recorded.** Persisting base64 instead puts megabytes into an append-only log read whole on every open; pointing at the original breaks the transcript the moment a screenshot is cleared out of `~/Downloads`. Loaded through `convertFileSrc`, hence `assetProtocol` scoped to exactly that directory. Non-image files are deliberately **not** copied — their mention has to name a real file in a real tree.
- **The drop target is the window.** Tauri intercepts the native drop before the webview sees it, so there are no HTML drag events to bind; `onDragDropEvent` reports paths, not `File` handles.
- **A queued prompt's attachments ride its queue entry**, resolved, handed over by the composer at send. `QueuedMessage.attachmentPaths` is deliberately *unresolved* so a cancel gives back what the user typed, so the row would otherwise describe them a second time — and holding them anywhere but that state gives them a lifetime free to disagree with it. Images draw through `ImageRef.url`, never `path`: the archived copy the asset scope allows is written at flush. A file draws nothing, since its `@path` mention is written at flush too and the delivered bubble has no tile for one either.

**A picture a tool hands back.** `Read` of a `.png` comes back as an `image` content block and nothing else. **The bytes arrive twice on one line**, and one copy was being persisted: the result carries an `image` block *and* the line's `tool_use_result` sidecar carries the same base64 at `file.base64`, which went straight onto `ToolResult.structured` — a screenshot session was 12MB of base64 in a 14MB log, read whole on every open and drawing nothing. The mapper now reads the block and `strip_image_bytes` drops the sidecar's copy. It mints an `ImageRef` carrying a `data:` URL, then `archive_result_images` in `read_stdout` decodes, writes and swaps the URL for a path **before emit**, so live and replayed transcripts load the same file; `read_stdout` strips the URL before both retained copies. **A call carrying a picture leaves its group** — "Read 3 files" is an honest summary of three files and no summary of three screenshots.

**The picker is one menu that must not take focus.** Every other composer control is a Radix menu focusing itself on open; this one can't, since the editor has to stay focused so typing keeps filtering. So [PickerMenu](apps/desktop/src/components/composer/PickerMenu.tsx) is a plain positioned listbox and every key it answers to is handled by `ChatInput`'s own `onKeyDown`. Enter completes the highlighted row instead of sending — the single place the Enter-sends rule gives way. Both pickers are that one component, and they are **mutually exclusive without arbitration**, since the caret sits in exactly one token.

- **The composer and the transcript share one segmenter** ([highlight.ts](apps/desktop/src/lib/highlight.ts)). What the composer draws and what `UserMessage` draws must agree about *what is marked*, or a word coloured while typing goes plain once sent. `highlightSegments` concatenates back to the input exactly, and the test asserting that round-trip is what the whole thing rests on.

- Four commands are withheld from the picker in `commands.rs` — `clear`, `fast`, `model`, `rename` — because the app already owns what they do and none of their effects come back on the wire. See _Known issues_ for why hiding them is a stopgap.

### The composer is a contenteditable, and the value is still a string

**[RichInput](apps/desktop/src/components/composer/RichInput.tsx) replaced a `<textarea>` and the mirrored overlay painted over it.** The overlay existed because a textarea shows its value character for character and cannot style part of it — a second copy of the text, held in register by a shared padding constant. That tie is also why `&Title (uuid)` put 36 characters of address in the reader's sentence. Breaking it is the point: a placed tag is drawn as a `contenteditable=false` chip whose *face* is short while `data-tag` holds the run whole.

**Reading the tree back yields the string that built it, exactly** ([readValue](apps/desktop/src/lib/richDom.ts)). Everything else here is in service of that, and anything breaking it sends different words than the reader typed. Two shapes are load-bearing: a newline at a block boundary, since WebKit answers `insertText` of `\n` with a `<div>`, and a trailing `<br>` marked `data-filler`, which a `pre-wrap` box needs to show a final newline and which must not read back as one. `insertText` therefore spells its own line breaks with `insertLineBreak`, so the tree only ever gains `<br>`.

**A tag chips once the word is finished and the caret has left it** ([placeSegments](apps/desktop/src/lib/richText.ts)). `@s` is already a mention to the parser, so chipping on the parser's word alone would rebuild the DOM under the reader on every keystroke of a path — the overlay's own fragility. A caret *at* either edge counts as inside, the end edge being where it sits for every character of a tag being typed. That is also the stated cost: a chip erodes character by character rather than deleting whole, since "caret at its end" means both *still typing* and *just backspaced onto it*.

**The subtree is uncontrolled while prose is typed.** React writes to it only when `chipSignature` moves — a text run growing by a character answers no, so the browser keeps its own caret and undo stack. Programmatic edits go through `diffRange` plus `execCommand`, which is what keeps ⌘Z working across a pick.

**A chip's face is shorter than its run, and each drops something different**: a mention keeps the filename and trades `@` for the file glyph, a session tag keeps its title and drops the uuid, an issue tag keeps `#` and swaps the identifier for the title, elided. An issue title has **no closing delimiter** — `#DRA-53 Some title` runs straight into the sentence — so nothing can read its end back out of the text; `rememberIssueTitle` records what the picker wrote and `withIssueTitles` joins the two segments with it. The transcript answers the same question from the prompt's persisted `IssueRef`s, so a replayed message reads as it did live.

**Chips carry no `title`.** What one hides is a caret press away, and a native tooltip is the one kind this app does not use.

## Current state

Several things are deliberately unfinished — don't mistake them for bugs.

- **Session status is a state machine in `session.rs` and it follows the turn alone.** `StatusTracker`: send or `init` → `in_progress`; `result` → `completed`, whatever background tasks are outstanding. A background subagent runs past `result` and the CLI opens a promptless `init` later to report findings, which reopens `in_progress` on its own. Holding *was* the rule and it hung every session running a dev server or `Monitor`, all `local_bash`, none of which ever end. The task set is recorded beside status for two things only: `has_outstanding_work()` guarding child-replacing paths (effort respawn, update install) and the subagent panel's per-task stop — fork is **not** among them, since it replaces no child, and **Stop is not either**. The frontend keeps tasks in a live `tasksBySession` map, not off the log, since a task outlives its turn; `read_stdout` mints an empty `background_tasks_changed` when the child exits, emitted and **never logged** (it runs after delete removed the file, where an append would recreate it). `buildTranscript` takes live task ids and keeps a spawning call pending while its task lives, joining on `SubagentRun.taskId`, since `task_id` ≠ `tool_use_id`. **That same set is what *closes* a run, since `subagent_completed` cannot be relied on to.** It is `task_notification`, which only the child holding the task can send — so a child killed, respawned for an effort change or lost with the app takes every outstanding notification with it, and those runs shimmered in the panel with a Stop button on them for the rest of the session. A run whose task is gone from the live set is done once its spawning call has answered — a real result for a backgrounded `Bash`, the abandoned stand-in for anything the log leaves open — so the mark is applied after the abandoned marks, and a task the child still holds is untouched. **A panel full of running "Wait for…" rows is usually not that bug** (DRA-264): measured live, they were real `until grep …; do sleep; done` loops the agent had left polling for a log line that never landed, eight of them under one child — the CLI was naming them and the panel was right. Two things follow. **`agent_id` is empty, deliberately** — it is the handle a stop names and fx publishes none, so `transcript.ts` reads an empty one as *no handle* and the panel withholds a Stop button whose request fx could not take. And **`SubagentRun.inline` keeps the chat row a tool row**: the spawning call is the whole run here, so a row that only navigated would send the reader to a panel holding what they were already looking at. It is keyed on the harness rather than on "has this run filed any events yet", which is true of every run for its first frame and would flip the row out from under a Claude subagent the moment it started working. The row carries the orb, and `request.model`/`request.effort` sit on it beside the task where the agent chose them for the child — the work went somewhere else, which should not need a click to find out. **The brief is the row's own text, and opening the row un-clamps it in place** — one line collapsed like every other row, the whole thing wrapped when open. Drawn as a block under a truncated summary it put the task on screen twice in the chat and three times in the panel, whose row title is the task as well. It **wraps back under the label** rather than hanging off it, which is why the label, the settings and the summary become one inline flow for this row alone (`contents` on the wrapper leaves every other row's three flex items exactly as they were, and the flex gap becomes real spaces, or the accessible name reads `Delegatinggpt 5.6 luna high…`). **The panel draws that brief as text rather than the spawning call's row**, since a row brings a caret of its own — a second thing to open inside the pane just opened — along with a tool name and a report the header and the agent already cover. Every other harness still gets the row there, where it carries the prompt. **The report is not drawn at all**: a delegated run answers *the agent*, which says what it made of it in the next message, so the row would carry the child's answer a second time. A failure still shows, since the agent may carry on without mentioning it. `tools.jsonl`. Two more things measured, not read off fx's docs, both pinned by fixture:

  **`fx acp` reads no MCP config of its own, so Dray hands it the list** ([harness/fx/mcp.rs](apps/desktop/src-tauri/src/harness/fx/mcp.rs)), off `~/.fx/mcp.json` — the file `fx mcp path` names — on **both** `session/new` and `session/resume`, since fx keeps none of it across a connection (measured: resumed with an empty list, the tools are gone). `mcpServers: []` was not "use your own", it was "this session has none", and it is what left Dray's fx sessions with no tools while the same machine's `fx` shell had all of them (DRA-220). Shapes are fx's own validation, not ACP's prose: stdio is `{name, command, args, env:[{name,value}]}`, http/sse is `{type, name, url, headers:[{name,value}]}`, `headers` is **required** on every http server and must be that **array** — an object map is refused outright.

  **Dray forwards only what the reader already wrote into their own fx config** — a literal `headers`, or `header_env`/`bearer_token_env` resolved from the process environment and then the **login shell** (`$SHELL -l -c 'printenv NAME'`, the name interpolated only after `is_env_name` — a `$1` positional looked safer and is wrong on fish, which has no `$1`, so `printenv` dumps everything and the last line is some other variable sent as a token), since a Dock-launched bundle inherits launchd's environment and a token exported from `.zprofile` would otherwise read as absent — `binpath`'s trap again. **A bearer token has one spelling, `bearer_token_env`** — fx refuses a literal `Authorization` under `headers` or `header_env` (`McpConfigInvalidHeaders`, "so credentials do not become ordinary profile data"), so the key lives in the environment and `.zprofile` is where it has to be exported for a Dock launch. Verified: `bearer_token_env: "LINEAR_API_KEY"` gave an ACP session Linear's 66 tools with the variable scrubbed from Dray's own env. fx's OAuth store is never read: it **refuses to lend its own credentials** to an ACP-supplied server, answering "supply an Authorization header in the ACP MCP server configuration" even for a name it holds a live authenticated connection for — and to an *approved workspace* `.mcp.json` server too, which logs `McpAuthenticationRequired` in ACP and reads `auth=required` even natively after `fx mcp auth` (0.0.10); its docs: "ACP never inherits servers from `~/.fx/mcp.json`" and "ACP is noninteractive, so an ACP host must supply headers for a protected MCP server". A Dray-side reuse of the Issues panel's Linear key was built, flagged in review as spending a credential given for another purpose, and reverted — `bearer_token_env` makes it unnecessary. **A headerless HTTP server is two cases one config line cannot tell apart** — an endpoint wanting no auth takes `headers: []` and works, an OAuth-backed one takes the same list and fails the open — so `fx mcp list` (no `--connect`, no network) is asked: `auth=none` earns the empty list, anything else or a failed probe is a skip. Measured: the same entry reads `auth=none` under a home with nothing stored and `auth=authenticated` under the reader's, so it is fx's credential store answering, not the file. Run from home, so a project `.mcp.json` cannot answer for a profile server of the same name.

  **Every server on the ACP surface is *required*, and `open_with_servers` is what keeps that from being fatal.** fx's shell tolerates a dead entry under `policy=optional`; over ACP the same entry fails the whole `session/new` with `-32602 Required MCP server '<name>' failed to start`, so one stale command in `~/.fx/mcp.json` would make fx sessions uncreatable in Dray while working fine in a terminal. The named culprit is dropped and the open repeated — a refusal naming none sheds them all — and the child stays usable across a refused open, measured for both `session/new` and `session/resume`. Each drop is logged, since the reader's only other signal is a tool the agent cannot find. **Only an MCP refusal is retried** (`is_mcp_refusal`: the flattened error's `(code -32602)` plus fx's "MCP server" wording) — a timed-out open may already have persisted a session, and repeating it mints a second one nothing tracks. Project-scoped `.mcp.json` is deliberately unread — a repo-supplied server names a command to execute, and there is no trust prompt to put in front of that.

- **`effort` is simply absent** from the `configOptions` of a model that does no reasoning, and which models those are does not follow the vendor — on the gateway `anthropic/claude-opus-5` carries one and `anthropic/claude-sonnet-4` does not, `openai/gpt-5.4-nano` offers a `none` rung and `spacexai/grok-4.6` offers nothing at all. No table written here could name that. `effort_ladder.jsonl`.
- **The option list is the model's ladder unioned with the level the session is on**, and a model switch does not clamp that level, so a list can name a rung its model refuses and `session/resume` restates it: a session moved from `gpt-5.6-sol` at `ultra` onto `gpt-5.6-luna` reports `ultra` among luna's options and is still answered `-32602` for it. `effort_carryover.jsonl`.

So **what is remembered is narrower than what is used**. The session takes the list whole — fx judges its own session, and over-offering costs one reported refusal where withholding costs a rung fx would have taken — while the *model* list reads one reply as **two bounds** (`LadderReading`): `options` minus the current level is every rung proven, `options` whole is every rung still on offer. The subtraction is sound whatever the level is, since every survivor is one the model takes. `learn_ladder` keeps a rung where this reading proves it or an earlier one did **and fx still offers it**, which is what lets the level in use come back from the next reading instead of the menu shuffling one in and out, while a rung fx stops offering altogether is dropped rather than cached for the life of the process. **fx accepting a level is the third statement and the only proof the active model takes it** — no reply can say so, that being exactly the level subtracted out — so `set_effort`'s reply is read back with the accepted level put in. Without it, opening a session on a perfectly valid level teaches the picker that level is unsupported and `usableEffort` moves the reader off the effort their conversation has been running on. Trusting only a reading sitting on fx's `auto` was the rejected alternative: it is sound too, and does nothing at all for a reader whose fx default effort is not `auto`. A definitive "no effort option" replaces the lot. The rule is checked against every reply in every fixture by test, so a future fx widening the list some other way fails there first.

A refused effort is **never fatal and never silent**. Fatal is the half with teeth: the spawn used to `?` on it and kill the child, so a session resumed onto a model that had stopped taking its recorded level could not be opened *at all*. Now the level is dropped, the send keeps its prompt, the index records what is actually running, and the transcript draws **Dray's own sentence** naming the levels the model does take — fx has two refusals one word apart ("is unavailable" for a model with none, "is not available" for a rung too high) and neither says which level, what the model takes, or what the session ended on. `models_changed` is what carries a learned ladder to the composer, so the picker stops offering a control mid-session rather than at the next restart. Stances are two — `manual` → `ask`, `auto` → `code` — and **no bypass is reachable**, so `stanceFor` falls fx to `auto`, its widest. **Provider is a composer control an existing session may still move, and the model is what carries it.** It writes `fx provider`, fx's global setting, because the picker's list is the *active* provider's and nothing else can make it follow. The session itself moves at the next send: `fx::set_model` sends `set_config_option provider` first where the model it is handed belongs elsewhere, since fx refuses a cross-provider model outright (`-32602`) — a `?` that used to fail the whole send and, on a resume, kill the child, so a session whose global provider had moved underneath it could not be opened at all. Safe because the switch is real: measured on 0.0.10, it moves the model with it and **persists onto fx's own session record**, so a `session/resume` in a fresh process comes back on it rather than on whatever the settings file names by then (`provider_switch.jsonl`, which leaves `settings.json` on the provider it started at throughout). **Disabled while the turn is in flight**, with the reason drawn under the row rather than hung off a tooltip a disabled button can never open. **Its slash commands are its skills**, walked off disk rather than asked for — `available_commands_update` is empty and nothing else on the wire answers — and sent as ordinary prompt text, which fx expands itself. Not in v1: fork (fx has none), images (the Codex provider answered `refused`). **Read [FX-PLAN.md](apps/desktop/FX-PLAN.md)** for the captured wire and what the docs got wrong.

**Dray's rules ride fx's first prompt, since fx has nowhere else to put them.** Claude Code and pi take `--append-system-prompt` and Codex takes `developerInstructions`; `fx acp` takes `--model` and `--log-file` and nothing else (0.0.10), `session/new` has no field for it, and `~/.fx/settings.json` holds no key — so `start_turn` appends [system_prompt.md](apps/desktop/src-tauri/src/harness/fx/system_prompt.md) to the **first prompt of a new session** alone, a resume carrying it in the thread's own history. Its own file rather than pi's, which names `~/.agents/skills` where fx reads `~/.claude/skills` among its global roots. **Only the wire text carries it** — `deliver_prompt` logs `user_message` from the reader's own string and sends to the transport separately, so the transcript never sees the block and there is nothing to strip on the way out. That makes fx **the one exception** to the rule that the transcript shows exactly what the model was told, stated at `deliver_prompt`'s `issues` argument; nothing else may take it.

**The rules go *after* the request, and that ordering is measured.** fx titles a session off its first turn, so a prompt opening with 4KB of them is titled about Dray: one captured request came back `Dray Agent Workflow Instructions` with the block first and `Add Verbose Flag to CLI Parser` with it last. Two content blocks in the `prompt` array read as block-first and title the same way. And fx **restates** that title on later turns rather than re-deriving it, so a first turn titled wrong stays wrong for the session's life — which is what rules out ignoring the first title instead. The rules are still honoured from down there, pinned live with a codeword rule the model obeyed on the turn it arrived. Pinned by test, since a refactor tidying the block to the front reads fine and costs nothing this build can see. **Dray titles fx sessions itself now**, so the order no longer decides what the sidebar says — it is kept because the measurement stands and because the model reading the request before 4KB of house rules is the order worth having anyway. **And the titler cuts the block back off**: `strip_dray_rules` in [title.rs](apps/desktop/src-tauri/src/title.rs) strips exactly what `preamble_block` builds, since nothing reaching that function carries the rules *today* and the refactor that would change it — preparing the wire text one step earlier — reads perfectly fine and shows up only as every fx session named after this app. **Matched whole and as a suffix, never searched for by tag**: the text there is the reader's own, and in this repo of all places a prompt may quote the markup outright, where cutting from a tag they typed to the end of their sentence hands the model a fragment and puts `Untitled` over a good prompt-derived title. One function builds the block and one strips it, or the cut silently matches nothing. The `<dray_system_prompt>` wrapper is a seam for a later reader, not something this build cuts on. Cost, stated: fx compaction can drop the block in a long session, and re-injecting per child process was the rejected alternative.
- **Only *ranged* `Read` renders its code; a whole-file read has no expander at all.** That read is the agent pulling a file into context, not showing it to the reader, and its result is the file itself. A *failed* read still expands, since its error text is the only place the reason lives. A read of an image is the exception.
- **The PR panel reads and acts, never writes prose.** No commenting, no replying to a review, no requesting review, no closing.
- **Forks copy the conversation whole and record no lineage.** The CLI exposes no fork-at-message, and `fork_from` is cleared once the CLI carries the fork out, so nothing on disk says which session a fork came from.
- **Dray writes only status and priority**, from the opened issue's header — no comment, no attachment, no assignee, no label — and there is **no issue-side project mapping**, the connection being workspace-wide. The `dray` CLI writes nothing.
- **The handoff row has no Revert, Amend or Stash** — each destroys or rewrites work, and a button that sends a prompt for one is a button whose blast radius is decided by the model. No Push either, and that one went on width.
- **The repo view reads — no fetch, no pull, no discard.** The ahead count is against the *last known* upstream, so a branch someone else pushed to reads as level until the push itself fails.
- **Sidebar PR marks say open, draft or merged; checks say running or failing.** No number, no per-check detail, no merge readiness, nothing at all for passing.
- **Spawned sessions inherit permission mode, so most block immediately.** The default stance is `auto`, so a fanned-out session stops at its first `Write` waiting for a card nobody is next to. `dray new` takes no `--permission-mode`, and adding one raises a real question: an agent in a `plan` session spawning a `bypassPermissions` child is an escalation past the stance the user set. Clamping the child to be no more autonomous than the parent is the likely shape of the fix.
- **No reading a transcript back.** Create, list and send exist; reading what another session said does not, and a parent cannot learn a child finished except by polling `dray ls`.
- **TS event types are generated, not written.** `ts-rs` derives them into `src/types/events.ts`, checked in so the frontend build needs no Rust toolchain. `cargo test` regenerates; never edit the output. Two settings live in `src-tauri/.cargo/config.toml`: the export path, and `TS_RS_LARGE_INT = "number"`, because `u64` otherwise becomes `bigint`, which `JSON.parse` never produces.

## Known issues

Diagnosed defects, not yet fixed. Unlike _Current state_ above, these are broken rather than unbuilt. Delete an entry when you fix it.

- **"Check for Updates…" answers into a void when the sidebar is collapsed.** The verdict draws in `UpdateRow`, which lives inside `<aside>`. Fix = a surface not tied to the sidebar.
- **Quit from the Dock's context menu is unguarded.** It bypasses the menu bar, so the custom Quit item never sees it. Nothing in the Tauri API reaches it today.
- **A blocked install has no way to say when it unblocks.** It waits on any session being mid-turn but names none. That sentence sits in the button's tooltip, which is why the button carries `aria-disabled` and guards its own click instead of taking `disabled` — a disabled button fires no pointer events to open a tooltip.
- **Changing effort respawns the child**, since the CLI has no `set_effort` control request. Harmless today, as the respawn happens inside `send_msg`. Revisit when queued or mid-turn messages land.
- **A live background task defer that respawn silently**, since `has_outstanding_work()` guard every child-replacing path and a `local_bash` task never end on its own. The reader change effort or model, nothing happen, nothing say why. Stop used to be the way out by draining the set; it deliberately isn't any more (DRA-185), so the subagent panel's per-task stop is now the only one. Cure = saying so, not putting the fan-out back.
- **A permission request stranded by a child dying mid-run is unanswerable.** The pending map lives in `Session`, so an effort-change respawn leaves a card whose buttons error. Restart is fine, and the CLI re-asks on resume.
- **`requires_user_interaction` is parsed and only half honoured.** `AskUserQuestion` is the one shape this app draws a card for, matched by tool name; anything else carrying the flag still gets Allow/Deny.
- **A worktree session's first baseline is a guess, and the reflog holds the answer.** `base_ref_tree` resolves the fork point the way the CLI does, but the CLI fetches `origin/<default>` first, so an upstream commit landing in between is attributed to that turn. `git worktree add -B` writes a reflog entry naming the commit it actually used, readable lazily even after the agent commits. Take the newest "Created from"/"reset" entry, not the oldest.
- **Nothing handles a command that restarts or replaces a session.** The picker hides `clear`, `fast`, `model` and `rename` for this reason, but hiding is not solving: each is still reachable by typing it. `clear` starts a fresh conversation the index never heard of; `rename` retitles a session whose title this app owns; `model` and `fast` move the running child off what the composer displays. None come back on the wire in a form the app can reconcile. The fix is a way to notice a session was replaced and re-adopt it — the same machinery a `/clear` button would need. `commands_changed` is a related loose end: the CLI publishes it when available commands change, which would fix the restart-to-see-a-new-plugin caveat.
- **A hard kill mid-dictation leaves the output muted.** The record of what to restore lives in the process, so `SIGKILL`, a panic or a power cut get past `RunEvent::Exit`. Quit and window close are covered. The cure is durable state or a watchdog, neither of which a mute is worth today; unmuting by hand is the recovery.
- **A prompt typed during a turn runs under the *old* model, stance and fast mode.** `send_msg` records the new pick on the index before queueing, and the queue's own flush hands the prompt to the transport without passing the live controls — so the composer and the sidebar show the new setting while the turn it delivers runs on the previous one. One gap for all three rather than three, and the cure is one too: applying pending settings at the flush, or routing a queued prompt back through the settings path. Longstanding; fast mode joins it rather than adding to it.
- **A background subagent's report-back is a second `completed`**, so a session with one raises two "Task finished" notices.
- **`fast_mode` in `~/.fx/settings.json` has two writers and they can undo each other.** fx's own TUI writes it — caught on disk 2026-09-15, a model switch turning it off four seconds after it was on (backups `0x43`, `0x44`) — and Dray writes it on every fx session creation whose value differs. Neither can lock against the other, so `write_setting`'s read-modify-rename window is a **real** race with a real counterparty rather than the theoretical one its doc comment describes. What it looks like: the reader turns fast mode off in their TUI, Dray creates a session moments later and puts it back, or the reverse — and the losing write is silent either way. The window is one rename wide, so it wants a reproducer before a cure; named, not fixed.
- **The PR polls share one GitHub rate-limit budget with every agent in every session.** Sidebar marks ask `gh` once per repo every 30s, the panel polls again at 15s while anything is in flight — against a *per-user* budget that every agent's own `gh` call spends too. **GraphQL's budget is 5000 *points* an hour, charged on the shape asked for, not on what comes back**: nested `first`s multiply, so the panel query at `20 × 50 × 50` cost 11 points per read of a branch with *no PR at all*, and two Dray instances (release beside a `tauri dev`) on one open PR tab drained the hour on their own (DRA-247). It is two aliased connections now — five open, two settled, thirty threads of fifty replies — measured at 2 points; measure any change to a query with `rateLimit{cost}` before shipping it. A second shape remains: `gh pr create` answering "API rate limit already exceeded" while `gh api rate_limit` reports the primary limit untouched is the **secondary** limit, which has no reset timestamp to wait on, and the cure at the agent's end is exponential backoff, which is GitHub's own guidance.
